一、alert 模态框 vs toast 轻提示：到底差在哪

两者是同一套告警通道的两个出口，按严重级别分流（app.js:handleAutoOrderAlerts）： severe → 模态框，warn → toast；另外引擎「刚才发生了什么」的播报也走 toast。 区别不在样式，而在「要不要人确认」——需要人确认的用模态框把你拦住，只是通知你的用 toast 自己飘走。

维度 alert 模态框 toast 轻提示
谁来用 severe 告警：需人工介入、引擎异常退出、运行中拦截切周期/合约、开关失败 warn 告警 + 引擎关键动作（开仓/平仓/保本/移动止盈/账单同步）
长什么样 屏幕正中卡片 + 全屏半透明遮罩（遮罩会吃掉点击，页面点不动） 屏幕正中卡片，无遮罩，页面照常可点（pointer-events:none 容器）
怎么关掉 改前：只能点「确定」
改后：点「确定」/ 点框外区域 / Esc Enter 		5 秒自动淡出，或点它一下立刻关
会不会自己消失 不会（必须有人看到） 会，5 秒
同屏几条 1 条（同类合并成一条 + 同 code 5 分钟冷却防连弹） 最多 5 条（超了丢最早的）

阻塞自动下单/交易引擎？ 都不阻塞。交易引擎是另一个操作系统进程（subprocess.Popen），行情走自己的 SSE 连接，页面这层关不关得掉都影响不到它下单。

二、⑵ 点弹窗之外也能关（等同点「确定」）

为什么必须换掉原生 alert，而不是「加个监听」

原生 alert() 是浏览器自己画的系统级模态框，页面拿不到它的 DOM，没有遮罩层可点， 也没有任何 API 能监听它的关闭或外部点击 —— 想满足「点框外＝点确定」只有一条路： 自己实现模态框。本次新增 [COMPONENT] AlertDialog，把全站 23 处原生 alert() 全部替换为 showAlert(msg)。

实现要点

  • 三个出口、语义等价：点「确定」按钮 / 点遮罩（框之外的区域）/ 按 Esc Enter。 点框内不关（不误触）。closed 标志保证三条出口同时到达时只收尾一次。
  • 复核了原生 alert 的既有行为，逐条对齐：一次只弹一个（用队列复刻原生 alert 的串行排队）、打开即聚焦「确定」（Enter 关框与原生一致）。
  • 长文不再撑破窗口：框 max-height:80vh、正文区 overflow-y:auto + min-height:0（flex 子项不加这条滚动不生效）。引擎日志尾部那种长文本现在框内滚动。
  • 层级 10001：高于既有弹层（10000）与 toast（9999），告警不会被别的弹层盖住。
  • 「确认＝人已看到」的 ack 语义原样保留：ackAutoOrderAlerts 改为挂在弹框关闭之后 （showAlert(...).then(ackIfAlertsSeen)），并加 autoOrderAlertAckHold 暂缓水位， 避免「每 5 秒轮询一趟就把后端队列清空、人还没看」。

六、你问的那个问题：到底哪个功能是「点框外＝取消」

先答结论：你要找的不是某一个"新功能" —— 「点框外＝取消」在这个仓里早就有了，就是 index.html 里那两个问答式弹窗。它们的遮罩行写法可以直接当证据：

所以仓库里从来就是两套语义、按弹窗形态分：

  • 提示式（只有一个出口，看完就完事）—— 例如我第 1 轮做的 AlertDialog、以及被它替掉的 23 处原生 alert： 点框外＝确定（反正除了"我知道了"没有别的意思）。
  • 问答式（要你回答"做还是不做"）—— 上面那两个既有弹窗，以及本轮收编的删除标注确认框： 点框外＝取消（不做任何事，安全）。

你印象里"点框外都是等于确定"，是因为你点过的都是提示式的框；而问答式的两个（标注输入、扫描选择）你多半是直接点按钮关的。

本轮把删除标注的确认框收编了（app.js:7379）

它原来的行为是：

if (confirm("确定删除当前股票 (" + code + ") " + freq + " 周期下的全部标注吗？")) { ...发删除请求... }

原生 confirm 的「点框外 / 按 Esc」＝取消（浏览器给的语义）。换成自实现模态后，我保持了这个语义： 点框外 / 按 Esc ＝取消，只有点「确定」或按 Enter 才返回 true 去发删除请求。

这是刻意的：删除是不可逆的 —— 一次要删掉「当前股票 + 当前周期」的全部标注。 如果为了"全站统一"把这里也改成「点框外＝确定」，等于把危险默认值调得更危险。而保持「取消」， 是纯 UI 升级、零行为变更（原生就是这么做的），所以无需你为它承担任何新风险。

按钮顺序也按仓里既有约定做成了「确定在左、取消在右」（我第一版按 Web 惯例写成"取消在左"，与仓内既有约定相反，已改回）。

保证：没点「确定」之前，一个字节都不会删 —— 行为矩阵里专门钉了这条：框弹出的瞬间发请求数 = 0；点框外 = 0；点「取消」= 0；点「确定」才 = 1， 且请求体是 {action:"delete_all", code, freq}。

一句话结论。自动下单运行中，真正需要人动手的只有 3 类模态框： 需人工介入！（严重告警）、交易引擎已退出！（异常退出）、 交易引擎运行中，请先关闭，再切周期 / 再切合约（运行期拦截）。 其余全部是 5 秒自动淡出的 toast； 另有 不支持自动下单 与 交易引擎开启/关闭失败（操作触发）、以及 交易引擎运行中…（运行期拦截）也是模态框，同样需要点掉。 这些模态框都不自动消失、也都不阻塞交易引擎（引擎在独立子进程里跑自己的行情流）； 它们唯一的作用是「把需要人判断的事摆到你面前」。
