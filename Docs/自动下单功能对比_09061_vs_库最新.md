### ② 信号适配层 —— 🟢 没动

**对应文件**：这一层不是单一文件，由三个文件共同承担——

| 子功能 | 对应文件 | 代码事实 |
|---|---|---|
| 1. 解析买卖点（SSE 帧 → 信号） | `tg/sources/sse_source.py` | `SseSource._on_frame` / `iter_sse` 把 SSE 推来的数据解析成信号事件；同目录 `base.py`（Source 基类）、`replay_source.py`（历史回放源，测试用） |
| 2. 快照冻结（信号值定住不变） | `tg/types.py`（Signal 结构）+ `tg/engine.py` 的 `on_signal` | 信号到达那一刻的 `price / high / low` 等值直接装进 `Signal` 对象定住，之后入场过滤、止损计算全部读这份冻结值，不存在"边算边变" |
| 3. 幂等去重（同 key 只处理一次） | `tg/store.py` + `tg/engine.py` 第一道门 | `store.try_mark_signal(key)` 用 sqlite 原子标记，重复信号直接写 `signal_dup` 事件返回；`engine.on_signal` 的第一行就是它，先于一切交易逻辑 |

**原先有哪些子功能**（负责把信号"接住、定住、去重"）：
1. **解析买卖点**：把 SSE 推来的数据解析成"买点开多 / 卖点开空"的买卖点信号。
2. **快照冻结**：信号到达那一刻的行情快照被"定住"，后续所有处理都用这份冻结值，不会边算边变。
3. **幂等去重**：同一个信号 key 只处理一次，重复推来直接忽略，防止一根 K 线被处理两遍。

**最新代码改了没**：**没改**。三个子功能全部原样保留（`sources/`、`store.py`、`types.py` 在本次 diff 中零变化）。这层的职责就是"干净地接住信号"，本次改动完全不涉及它。

**边界说明**：这一层的"适配"到 `on_signal` 拿到干净信号为止。之后按引擎状态分流（OPENING/EXITING→忽略、IN_TRADE→仅离场、IDLE→开仓）属于「⑤ 执行层」的信号门，不算适配层的职责。

### ④ 风控闸门 —— 🔵 只删了"分仓"相关的仓位计算，硬闸门全保留

这层分两块：**五项硬闸门**和**仓位管理（算开几手）**。

**对应文件**：这层由三个文件 + 配置共同承担——

| 模块 | 对应文件 | 代码事实 |
|---|---|---|
| 五项硬闸门 | `tg/risk.py` | `RiskChecker.check_open(side, volume, bar_date, max_volume)`，按顺序过五道门，任何一道不过就拒单；`on_trade_closed(net_points, volume)` 负责日亏累加（点数×手数） |
| 仓位管理（算开几手） | `tg/sizing.py` | `PositionSizer.size(equity, price)`：三模式算法 + `_fixed_volume`（非仓位管理固定手数）+ `max_volume`（算法结果截断上限，默认中金所单笔上限 20）+ `unlock_no_new_open` |
| 资金闸门（账户最多开几手 X） | `tg/engine.py` 的 `_capital_gate` | `K = 一手保证金 + 一手名义价值 × risk_unit_pct`，`X = floor(可用资金 / K)`；钱不够 K 直接拒（capital_insufficient） |
| 全部参数默认值 | `tg/config.py` | `RiskConfig` / DEFAULT_CONFIG 的 `risk` 节与 `sizing` 节 |

#### A. 五项硬闸门 —— 🟢 全保留
交易时段限制、尾盘不开仓、单笔手数上限、单日往返笔数上限、单日最大净亏——这五条**一条没动**。当前配置值（`config.py` risk 节）：

| # | 闸门 | 配置键 | 当前默认 | 拦截行为 |
|---|---|---|---|---|
| 1 | 交易时段 | `enforce_session` + 品种 spec | 开 | 不在交易时段（IF 09:30–11:30 / 13:00–15:00）拒单 |
| 2 | 尾盘不开仓 | `no_open_after` | 14:50 | 到点后拒绝任何新开仓 |
| 3 | 单笔手数上限 | `max_volume`（或由 sizer 传入） | 2 | 委托手数超上限拒单 |
| 4 | 单日往返笔数 | `max_trades_per_day` | 20 笔 | 当日成交笔数到顶停开新仓 |
| 5 | 单日最大净亏 | `max_daily_loss_points` | 60 点 | 量纲=点数×手数，触达 −60 当日停开新仓 |

**两个刻意的语义设计**：①第 3 道的"手数上限"由 sizer 的有效上限传入（sizing 关闭时 = risk.max_volume），避免"算法算 4 手、风控按 1 手拦"的死角；②硬闸门只拦**开仓**——已持仓仍按原计划出场，绝不强行平仓。另外"同时持仓笔数上限"（`max_open_positions`）不在这道门里硬拒，由引擎层"静默截断"处理——刻意区分"硬拒"和"软截断"两种语义。

#### B. 仓位管理（sizing）—— 🔵 简化

**原先怎么算手数**：分两步——先算出"这一次该开几手"，再决定"拆成几笔"。
- 三种手数算法（固定手数 / 按资金比例 / 按 ATR 风险）—— 🟢 **没改**，还是这三选一。
- `batch_open` / `batch_unlock`（开仓拆几笔 / 解锁拆几笔，两个独立参数）—— 🔴 **删除**。因为现在不再拆多笔了，这俩参数失去意义。
- `unlock_no_new_open`（解锁后不补开新仓，规避平今高手续费）—— 🟢 **保留**，语义微调成"补开缺口的开关"。
- 资金门槛缓冲（`risk_unit_pct`，算"一手保证金 + 名义价值 × 缓冲比例"）、权益口径（用可用资金还是总资产）—— 🟢 **没改**。

#### C. 资金闸门（算账户最多能开几手）—— 🔵 简化

**原先**：先算出账户最多能开 X 手，再**除以要拆的笔数**，得到"每笔最多开几手"。例如账户能开 8 手、要拆 2 笔，那每笔最多 4 手。

**现在**：直接算出 X 手就是上限（比如能开 8 手就是 8 手）。因为"一笔报单挂 N 手"，不存在"每笔分几手"了，不用再除。

**配套**：单笔/持仓上限校验 `check_open` 删掉了 `batch_count`（批次数）、`existing_same_side`（已有同向仓）两个参数，签名变简单。

**大白话总结**：风控的"五道硬闸门"原封不动；动的只是"分仓"带来的那一套算数——因为不分仓了，所以"按笔数均分资金"的除法逻辑整个删掉。

### ⑤ 执行层 —— 🔴/🟡 改动最大，但骨架没动

这层是交易网关的大脑（`engine.py` + `position_book.py`）。改动集中在"入场怎么开"，离场语义完全没动。

**对应文件**：这层的职责分布——

| 模块 | 对应文件 | 代码事实 |
|---|---|---|
| 状态机 + 信号门 | `tg/engine.py` 的 `on_signal`（第一道去重门之后）+ `tg/types.py` 的 `EngineState` | 四态（IDLE/OPENING/IN_TRADE/EXITING）按持仓推断并可从 sqlite 恢复；OPENING/EXITING→in_flight 忽略、IN_TRADE→反向 close_only / 同向 skip、IDLE→开仓 |
| 开仓入场 | `tg/engine.py` 的 `_open_position` | 一笔 FOK 挂 N 手；含 `_CFFEX_LIMIT_MAX=20` 上限、`open_silenced` 静默截断 |
| 解锁入场 | `tg/engine.py` 的 `_unlock_position` + `_book_unlock_trade` | 对反向锁仓发一笔 FOK 整笔解锁；成交后默认**不补开**（`unlock_no_new_open=True` 默认）。注：正常流程簿内仅一笔锁仓候选，代码按 `entry_bar_seq` 升序取最老只是兜底外部手动交易残留的防御性定序（见下节澄清） |
| 离场结算 | `tg/engine.py` 的 `_settle_positions` / `_exit_intent` / `_close_positions` | 止盈/止损/时间逐笔结算；`_exit_intent` 硬编码"入场方式决定离场方式"（OPEN_FIRST→LOCK、UNLOCK_FIRST→CLOSE、LOCKED→UNLOCK）；多仓按 seq 先进先出 |
| 锁仓落簿 | `tg/engine.py`（LOCK 成交分支，`entry_mode=EntryMode.LOCKED`） | 锁仓成交后反向仓以 LOCKED 身份落簿，次日对向信号自动解锁 |
| 关闭锁全部 | `tg/engine.py` 的 `shutdown_and_lock_all` | 自动下单关闭时把所有持仓强转锁仓 |
| 对账与卡单复核 | `tg/engine.py` 的 `_check_unlock_stuck`（F1）/ `_reconcile_positions` | 解锁在途标记跨 K 线复核防幽灵持仓；持仓对账检测外部平仓 |
| 持仓账本 | `tg/position_book.py` 的 `PositionBook` + `tg/types.py` 的 `Position` | 簿内增删查、同向/反向仓筛选（`same_side_positions`/`opposite_positions`）、单仓视图 `legacy_single` |

#### A. 状态机 + 信号门（交易串行化）—— 🟢 没动

**原先**：四态状态机（空闲 / 开仓中 / 交易中 / 离场中）+ 信号门。核心约束是"一次只跑一笔交易"：交易进行中，同向信号直接忽略、反向信号只触发离场绝不反向开新仓，直到全部持仓离场才回到空闲，允许下一次交易。

**现在**：没改。四态、in_flight 忽略、同向 skip、反向 close_only 全部原样保留。这是整个系统"不会乱"的骨架，本次一根筋没动。

#### B. 开仓入场 —— 🔴 核心改动：从"拆 N 笔"改成"一笔挂 N 手"

**原先**：一个信号来了，如果仓位管理说"开 3 手、分 2 笔"，系统会连续发 **2 笔独立买单**（比如 2 手 + 1 手），每笔成交后在账本里**各记一条独立持仓**。这是"金字塔式分批加仓"——第一笔试探、第二笔确认再加。

**现在**：同样一个信号，系统只发 **1 笔买单**，一次性挂满 3 手（FOK 全成或全撤），成交后账本里**只记一条持仓（3 手）**。

**改了什么（大白话）**：删掉了"一信号拆多笔、每笔一个持仓"的能力，收敛成"一信号 = 一笔报单 = 一笔持仓"。账本从"多条同向持仓"变成"一条持仓"。

#### C. 解锁入场 —— 🔴 核心改动：从"一次解多笔"改成"一次解一笔 + 补开"

**原先（H2 批次解锁）**：账户里有多笔反向锁仓时，一次信号可以串行解多笔（`unlock_count = min(反向仓数, N)`），还有一套"批次截止 5 秒复核 → 三分支结算（全成/半成补开/全弃）"的复杂逻辑。

**现在**：一次信号**只解一笔**锁仓（发一笔 FOK 整笔解锁），成交后默认**不补开**（`unlock_no_new_open=True` 是默认值；显式设 False 才按缺口补开 N−V 手）。

> **澄清"取最老一笔"**：既然"一次一笔、离场前不开第二笔"，簿内何来多笔锁仓？确实——**自动化正常流程里簿内最多只有一笔锁仓候选**（开仓→锁仓→留一笔 LOCKED→对向信号解锁→簿清空，严格串行；且 IDLE + 同向残留 + 新同向信号会被 `idle_with_same_side` 守卫直接 skip，堵死了"锁仓遗留时再开新仓"的路）。代码里 `sorted(按 entry_bar_seq 升序) 取 [0]` 是**防御性定序**，只兜三类边界状态：①同一账户在外部终端手动交易留下的持仓残留；②从 09061（分仓时代，一笔交易可产生多笔持仓/锁仓）迁移过来的历史账本；③`max_open_positions≥2` 配置下外部反复平仓留下的"沉睡仓位"（E3.2 守卫注释明确点名此场景）。有多笔候选时按"先锁先解"（FIFO）保证行为确定；平时永远只有一笔，排序不起作用——它不是常规路径，是保险丝。

**改了什么（大白话）**：解锁从"一次可能解好几笔"收敛成"一次只解一笔"，原来那套"批次复核 + 三分支结算"的复杂代码整块删掉，补开逻辑直接并进单笔解锁路径。

#### D. 离场语义 —— 🟢 全保留（这是重点）

以下几条**一行没动**：
- **入场方式决定离场方式**：开仓入场 → 离场用锁仓（避开平今高手续费）；解锁入场 → 离场用平仓（平昨无费）；锁仓状态 → 反向信号解锁。这是手续费最优的数学约束，硬编码、无开关。
- **锁仓落簿**：锁仓成交后，反向仓以"锁仓"身份落簿，次日对向信号自动解锁。
- **反向信号仅离场**：交易中遇到反向买卖点，只平仓/锁仓，绝不反手开新仓。
- **止盈/止损/时间结算**、**收盘强平**、**关闭时锁全部**、**多仓 FIFO 逐笔平仓**（按先进先出）。

> 注：多仓 FIFO 平仓的代码还在，但分仓删除后，开仓不再产生"同向多仓"，多仓只剩"锁仓落簿"这一个场景会用到。

#### E. 对账与卡单复核 —— 🟢 全保留

- **解锁卡单监控（F1）**：解锁报单后记"在途"标记并持久化，5 根 K 线后用真实成交回报复核，防"回报丢失"造成的幽灵持仓。
- **持仓对账**：检测外部平仓/幽灵持仓并修正引擎账目。
- **启动首拉对账**：重启后先跟真实账户对一次账。

#### F. 中金所 20 手上限 —— 🆕 新增

开仓时新增一道防御：单笔超过 20 手直接拒单（中金所股指期货单笔上限）。正常情况被资金闸门和手数上限钳住，这是兜底防线。

**大白话总结**：执行层"状态机、信号门、离场语义、对账"这些骨架全没动；动的是"入场怎么开"——开仓和解锁都从"拆多笔"改成"一笔搞定"，顺手删掉了两套复杂的分仓/批次代码。

### ⑥ Broker 适配器（可替换）—— 🟡/🆕 报单升级为 FOK

这层是真正跟券商打交道的通道（dry_run 模拟 / SimNow / 创元实盘，同一套接口）。

**对应文件**：`tg/brokers/` 目录三个文件 + 仓库根 App 包——

| 模块 | 对应文件 | 代码事实 |
|---|---|---|
| 接口骨架 + 注册表 | `tg/brokers/base.py` | `Broker` 抽象基类定义 6 个方法（`submit` 报单 / `pulse` 心跳 / `real_position` 查真实持仓 / `trade_confirmed` 成交复核 / `cancel_pending` 撤单 / `equity` 查资金）；`BROKERS` 注册表 + `build_broker` 工厂按配置名实例化 |
| 三个实现 | `tg/brokers/dry_run.py`（本地模拟撮合）、`tg/brokers/simnow.py`（SimNow / 创元实盘共用，`live` 由 App 层路由） | 全部走同一套 `Broker` 接口，可替换 |
| 全 FOK 报单 + 追价 | `tg/brokers/simnow.py` 的 `_submit_open` / `_submit_unlock` / `_submit_lock` / `_submit_close` | 前两者恒定 FOK 不追价；后两者 FOK 全撤后隔 `chase_interval` 秒按 `_overprice_limit` 重报，最多 `close_max_chase` 轮 |
| 成交判定（P6） | `tg/brokers/simnow.py` 的 `_traded_volume_from_records` / `_traded_price_from_records` | 只认 CTP `order.trade_records`（交易所确认的成交回报），不信持仓缓存 |
| 持仓对账 | `tg/brokers/simnow.py` 的 `_verify_position_delta` / `_capture_initial_account_state` | position delta 诊断 + 启动基线首拉 |
| 主连映射 | `tg/brokers/simnow.py` 的 `_resolve_trade_symbol` | 用行情快照 `underlying_symbol` 动态解析当月主力合约 |
| 连接重试 + 心跳 | `tg/brokers/simnow.py` 的 `_connect`（`connect_retries`）+ `pulse` / `_probe_alive` | CTP 短连接敏感，重试 + 定期心跳保活 |
| 平仓方向修复 | `tg/brokers/simnow.py` 的 `_CLOSE_DIRECTION` | 平多=SELL、平空=BUY |
| 实盘安全闸门 | 仓库根 `App/AppTrader.py` 的 `_check_live_gate` | live 必须 `confirm_live_trading=true` 双确认，否则抛 AppError（不在 trader_gateway 包内，属 App 壳层） |

#### A. 接口骨架 —— 🟢 没动

5 个方法（报单 / 心跳 / 查真实持仓 / 成交复核 / 撤单）的定义、以及以下能力**全保留**：
- **成交判定**：以 CTP 真实成交明细（`trade_records`）为唯一可信依据，不信持仓缓存。
- **主连映射**：把 `KQ.m@` 主连代码解析成当月主力合约。
- **账户路由 + 实盘安全闸门**：模拟/实盘分流 + 实盘双确认。
- **连接重试 + 心跳**、**平仓方向修复**（平多=卖、平空=买）。

#### B. 报单方式 —— 🟡 核心升级：普通限价 → FOK

**原先**：下单是普通限价单（对手价 ± 0.6 点超价抢成交），如果几秒没成交就**由软件主动撤单**。这中间存在"成交了一部分、还剩一部分"的尴尬中间态。

**现在**：四类报单（开仓/解锁/锁仓/平仓）**全部改成 FOK**（要么全成交、要么全撤）。由交易所撮合引擎硬保证：3 手要么全成、要么全撤，**从根上消灭部分成交残留**。

#### C. 卡单处理 —— 🟡 机制变了，语义不变

**入场卡单（开仓/解锁）**：
- 原先：超时 → 主动撤单 → 不追价 → 等下一信号。
- 现在：FOK 全撤 → 不追价 → 等下一信号。**语义不变**（"最多不赚钱、不亏钱"），只是"撤单"这一步从软件自己超时撤，变成交易所 FOK 自动全撤。

**离场卡单（锁仓/平仓）**：
- 原先：超时撤单后直接重报，最多 20 轮追价。
- 现在：FOK 全撤后**隔 1 秒**（新增 `chase_interval`）按最新对手价重报，循环到成交或 20 轮用尽。**语义不变**（"离场必须追单"），只是重报节奏从"撤了立刻报"改成"撤了歇 1 秒再报"，防报撤频率超限。

#### D. 超价幅度 —— 🟡 0.6 → 1.0

原先有两个超价参数（开仓/平仓各一个），现在合并成一个默认值 `1.0` 点。

**大白话总结**：Broker 层的核心变化就一句话——**报单从"普通限价 + 软件超时撤单"升级成"FOK 全成或全撤 + 交易所硬保证"**，配套调整了追价节奏和超价幅度。成交判定、对账、路由、重连这些通道能力全没动。

### ⑥+ App 壳层·进程托管（FastAPI ↔ 交易子进程生命周期）—— 🟢 骨架没动（本次 diff 未触及）

这套路由**不在 trader_gateway 6 层之内**，属 App 壳层，但它是"自动下单"从功能变成服务的桥梁，单独列一节。

**对应文件**：

| 模块 | 对应文件 | 代码事实 |
|---|---|---|
| 托管单例 | 仓库根 `App/AppTrader.py` | 子进程启动/停止/探活/状态持久化；实盘安全闸门 `_check_live_gate` 也在这里 |
| 服务退出钩子 | `FrontAPI.py` 的 lifespan | FastAPI 优雅退出时 `call_trader_stop(30)`：给 30 秒锁仓宽限，超时强杀兜底 |
| 子进程侧协议 | `trader_gateway/run_gateway.py` | 看护线程 0.2 秒轮询 `.stop_request` flag；主循环 finally 收尾 |

**为什么用子进程**：交易子进程持有自己的 CTP 长连接，与 FastAPI 行情服务各自独立——子进程崩溃/卡单不影响行情页面，也不会被服务重启顺手带走。

**正常的开/停（即"关闭锁全部"那条路径）**：开=拉起子进程（`--no-fresh` 保留持仓与幂等键）；关=写 `{out_dir}/.stop_request` flag 文件（跨平台，绕开 Windows SIGTERM=TerminateProcess 与 venv pid shim 两个平台陷阱）→ 子进程看护线程观测到 → `shutdown_and_lock_all()`（停信号 + 锁全部未锁定持仓）→ 退出 0。用户主动关给 150 秒宽限（覆盖最坏锁仓 ~100 秒）超时强杀；"优雅"按**结果**校验（必须出现 auto_order_off 事件，不是"退出来即优雅"）。

#### A. FastAPI 进程重启 —— 🟢 有完整流程：重启后查孤儿

- **pid 探活恢复**（`_restore_from_file`）：托管单例构造时读 `App/auto_trader_state.json`（记录 pid/out_dir/cfg_path/started_at/broker），对 pid 做 `os.kill(pid, 0)` 探活——pid 已死 → 清状态文件、视为未运行；pid 仍活 → 恢复成"无句柄托管态"，之后 `stop()` 照样能按 pid 写 flag 关掉孤儿进程。
- **多实例防御（P3-2）**：本地无句柄但状态文件记录的 pid 仍活着 → 告警"疑似多 worker 双开托管"，**不主动杀**（防误伤别的 worker 的进程），让部署问题第一时间暴露。
- **遗留 flag 清理（P1-3）**：`start()` 前清掉上次遗留的 `.stop_request`（子进程启动时也清，双保险）——否则残留 flag 会让新子进程"秒退"。

#### B. FastAPI 不再重启（孤儿彻底失管）—— 🔴 当前无超时销毁（已知缺口）

子进程的停止触发源只有三个：`.stop_request` flag / SIGINT·SIGTERM 信号 / SSE 源自然结束。它**没有**任何父进程死亡检测（无 getppid、无 stdin EOF 监控、无"长时间收不到 K 线"超时），而 SSE 源 `max_retry` 默认 **0 = 无限重连**（退避上限 60 秒），AppTrader 启动命令也未配置重试上限。

**因此：FastAPI 崩溃且不再重启时，孤儿下单进程不会自行退出**——它无限重连 SSE，CTP 连接保持登录，持仓挂在簿内；但收不到 K 线 → 止盈止损/收盘强平都不会再执行（这些都依赖 on_bar），持仓处于"无人看管"状态。

当前唯一的收场方式：① 人工向 out_dir 写 `.stop_request`（子进程会正常锁仓收尾）；② 手动杀进程；③ FastAPI 复活后被 `_restore_from_file` 探活查到，再走正常 stop。

**建议的补强方向**（未实现，供拍板）：子进程加"父进程心跳文件"（AppTrader 定期 touch，子进程超时未更新 → 锁仓自退）；或"SSE 无数据 N 分钟超时 → shutdown_and_lock_all 退出"；或给启动参数显式配 `max_retry`。

## 四、结论

1. 这次改动**只动了 6 层里的两层半**：执行层（开仓/解锁从拆多笔改成一笔）、Broker 层（报单升级为 FOK）、风控/配置的"分仓"相关计算。信号源、信号适配、策略层**一行没动**。
2. **离场语义零变化**：入场方式决定离场方式、锁仓落簿、反向仅离场、收盘强平、关闭锁全部、F1 解锁卡单监控——全部原样保留。
3. 本质是**收敛 + 升级**：删掉"金字塔分仓 + H2 批次解锁"两条复杂路径，统一为"一信号 = 一笔报单 = 一笔持仓"的单一模型；报单层从"限价超价 + 主动撤单"升级为"恒定 FOK（交易所保证全成或全撤）"。
4. 风险：分仓删除后，"同 K 线加仓金字塔"能力随之消失，这是本次刻意删除（用户拍板"删除分仓"），非回归。
