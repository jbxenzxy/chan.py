01现状诊断：单文件巨石架构

当前程序的核心问题可以用一个词概括：单文件巨石。 但更准确地说，是两个巨石文件： api_server.py（约 1004 行，FastAPI 路由入口）与 my_chan_main.py（约 14115 行，其中前端模板 HTML_TEMPLATE 占 7594 行、纯 Python 逻辑约 6521 行）， 两者共同承载了从 HTTP 路由到缠论分析、从数据拉取到缓存标注的全部职责。 系统在功能、并发、可维护性三个维度上同时触顶。 本章只做诊断、列出问题，不给出解决方案（解决方案见后续章节）。

1.1问题一：职责混杂，一文件多角色

两个文件各自职责混杂、角色重叠： api_server.py 是「入口」层，却同时承载路由、SSE 与部分业务调用； my_chan_main.py 是「业务核心 + 数据访问 + 前端模板」的巨型文件， 缠论分析引擎、数据拉取、缓存、标注、自选股、批量扫描、前端模板全部堆在其中。 任何一个角色发生变化，都可能波及其余角色，改一处、动全局。

1.2问题二：代码膨胀，函数过长

两个文件体量持续膨胀（尤其 my_chan_main.py 达 14115 行），大量函数超过百行，分析、扫描、拉取逻辑相互交织。 函数之间通过隐式的模块级状态传递数据，调用链难以追踪，新人接手成本极高。

1.3问题三：修改风险高，回归成本大

由于职责混杂，一次「看似局部」的修改往往需要全量回归。 没有模块边界，也就没有局部可验证性——任何改动都必须重新验证整条链路。

1.4问题四：并发能力弱，交互与扫描互相拖累

批量扫描是 CPU 密集 + 长耗时任务（遍历全市场 K 线、逐票跑缠论分析）， 与短耗时、低延迟敏感的交互请求共享同一执行通道，导致交互请求被批量任务「饿死」， 或批量任务被交互请求频繁打断，两端体验都差。

1.5问题五：数据获取耦合，数据源不可替换

数据拉取直接调用 TDX / TqSdk 的底层接口，未经过统一抽象层。 数据源一旦变更或需要多源切换，必须改动分析逻辑所在的核心代码，耦合严重。

1.6问题六：前端与后端耦合，模板与逻辑混杂

前端模板内嵌在 my_chan_main.py 中，与后端逻辑耦合在一起，图表渲染、面板交互、扫描逻辑没有独立边界， 无法单独演进，也无法复用。

1.7问题七：无测试基线，重构无安全网

当前没有自动化测试基线。对于「重构」而言，没有测试就意味着没有安全网—— 任何结构性的改动都只能靠人工回归，风险不可控，这也是重构迟迟无法推进的根本原因之一。

1.8问题八：配置硬编码，散落各处

数据源地址、周期参数、运行参数等配置以硬编码形式散落在代码各处， 没有统一的配置中心，环境切换（本地 / 生产）与参数调整都极其不便。

本章小结

以上八个问题相互叠加，构成「巨石」的恶性循环：越膨胀越难改，越难改越不敢动，越不敢动越膨胀。 本章只做诊断。从第 4 章开始，将给出目标结构与拆分方案。

02api_server.py 代码审查

2.1审查范围与方法

审查对象为 api_server.py 及其调用的 my_chan_main.py。 方法：按职责域拆解两个文件，统计规模与函数结构， 定位耦合点与全局状态，最终给出拆分结论。审查只针对「现状」，不预设方案。

2.2规模与结构

  • 两个文件共同承载全部后端逻辑：api_server.py 约 1004 行（FastAPI 路由层），my_chan_main.py 约 14115 行（分析引擎 + 前端模板），体量巨大且仍在持续增长。

  • 模块级全局变量保存缓存与连接对象，生命周期不清晰，难以测试与替换。

2.4主要问题

  • 职责混杂：一个文件同时是「入口」和「业务核心」，改一处影响全局。
  • 函数过长：分析、扫描、拉取逻辑交织，难以独立单测。
  • 数据获取耦合：直接创建 TDX / TqSdk 连接，无法替换数据源。

2.5审查结论

结论

api_server.py 已到必须拆分的临界点。拆分原则是 按职责分层（API / 服务 / 数据），而不是按功能横向切—— 横向切只会得到多个「小巨石」，纵向分层才能真正解除耦合。

03K 线图表方案选型

3.1需求梳理

  • 核心展示：K 线（日 / 周 / 月 / 分钟级别）。
  • 缠论标注：分型、笔、线段、中枢的绘制——这是与普通行情软件最大的差异点。
  • 交互：缩放、平移、十字光标、选点。
  • 性能：万级 K 线流畅渲染，不卡顿。
  • 联动：与后端 SSE 实时行情联动，新数据即时上屏。

3.2候选方案

  • ECharts：成熟、文档全，k 线图 + markPoint / markArea 可做基础标注。
  • lightweight-charts（TradingView）：轻量、性能好，但标注能力弱，缠论标注需大量 hack。
  • 手写 Canvas 渲染引擎（KLineChart 组件）：完全可控，专为缠论标注设计。

3.4选型结论

结论：手写 Canvas 渲染引擎（KLineChart 组件）

缠论标注是本程序的核心功能。ECharts 的 markPoint / markArea 无法表达分型、笔、线段、中枢之间 复杂的几何关系；lightweight-charts 的标注能力更弱。手写 Canvas 渲染引擎可以完全控制渲染细节， 性能与交互体验最佳，且不依赖任何第三方图表库。

相应地，前端整体采用原生 HTML / CSS / JS，不引入 React / Vue 等框架 （理由详见 第 4 章 4.3 节）。

为什么是扁平结构（不新建 Backend/ 目录）？
  • 不物理搬动已有分析引擎：ZS/、Seg/、KLine/、Bi/、BuySellPoint/ 等已在顶层，搬进 Backend/ 会破坏大量 import。因此保持扁平，顶层所有非 Frontend/ 内容即后端；新增的 App/ 只收纳应用层文件（AppOrch / AppData / AppConfig），不搬动已有引擎目录。
  • 新增 1 个顶层文件 + App/ 目录：FrontAPI.py（面向前端 API）置于顶层；AppOrch.py（业务编排）、AppData.py（业务数据）、AppConfig.py（基础设施配置）放入 App/ 目录，命名规则一致（大写开头）。
  • App/AppData.py 不放 DataAPI/ 内：DataAPI/ 是数据源抽象层（外部适配器，负责从哪拿数据），App/AppData.py 是业务数据层（内部存储，负责存哪、怎么存）。两者职责不同，混放会混淆「数据来源」与「数据存储」。
  • 配置双文件：不新建 config.py。新建 App/AppConfig.py（基础设施配置：端口 / 路径 / 并发 / 凭据）与已有的 ChanConfig.py（算法参数）并行，职责分离。

4.3为什么不用 React / Vue

决策：前端采用原生 HTML / CSS / JS，不引入框架
  • 复杂度有限：本程序是单机自用工具，前端仅由「图表 + 面板 + 扫描」构成，原生 JS 完全足够。
  • 图表引擎不依赖框架：手写 Canvas 渲染引擎（KLineChart）本身与框架无关，无需框架支撑。
  • 零构建链：不引入 webpack / vite、node_modules 与编译步骤，降低维护成本，开箱即用。
  • 无协作与复用需求：无团队协作、无组件生态复用诉求，框架带来的收益趋近于零。

结论：保持零构建、零依赖的原生前端，把精力集中在 K 线渲染引擎与缠论标注上。

05双路径并发模型

本章是本方案的核心架构决策。它回答一个问题：交互请求与批量扫描，如何共存而不互相拖累？

5.1并发问题分析

  • 现状：FastAPI 同步路由在线程池（threadpool）中运行，交互请求与批量扫描共享同一线程池。
  • 批量扫描：CPU 密集 + 长耗时（遍历全市场 K 线、逐票跑缠论分析），会占满线程池。
  • 交互请求：短耗时、低延迟敏感，需要快速响应。
  • 冲突：两者混跑 → 批量任务饿死交互请求，或交互请求频繁打断批量任务，两端体验都差。

5.2GIL 与线程

CPython 的 GIL 使得多线程无法真正并行执行 Python 字节码。缠论分析（CChan 遍历分型、笔、线段、中枢） 是纯 Python 计算，受 GIL 限制，多线程无法加速。 真正能利用多核的方式是多进程（ProcessPool / Celery worker）。但多进程伴随进程间通信与状态同步成本， 因此「是否值得上多进程」取决于任务的性质与频率。

5.3V3 的教训：单一 Celery 路径

V3 的错误

V3 尝试把交互请求与批量扫描统一进同一条 Celery 队列。 结果：交互请求延迟高（进队列 → worker 调度 → 返回），体验差； 队列被批量任务占满时交互被饿死；短小请求也走消息中间件，成本高。

5.4V4 的洞察（采纳）：统一函数，分离通道

V4 洞察：unify function, separate channels

核心思想：分析函数（analyze_stock）是统一的，但承载它的通道按场景分离。

  • 交互请求 → 线程池快速路径（API 进程内，run_in_threadpool）。
  • 批量扫描 → ProcessPool 进程池路径（多进程 worker）。
  • 两条通道共享同一套 service 层函数，只是执行环境不同。

函数统一保证逻辑一致，通道分离保证互不干扰。本版采纳此洞察作为并发模型的基础。

下图（图 2）为双路径并发模型：左侧交互路径走线程池快速路径，右侧批量扫描路径走 ProcessPool 进程池， 两者通过共享缓存（进程内 / 可选 Redis）交换状态。

5.6SSE 实时行情：留在 API 层

  • SSE 实时推送必须留在 API 层，作为常驻 async 任务。
  • 原因：SSE 本质是长连接流，生命周期与请求绑定；任务模型（ProcessPool / Celery）是短任务模型，不是长连接模型，无法承载 SSE。
  • TqApi 连接池：复用连接，避免每个 SSE 连接新建 TqApi 实例。
  • 实时行情不走队列，直接写入 Redis 共享缓存，供前端与后续任务读取。

5.7批量路径选型：ProcessPool 先行

批量扫描路径先用 ProcessPoolExecutor（Python 标准库，零额外依赖、零运维成本）， 满足单机自用工具的实际需求：多进程天然利用多核、批量扫描失败后手动重新触发即可。 在文档中记录升级到 Celery 的决策条件（满足任一即可触发评估）：

  • 需要任务优先级队列。
  • 需要任务持久化（worker 崩溃后恢复）。
  • 扫描任务超时严重且 ProcessPool 无法满足。
  • 未来确实需要分布式能力。

5.8ProcessPool vs Celery 对比

维度ProcessPool（concurrent.futures）Celery
进程管理简单，固定进程池独立 worker 进程，可水平扩展

失败重试无内建内建重试

运维复杂度低中
适用场景批量扫描（当前首选，零依赖）批量扫描（按需升级，见 5.7 决策条件）

5.9为什么现在不用 Celery

ProcessPool 已覆盖当前需求，Celery 的缺点正是我们推迟引入的原因：

  • 引入 Redis 依赖，运维复杂度上升。
  • 任务序列化 / 反序列化开销。
  • 调试难度增加（跨进程调用链）。

单机自用工具没有「多机分布式 / 任务持久化 / 优先级队列」的硬需求，这些缺点带来的成本无法被收益覆盖。 因此先用 ProcessPool，仅在 5.7 决策条件被触发时再评估 Celery——届时 Redis 本就是共享缓存方案的一部分， broker 与缓存复用同一实例，边际成本可控。

5.10共享缓存方案

ProcessPoolExecutor 的 worker 是独立进程，API 进程的内存字典对 worker 不可见。 因此共享缓存采用分层设计，按数据访问范围选择介质：

缓存数据介质理由
K 线 / 股票名 / PE / 实时行情快照进程内字典交互请求与 SSE 都在 API 进程内，无需跨进程，避免序列化开销
扫描结果（task_id → 结果）SQLiteworker 写入、API 进程读取供前端轮询，需跨进程共享；零额外依赖

Redis 作为可选升级：仅在升级到 Celery 或确有跨进程共享需求时引入， 届时 SQLite 替换为 Redis，接口不变。缓存内容与边界如下：

缓存什么

  • K 线数据（按 代码 + 周期 + 复权 维度，设置适中 TTL）→ 进程内字典。
  • 股票名称 / 代码映射 → 进程内字典。
  • PE 等基本面快照 → 进程内字典。
  • 扫描结果（task_id → 结果，供前端轮询）→ SQLite。
  • 实时行情快照（SSE 写入，前端与任务读取）→ 进程内字典。

不缓存什么

  • 交互请求的实时分析结果：每次实时计算，保证数据最新。
  • 大对象 / 二进制：避免内存膨胀。
  • 用户标注 / 自选股等强一致数据：走持久化，不缓存。

06AppOrch.py 模块化设计

服务层 App/AppOrch.py 是后端的中枢，承载从 API 层到数据层之间的全部业务逻辑。 并发模型（双路径）已在第 5 章确定，本章只回答一个问题：App/AppOrch.py 内部如何组织， 才能同时支撑交互快速路径与批量 ProcessPool 路径。

6.1职责分区总览

App/AppOrch.py 按职责划分为三个分区：消费侧（分析引擎）、获取侧（数据拉取与注入）、 扫描（批量扫描服务）。每个分区对外只暴露少量稳定接口，内部实现可自由演进。 第一版三个分区都在 App/AppOrch.py 单文件内（逻辑分区），阶段 8 再拆为 engine/、fetch/、scanner/ 子包。

分区职责核心接口
消费侧（分析引擎）analyze_stock / CChan 编排；extracted_realtime_snapshot 实时快照提取analyze_stock(code, freq, ...)
获取侧（数据拉取）拉取 K 线、set_data 注入fetch_and_inject(code, freq, source)
扫描（批量扫描）批量扫描编排、进度追踪ScannerService.scan(codes, ...)

消费侧：分析引擎

  • analyze_stock 是统一的缠论分析入口（第 5 章的「统一函数」）：输入代码 + 周期 + 参数，输出笔、线段、中枢、买卖点与选点标注。
  • extracted_realtime_snapshot 从实时行情快照中提取分析所需字段，供 SSE 路径使用。
  • 无状态：不持有任何会话级状态，可在线程池（交互路径）与 ProcessPool worker（批量路径）中安全复用。

获取侧：数据拉取与注入

  • fetch_and_inject(code, freq, source)：判断股票 / 期货 → 拉取 K 线 → set_data 注入到 CChan。
  • 通过 source 参数选择数据源（TDX / TqSdk），阶段 5 之后统一走 DataAPI 抽象层。

扫描：批量扫描服务

  • ScannerService 类封装批量扫描：遍历代码列表、逐票调用 analyze_stock、汇总结果、追踪进度。
  • 进度状态收敛到类内部（见 6.3），对外通过 scan(codes, ...) 提交任务。

6.2接口优先原则

依赖方向严格单向：FrontAPI.py → App/AppOrch.py → App/AppData.py，禁止反向依赖。 实现顺序上「先定义接口，再写实现」——接口是各层之间的契约，先锁定签名与返回结构， 各层即可并行开发、独立测试（mock 相邻层）、按需替换实现。 

# FrontAPI.py —— 只依赖 App/AppOrch.py 的公开接口
from App/AppOrch import analyze_stock, ScannerService

# App/AppOrch.py —— 只依赖 App/AppData.py 的公开接口
from App/AppData import get_cache, save_annotation

接口优先带来的直接收益：FrontAPI.py 保持薄（只做路由与参数校验）、 App/AppOrch.py 可被两条通道复用、App/AppData.py 可独立演进。

6.3全局状态收敛

现状的模块级全局状态（scan_state、cache 等）是隐式耦合的根源，也是并发与测试的障碍。 收敛原则：状态归位到最贴近它的地方，App/AppOrch.py 本身保持无状态。

现状全局状态问题收敛目标
scan_state（模块级）多进程 / 多线程下不可靠，无法跨通道共享ScannerService 类实例内部
cache（模块级字典）与数据层职责混淆App/AppData.py 统一管理
其它模块级可变状态隐式耦合、难以测试收敛为无状态函数 + 显式参数

无状态的 service 函数是第 5 章双路径模型的前提：同一份 analyze_stock 既能跑在线程池， 也能跑在 ProcessPool worker，逻辑一致、互不干扰。

  • 浮点：相对容差 1e-6。浮点计算误差不可避免，逐位相等不可行。
  • 时间戳：1s 容差。时间字段存在精度差异，允许秒级偏差。

7.7错误处理策略

现状 api_server.py 每个路由单独 try/except + traceback.print_exc()， 33 个路由重复同一模式。迁入 FrontAPI.py 后必须建立统一策略，否则只是把散乱的错误处理搬了个家。

领域异常层级

# 领域异常基类（App/AppOrch.py 定义）
class AppError(Exception): ...          # 基类 · status_code 默认 500
class DataFetchError(AppError): ...     # 数据源获取失败 · 502
class AnalysisError(AppError): ...      # 缠论分析失败 · 500
class ConfigError(AppError): ...        # 配置错误 · 500
class NotFoundError(AppError): ...      # 股票 / 期货不存在 · 404
class PersistenceError(AppError): ...   # 持久化失败 · 503

统一错误处理中间件

# FrontAPI.py —— FastAPI 异常处理中间件
from fastapi.responses import JSONResponse

# 各子类设定各自的状态码，中间件读取 exc.status_code
class AppError(Exception):
    status_code = 500          # 默认
class NotFoundError(AppError):
    status_code = 404
class ConfigError(AppError):
    status_code = 500
class DataFetchError(AppError):
    status_code = 502
class PersistenceError(AppError):
    status_code = 503
class AnalysisError(AppError):
    status_code = 500

@app.exception_handler(AppError)
async def app_error_handler(request, exc: AppError):
    # 统一日志 + 统一 JSON 响应格式 · 状态码读取异常自身
    return JSONResponse(
        status_code=exc.status_code,
        content={"error": exc.__class__.__name__, "detail": str(exc)}
    )

规则

  • 服务层：只抛领域异常，不 catch（除非需要附加上下文）。
  • API 层：只通过中间件捕获领域异常，不写逐路由的 try/except。
  • 校验错误：利用 FastAPI 内建 ValidationError + Pydantic 模型校验，不走自定义异常。
  • 未预期异常：Exception 兜底，返回 500 + 日志，不泄漏内部细节。
  • SSE 路径：SSE 是流式协议，handler 开始 yield 后响应头已发送，异常中间件无法改写为 JSONResponse。因此 SSE handler 内用 try/except 捕获领域异常，通过事件流发送 {"type": "error", "detail": "..."} 事件，前端收到后展示错误提示并关闭连接；不在 SSE handler 中 raise HTTPException。
# FrontAPI.py —— SSE 专属错误处理（示例）
@app.get("/api/stock_stream")
async def stock_stream(...):
    try:
        async for event in generate_events(...):
            yield {"event": "data", "data": json.dumps(event)}
    except AppError as exc:
        yield {"event": "error", "data": json.dumps({
            "type": "error",
            "error": exc.__class__.__name__,
            "detail": str(exc)
        })}

10结论

10.1方案总结

本方案将单文件巨石 api_server.py / my_chan_main.py 演进为「前端 / API / 服务 / 数据 / 数据源抽象」的分层模块化架构： 服务层按消费侧 / 获取侧 / 扫描分区，接口优先、状态收敛；配置集中化、凭据本地化； 以快照回归测试作为重构安全网；分 10 个阶段逐步迁移。 迁移完成后，api_server.py 与 my_chan_main.py 不再存在，职责被各层文件完全吸收，程序入口统一为 FrontAPI.py。

10.2关键决策

  • 采纳 V4 双路径洞察：统一函数，分离通道——交互走线程池快速路径，批量扫描走 ProcessPool 路径。
  • 配置双文件：App/AppConfig.py（基础设施）+ ChanConfig.py（算法参数），职责分离。
  • ProcessPool 先行：批量路径先用 ProcessPoolExecutor，记录升级到 Celery 的决策条件；避免过度工程。
  • 前端保持原生：零构建、零依赖，专注 K 线渲染与缠论标注。
