## 0.2 术语表

以电脑A为例：`.env` 配了 `SN_ACCOUNT=2000001`（仿真账户）和 `LIVE_ACCOUNT=8888`（实盘账户）。

| 术语 | 含义 | 例子 |
|---|---|---|
| 账户 | 真实的交易账户，配在本机 `.env`。每台电脑每类至多一个：`SN_ACCOUNT`（仿真）+ `LIVE_ACCOUNT`（实盘） | `2000001`（仿真）、`8888`（实盘） |
| 登录方式 | 开自动下单时选的"仿真 / 实盘"。**本机上与账户一一对应**：选仿真 = 用 `SN_ACCOUNT`，选实盘 = 用 `LIVE_ACCOUNT` | SimNow / 实盘 |
| 品种键 | 合约归一后的品种标识（`parse_product_key`）：主连、月份合约归到同一个品种 | `KQ.m@CFFEX.IF`、`CFFEX.IF2609` → `IF` |
| 实例键 | 运行互斥键 = 品种键：本机一个品种至多一个运行中实例，与登录方式无关；实例目录仍按 登录方式+品种 分开（账本隔离） | `IF` |
| 实例 | 某品种下的自动下单引擎整体（进程 + 数据）。两种状态：**运行中**（引擎进程在跑）/ **已停止**（进程退出，实例目录与账本数据仍在）。实例是否存在以**实例目录**为准 | 仿真账户的 IF 实例，以 5分周期运行中 |
| 实例目录 | 实例的数据落盘位置 `Trading/State/<登录方式>/<品种键>/`（state.db / events.jsonl / gateway.log / 停止旗标）。一个叶子目录 = 一个实例的一套文件，停机后保留——"不开自动下单也能看账本"读的就是它 | `Trading/State/SimNow/IF/` |
| 实例表 | 后端 `AppTrader` 托管的全部实例（取代旧单实例句柄 `_handle`） | `{(simnow,IF), (simnow,RB), (live,IF)}` |

一段话串起来（电脑A的实际使用）：打开 IF 5分K线 → 点开开关选"仿真" → **建立实例 (仿真, IF)**，数据落 `Trading/State/SimNow/IF/`；再开 rb 日线选"仿真" → 第二个实例 (仿真, RB)；再开 IF 1分选"实盘" → **被拒绝**——IF 已在仿真账户跑，同品种同机至多一个实例；换账户 = 先关闭仿真实例（持仓走优雅离场）再以实盘重启，数据落 `Trading/State/Live/IF/`。打开账本：全部实例按登录方式分区显示（SimNow 区：IF、RB；实盘区 IF 若曾以实盘运行过则显示为已停止小节）。关掉 (仿真, IF) → 进程退出、目录还在 → 账本里该小节仍显示（已停止），账本照常可看；在 IF 页关闭自动下单 → 直接停该品种唯一运行中实例。

### 1.2 两个推论（用户痛点的直接根因）

- **同品种第二实例开不了**：第二个 start 静默吞掉（§1.1 #2）。这是**应该保留的禁止项**——柜台持仓按账户+合约聚合，两本账对同一份 `real_position` 读数会互相污染（反向单净持仓归零→双方账本被当"外部平仓"清空，`Reconcile.py:39`；同向单→每根 bar 刷 `position_mismatch`，`Reconcile.py:42`）。
- **不同合约也开不了**：同样是 #2 的单实例互斥所致，而这部分是**可以放开的**——对账按合约过滤（#8）、账户三态读自身账本（#9）、行情连接自包含（#7），不同品种实例之间没有共享可变状态。

### 1.3 凭据与登录链路的现状流

- 凭据只走环境变量，`Trading/Config.py` 不落账号密码（`Trading/Config.py:96-105`）；读取点 `Trading/Broker/SimNow.py:590/592-593/612-613`（`_cred`：`os.environ.get(env_key)` 原名读取，非 `TRADING_` 前缀）。
- 父进程起子进程时 `env = dict(os.environ)` 原样继承，再叠加登录链路三键覆盖（`App/AppTrader.py:489-493`；`_link_env` 见 `:1297-1309`：`TRADING_BROKER` / `TRADING_BROKER_PARAMS__TQ_MARKET` / `TRADING_BROKER_PARAMS__CONFIRM_LIVE_TRADING`）。
- 登录方式选择（simnow/live）已在**每次 start 的 body** 里（`Frontend/app.js:9340-9346` `link` 字段），且持久化按 out_dir 落各自 state.db（`:1310-1325`）——多实例化的地基已在。

## 2. 目标、非目标、可行性结论

### 2.1 目标

1. ⑴ 同一账户下，不同品种各自拉起独立交易引擎实例，互不干扰，可同时运行。
2. ⑵ 不同账户下的同品种多周期：**同机不支持**（一个品种同机至多一个实例，无论登录方式），由第二台电脑承载（电脑B 的 `.env` 配另一账户）。同机支持的是**换账户**：先关闭当前实例，再以另一登录方式重新开启。
3. 前端常驻 UI 只有两个入口：**自动下单开关 + 账本面板**（全量分区显示）；保护价线、告警跟随实例。
4. `Trading/` 计算与交易域**零改动**（子进程已参数化，§1.1 #6）。

### 2.2 非目标（明确不做）

- 同品种开两个实例（无论账户/登录方式/周期是否相同，含分属两个 Web 页面）：**永久禁止**，启动期拒绝（底层原因：柜台持仓按账户+品种聚合，两本账对同一份真实持仓读数会互相污染，§1.2）。
- 同机同类型多账户（第二 SimNow/第二实盘）：**不支持**，第二台电脑承载。
- 账户级总保证金/总手数闸门：不新增旋钮（2026-09 风控旋钮两度被裁的拍板口径）。多实例下各引擎风控独立，保证金占用叠加是**边界事实**，写进 §6 提示，不做代码。
- 多策略/多参数同品种并行、引擎内多周期信号融合（策略层功能，另行立项）。

### 2.3 可行性结论

⑴ 的全部共享状态已被证实按合约/目录隔离（§1.1 #7 #8 #9 #10 #11）；同品种互斥（§3.1）保证任何时刻同一柜台持仓只归一个实例；⑵ 由多机承载，柜台级账户隔离使对账/锁仓/平今天然安全。唯一需实测的外部事实：同账号多交易会话（§6 开放项 1）。

## 3. 总体设计

### 3.1 实例模型与唯一键

- **账户 = 登录方式（每机每类一账户）**：每台电脑 `.env` 里至多一个 SimNow 账户（`SN_ACCOUNT`）+ 一个实盘账户（`LIVE_ACCOUNT`），因此**本机登录方式即唯一确定账户**：simnow = 本机 `SN_ACCOUNT`，live = 本机 `LIVE_ACCOUNT`，两者是不同账户。第二个仿真/实盘账户 → 第二台电脑。
- **实例键 = 品种键**：本机一个品种至多一个运行中实例，**与登录方式无关**——仿真在跑时实盘的启动请求被拒，反之亦然。品种键 = `parse_product_key` 归一（`KQ.m@CFFEX.IF` 与 `CFFEX.IF2609` 都归一为 `IF`）——主连与月份合约可能重叠同一柜台持仓，按品种归一才能保证"同一柜台持仓只归一个实例"。实例的数据目录仍按 (登录方式, 品种键) 分开（§3.3）：两个账户的账本必须隔离，恢复（restore）不能串账。
- **唯一性约束：同品种运行中实例全局至多一个**：
  - ⑴ 同机不同品种 → 各自一个实例，可多开；
  - 同品种 → 本机至多一个运行中实例，无论登录方式；
  - **换账户 = 先关闭再开启**：关闭走现有优雅收尾（运行态持仓离场/锁仓保持），随后以另一登录方式重启；拒绝文案须带在跑信息（"IF 已在仿真账户以 5分周期运行"）；
  - 跨机不受此约束：第二台电脑配另一账户可跑同品种。
- **freq 不进键**：freq 是实例的启动参数（实例绑定某个周期运行），不是身份。同品种重复 start 且登录方式相同 = 幂等返回（沿用现语义，`AppTrader.py:334`）；同品种不同登录方式 = 按品种互斥规则处理（§3.10.2）。
- 页面与实例的关系：**页面绑定 = 当前页面品种的实例**。同一实例可被多个页面同时观察（Web1 开 IF 引擎后，Web2 打开 IF 页也看到"运行中"——绑的是同一个实例）。

### 3.2 生命周期（后端）

| 动作 | 现状 | 多实例化后 |
|---|---|---|
| start | 单实例幂等（`:334`） | 按 `品种键` 查运行中实例：无 → 拉起子进程（目录按所选登录方式，§3.3）；有且登录方式相同 → 幂等返回；有但登录方式不同 → 拒绝并提示在跑账户/周期；有但已退出 → 清理后按新登录方式重建 |
| stop | `call_trader_stop()` 无参数 | `stop(symbol?)`；带品种停单个（该品种至多一个运行中实例），不带品种停全部（兼容旧前端调用） |
| status | 返回唯一实例 | 返回 `{instances: [实例投影...], running: 任一在跑}`；实例投影 = 现 `to_dict()` 字段 + `link`/`instance_key` |
| ack / signal-filter | 写唯一 out_dir 的 state.db | **保持无实例键（页面级偏好）**：后端广播写全部实例库，新实例启动时继承当前值（§3.10.3/§3.10.4） |
| trades 统计 | `_discover_state_dbs()` 扫 `Trading/State*`（`:205-219`） | 聚合扫描改为两层（`Trading/State/<登录方式>/<品种键>`，App 侧一处小改，§3.3） |
| product-check | 无实例概念 | 不动（品种白名单 per instance 启动闸门照旧，`:455-463`） |

启动预检顺序（新增第 2 条，其余沿用现路径）：配置可加载 → **品种互斥查重（新增）** → 实盘安全闸门 → 品种白名单 → Popen。

### 3.3 状态目录与托管记录

- **实例 out_dir 命名（用户拍板：收进 State 根目录，两级组织）**：`Trading/State/<登录方式>/<品种键>/`（如 `Trading/State/SimNow/IF`、`Trading/State/SimNow/RB`、`Trading/State/Live/IF`）——`Trading/` 根下只保留一个 `Trading/State` 根目录，不再出现多个 State* 目录；`Trading/State` 下按登录方式（SimNow / Live）、品种键两级分目录。每个叶子目录 = 一个实例的一套文件（state.db / events.jsonl / gateway.log / 停止旗标）。同一品种允许并存两个叶子（仿真/实盘各一，来自历史运行）——账本按此分区显示（§3.10.1）；运行中的至多其一（§3.1 品种互斥）。
- **为什么按实例分目录，而不是共享一个 state.db/events.jsonl/gateway.log**：目录就是实例的隔离边界，是"`Trading/` 零改动 + 实例间无共享可变状态"（§1.1 #7 #8 #9）成立的前提。共享单目录会逐项破坏现有机制：
  - 停止旗标 `.stop_request`/`.ready` 写在 {out_dir} 下（`App/AppTrader.py:79-80`），共享目录会让"停一个品种"的请求变成"停全部引擎"，除非给旗标加实例后缀并改 `Trading/main.py` 的读取——`Trading/` 改动；
  - state.db 的单值键（`auto_order_enabled` 开关态、`ao_link` 上次登录方式）会互相覆盖；`processed_signals`/持仓表混写后，restore 与首拉对账的账本隔离不复存在（§1.2 的污染类事故从柜台层搬进库层）；
  - 多进程并发写同一 SQLite 库，需要 StateDB 层具备并发写保障（WAL/重试）——`Trading/` 改动；
  - events.jsonl 的优雅关闭判定按 out_dir 统计 `auto_order_off` 增量（`App/AppTrader.py:230-244`），共享文件必须按实例过滤；
  - gateway.log 双进程同写有交错/句柄风险，且多实例日志无法按实例阅读。
  代价侧几乎为零：叶子目录数 = 实例数（个位数），每叶子仅 db/事件流/日志/两个旗标小文件；成交统计聚合的扫描从一层 glob 改为两层（`App/AppTrader.py:205-219` 的 `_discover_state_dbs()`，App 侧一处小改）。
- **目录规则（无兼容负担，用户拍板：旧数据由用户清空）**：out_dir 一律按实例键派生，不做旧路径沿用；`out_dir` 不再是 `start()` 入参，`TRADING_STATE_DIR`/`_cfg_out_dir()` 在托管路径上退役（不经 App 直跑引擎的调试场景不受影响）。**升级清理请在空仓状态下做**：旧 state.db 若有未平持仓，清空后实例重启恢复是空账本，引擎对"柜台有仓、账本无仓"只告警不接管（`Reconcile.py:42`），持仓跟踪会断档。
- **托管记录**：`App/trader_launch_record.json`（`:75`）改为记录列表 `{"instances": [ {...}, ... ]}`，不读旧单记录格式，升级时该文件一并删除。服务重启恢复循环化：`_restore_from_file`（`:284-306`）逐条恢复，pid 已死的条目清理。
- **reader 线程与退出上报**：`self._readers`（pid → 线程）与 `self._exit_logged`（pid 集合）本就按 pid 键控（`:288-293`），多实例无需改结构，只改清理时机（对应实例退出时）。

### 3.4 账户模型（每机每类一账户）

> **账户 = 一个真实的交易账户**。每台电脑**每类至多一个**：至多一个 SimNow 账户 + 至多一个实盘账户，配在本机 `.env`。因此**本机"登录方式"唯一确定账户**——simnow = 本机 `SN_ACCOUNT`，live = 本机 `LIVE_ACCOUNT`，两者是不同账户。第二个仿真/实盘账户 → 第二台电脑（各自的 `.env` 配各自的账户）。

- **变量命名（沿用既有原名）**：

  | 变量 | 用途 | 个数 |
  |---|---|---|
  | `TQ_ACCOUNT` / `TQ_PASSWORD` | 天勤平台账号，**仅作 tqsdk 库鉴权**（`TqAuth`，`Trading/Broker/SimNow.py:716`），仿真/实盘共用（`:585` 注释明写"两种模式共用"） | **一份，全实例共享** |
  | `SN_ACCOUNT` / `SN_PASSWORD` | 本机 SimNow 交易账户（`TqAccount("simnow", sn_account, sn_password)`，`:689`/`:715`） | 每机一个（用仿真才配） |
  | `LIVE_ACCOUNT` / `LIVE_PASSWORD` | 本机实盘交易账户（`TqAccount(tq_market, live_account, live_password)`，`:690`/`:715`） | 每机一个（用实盘才配） |
  | `TQ_MARKET` | 期货公司名（仅实盘需要；缺省 `simnow`，并参与 is_live 判据 `:588-598`） | 一份 |

- **子进程凭据零注入**：本机账户就是全局 env，子进程 `env = dict(os.environ)` 原样继承（§1.3），无需任何按账户注入；登录链路三键（`_link_env`，`App/AppTrader.py:1297-1309`）照旧。`_cred()` 用原名读 env（§1.3），**`Trading/` 零改动**维持。
- **开启时无需选账户**：点开开关 → 现有"登录方式"框（`pickTradeLink`，`app.js:9299-9313`）选 SimNow/实盘即可。"开的是哪个账户"的答案恒为：仿真 = 本机 `.env` 的 `SN_ACCOUNT`，实盘 = 本机 `.env` 的 `LIVE_ACCOUNT`。
- **实盘安全闸门**：`confirm_live_trading` 语义不变，逐实例在 start 时经登录链路选择注入（现路径）。
- **`.env` 用户配置全量口径**：

  ```
  # ── 天勤平台账号：全实例共用一份，仅库鉴权 ──
  TQ_ACCOUNT=你的天勤账号
  TQ_PASSWORD=你的天勤密码

  # ── 本机 SimNow 交易账户（用仿真才配）──
  ```

### 3.5 日志

- 子进程自身日志已按 out_dir 隔离（`gateway.log` 落各自实例目录，`AppTrader.py:359-362`）。
- App 侧的全局 tee handler（`_set_engine_log_handler`，`:1060`，把 App 日志指到最后一次启动的实例 gateway.log）在多实例下语义破损：改为**去掉全局 handler**，App 侧实例相关日志直接用 `_engine_log(该实例的 log_file, ...)`（该函数本就接收 log_file 参数，`:371-375` 等），App 自身日志留在主日志。

### 3.6 API 面（App/FrontAPI.py）

- `POST /api/trader/auto-order/on`：body 与今天完全一致（`link` = 登录方式，本机即唯一确定账户）；`symbol`/`freq`/`sse_base` 语义不变。
- `POST /api/trader/auto-order/off`：body 可选 `{link, symbol}`；缺省 = 停全部（并逐实例走现有优雅收尾协议）。
- `GET /api/trader/auto-order/status`：返回结构加 `instances[]`；顶层保留 `running`（任一实例在跑）以兼容渐进改造期的旧消费方。
- `GET /api/trader/auto-order/ledger`（新增，无参数）：账本面板聚合只读接口，一次返回全部分组数据（§3.10.1）。
- `POST /api/trader/auto-order/ack`、`/api/trader/signal-filter`（GET/POST）：**不加实例键**——两者是页面级偏好/水位线，语义与路由形态都保持现状，由后端广播到全部实例（§3.10.3/§3.10.4）。
- `GET /api/trader/trades`、`product-check`：不动（§3.2）。
- 路由形变后需重冻 `Test/snapshots/phase3_routes.json`（`--update`），并同步 phase6 window 白名单（§5）。

### 3.7 前端（Frontend/app.js）

- **实例态 UI 的归属（不设实例级选择器）**：页面只有自动下单开关 + 账本两个常驻入口，三类实例态 UI 的归属由"当前页面品种"决定：
  - **开关**：开启自动下单 → 现有"登录方式"框选仿真/实盘 → start（本页品种已有运行中实例且登录方式不同 → 后端拒绝并提示在跑信息；相同 → 幂等绑定）。关闭自动下单 → 直接停本页品种的唯一运行中实例（同品种单实例，无歧义，§3.10.2）。同品种实例可被多个页面同时观察，任一页面关闭自动下单都会停掉它。
  - **账本**：显示全部实例、按登录方式分区（§3.10.1）——不做品种过滤，账本即全局总览。
  - **保护价分段线**：至多一条线——同品种至多一个运行中实例，`drawRunSegments` 的 symbol + freq 匹配防线保留（实例周期 ≠ 页面周期 → 不画，`app.js:8658-8661`）；回到现状单线形态，无需改。
- **切合约/切周期守卫保留（条件收窄）**：守卫防的是"页面离开正在交易的品种"这一操作风险，与实例数量无关。多实例下守卫条件从"全局有实例在跑"收窄为"**本页品种有运行中实例**"——切合约/切周期时，若当前页面品种存在运行中实例（无论登录方式），拦截并提示"IF 正在仿真账户以 5分周期自动下单——请先关闭自动下单再切换"；本页品种无运行中实例时不拦（其它品种的实例独立运行，不受页面导航影响）。守卫沿用现有两个入口（切合约 loadStock / 切周期 switchFreq）。多页面下同品种的每个页面都被守卫覆盖；要看其它品种，另开浏览器页签即可（该页签无守卫）。
- **轮询**：仍单一 `/status` 5s 轮询 + 账本面板打开期间的 `/ledger` 刷新；前端本地按品种取用，不必 per-instance 多路轮询。
- **版本号**：`app.js?v=45` → 顺延；`Test/test_aol_ledger_display.py` 钉死点与残留断言同步（其自身注释即操作说明，`Test/test_aol_ledger_display.py:127-132`）。

### 3.8 风控与边界事实

- 各实例风控独立（入场/出场/锁仓全部 per 进程）；保证金占用**跨实例叠加，无总闸**（§2.2，拍板口径，文档级提示）。
- 品种白名单（8 个可下单品种）逐实例照旧生效。
- 同账户不同实例共享"今日开仓/平今"额度与手续费统计口径（柜台侧），引擎互不知晓——属账户级事实，不做引擎间协调。

### 3.9 设计决策要点

1. **实例键 = 品种键**：把"同品种同机只能跑一个，无论登录方式"表达成数据约束而非散落判断，禁止项与多开项同源（§3.1）。
2. **每机每类一账户**：本机登录方式即账户——无编号、无选择弹框、零 env 注入，把跨账户需求降为"登录方式维度"或"第二台电脑"（§3.4）。
3. **实例目录收进 `Trading/State/` 单一根目录**（State/<登录方式>/<品种键> 两级）：`Trading/` 根不再出现多个 State* 目录；统计聚合扫描改两层，App 侧一处小改（§3.3）。
4. **守卫保留、条件收窄**：守卫防的是"页面离开正在交易的品种"的操作风险，与实例数量无关——多实例下条件从全局收窄为本页品种有运行中实例（§3.7）。
5. **拒绝要显式**：同品种重复启动从"静默返回"改为"幂等绑定或拒绝 + 明确提示在跑实例的账户与周期"（现状 `:334` 静默吞掉新参数，是用户困惑的直接来源）。
6. **账本全量分区显示**：账本是全局总览（登录方式→品种两级分区），不做实例选择器；常驻 UI 只有两个入口（§3.10.1）。

### 3.10 面板与交互的多实例行为

> 设计原则：**实例态 UI 由"当前页面品种"决定，本来就是全局偏好的保持全局**。逐面板给规则。

#### 3.10.1 账本面板（"账本"按钮 → auto-order-ledger-panel；全量分区显示）

- 现状：数据 = 状态轮询 `/api/trader/auto-order/status` 的 `auto_order.positions`（唯一实例投影）；点击仅切换显隐，持仓行带建仓序号（`Frontend/app.js:8510-8516` 面板注释、`:8560-8604` 渲染；序号为 2026-09-24 拍板）。
- **多实例规则（用户拍板）：账本显示全部实例，按"登录方式 → 品种"两级分区**，不设任何实例选择器（常驻 UI 只保留自动下单开关 + 账本两个入口）：
  - 顶层分区 = 登录方式（SimNow 一区、实盘一区）；某方式下无任何实例 → 整区不显示。
  - 区内每实例一个小节，标题 = "⑴ 品种（周期 · 运行中/已停止）"，区内按品种键稳定排序；小节之下是该实例的持仓行，持仓序号保持**实例内**语义（"1 号仓" = 该实例的第一笔建仓，标题带实例标识后无歧义）。
  - 运行中实例随轮询实时刷新；已停止实例显示其 state.db 持久投影——2026-09-22 拍板"引擎关着也能点账本"的延续，并升级为"全部实例一屏总览"。
  - 数据接口：聚合只读接口 `GET /api/trader/auto-order/ledger`（无参数）→ 一次返回全部分组（后端聚合 = 运行中实例投影 ∪ 全部实例目录持久投影，扫描 `Trading/State/<登录方式>/<品种键>` 两层；实例数为个位数，逐库只读开销可忽略）；面板打开期间随 5s 轮询刷新。
  - 空态：一个实例都没有 → "还没有自动下单记录"（全局空态；无"本页品种"过滤概念）。
- 旧全局兜底（上次运行目录 → 默认目录）退役：其职责由聚合接口扫描全部实例目录取代。

#### 3.10.2 品种互斥与换账户

- **同品种运行中实例至多一个，与登录方式无关**（含分属两个 Web 页面的尝试：Web1 开 IF 跑仿真，Web2 再开 IF 选实盘 → 拒绝）。
- **换账户 = 先关闭再开启**：关闭走现有优雅收尾（运行态持仓离场——平今/平昨至空仓、锁仓保持，然后退出）；随后以另一登录方式重新开启，数据落各自的实例目录（两账户账本隔离）。**不能带着仓位换账户**（现有引擎语义的自然结果）。
- **拒绝文案带在跑信息**："IF 已在仿真账户以 5分周期运行中——同一品种不允许并跑；换账户请先关闭再重新开启。"
- 跨机不受限：第二台电脑配另一账户可跑同品种（诉求⑵的承载路径，§2.1）。

#### 3.10.3 买卖点类型过滤（"显示设置 → 买卖点类型"勾选）

- 现状：一份勾选三处消费——图上画哪些买卖点（页面本地）、引擎信号过滤（`POST /api/trader/signal-filter` 写**该实例** state.db，`Frontend/app.js:5170-5177`）、统计口径（后端 `trades_stats` 读同一份，`App/AppTrader.py:936-944`）。引擎侧约束：过滤值必须落在**实例自己的 state.db**（引擎每个信号现读，`Trading/` 零改动 ⇒ 存储位置不可迁移）。
- **多实例规则：勾选保持页面级全局偏好（一份），不按实例分**：
  - **写入广播**：POST signal-filter（路由形态不变、无实例键）→ 后端把值写进**全部已发现实例**的 state.db（`_discover_state_dbs()` 目录集合）。引擎每信号现读自己库，广播后全体一致。
  - **启动继承**：新实例 start 时，App 把当前过滤值写进新实例库（源 = 任一既有实例库；一个都没有 = 未设置/全放行）。消除"后建实例缺过滤值"的分歧。
  - **GET 回填**：路由不变；后端返回全局口径（各库经广播写保持一致，任取一个库的值，实现上取第一个发现的库并注释说明）。
- 该规则下，统计口径（§3.10.5）继续沿用"单一过滤值套全部历史"的现有实现，`filter_trades_by_bsp_type` 一行不改。

#### 3.10.4 告警 / 轻提示 / ack

- 现状：运行时告警队列只属于运行中的进程（`App/AppTrader.py` `status()` docstring），前端弹框后回 ack 水位线（D11），已确认不再下发。
- **多实例规则：展示合并、确认全局**：
  - 展示：轮询把**全部运行中实例**的 alerts/toasts 合并弹出（带实例前缀，如"[仿真 IF]"），用户在任一页面都能看到任一实例的严重告警——多实例下"只看本页实例的告警"会漏掉另一引擎的风险事件，不可取。
  - ack：保持无实例键 + 全局水位线，后端广播写全部实例库。与"弹窗一次显示全部实例告警"一致（用户关弹窗时已看到全部实例截至当前时刻的告警，全局确认无过认风险）。
  - 前端本地水位（`autoOrderSeenAlertTs`/`autoOrderSeenToastTs`，`app.js:8235/8239`）改为 per 实例键控，防 A 实例水位掩盖 B 实例新告警。

#### 3.10.5 统计弹窗（"统计"按钮 → stats-panel）

- 现状：数据 = `GET /api/trader/trades?symbol=<当前页合约>&union=true`（`Frontend/app.js:4726-4741`）；后端 `trades_stats` 按品种键归一（主连/月份合约合并，2026-09 拍板口径）、**跨全部发现的 state.db 合并**（`_discover_state_dbs()`，`App/AppTrader.py:897-977`），并回传读库可见性（`dbs_scanned`/`sources`/`read_errors`）与统计口径（bsp 过滤，§3.10.3）。
- **多实例规则：语义零变化，来源标注升级**：
  - 合并口径本来就是"账户无关、按品种合并"（既有拍板），多实例下**继续跨登录方式（仿真+实盘）合并，不区分登录方式**（用户确认）——统计回答的是"这个品种在我所有账号上的历史成交表现"，不是"某个实例的表现"。实例目录收进 `Trading/State/` 两层结构（§3.3），`_discover_state_dbs()` 扫描改两层后聚合逻辑不变。
  - **不按登录方式过滤、不加登录方式切换**（与账本的"跟实例走"刻意不同：账本是运行态盯盘视图，统计是历史汇总视图）。若日后要按登录方式拆分，属新需求（可从 `sources[].path` 解析实现），本期不做。
  - **来源可见性升级**：面板增加"数据来源"行，列出本次合并了哪些实例目录（从 `sources[].path` 显示 `登录方式+品种` 与各自笔数）——多实例下"合了哪几个库"必须可见，否则用户无法解释统计数字的构成；`read_errors` 警示行照旧。
  - `union=true` 由前端固定传（现状），不暴露开关。

## 6. 风险与开放项

1. **同账号多交易会话（CTP/SimNow 上限与互踢行为）**：未独立核实，无官方口径。行情侧多会话已被现网证实（每条 SSE 连接独立 TqApi，`DataAPI/TqSdkCSSESource.py:216`；双页面+引擎已是 ≥3 会话并存）。**交易会话**在 Phase 1 验收前先 SimNow 双进程实测（⑴ 同账户多品种并跑必然构成多交易会话）。
