## 阅读约定：怎么引用代码位置（v1.0 定稿，v1.2 沿用）

行号会腐烂，符号名不会。一次普通提交就能让全文行号失效（v0 就是这么废掉的），
而"文档里的行号是错的"比"文档里没写行号"更有害——它会让人对着错误的行下结论。

**约定如下：**

```
① 主索引（默认）：  文件 :: 符号名
      例：App/AppData.py :: names_cache
          App/AppSSE.py :: _per_frame_session

② 需要精确定位到某条语句时：  文件 :: 符号名 @ L行号 (commit 前 7 位)
      例：App/AppRefresh.py :: _refresh_pe_ttm @ L289 (9cbd85d)

③ 文档头部必须标注基线 commit 与生成日期（见本文开头）。

④ 读者若发现行号对不上：先 git diff 该区间确认代码是否已变，
   不要凭旧行号下结论。符号名仍然有效，用它重新定位。
```

**为什么是"符号名为主、行号为辅"，而不是二选一：**
- 不能只用行号——它会腐烂（已实证）。
- 不能只用符号名——有些判断必须看具体语句，比如"`list(...)` 在 `with` 体内还是体外"、
  "return 在第 289 行还是第 267 行"，符号名给不了这个精度。
- 所以是主辅关系：符号名负责**找得到**，行号（带 commit）负责**看得准**。

## 0. 总原则：先消灭共享，再谈锁

锁不是"保护"，是"给并发加约束"——它同时带来复杂度、性能损耗、死锁风险和"看起来安全其实没护住"的错觉。所以第一步永远是问：

> **能不能让这块数据根本不被并发访问？**

能，就别加锁。常见手段：
- 把数据做成**不可变快照**再发布（chan.py 的期货下窗 CChan 若只发布 REST 实际需要的序列，就不会有"发布活对象"问题）。
- 用**每请求/每连接私有实例**替代共享单例。
- 用**消息/队列**串行化，而非共享内存。

只有"共享无法消除"时，才进入下面的维度。

### 0.1 判断顺序

**一问：能不能消除共享？** 能 → 消除，结束。
**二问：共享消不掉，它的归属是什么？** → 走 0.2。
**三问：归属清楚了，走维度 1 起的常规流程。**

### 0.2 作用域归属：这个状态是「会话级」还是「进程级」？【v1.0 新增】

这是 v1.0 最重要的一条补充。它是维度 0「先消灭共享」的**正面表述**——
v0 的写法（"能不能让这块数据根本不被并发访问"）容易被读成"要不要加锁"的前置判断，
而不是"要不要**重新设计归属**"。

#### 0.2.1 先定义：什么叫"会话"？

"进程级"是 OS 概念，边界清晰。但**"会话级"不是操作系统概念，是业务概念——它没有默认值，必须由你定义**。

不要抽象地问"什么是会话"，那会陷入空转。**反过来问：**

> **"如果两个人同时用，什么东西应该是每人一份的？"**

**这个"每人一份"的载体，就是会话边界。** 也就是说，会话边界不是先定义后套用的，
而是从"什么该隔离"这个问题里**推出来**的。

常见的会话边界（由小到大）：

| 层级 | 边界由什么定义 | 生命周期 | chan.py 中的例子 |
|---|---|---|---|
| **请求级** | 一次 HTTP 请求 / 一个协程 | 毫秒 ~ 秒 | 每请求的 `tdx_data_context` 线程局部注入 |
| **连接级** | 一条 SSE / WebSocket | 连接存续期 | `CTqSdkSession`（每 SSE 连接独立 TqApi + 记录缓存）✅ 做对了 |
| **任务级** | 一个 task_id | 任务存续期 | 批量扫描任务——**当前错放在进程级** |
| **标签页级** | 一个浏览器标签页 | 页面存续期 | 前端 `chartData`（单页内并发的竞态场，见 1.5） |
| **用户级** | 一个登录用户 | 登录会话期 | 选点、标注（持久化，按用户隔离） |
| **进程级** | OS 进程 | 进程存续期 | `_ACTIVE_SOURCES`、`app_data` 单例 |
| **主机级** | 跨进程（文件系统 / DB） | 永久 | `zxg.blk`、`text_annotation.json` |

**判据：找出"谁的"。** 每引入一份状态，问它属于谁——属于某次请求？某条连接？某个任务？某个用户？还是这台机器上所有人？
答案是"所有人"的，才放进程级。

#### 0.2.2 两种作用域错配模式

这是这一节最实用的部分。两类问题的形态完全不同，修法也不同。

**模式 A：会话级数据，存放在进程级容器里**
数据本身就是该"每人一份"的，却被放进了全局。
> 案例：`_page_index_code`（`AppScan.py :: _page_index_code @ L100`）、`_scan_start_time`（`@ L97`）、`scanner` 单例（`@ L760`）。
> 三者都是模块级全局、**全部无锁**、且**全部逃出了共享资源登记表**（`AppOrch.py :: SHARED_RESOURCE_REGISTRY @ L85`）。
> 最危险的是 `_page_index_code`：A 页选沪深300成分股、B 页选中证500 → 两页的扫描都按最后设置的那个来，
> **静默扫错一整批股票**，日志里不留任何痕迹。
> 修法：把扫描上下文挂到 `task_id` 任务对象上（`submit_batch_scan` 已经返回 task_id），板块指数随提交参数传入而非后置设置。

**模式 B：会话级资源，被进程级操作管理** ← **更隐蔽**
对象本身是每会话一份的（**这部分做对了**），但管理它的**清理/重置/遍历动作是进程级的**。
> 案例：`CTqSdkSession` 本身是每 SSE 连接一份的（✅ 设计正确，含独立 TqApi + 记录缓存）。
> 但 `close_all()` 遍历的是**全局注册表** `_ACTIVE_SOURCES`（`TqSdkCSSESource.py :: close_all @ L66`），
> 一次调用把**所有**连接全关掉；紧接着 `AppSSE.py :: _cleanup_all_futures_data @ L1808` 清空所有会话的 K 线缓存、
> 删掉所有 `KQ.` 前缀选点、清空整个期货分析缓存。
> 完整链路：页面 B 把期货代码换成股票 → 前端 fire-and-forget 发 `POST /api/futures/cleanup`
> （`Frontend/app.js:4134`，`.catch(()=>{})` 静默，无确认无提示）→ 页面 A/C/D 的 SSE 全部断连。
> **这不是概率事件，是每次必错。** 它在单用户时代完全合理（一人一屏，切走就该清理），多用户下就是事故。
> 修法：cleanup 作用域从"全局"收窄为"按会话"或"只清无主孤儿缓存"；连接关闭由生成器 `finally` 自行回收。

**模式 B 为什么更容易漏**：因为审查时你会看到"`CTqSdkSession` 是每连接的，没问题"，
然后就翻篇了。错的是**管理它的那个动作**，不在对象本身。

**判据（对应两种模式）：**
| | 检查问题 |
|---|---|
| 模式 A | 第二个任务/用户进来，会不会覆盖第一个的**参数或数据**？ |
| 模式 B | 清理/重置动作的作用域，是否**大于**被清理对象的生命周期归属？ |

**口诀：会话级状态放进程级 = 定时炸弹，加锁只是把引信接长，不是拆弹。**

#### 0.2.3 这类问题的可怕之处

**它在单用户测试时 100% 表现正常。** 只在"第二个用户出现"的那一刻爆炸，
而且往往是静默的——不报错，只是数据错了或连接断了。
所以它需要专门的检查动作，不能指望常规测试兜住（详见维度 8.6 场景级回归）。

**交付物：** 每份共享状态旁边标注「归属层级（请求/连接/任务/标签页/用户/进程/主机）」+ 两种模式的检查答案。

#### 0.3 层级 ↔ 锁：能一一对应吗？【v1.1 新增】

上表列了 7 个层级，一个自然的追问是：**每一级对应什么锁？线程锁、进程锁，还是别的？**

**答：不能一一对应。强行做 1:1 映射是范畴错误——层级和锁是两个正交维度。**

理由是：那 7 个层级描述的是**"这份状态属于谁"**（归属），
而锁的类型描述的**"谁会同时访问它"**（并发关系）。
这两件事由完全不同的因素决定，没有理由同步变化。

代码里其实已经写下了正确的说法（`AppOrch.py :: SHARED_RESOURCE_REGISTRY @ L74` 上方注释）：

```
锁的作用域必须与资源的作用域同级：
   进程内堆对象 → threading.Lock / RLock
   跨进程       → OS 层（SQLite WAL / fcntl / multiprocessing.Lock）
                  ⚠ threading.Lock 跨进程**无效但看起来有效**，是最大陷阱
   事件循环内   → asyncio.Lock，且临界区不得跨 await
```

注意它说的是「锁的**作用域**与资源的**作用域**同级」，**不是**「层级 → 锁类型」。
而且它只分了 3 类（进程内 / 跨进程 / 事件循环内），对应不了 7 个层级——这本身就是"不能 1:1"的旁证。

##### 0.3.1 真正能对应的两样东西

**① 层级 → 要不要锁 + 锁的分片键（shard key）**

| 层级 | 同时有几个所有者 | 要不要锁 | 分片键（该按什么 key 分） |
|---|---|---|---|
| 请求级 | 1（该请求独占） | **通常不要**——优先消灭共享 | 无（压根别共享） |
| 连接级 | 1，但可能被**多线程**访问 | 看访问者：SSE 逐帧换线程 → **要** | `conn_id` |
| 任务级 | N 个任务并存 | 要 | `task_id` |
| 标签页级 | N 个标签页 | 前端 JS 单线程 → **不要**（互斥用不上）；后端归入任务/用户级 | `tab_id`（前端只用于**取消**，非互斥） |
| 用户级 | N 个用户 | 要 | `user_id` |
| 进程级 | 进程内全体 | 要 | 无（全局一把） |
| 主机级 | 机器上所有进程 | 要 | 文件路径 / DB 行 |

**分片键是层级最有用的产物。** 同样是"加锁"：进程级是一把全局锁把所有操作串成一行；
任务级按 `task_id` 分片后，两个不同任务**互不阻塞**。选错层级，性能可能差一个数量级。

**② 访问者之间的关系 → 锁的原语类型**

| 并发访问者之间的关系 | 该用什么锁 | 典型误用 |
|---|---|---|
| 同进程，不同线程 | `threading.Lock` / `RLock` | — |
| 同进程，不同协程 | **通常不需要**（单线程调度）；跨 `await` 的 RMW 才用 `asyncio.Lock`，且临界区不得跨 `await` | 用 `threading.Lock` 护协程 = 无谓串行 |
| 同主机，不同进程 | OS 文件锁（`fcntl.flock` / `msvcrt.locking`）、`multiprocessing.Lock`、SQLite WAL | ❌ `threading.Lock`——**无效但看起来有效，最大陷阱** |
| 不同主机 | 分布式锁（DB 行锁 / Redis / etcd） | 文件锁（只在单机有效） |

> 这两张表**正交**：一张决定 key，一张决定原语。任何一份共享状态都要**各查一次**。

##### 0.3.2 一份资源可以同时落在多个层级 → 多层锁必须叠加

这是 0.3 最反直觉、也最容易出错的一点。**层级不是互斥的分类，而是可以叠加的。**

实测（Windows / `msvcrt.locking`，脚本 `verify_lock_layers.py`，4/4 确定性命中）：

| 用例 | 结果 |
|---|---|
| Q1 持锁时，**同进程另一线程**用新句柄抢 OS 文件锁 | 没抢到 ✅ 能挡住 |
| Q1b 持锁时，**另一个进程**抢 OS 文件锁 | 没抢到 ✅ 能挡住 |
| Q2a 只有进程级锁，两进程各做 60 次自增（应得 120） | 终值 **105** → ❌ 丢失 15 次更新 |
| Q2b 进程级锁 + 主机级文件锁**叠加** | 终值 **120** ✅ 无丢失 |

两条结论：

- **主机级锁不能省**：Q2a 证明进程级锁跨进程**完全无效**（`threading.Lock` 是进程内对象，另一进程持有的是另一个副本）。
- **进程级锁也不能省**：Q1 显示文件锁在 Windows 上能挡住同进程异线程，但这是**平台行为**——
  POSIX `flock` 的锁关联的是 open file description，语义与 `msvcrt.locking` 不同。**依赖它等于把正确性押在 OS 实现细节上。**

**本项目正例**（`AppData.py :: save_zxg_blk @ L2495`）——两层锁嵌套叠加，不是二选一：

```python
with self._user_store_lock:               # ① 进程级：挡住本进程内并发的路由线程
    with file_lock(blk_path + ".lock"):   # ② 主机级：挡住独立同步脚本进程
        preserved = _read_preserved_zxg_lines(blk_path)
        ...                               #    读-改-写
        _atomic_write_text(blk_path, "\n".join(final) + "\n", encoding="gbk")
```

`zxg.blk` 确实**同时**落在两个层级：API 进程内的多条路由线程（进程级）+ 独立脚本
`Script/ths_sync_to_tdx.py`（主机级）。所以它必须有两层锁。

**锁顺序必须固定：先进程内、后跨进程（先小作用域，后大作用域）。**
反过来会在"持大锁等小锁"的路径上放大阻塞范围——大作用域锁的等待队列更长。

##### 0.3.3 决策流程：从层级到锁

1. 用 **0.2.1** 判定归属层级。
2. 该层级只有唯一所有者、且只被单线程访问？→ **不加锁**，改成局部 / 线程局部（消灭共享优先于加锁）。
3. 否则按 **0.3.1①** 取分片键（没有 key 就是一把全局锁，但要清楚这是**退让**）。
4. 按 **0.3.1②** 选原语类型；若访问者**既跨进程又跨线程** → 按 **0.3.2** 叠两层。

> **反例（本项目）**：`_page_index_code`（`AppScan.py :: _page_index_code @ L100`）是**任务级**状态，
> 却放在进程级、无锁、无分片键。即使补一把 `threading.Lock`，也只是让两个页面的扫描**串行地互相覆盖**——
> 锁的类型选对了，层级错了，结果仍然错。
> 这就是 0.2 那句口诀的另一种表述：**加锁只是把引信接长，不是拆弹。**

**交付物：** 每份共享状态标注「归属层级 + 分片键 + 锁原语（**可能是多层**）」。

## 0.4 会话隔离作为一种策略：何时该用、何时不能用【v1.2 新增】

维度 0「先消灭共享」与维度 0.2「作用域归属」讲的是"能不能让这块数据根本不被并发访问""这份状态该归谁"。
这一节把它们往前推一步：**主动把状态做成"每会话一份"，用隔离替代加锁**——这是一种比"加锁保护共享"更彻底的策略，也是本项目 X1 / X3 两个已修缺口的本质解法。

### 0.4.1 粒度：会话的载体是标签页，不是请求

> 每个前端标签页 = 一个会话；该标签页内发起的**所有**请求都属于这个会话。

一个标签页在生命周期里会发起很多请求（查询、切周期、开关双窗、轮询……），它们共享同一份 `CChan` / `chartData`，
**必须属于同一个会话**。若把"每个请求"都当成一个会话，状态被切碎，跨请求连续性丢失——所以载体是标签页，不是请求。
（期货侧 `CTqSdkSession` 已是"每 SSE 连接一个会话"，与此对齐；股票侧与扫描侧此前还没这么建模。）

### 0.4.2 它消灭了什么、没消灭什么

**消灭的（按构造）：** 跨标签页的数据破坏类 bug。这正是 X1、X3 的本质——
- 模式 B 的 cleanup 核弹（`/api/futures/cleanup` 的 `close_all()` 关掉**所有**页面的连接）→ 改为"按会话回收 / 只清孤儿缓存"后，一页切走不再破坏其他页。
- 扫描参数串（`_page_index_code` 等全局态）→ 改为按 `task_id` 的会话对象后，两页同扫不再静默扫错。

**没消灭的：**
- 它**没有消除锁**，只是把锁**从进程级全局一把，重定域成会话级每会话一把**。锁的数量没归零，作用域缩小了。
- **单会话内部的并发仍在**：同一条会话里，SSE 写线程、后台刷新线程、扫描收割线程、用户触发的操作会并发改同一个 `CChan`——这些仍要锁，只是锁的作用域收窄到本会话。
- **进程级单例资源不能会话化**：行情连接（TqSdk/tdx）、全市场扫描引擎、`zxg.blk` 文件天生全进程唯一，强行会话化是另一种错配（见 0.2.1：只有"所有人"才放进程级）。它们仍需进程级协调。

> 结论：**会话隔离让锁"更局部、更易推理"，但不是"锁消失"。真正被消灭的是跨标签页的数据破坏类 bug。**

### 0.4.3 四层隔离模型（何时会话化、何时不能）

| 层 | 归属 | 例子（chan.py） | 协调机制 |
|---|---|---|---|
| **L1 会话/连接级** | 每标签页一份 | 该页的 `CChan` + 派生分析 | 每会话一把 RLock，**跨标签页不互相阻塞** |
| **L2 进程级只读共享** | 全进程、不可变 | 原始 K 线抓取结果、参考数据 | 不可变快照 / 读写锁（copy-on-read） |
| **L3 进程级单例资源** | 全进程、天然唯一 | 行情连接、扫描引擎、`zxg.blk` | 进程级锁 / 单所有者 + 发布订阅扇出 |
| **L4 主机级** | 跨进程 | `zxg.blk` 文件 | OS 文件锁（见 2.3 / 6.3 / 0.3.2） |

要点：
- **L1 就是会话化**，价值在于把全局锁的"爆炸半径"从全进程缩到单会话——不同标签页互不阻塞、互不污染。
- **L2 是必须补的底层**：若 L1 每标签页各存一份 `CChan`，两页看同一只股票 = 两份相同昂贵解析，多标签页还会把行情源限频打爆。
  所以 L1 的"会话视图"应架在 L2 进程级只读数据层之上——共享抓取/解析结果，会话只持有自己的可变派生。
  既去除跨标签页的*可变*共享，又保住去重/缓存的好处。
- **L3 不能会话化**；L4 是 L3 中涉及磁盘文件的跨进程兜底。

### 0.4.4 被新增的复杂度（别只看到好处）

会话化把"跨标签页竞争"换成了三件新负担：

1. **内存 / 重算成本**：每会话一份可变状态，标签页多时内存线性增长；同代码多标签页重复解析。
2. **会话生命周期管理（头等公民）**：必须有"会话注册表 + 心跳/超时回收"。这恰恰是 X1 当年出事的根因——没有会话概念，清理只能核弹全清。会话化让清理从"顺手核弹"变"头等公民"，但**注册表本身是新复杂度**。
3. **进程级单例仍要协调**：L3 资源无论怎么会话化，最终都汇聚到一个进程级连接/引擎，那里仍需锁或单所有者扇出。

> **判据（决定一份状态该放哪层）**：先问 0.2.1 的"属于谁"。属于某标签页 → L1；属于全进程且只读 → L2；全进程且唯一 → L3；跨进程 → L4。
> **不要因为"会话化很香"就把 L3 强行拉到 L1**——那会把单例资源变成 N 个会话抢同一份的竞态场。

**交付物：** 在共享资源登记表（3.2）中，每份状态除标注「归属层级 + 分片键 + 锁原语」外，再标注「是否可会话化（L1）还是必须进程级（L3）」。

### 0.4.5 业界标准架构对照【v1.2 新增】

上面的"会话隔离"不是拍脑袋，它对应业界对"多标签页前端 → 后端"这类软件的标准做法。核心只有一句话，也是最容易混淆的点：

> **传输身份 ≠ 逻辑会话身份。**
> - **传输/执行身份**：哪个线程、哪条连接、哪个协程。运行时决定，**易变、可互换**（本项目实测：starlette 把每个 SSE 帧派到不同线程，100% 跨线程）。
> - **逻辑会话身份**："这条消息属于哪个标签页"。它是**消息显式携带的数据**，由客户端在打开标签页时生成、每次请求都带上。
> 后端**绝不靠传输身份推断会话，而是读消息信封里的会话 ID**。传输层只负责把消息送到，会话 ID 是消息自带的"寄件人地址"。

**后端怎么认出是哪个标签页？** 两条路：
- **HTTP/REST（短连接）**：客户端在标签打开时生成 `tab_id`（如 `crypto.randomUUID()`），存**标签页级存储**，每个请求带 `X-Tab-Id` 头。事件循环在**边缘**（单线程里、交给线程池之前）就解析出该头，连同请求传下去——"认出标签页"发生在事件循环，不劳 worker 线程猜。
- **SSE/WebSocket（长连接）**：连接本身就是会话。服务端在 `on_open` 时建一个 per-connection 状态对象，该连接后续消息天然归它（chan.py 期货侧 `CTqSdkSession` 即此）。原生 `EventSource` **不允许自定义头**，故 `tab_id` 须作为 **URL 查询参数**传入握手（与整改中扫描端点改走参数同一思路）。

**线程池共享父进程内存，怎么做到不同会话对应不同资源？**
共享内存不是障碍，恰恰是会话注册表成立的前提。隔离靠**数据结构设计**，不是内存边界。标准模式叫 **"无状态 worker + 有状态会话注册表"**：

```
SESSION_REGISTRY: dict[tab_id -> SessionState]   # 共享内存里的一个字典
SessionState = { CChan, chartData, 各缓存, 每会话 RLock }
```

worker 线程可互换、无状态；它们从请求取 `tab_id` → `REGISTRY[tab_id]` 取本会话 `SessionState` 操作。不同标签页 → 不同 `SessionState` 对象 → 不同内存区块 → **会话间无共享可变状态 → 会话间无需加锁**。每会话一把 RLock 只保护**同一会话内**的并发（SSE 写 / 刷新 / 扫描收割 / 用户操作同改一个 `CChan`）。仍须进程级锁的，只有 L3 单例（行情连接、扫描引擎、`zxg.blk`）。

**业界三类标准形态：**

| 形态 | 适用 | 会话状态放哪 | 代表 |
|---|---|---|---|
| **A. 无状态后端 + 外部会话存储** | 真·Web 规模（多实例负载均衡） | Redis / 数据库 / 会话服务，后端本身无状态 | 谷歌、亚马逊 |
| **B. 单进程桌面应用内嵌 Web 服务** | 本地跑一个进程、浏览器开 localhost 的 UI（**chan.py 即此**） | 进程内 `dict` 当注册表，无需 Redis | chan.py、各类本地分析工具 |
| **C. 连接即会话（实时型）** | SSE/WebSocket 长连接为主 | 每连接一个 actor/状态对象 | 聊天室、行情推送、`CTqSdkSession` |

> **浏览器存储的坑（决定方案能否真隔离）**：浏览器默认把 cookie / localStorage 按"同源"共享给**同浏览器所有标签页**——不特意处理则两标签是同一会话（如 Gmail 多标签共享登录）。要做到"每标签页独立会话"必须用语**标签页级存储**（每标签独有、关标签即清），而非 cookie/localStorage。
> 推论：**跨浏览器（Edge vs Chrome）天然隔离**（独立用户数据目录，存储互不可见），不用操心；**同浏览器开多标签**才是必须用标签页级存储才能区分的场景。若前端完全不实现"生成 + 带 id"机制，后端看到的是匿名请求，连 Edge 与 Chrome 都分不清。

**chan.py 落地（形态 B）最小路径：** ① 前端标签打开时生成 `tab_id` 存标签页级存储，每 API 调用带 `X-Tab-Id`，SSE 握手把 `tab_id` 作查询参数；② 后端在 `AppOrch` 维护 `SESSION_REGISTRY`，首请求/握手建 `SessionState`（含 `CChan`、各缓存、一把 RLock），标签关闭（SSE 断开或心跳超时）回收；③ 各端点取 `tab_id → state`，在 `state.lock` 下操作；④ 行情连接、扫描引擎、`zxg.blk` 维持进程锁。这正把已修的 X1/X3 从"局部会话化"推广为"全局会话化"。

## 维度 1：并发地形图 —— 操作到底在哪个执行体上跑？

你无法判断任何锁的正确性，除非先搞清楚**并发模型**。这一步要画出"执行体 × 操作"的映射。

**1.1 枚举所有执行体。** 常见三类：
- 事件循环线程（asyncio / 单线程跑协程）
- 线程池线程（`run_in_executor` / `anyio.to_thread` / 框架的线程派发）
- 进程池进程（`multiprocessing.Pool`）

**1.2 标注每个请求/任务落在哪类执行体。** 不要靠印象，要追到路由层。在 chan.py 里：`FrontAPI.py` 把股票部分请求直接丢事件循环、部分丢线程池、扫描丢进程池；期货 SSE 走线程池。

**1.3 致命陷阱：执行体的"连续性"假设。**
很多人默认"SSE 一条连接 = 一条常驻线程，全程不换"。**这条假设要实测，不能信文档。**
在 chan.py 里，源码核实 + 实测都推翻了它。

*源码依据*（`starlette/concurrency.py:57`，版本 starlette 1.6.0）：
```python
async def iterate_in_threadpool(iterator):
    as_iterator = iter(iterator)
    while True:
        try:
            yield await anyio.to_thread.run_sync(_next, as_iterator)   # ← 每一帧一次独立派发
        except _StopIteration:
            break
```

*实测数据*（6 条并发 SSE 连接 × 12 帧，帧间 await 模拟推送间隙）：
```
conn0: 帧落线程数=6 跨线程切换=11/11
conn1: 帧落线程数=5 跨线程切换=11/11
conn2: 帧落线程数=4 跨线程切换=11/11
conn3: 帧落线程数=6 跨线程切换=11/11
conn4: 帧落线程数=5 跨线程切换=11/11
conn5: 帧落线程数=5 跨线程切换=11/11
```
**6/6 条连接全部跨线程，11/11 次帧切换全部换线程——100%，不是偶发。**
（v0 记录的是"4/6 发生跨线程迭代"，实测比这更严重。该结论后来已被写进代码注释，
见 `AppOrch.py::SHARED_RESOURCE_REGISTRY` 中 `futures_analysis_cache` 条目的【v6 更正】。）

> 案例：期货下窗的 `session_set(src)` 只在生成器入口设一次 thread-local，但实时循环每根 K 线 `step_load()` 都新建数据源读该线程局部——落在别的线程就串品种，落在没绑定过的线程就回退空缓存。**这是唯一会静默产生错误行情数据的 P0。**
> **✅ 已修**：`AppSSE.py :: _per_frame_session @ L243` 包装器，在**每一次 `next()` 派发**上重新绑定本连接会话，帧末用 `session_context` 还原该线程旧值。单窗（`@ L285`）、双窗（`@ L672`）两条路径均已包装。

**1.4 交付物：** 一张表 —— 操作名 / 执行体 / 是否跨执行体切换 / 线程局部依赖与否。

### 1.5 地形图不能只画后端：单页内的并发请求【v1.0 新增】

画地形图时，"并发"至少有三个正交来源，多数人只想到第一个：

| 来源 | 含义 | 特点 |
|---|---|---|
| **多页并发** | 多个标签页 / 多个浏览器 / 多台机器 | 共享后端进程；跨页还可能共享 localStorage |
| **单页内并发** | 一个页面同时发出的多个飞行中请求 | **一个用户一个页面就能制造竞态** |
| **跨进程并发** | 生产进程 vs 独立脚本进程 | 见维度 2.3 |

**单页内并发**最容易被漏掉，因为它不需要第二个用户。典型形态：

> 案例：chan.py 的 `analyze` 请求**全篇没有 `AbortController`**（`Frontend/app.js` 无一处取消逻辑）。
> 快速连点"查询 / 切周期 / 开关双窗"会产生多个飞行中的请求，**后到的响应覆盖先到者**
> （`chartData = data` 全文替换，如 `app.js:3606`）。
> 用户看到"图表闪了一下又变回去"，且**完全无法稳定复现**——因为它依赖请求到达顺序。
> 修法：发新请求前 `abort()` 旧请求，或给响应带序号、丢弃过期序号的响应。
> **这类问题不是后端加锁能解决的**，竞态发生在前端的共享变量上。

**推论：维度 3 的"数据落点"表里，必须包含前端单例。** 见 3.3。

## 维度 2：隔离边界 —— 谁和谁真正共享内存？

**2.1 进程级天然隔离。** 进程池的多个进程有各自独立的地址空间，内存数据**完全不共享** → 一般**不需要锁**。

**2.2 线程级天然共享。** 同进程的多线程共享：堆、全局变量、模块级变量、类级/静态变量、导入的单例。**这些才需要锁。**

**2.3 非内存资源要单列。** 文件、socket、外部句柄即使进程隔离，一旦多进程/多线程共享同一物理文件，仍需文件锁。

> 案例：`zxg.blk` 有两条写路径。生产路由走**无锁非原子 append**；另一条在**独立的脚本进程**里持 `threading.Lock` + 原子写。后者这把锁是**进程内锁**，跨进程天然无效——这正是进程间共享文件必须上文件锁（而非 threading.Lock）的典型陷阱。
> **✅ 已修**：两条写路径现均加 OS 级文件锁（`AppData.py :: file_lock @ L99`，POSIX `fcntl.flock` / Windows `msvcrt.locking`），落点 `AppData.py :: save_to_zxg_blk @ L2438` 与 `:: sync_zxg_blk @ L2503`；独立脚本侧已收敛到单一写入源 `Script/ths_sync_to_tdx.py:289`，不再自持 `threading.Lock`。

**2.4 共享池会打破隔离。** 即便"进程隔离"，一旦用了**进程池 + 共享内存 / Manager / 共享队列**，隔离就被打开，需要重新评估。
> 口诀：**进程池默认免锁，共享池才要锁。**

**2.5 交付物：** 隔离边界矩阵 —— 资源 / 是否跨线程 / 是否跨进程 / 是否跨非内存介质。

## 维度 3：数据落点 —— 共享的东西存在哪一层？

同一份"共享数据"，落点不同，保护方式天差地别：

| 落点 | 例子 | 风险 |
|---|---|---|
| 实例字段（堆上） | `self._names` | 若被多个执行体引用，需锁 |
| 模块级全局 | `app_data` 单例 | 几乎一定共享，必须登记 |
| 类级/静态 | `_scan_skip_log` | 所有实例共享 |
| 线程局部 | `threading.local()` 会话 | 仅当前线程可见，但**跨线程失配**（见维度 1.3） |
| `contextvars` | 协程上下文 | **逐帧线程派发下不可靠**（见维度 6） |
| **前端模块级单例**【v1.0 新增】 | `chartData`、`realtimeEventSource` | 单页内并发请求的竞态场（见 1.5） |

**3.1 关键陷阱：裸出口 = 暴露共享对象。**
即便方法内部加了锁，如果还留了 `return self._names` 这种裸 `@property`，下游会把它绑成模块级别名（chan.py 里 `AppEngine:200/220/224/304`、`AppRefresh:35/38/42`、`AppScan:50` 全是 `xxx = app_data.names` 这种别名）。这些别名的注释写着"共享同一对象，零漂移"——**零漂移是目的，代价是零保护**，任何线程都能在无锁状态下改它。

> 案例：`AppData.py` 有 **8 个**裸 `@property` 直接返回可变容器——
> `stocks_analysis_cache@L1466`、`futures_analysis_cache@L1470`、`names_cache@L1474`、`pe_cache@L1478`、
> `belong_cache@L1482`、`float_mc_cache@L1486`、`saved_point_times@L1494`、`annotations_cache@L1498`。
> （v0 记的是"1376-1410 的 9 个"：行号已整体前移；且其中 1 个返回标量 bool 不构成风险，精确数字是 8。）
> **❌ 未修**：8 个原样保留，仅配套新增了 `names_snapshot()` / `pe_snapshot()` / `belong_snapshot()`。
> 契约靠注释和 `Test/test_lock_completeness.py` 的 ALLOWLIST 维护，**无任何机器校验下游是否真的用了快照**——3.4 就是这条契约被打破的实证。

**3.2 交付物：** 共享资源登记表（参考 chan.py 的 `AppOrch.py :: SHARED_RESOURCE_REGISTRY @ L85`）。每条至少含：字段名 / 落点 / 执行体 / 是否 RMW / 谁持锁 / **归属层级（见 0.2）**。

> 案例（登记表完备性）：`_scan_skip_log` **整个逃出了登记表**——它不是"加错锁"，是"根本没人管"。
> **✅ 已修**：已登记（`AppOrch.py @ L127-132`）+ 加锁（`AppScan.py :: _scan_skip_log_lock @ L62`）+ 收口为 4 个访问器（`@ L65-86` append/clear/snapshot/count），AST 实证无残留直连。
> **❌ 但登记表仍有漏网**：`_scan_start_time`、`_page_index_code`、`scanner`、`_refresh_starting`、`_scan_store` 单例未登记；
> `_float_mc` 则属"挂名不实"——登记表条目写作 `meta_caches（_names / _pe / _belong）` 没包含它，
> 而它实际被**两把互不相干的锁**分管：加载路径 `AppData.py @ L1982` 持 `_meta_cache_lock`，更新路径 `@ L2010` 持 `_user_store_lock`，
> 读侧 `get_float_mc_from_cache`（`@ L2026`）与 `float_mc_cache_stale`（`@ L1994`）**裸读无锁**。
> 这违反登记表自己在 `AppData.py @ L1384` 立的"一个资源一把锁"纪律。

**3.3 前端落点也不能漏。** 【v1.0 新增】
前端的模块级全局变量同样是共享状态，同样会被并发写（`chartData = data`、`realtimeEventSource = new EventSource(...)`）。
它们不受任何锁保护，而且**后端加锁对它们完全无效**。判据同 3.1：凡是"全局唯一句柄 + 全文替换赋值"的，都是竞态场。

**3.4 案例：契约被打破的实证。**
`AppRefresh.py` 用模块级别名 `_pe_ttm_cache`（= `app_data._pe` 本体）做全表迭代，**无锁**：

all_keys = set(_pe_ttm_cache.keys()) | set(_index_belong_cache.keys())   # AppRefresh.py @ L289，无任何锁
```
而 `AppData.py` 侧的正门已经修好了（快照读、锁内提交）——**修好了正门，别名这扇侧门没关**。详见维度 4.2。

## 维度 4：操作原子性 —— 是不是读-改-写（RMW）？

锁只在"复合操作"上有意义。先把每个操作拆成基本动作：

**4.1 纯单读 / 纯单写：** 若读写方各只有一个执行体，或只读不变，可不加锁（配合不可变快照最佳）。

**4.2 遍历 + 可能外部修改：** 字典/列表迭代期间被 `clear()` 或增删 → `RuntimeError: dictionary changed size during iteration`。

> 案例 a：`get_annotated_codes` 无锁遍历标注表，刷新线程的 `replace_names` 同时 `clear()+update()` → 路由直接 500。

## 维度 5：锁的粒度与覆盖 —— 护容器，还是护对象图？

这是最多人栽的地方：**以为锁了 dict 就万事大吉，其实只护了 dict 的四个瞬间（get/set/del），没护里面那个"还活着的"对象。**

**5.1 容器级锁够不够？** 如果共享的是"一个 dict，value 是不可变标量"，锁 dict 就够。

**5.2 对象图共享：** 如果 value 是**可变对象（CChan、list、嵌套 dict）**，锁只保住"取到指针"这一步，取到后在锁外遍历/修改 `bi_list`、替换 `kl_datas`，就完全无保护。

> 案例（期货下窗）：`_futures_cache_lock` 护住 dict 写入，但 REST 侧 `AppChart.py`、`BSPointList.py` 取到指针出锁后遍历 `bi_list`；而实时循环每根 K 线 `do_init()`（`Chan.py`）把 `kl_datas` 整个换成新的空对象。读到的缓存瞬间过期 → "红框内无完整笔""下窗缓存已过期"类报错很可能就是撞这儿。
> **✅ 已修**，且是本项目修复质量最高的一处：
> - 写侧：`AppSSE.py @ L1064-1069`，`_drain_chan`（含 `step_load → do_init` 整条替换）整体包进**按 key 的 RLock**
> - 读侧 1：`AppChart.py @ L376-380`，锁内取对象 + 锁内 `list(kl_list.bi_list)` 浅拷贝，出锁遍历
> - 读侧 2：`BSPointList.py @ L762-771`，同形
> - 锁同一性由 `AppData.py :: _futures_chan_lock_for_key @ L1700-1705` 保证：写侧与读侧解析出同一 key → 同一把 RLock

> 案例（股票下窗 · **❌ 未修**）：同一处修复在股票侧漏了。
> ```python
> with app_data.stocks_sub_chan_guarded(parent.code, sub_freq) as sub_chan:   # BSPointList.py @ L722
>     sub_kl_list = sub_chan[sub_kl_type]                                     # @ L730 锁内取指针
> # ← 锁在此释放
> if is_stocks:                                                               # @ L773（已在 with 外）
>     sub_bi_list = list(sub_kl_list.bi_list)                                 # @ L776 ★ 锁外才快照
> ```
> 对比期货侧 `@ L771`（`list(...)` 在 `with` 体内），股票侧把它放到了锁外——正是 5.2 描述的"锁只护住取指针这一步"。
> **严重度中等**：`AppEngine.py @ L686-688` 是"先 drain 完再 put"，替换是整体换槽（`@ L1783`）而非就地改写，旧对象保持自洽，
> 故表现为**读到过期下窗笔结构**（区间套判据失真），不会抛 `RuntimeError`。
> 附注：`@ L772` 的注释"以下对 sub_bi_list 的使用均在锁外（快照已与引擎内部状态解耦）"与 `@ L776` 的实际语义矛盾（此时还没快照），属误导性注释。

**5.3 两条正路：**
- （A）**发布不可变快照**：提取下游真正需要的序列（而非活 CChan），发布那一刻 deepcopy/冻结。
- （B）**锁覆盖读取方全过程**：把"取指针 + 遍历 + 使用"整个包进同一把锁（性能差，首选 A）。

**5.4 临界区内不做重活**【v1.0 新增】

锁的代价不止是"串行化"，还有**阻塞放大**：临界区内做的每一点工作，都会被所有等待该锁的线程摊上。
所以"锁粒度过小"（5.2 的问题）和"临界区过重"是同一个维度的两端。

> 案例（**❌ 未修**）：`AppData.py :: _cache_put_locked @ L1580-1584` 在**持 `_stocks_cache_lock` 时**执行 `gc.collect()`：
> ```python
> if len(self._stocks_analysis_cache) >= self.MAX_CACHE_SIZE:      # MAX_CACHE_SIZE = 50 (@ L1355)
>     oldest_key = next(iter(self._stocks_analysis_cache))
>     self._stocks_analysis_cache.pop(oldest_key)
>     gc.collect()                                                  # ★ 持锁时做 stop-the-world 全量 GC
> ```
> 一次全量 GC 发生在临界区内，意味着所有等待 `_stocks_cache_lock` 的线程都被多拖一个 GC 周期。
> 修法：把 `gc.collect()` 移出临界区（出锁后异步或条件触发）。

**判据：临界区内只允许做"必须互斥"的那几行。** 凡是可以挪到锁外的（I/O、GC、重计算、日志格式化），都挪出去。

## 维度 6：选对并发原语 —— 别用错工具

**6.1 `threading.Lock`：** 线程间互斥，最常用。

**6.2 `threading.RLock`：** 可重入，仅用于"同一线程可能嵌套加锁"的少数场景。**不要默认用 RLock**——它会掩盖锁顺序设计缺陷。

**6.3 文件锁（`fcntl.flock` / `msvcrt.locking` / `portalocker`）：** 跨进程共享文件时**必须**用它，不能用 `threading.Lock`。

**6.4 线程局部 / `contextvars` 的陷阱集：**
- **线程局部只在"绑定线程全程不变"的前提下有效。** 逐帧换线程（维度 1.3）下，入口设一次 = 后面帧读不到。
- **`contextvars` 在 `anyio.to_thread.run_sync` 里不可靠。** 实测：`run_sync` 在调用方上下文的**副本**中执行，帧内 `set()` 不回传，同一条线程第 2 帧就丢值——会把"偶发失配"变成"必然失配"。**别把线程局部戏法换成 contextvars 了事。**

**6.5 信号量 / 条件变量：** 限流、等待-通知专用，不是互斥锁的替代品。

## 维度 7：死锁、重入、生命周期

**7.1 锁顺序：** 多把锁同时持有时，全局固定获取顺序，否则交叉等待 → 死锁。
> chan.py 的顺序纪律已明文固化在 `AppData.py @ L1384`：`_user_store_lock → _meta_cache_lock → _stocks_cache_lock → _futures_cache_lock`，`_meta_cache_lock` 为叶子锁。实测未发现逆序，无死锁路径。

**7.2 重入：** 同一执行体递归进入持锁区，`Lock` 会自死锁，`RLock` 不会——据此判断是否真需要 RLock。
> chan.py 的 4 把业务锁均为 RLock；唯一非重入锁 `_refresh_state_lock`（`AppRefresh.py @ L49`）已核实其临界区内无自调用（`@ L67-69` 有显式警告）。

**7.3 释放与 `try/finally`：** 资源"递增"和"释放"必须在同一 `try/finally`，否则异常路径下永久泄漏。
> 案例：`_active_scans` 递增在扫描开始、释放在结束，但不在同一 `try/finally`，扫描抛异常时一次进程池任务永不销毁。
> **✅ 已修**：`AppScanPool.py @ L113` 在锁内递增、与池装配原子；`@ L230` 收割线程 `finally` 归还；`@ L302` 坏池自愈、`@ L310` 启动期异常显式归还。三条出口（正常 / 异常 / 派发失败）全部闭合。

> 案例（v1.0 新增 · **❌ 未修**）：`_futures_chan_locks`（`AppData.py @ L1396`）**只增不删**。
> 全项目仅 3 处引用（`@ L1396` 初始化、`@ L1701` 读、`@ L1704` 写），**无任何清理点**；
> `pop_futures_sub_chan`（`@ L1679`）与 `futures_cache_clear`（`@ L1654-1665`）都只清缓存不清锁表。
> 后果：每个 `symbol:sub_freq` 永久留一把 RLock。按用户输入键控、无上限，长跑缓慢泄漏。
> 不影响正确性，但违反"锁生命周期 = 资源生命周期"。

**7.4 进程池里的锁无效：** `multiprocessing` 子进程拿到的是父进程的**副本**，父进程持有的 `threading.Lock` 对子进程毫无约束力。跨进程协作必须走 `multiprocessing.Manager` / 队列 / 文件锁。
> chan.py 现状：**无危害残留**。worker 经 `spawn` 起独立进程，进程内 `app_data` 各持一份锁副本——无共享即无需锁；`AppScanStore.py @ L104-110` 已把"`_init_lock` 跨进程无效、靠时序而非靠锁"登记为已知边界。

## 维度 8：验证方法论 —— 别用信仰代替证据

锁对不对，**靠推理不够，要验证**。

**8.1 用框架源码核实执行体假设。** 不要"框架应该是一连接一线程吧"。去读 `starlette/concurrency.py`、`anyio` 源码确认派发方式（维度 1.3 就是这样推翻 chan.py 的）。

**8.2 确定性交错复现，不靠调度运气。** 用 `threading.Event` 在关键点卡住一方、放行另一方，强制构造竞态，再断言是否抛错/串值。比"跑很多次看会不会崩"可靠 100 倍。

**8.3 静态扫描兜底（v1.0 扩充）。** 不要只靠"肉眼 review"。写一条 `ast` 静态检查：凡是触碰受保护字段的方法，必须出现在持对应锁的代码路径里。

> 教训：chan.py 现有 `Test/test_lock_v5_guards.py` 用计数包装锁，断言"这些入口持锁"——它问的是"这扇门有没有锁"，**没问"是不是所有门都上了锁"**。上面 5 个缺口因此一路溜过去。静态扫描要反向：从"受保护字段"出发，查所有访问点。

**扫描器必须覆盖三种形态**（漏一种就有系统性盲区，这是 v1.0 补的关键一条）：

| 形态 | 说明 | chan.py 实证 |
|---|---|---|
| **实例字段** | `self._pe` + `with self._锁:` | 现有扫描器只认这一种 |
| **模块级别名** | `_pe_ttm_cache = app_data.pe_cache`，此后绕开 `self.` 直接读写 | `AppRefresh.py @ L38/42` → `@ L289` 无锁遍历，**完全逃出现有扫描器** |
| **跨模块守卫方法** | `with app_data.futures_sub_chan_guarded_by_key(key)` | 不被识别为持锁 |

另：chan.py 的 `Test/test_lock_completeness.py` **只扫 `AppData.py` 一个类**（`@ L159`），
`AppEngine` / `AppRefresh` / `AppScan` / `AppChart` 全在视野外。方向对了（反向扫描），覆盖面太窄。

**8.4 警惕验证脚本自身的假阴性（v1.0 新增）。** 【关键补充】

8.2 讲"要确定性复现"，但没讲一件同样重要的事：**复现脚本本身也可能有 bug，而它给出的"没发现问题"比"发现问题"更危险**——因为你会信它。

> 实例（本次审计真实踩到的坑）：验证 starlette SSE 是否逐帧换线程时，第一版用 `threading.current_thread().name` 统计：
> ```
> conn0: 帧落线程数=1 跨线程切换=0 线程=['AnyIO worker thread']    ← 假阴性
> conn5: 帧落线程数=1 跨线程切换=0 线程=['AnyIO worker thread']    ← 假阴性
> ```
> 结论是"不换线程"——**错的**。原因：AnyIO 工作线程的 `name` **全都叫 `"AnyIO worker thread"`**，
> 名字不是唯一标识，必须用 `threading.get_ident()`。改用线程 ID 后：
> ```
> conn0: 帧落线程数=6 跨线程切换=11/11                             ← 真阳性
> conn5: 帧落线程数=5 跨线程切换=11/11
> ```

**判据：验证脚本要先自证能检出已知问题。** 具体做法——先构造一个**必然**触发该问题的场景跑一遍，
确认脚本能报出来，再拿它去测未知场景。这一步花不了多少时间，但它能挡住"因为测法错了所以什么都没测出来"。

**8.5 大小相同 ≠ 安全。** `replace_names` 用条数相同的 dict 替换，绕过 CPython 的 `ma_used` 迭代检查，不抛错但**静默串表**。验证要同时检查"不崩"和"值对"。

**8.6 补一层场景级回归（v1.0 新增）。** 单元级和静态扫描都查不出的，是"多用户互相影响"这类问题——
因为它的触发条件不在代码里，在**使用方式**里（见 0.2.3）。

建议直接把业务场景写成回归测试：起 N 个并发客户端，分别跑真实的场景组合
（如"多页同时开期货 + 一页切走"、"两页同时扫描不同板块"），
断言"前者不断连""后者结果集正确"。这类测试比任何静态扫描都更贴近真正关心的问题，
而且它能兜住维度 0.2（作用域归属）这一整类——那类问题在单用户测试里 100% 表现正常。
