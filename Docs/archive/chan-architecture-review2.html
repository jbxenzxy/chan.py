3 · 本轮新引入的问题

3.1 新引入 .gitignore 对已跟踪文件无效（item5.1 未真正落地）

实证（在干净副本上真实操作）：
  $ echo "App/*.json" >> .gitignore
  $ 修改 App/stock_names.json
  $ git status --short
   M .gitignore
   M App/stock_float_mc.json      ← 仍然被跟踪
   M App/stock_names.json         ← 仍然被跟踪

原因：.gitignore 只对「未跟踪」文件生效。
      App/last_code_freq.json、stock_float_mc.json、stock_names.json、
      stock_pettm_index.json 这 4 个早已 git ls-files 在册。
补一步即可生效： 
git rm --cached App/*.json
git commit -m "chore: 停止跟踪运行时缓存（配合 .gitignore 的 App/*.json）"
执行后这 4 个文件会从索引移除、但保留在工作目录，刷新产生的数值漂移不再进 diff。 否则上一轮出现过的「缓存文件混进修复提交」还会再发生。

3.2 小瑕疵 注释中英混排

# App/AppScanPool.py:227-228
# 修复：先前 task is None 走 return 早退、且无 try/finally，get_task/
# set_status 抛异常会让收割线程带未归还引用死亡 → 池永不销毁。now 无论

纯文字问题，不影响运行。但这段是「修复说明」注释，将来别人读到这里会被绊一下， 建议把 now 改成「现」。

3.3 残留 B 的 try/finally 未覆盖最外层获取

def _monitor_task(task_id, futures):
    from App.AppScanStore import get_scan_store
    store = get_scan_store()        # ← 仍在 try 之外
    ...
    try:
        task = store.get_task(task_id)
        ...
    finally:
        _release_scan()

若 get_scan_store()（首次访问会建库、建表）抛异常，引用仍然泄漏。 概率很低，但把 try 提到函数第一行即可彻底封死——建议顺手做了，一行的事。
