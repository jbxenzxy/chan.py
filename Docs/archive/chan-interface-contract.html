1契约总览

四个核心接口构成阶段 3 拆分的安全边界。接口一经锁定，实现可自由演进（薄封装 → 搬移 → 重构），调用方不受影响。

接口所在层职责调用方
analyze_stockAppOrch统一缠论分析入口（无状态）FrontAPI 路由 / ScannerService / 手动选点
ScannerService.scanAppOrch批量扫描编排、进度追踪FrontAPI 扫描路由
fetch_and_injectAppOrch数据拉取与注入（阶段 5 后走 DataAPI 抽象层）分析引擎 / 扫描
AppDataAppData缓存 / 持久化 / 标注 / 自选股AppOrch / FrontAPI
依赖方向（严格单向，禁止反向）
FrontAPI.py → App/AppOrch.py → App/AppData.py。AppOrch 只依赖 AppData 的公开接口，AppData 不反向依赖 AppOrch。

2analyze_stock 契约

统一的缠论分析入口：输入代码 + 周期 + 参数，输出笔、线段、中枢、买卖点与选点标注。无状态，可在线程池与 ProcessPool worker 中安全复用。

2.1 签名

analyze_stock(code: str, freq: str = "d", end_date: str | None = None, cache_chan: bool = True, dual: bool = False, step: int | None = None, sub_freq: str | None = None) -> dict

2.2 参数

参数类型默认说明
codestr必填股票 / 指数 / 期货代码。支持 SH000001、000001.SH、KQ.m@CFFEX.IM（期货）等格式，内部经 _get_market_code 归一化
freqstr"d"周期：y / q / m / w / d / 60m / 30m / 5m / 1m / 15s
end_datestr | NoneNone复盘日期（如 "2026/06/29"，仅支持斜杠格式 %Y/%m/%d，连字符格式必须被拒）；None = 实时模式
cache_chanboolTrue是否缓存 CChan 对象（扫描模式传 False 以省内存）
dualboolFalse双窗口模式（主级别 + 子级别）
stepint | NoneNone步进复盘：第 N 步（0 = 最新）
sub_freqstr | NoneNone双窗口下窗周期；None 时用默认映射（股票 w→d, d→30m, 30m→5m；期货 30m→5m, 5m→1m, 1m→15s）

2.5 缓存键约定

模式缓存键格式
单窗口single_{market}_{code}_{freq}_live
双窗口主级别dual_main_{market}_{code}_{freq}_live
双窗口子级别dual_sub_{market}_{code}_{sub_freq}_live
复盘 / 步进single_{market}_{code}_{freq}_{end_date}
不变性
同一 (code, freq, end_date, dual, sub_freq) 输入，返回结构稳定（键集合不变）。阶段 2.5 回归基线已对 analyze_stock 输出做快照校验。

4fetch_and_inject 契约

数据拉取与注入：判断股票 / 期货 → 拉取 K 线 → set_data 注入到 CChan。阶段 5 后统一走 DataAPI 抽象层（source 参数选择数据源）。

4.1 签名

fetch_and_inject(code: str, freq: str = "d", source: str = "tdx", end_date: str | None = None, dual: bool = False, step: int | None = None, sub_freq: str | None = None) -> dict

4.2 参数

参数类型默认说明
codestr必填股票 / 期货代码（同 analyze_stock）
freqstr"d"周期
sourcestr"tdx"数据源：tdx（通达信）/ tqsdk（天勤期货）。阶段 5 后扩展
end_date / dual / step / sub_freq——同 analyze_stock

4.3 数据注入协议

步骤说明实现位置
1. 市场识别经 _get_market_code 判断股票 / 期货，归一化代码AppOrch 消费侧
2. 数据拉取股票：通达信 CTdxAPI 读 K 线 + 前复权；期货：天勤 CTqSdkAPI.fetch_futures_klineDataAPI（TdxAPI / TqSdkAPI）
3. 注入chan.set_data(...) 注入到 CChan，再执行缠论计算AppOrch 消费侧
第一版实现
当前 fetch_and_inject 为薄封装，直接委托 analyze_stock（其内部完成拉取 + 分析）。阶段 5 后拆分为独立的数据拉取 + 注入流程，接口签名保持不变。

6错误处理约定

服务层只抛领域异常，API 层通过统一中间件捕获并映射 HTTP 状态码（设计文档 7.7 节）。

异常HTTP 状态码触发场景
AppError500领域异常基类（含 AnalysisError / ConfigError）
DataFetchError502数据源获取失败
AnalysisError500缠论分析失败
ConfigError500配置缺失 / 不一致
NotFoundError404标的 / 资源不存在
PersistenceError503持久化失败（AppOrch.py 实现 503，HTTP 503 = Service Unavailable 语义更准确）
返回约定
业务函数成功返回数据字典；失败返回 {"error": "..."}（REST 层转为 4xx/5xx）。SSE 路径通过 error 事件推送错误。
