3 · 新引入的缺陷（均已脚本实证）

缺陷 A · AppRefresh 装饰器破坏重入守卫 新引入 潜伏

# App/AppRefresh.py:405-425
def _reset_refresh_running(fn):
    @functools.wraps(fn)
    def _wrapper(*args, **kwargs):
        try:
            return fn(*args, **kwargs)
        finally:
            _refresh_status["running"] = False     # ← 无条件复位
    return _wrapper

@_reset_refresh_running
def _refresh_stock_names():
    if _refresh_status["running"]:
        return                                     # ← 守卫早退，本不该动标志
    _refresh_status["running"] = True
    ...
实证输出（verify_newbugs.py）：
  前置: running = True  (模拟另一线程刷新中)
  B 调用后: running = False
  [缺陷成立] B 只是撞到守卫返回，却把 running 清成 False
影响判断（说清楚严重度）：HTTP 路径 refresh_stock_names_async 在起线程前先检查 running，所以经由 API 目前触发不到，属潜伏缺陷，不是现网故障。
但它确实把守卫改坏了：refresh_stock_names()（阻塞版）已由 AppOrch 导出， 将来一旦有人接上这个入口，两个刷新就会并发跑，同时写 stock_names.json / stock_pettm_index.json 并各自 replace_names（整表替换，最后写者胜）。
建议修法（把置位移进装饰器，守卫只判不写）： 
def _reset_refresh_running(fn):
    @functools.wraps(fn)
    def _wrapper(*a, **kw):
        if _refresh_status["running"]:
            return                      # 撞守卫：直接返回，不进 finally 的复位
        _refresh_status["running"] = True
        try:
            return fn(*a, **kw)
        finally:
            _refresh_status["running"] = False
    return _wrapper

缺陷 B · 扫描池引用计数泄漏 新引入

# App/AppScanPool.py:211-212  —— 早退，不归还引用
    task = store.get_task(task_id)
    if task is None:
        return                          # ← _release_scan() 没被调用

# 且 _monitor_task 函数体无 try/finally：
#   store.get_task / store.set_status 任一步抛异常 → 线程直接死 → 引用永久泄漏
实证输出（verify_newbugs.py）：
  前置: _active_scans = 1 (模拟 1 批扫描在跑)
  _monitor_task(不存在任务) 后: _active_scans = 1
  [缺陷成立] 引用未归还 (泄漏 1 个)
为什么比改前更差：改前每批结束必定 destroy_pool()，最坏情况是并发互取消（可重试、可感知）。 改后一旦泄漏，_active_scans 永不归零 → _release_scan 永远走不到销毁分支 → worker 进程长驻到进程退出，内存不再归还，且此后每次扫描都在累加一个回不来的计数。 这与「即用即弃、内存归还」的设计目标正好相反。

触发条件：task is None 需要任务行消失（概率低）；但更一般的形态是 函数体没有 try/finally——get_task/set_status 遇到 SQLite 异常 （锁超时、磁盘满）就会让线程带着未归还的引用死掉。
建议修法（把归还放进 finally）： 
def _monitor_task(task_id, futures):
    try:
        ...原逻辑...                    # task is None 的早退也改成 fall through
    finally:
        _release_scan()                 # 无论如何都归还

缺陷 C · destroy_pool() 变死代码，且其注释现在说反了 新引入

# 生产代码中的 destroy_pool 调用点：0 处（仅定义 + 注释提及）
# App/AppScanPool.py:332 的 docstring 仍写着：
#   「destroy_pool 是每次扫描完成后主动调用」   ← 现在是 _release_scan()，此句已假
