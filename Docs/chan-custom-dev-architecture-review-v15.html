一、目标架构（针对本软件功能的最优形态）

先回答「最优目标架构是什么」，作为后续差距判定的基准。

1.1 纵向分层（依赖严格单向）

Frontend/→ FrontAPI.py
API 层·薄路由→ App/AppOrch.py
服务层·编排→ App/AppData.py
数据层·缓存/持久化 + DataAPI/
数据源抽象层·唯一可见 tqsdk

依赖方向：Frontend → API → 服务 → 数据 + 数据源抽象，禁止反向；API 层保持「薄」（只做参数校验 + 转发 + 响应组装）。

1.2 横向模块化（按业务能力切分）

功能域模块核心职责
更新AppRefresh.py名称 / PE / 市值 / 归属刷新
配置AppConfig.py + ChanConfig.py基础设施配置 / 算法参数（双文件分离）
图表交互AppChart.py分析漏斗 / 搜索 / 选点 / 红框 / 标注
批量扫描AppScan.py + AppScanPool.py + AppScanStore.py扫描编排 / 进程池 / SQLite 结果共享
盘后下载AppDownload.py委托 ElTdxAPI 薄封装
SSE 实时流AppSSE.py期货实时推送 / 静态分析 / 期货选点 / 元数据

1.3 并发模型（双路径）

  • 交互路径：线程池 + 全局串行锁（引擎缓存非线程安全前提下的保守策略）。
  • 批量路径：ProcessPoolExecutor（spawn）+ SQLite WAL 跨进程共享结果，绕开 GIL。
  • SSE 路径：每连接独立 TqApi + CChan（SELF_CONTAINED），不加引擎锁。

1.4 数据源抽象（单一抽象原则）

  • DataAPI/ 定义统一接口（CommonStockAPI），屏蔽 TDX / TqSdk / 其它源差异。
  • 「从哪拿」归 DataAPI，「存哪/怎么存」归 AppData，两者互不依赖。

职责边界判定（AppData vs DataAPI，归档自《AppData-vs-DataAPI-职责边界》）：判定不依结果形态，而依数据所有权与是否构成应用长期状态。

归属判据典型职责数据所有权
AppData.py数据归应用持有 / 决定缓存+写盘 / 计算产物缓存、持久化、标注、自选股、行业映射、计算产物缓存（LRU / CSV/JSON 持久化 / CRUD / 标注去重）应用一方 · 长期持有 · 可靠写盘 · 原子操作
DataAPI/只从外部读取、用完即释放（不构成应用长期业务状态）通达信文件、AKShare、深交所官网、TqSdk、取K线（网络/盘面适配、格式解析、行情获取）外部源 · 瞬时拉取 · 用完释放（仅保留拉取侧优化缓存）

依赖方向：FrontAPI → AppOrch → AppData → AppConfig，AppData 与 DataAPI 互不依赖（设计 4.4）。四选股来源归属：自选股 / 板块指数2·3（应用自有映射文件）归 AppData；指数成分股（外部瞬时读取）归 DataAPI。
