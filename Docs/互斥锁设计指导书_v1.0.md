## 0. 总原则：先消灭共享，再谈锁

锁不是"保护"，是"给并发加约束"——它同时带来复杂度、性能损耗、死锁风险和"看起来安全其实没护住"的错觉。所以第一步永远是问：

> **能不能让这块数据根本不被并发访问？**

能，就别加锁。常见手段：
- 把数据做成**不可变快照**再发布（chan.py 的期货下窗 CChan 若只发布 REST 实际需要的序列，就不会有"发布活对象"问题）。
- 用**每请求/每连接私有实例**替代共享单例。
- 用**消息/队列**串行化，而非共享内存。

只有"共享无法消除"时，才进入下面的维度。

### 0.1 判断顺序

**一问：能不能消除共享？** 能 → 消除，结束。
**二问：共享消不掉，它的归属是什么？** → 走 0.2。
**三问：归属清楚了，走维度 1 起的常规流程。**

### 0.2 作用域归属：这个状态是「会话级」还是「进程级」？【v1.0 新增】

这是 v1.0 最重要的一条补充。它是维度 0「先消灭共享」的**正面表述**，但 v0 的写法（"能不能让这块数据根本不被并发访问"）容易被读成"要不要加锁"的前置判断，而不是"要不要**重新设计归属**"。

**核心判据：每引入一份共享状态，先回答三个问题。**

| 问 | 若答"是" | 若答"否" |
|---|---|---|
| 这份状态**只属于当前用户/连接/任务**吗？ | 它就不该放在进程级 | 才能放进程级 |
| 第二个用户进来时，应该看到**自己的一份**吗？ | 同上 | —— |
| 某个用户结束操作时，应该**连带清理**它吗？ | 同上 | —— |

三问全"否"才可以放进程级（真正全局的配置、缓存、只读元数据）。**只要有一问答"是"，它就是会话级状态，放在进程级就是埋雷。**

**这条的可怕之处：这类问题在单用户测试时 100% 表现正常。** 它只在"第二个用户出现"的那一刻爆炸，而且往往是静默的——不报错，只是数据错了。

> 案例 A（进程级误用 · P0）：`/api/futures/cleanup` 是全局核弹。
> 页面 B 把期货代码换成股票代码 → 前端 fire-and-forget 发 `POST /api/futures/cleanup`（`app.js:4134`，`.catch(()=>{})` 静默，无确认无提示）→
> `FrontAPI.py:518` 调 `close_all()`，而它遍历的是**全局注册表** `TqSdkCSSESource.py:74-78` 的 `_ACTIVE_SOURCES`，
> 把**所有**页面的 TqApi 全部关掉；紧接着 `AppSSE.py:1808` 的 `_cleanup_all_futures_data()` 清空**所有**页面的期货 K 线缓存、
> 删掉**所有** `KQ.` 前缀选点、清空整个期货分析缓存。
> 结果：页面 A/C/D 正在看的期货 SSE 全部断连。**这不是概率事件，是每次必错。**
> 它在单用户时代完全合理（一人一屏，切走就该清理），多用户下就是事故。
> 修法**不是加锁**，是收窄作用域：cleanup 从"全局"改为"按会话/只清孤儿缓存"。

> 案例 B（进程级误用 · 高）：扫描域三个全局态。
> `_scan_start_time`（`AppScan.py:97`）、`_page_index_code`（`AppScan.py:100`）、`scanner` 单例（`AppScan.py:760`）——
> 三个都是模块级全局、**全部无锁**、且**全部逃出了 `SHARED_RESOURCE_REGISTRY`**（登记表在 `AppOrch.py:85`）。
> 最危险的是 `_page_index_code`：A 页选沪深300成分股、B 页选中证500 → 两页的扫描都按最后设置的那个来，
> **静默扫错一整批股票**，日志里没有任何痕迹。
> 修法同样不是加锁：`submit_batch_scan` 已经返回 `task_id`，把扫描上下文挂到任务对象上；板块指数随提交参数传入而非后置设置。

**口诀：会话级状态放进程级 = 定时炸弹，加锁只是把引信接长，不是拆弹。**

**交付物：** 每份共享状态旁边标注「会话级 / 进程级」+ 三问的答案。

## 维度 1：并发地形图 —— 操作到底在哪个执行体上跑？

你无法判断任何锁的正确性，除非先搞清楚**并发模型**。这一步要画出"执行体 × 操作"的映射。

**1.1 枚举所有执行体。** 常见三类：
- 事件循环线程（asyncio / 单线程跑协程）
- 线程池线程（`run_in_executor` / `anyio.to_thread` / 框架的线程派发）
- 进程池进程（`multiprocessing.Pool`）

**1.2 标注每个请求/任务落在哪类执行体。** 不要靠印象，要追到路由层。在 chan.py 里：`FrontAPI.py` 把股票部分请求直接丢事件循环、部分丢线程池、扫描丢进程池；期货 SSE 走线程池。

**1.3 致命陷阱：执行体的"连续性"假设。**
很多人默认"SSE 一条连接 = 一条常驻线程，全程不换"。**这条假设要实测，不能信文档。**
在 chan.py 里，源码核实 + 实测都推翻了这个假设。

*源码依据*（`starlette/concurrency.py:57`，版本 starlette 1.6.0）：
```python
async def iterate_in_threadpool(iterator):
    as_iterator = iter(iterator)
    while True:
        try:
            yield await anyio.to_thread.run_sync(_next, as_iterator)   # ← 每一帧一次独立派发
        except _StopIteration:
            break
```

*实测数据*（6 条并发 SSE 连接 × 12 帧，帧间 await 模拟推送间隙）：
```
conn0: 帧落线程数=6 跨线程切换=11/11
conn1: 帧落线程数=5 跨线程切换=11/11
conn2: 帧落线程数=4 跨线程切换=11/11
conn3: 帧落线程数=6 跨线程切换=11/11
conn4: 帧落线程数=5 跨线程切换=11/11
conn5: 帧落线程数=5 跨线程切换=11/11
```
**6/6 条连接全部跨线程，11/11 次帧切换全部换线程——100%，不是偶发。**
（v0 记录的是"4/6 发生跨线程迭代"，实测比这更严重。这个结论后来已被写进代码注释，见 `AppOrch.py` 登记表中 `futures_analysis_cache` 条目的【v6 更正】。）

> 案例：期货下窗的 `session_set(src)` 只在生成器入口设一次 thread-local，但实时循环每根 K 线 `step_load()` 都新建数据源读该线程局部——落在别的线程就串品种，落在没绑定过的线程就回退空缓存。**这是唯一会静默产生错误行情数据的 P0。**
> **✅ 已修**：`AppSSE.py:243` 的 `_per_frame_session` 包装器，在**每一次 `next()` 派发**上重新绑定本连接会话，帧末用 `session_context` 还原该线程的旧值。单窗（`:285`）、双窗（`:672`）两条路径均已包装。

**1.4 交付物：** 一张表 —— 操作名 / 执行体 / 是否跨执行体切换 / 线程局部依赖与否。

### 1.5 地形图不能只画后端：单页内的并发请求【v1.0 新增】

画地形图时，"并发"至少有三个正交来源，很多人只想到第一个：

| 来源 | 含义 | 特点 |
|---|---|---|
| **多页并发** | 多个标签页 / 多个浏览器 / 多台机器 | 共享后端进程；跨页还可能共享 localStorage |
| **单页内并发** | 一个页面同时发出的多个飞行中请求 | **一个用户一个页面就能制造竞态** |
| **跨进程并发** | 生产进程 vs 独立脚本进程 | 见维度 2.3 |

**单页内并发**最容易被漏掉，因为它不需要第二个用户。典型形态：

> 案例：chan.py 的 `analyze` 请求**全篇没有 `AbortController`**（`Frontend/app.js` 没有一处取消逻辑）。
> 快速连点"查询 / 切周期 / 开关双窗"会产生多个飞行中的请求，**后到的响应覆盖先到者**（`chartData = data` 全文替换，如 `app.js:3606`）。
> 用户看到的现象是"图表闪了一下又变回去"，且**完全无法稳定复现**——因为它依赖请求到达顺序。
> 修法：发新请求前 `abort()` 旧请求，或给响应带序号、丢弃过期序号的响应。这类问题**不是后端加锁能解决的**，因为竞态发生在前端的共享变量上。

**推论：维度 3 的"数据落点"表里，必须包含前端单例。** 见 3.3。

## 维度 2：隔离边界 —— 谁和谁真正共享内存？

**2.1 进程级天然隔离。** 进程池的多个进程有各自独立的地址空间，内存数据**完全不共享** → 一般**不需要锁**。

**2.2 线程级天然共享。** 同进程的多线程共享：堆、全局变量、模块级变量、类级/静态变量、导入的单例。**这些才需要锁。**

**2.3 非内存资源要单列。** 文件、socket、外部句柄即使进程隔离，一旦多进程/多线程共享同一物理文件，仍需文件锁。

> 案例：`zxg.blk` 有两条写路径。生产路由走**无锁非原子 append**；另一条在**独立的脚本进程**里持 `threading.Lock` + 原子写。后者这把锁是**进程内锁**，跨进程天然无效——这正是进程间共享文件必须上文件锁（而非 threading.Lock）的典型陷阱。
> **✅ 已修**：两条写路径现在都加 OS 级文件锁（`AppData.py:99-147`，POSIX `fcntl.flock` / Windows `msvcrt.locking`），落盘点 `AppData.py:2438` 与 `:2503`；独立脚本侧也已收敛到单一写入源 `Script/ths_sync_to_tdx.py:289`，不再自持 `threading.Lock`。

**2.4 共享池会打破隔离。** 即便"进程隔离"，一旦用了**进程池 + 共享内存 / Manager / 共享队列**，隔离就被打开，需要重新评估。
> 口诀：**进程池默认免锁，共享池才要锁。**

**2.5 交付物：** 隔离边界矩阵 —— 资源 / 是否跨线程 / 是否跨进程 / 是否跨非内存介质。

## 维度 3：数据落点 —— 共享的东西存在哪一层？

同一份"共享数据"，落点不同，保护方式天差地别：

| 落点 | 例子 | 风险 |
|---|---|---|
| 实例字段（堆上） | `self._names` | 若被多个执行体引用，需锁 |
| 模块级全局 | `app_data` 单例 | 几乎一定共享，必须登记 |
| 类级/静态 | `_scan_skip_log` | 所有实例共享 |
| 线程局部 | `threading.local()` 会话 | 仅当前线程可见，但**跨线程失配**（见维度 1.3） |
| `contextvars` | 协程上下文 | **逐帧线程派发下不可靠**（见维度 6） |
| **前端模块级单例**【v1.0 新增】 | `chartData`、`realtimeEventSource` | 单页内并发请求的竞态场（见 1.5） |

**3.1 关键陷阱：裸出口 = 暴露共享对象。**
即便方法内部加了锁，如果还留了 `return self._names` 这种裸 `@property`，下游会把它绑成模块级别名（chan.py 里 `AppEngine:200/220/224/304`、`AppRefresh:35/38/42`、`AppScan:50` 全是 `xxx = app_data.names` 这种别名）。这些别名的注释写着"共享同一对象，零漂移"——**零漂移是目的，代价是零保护**，任何线程都能在无锁状态下改它。

> 案例：`AppData.py` 有 **8 个**裸 `@property` 直接返回可变容器——
> `stocks_analysis_cache:1466`、`futures_analysis_cache:1470`、`names_cache:1474`、`pe_cache:1478`、
> `belong_cache:1482`、`float_mc_cache:1486`、`saved_point_times:1494`、`annotations_cache:1498`。
> （v0 记的是"1376-1410 的 9 个"：行号已整体前移，且其中 1 个返回标量 bool 不构成风险，精确数字是 8。）
> **❌ 未修**：8 个原样保留，仅配套新增了 `names_snapshot()` / `pe_snapshot()` / `belong_snapshot()`。
> 契约靠注释和 `Test/test_lock_completeness.py` 的 ALLOWLIST 维护，**无任何机器校验下游是否真的用了快照**——3.4 就是这条契约被打破的实证。

**3.2 交付物：** 共享资源登记表（参考 chan.py 的 `AppOrch.py:85` 的 `SHARED_RESOURCE_REGISTRY`）。每条至少含：字段名 / 落点 / 执行体 / 是否 RMW / 谁持锁 / **作用域（会话级 / 进程级，见 0.2）**。

> 案例（登记表完备性）：`_scan_skip_log`（`AppScan.py:61`）**整个逃出了登记表**——它不是"加错锁"，是"根本没人管"。
> **✅ 已修**：已登记（`AppOrch.py:127-132`）+ 加锁（`AppScan.py:62`）+ 收口为 4 个访问器（`:65-86` append/clear/snapshot/count），AST 实证无残留直连。
> **❌ 但登记表仍有漏网**：`_scan_start_time`、`_page_index_code`、`scanner`、`_refresh_starting`、`_scan_store` 单例未登记；
> `_float_mc` 则属"挂名不实"——登记表条目写作 `meta_caches（_names / _pe / _belong）` 没包含它，
> 而它实际被**两把互不相干的锁**分管：加载路径 `AppData.py:1982` 持 `_meta_cache_lock`，更新路径 `:2010` 持 `_user_store_lock`，
> 读侧 `get_float_mc_from_cache`（`:2026`）与 `float_mc_cache_stale`（`:1994`）**裸读无锁**。
> 这违反登记表自己在 `AppData.py:1384` 立的"一个资源一把锁"纪律。

**3.3 前端落点也不能漏。** 【v1.0 新增】
前端的模块级全局变量同样是共享状态，同样会被并发写（`chartData = data`、`realtimeEventSource = new EventSource(...)`）。
它们不受任何锁保护，而且**后端加锁对它们完全无效**。判据同 3.1：凡是"全局唯一句柄 + 全文替换赋值"的，都是竞态场。

**3.4 案例：契约被打破的实证。**
`AppRefresh.py:289` 用模块级别名 `_pe_ttm_cache`（= `app_data._pe` 本体）做全表迭代，**无锁**：
```python
all_keys = set(_pe_ttm_cache.keys()) | set(_index_belong_cache.keys())   # AppRefresh.py:289，无任何锁
```
而 `AppData.py` 侧的正门已经修好了（快照读、锁内提交）——**修好了正门，别名这扇侧门没关**。详见维度 4.2。

## 维度 4：操作原子性 —— 是不是读-改-写（RMW）？

锁只在"复合操作"上有意义。先把每个操作拆成基本动作：

**4.1 纯单读 / 纯单写：** 若读写方各只有一个执行体，或只读不变，可不加锁（配合不可变快照最佳）。

**4.2 遍历 + 可能外部修改：** 字典/列表迭代期间被 `clear()` 或增删 → `RuntimeError: dictionary changed size during iteration`。

> 案例 a：`get_annotated_codes` 无锁遍历标注表，刷新线程的 `replace_names` 同时 `clear()+update()` → 路由直接 500。
> **✅ 已修**：`AppData.py:2352-2357` 在锁内构造**两层**快照（dict + 逐键 list），锁外遍历副本。
> 两层拷贝是必要的——写者 `add_annotation`（`:2280`）是就地 `append`，只拷一层不够。

> 案例 b（v1.0 新增 · 唯一有真实并发写者的未修缺口）：`AppRefresh.py:286-307`。
> ```python
> try:
>     all_keys = set(_pe_ttm_cache.keys()) | set(_index_belong_cache.keys())   # 289 ★ 全表迭代，无锁
>     ...
>     _safe_write_json_file(app_config.stock_pe_ttm_file, combined, ...)
> except Exception as e:
>     log.info(f"[PE-TTM] 保存失败: {e}")      # 306 ★ 静默吞掉
> ```
> 并发写者有两个，均持 `_meta_cache_lock`：`AppData.py:1933-1934`（`_pe.update()`）与 `:1957-1958`（`replace_index_belong` 的 `clear()+update()`）。
> **后果**：抛 `RuntimeError` 但被 `:306` 吞掉，只打一行日志 → **静默丢失整轮 PE/指数归属落盘**；
> 若条数恰好相同，则按维度 10.5 的机理**静默串表**。
> 同函数还有一处无锁 RMW：`:267-268`（检查 → 写）。

## 维度 5：锁的粒度与覆盖 —— 护容器，还是护对象图？

这是最多人栽的地方：**以为锁了 dict 就万事大吉，其实只护了 dict 的四个瞬间（get/set/del），没护里面那个"还活着的"对象。**

**5.1 容器级锁够不够？** 如果共享的是"一个 dict，value 是不可变标量"，锁 dict 就够。

**5.2 对象图共享：** 如果 value 是**可变对象（CChan、list、嵌套 dict）**，锁只保住"取到指针"这一步，取到后在锁外遍历/修改 `bi_list`、替换 `kl_datas`，就完全无保护。

> 案例（期货下窗）：`_futures_cache_lock` 护住 dict 写入，但 REST 侧 `AppChart.py`、`BSPointList.py` 取到指针出锁后遍历 `bi_list`；而实时循环每根 K 线 `do_init()`（`Chan.py`）把 `kl_datas` 整个换成新的空对象。读到的缓存瞬间过期 → "红框内无完整笔""下窗缓存已过期"类报错很可能就是撞这儿。
> **✅ 已修**，且是本项目修复质量最高的一处：
> - 写侧：`AppSSE.py:1064-1069`，`_drain_chan`（含 `step_load → do_init` 整条替换）整体包进**按 key 的 RLock**（`if chan_lock is not None: with chan_lock: _drain_chan(chan)`）
> - 读侧 1：`AppChart.py:376-380`，锁内取对象 + 锁内 `list(kl_list.bi_list)` 浅拷贝，出锁遍历
> - 读侧 2：`BSPointList.py:762-771`，同形
> - 锁同一性由 `AppData.py:1700-1705` 的 `_futures_chan_lock_for_key` 保证：写侧 `futures_sub_chan_lock(symbol,sub_freq)`（`AppSSE.py:798`）与读侧 `futures_sub_chan_guarded_by_key(cache_key)` 解析出同一 key → 同一把 RLock

> 案例（股票下窗 · **❌ 未修**）：同一处修复在股票侧漏了。
> ```python
> with app_data.stocks_sub_chan_guarded(parent.code, sub_freq) as sub_chan:   # BSPointList.py:722
>     sub_kl_list = sub_chan[sub_kl_type]                                     # :730 锁内取指针
> # ← 锁在此释放
> if is_stocks:                                                               # :773（已在 with 外）
>     sub_bi_list = list(sub_kl_list.bi_list)                                 # :776 ★ 锁外才快照
> ```
> 对比期货侧 `:771`（`list(...)` 在 `with` 体内），股票侧把它放到了锁外——正是 5.2 描述的"锁只护住取指针这一步"。
> **严重度中等**：`AppEngine.py:686-688` 是"先 drain 完再 put"，替换是整体换槽（`:1783`）而非就地改写，旧对象保持自洽，
> 故表现为**读到过期下窗笔结构**（区间套判据失真），不会抛 `RuntimeError`。
> 附注：`:772` 的注释"以下对 sub_bi_list 的使用均在锁外（快照已与引擎内部状态解耦）"与 `:776` 的实际语义矛盾（此时还没快照），属误导性注释。

**5.3 两条正路：**
- （A）**发布不可变快照**：提取下游真正需要的序列（而非活 CChan），发布那一刻 deepcopy/冻结。
- （B）**锁覆盖读取方全过程**：把"取指针 + 遍历 + 使用"整个包进同一把锁（性能差，首选 A）。

## 维度 6：选对并发原语 —— 别用错工具

**6.1 `threading.Lock`：** 线程间互斥，最常用。

**6.2 `threading.RLock`：** 可重入，仅用于"同一线程可能嵌套加锁"的少数场景。**不要默认用 RLock**——它会掩盖锁顺序设计缺陷。

**6.3 文件锁（`fcntl.flock` / `msvcrt.locking` / `portalocker`）：** 跨进程共享文件时**必须**用它，不能用 `threading.Lock`。

**6.4 线程局部 / `contextvars` 的陷阱集：**
- **线程局部只在"绑定线程全程不变"的前提下有效。** 逐帧换线程（维度 1.3）下，入口设一次 = 后面帧读不到。
- **`contextvars` 在 `anyio.to_thread.run_sync` 里不可靠。** 实测：`run_sync` 在调用方上下文的**副本**中执行，帧内 `set()` 不回传，同一条线程第 2 帧就丢值——会把"偶发失配"变成"必然失配"。**别把线程局部戏法换成 contextvars 了事。**

**6.5 信号量 / 条件变量：** 限流、等待-通知专用，不是互斥锁的替代品。

## 维度 7：死锁、重入、生命周期

**7.1 锁顺序：** 多把锁同时持有时，全局固定获取顺序，否则交叉等待 → 死锁。
> chan.py 的顺序纪律已明文固化在 `AppData.py:1384`：`_user_store_lock → _meta_cache_lock → _stocks_cache_lock → _futures_cache_lock`，`_meta_cache_lock` 为叶子锁。实测未发现逆序，无死锁路径。

**7.2 重入：** 同一执行体递归进入持锁区，`Lock` 会自死锁，`RLock` 不会——据此判断是否真需要 RLock。
> chan.py 的 4 把业务锁均为 RLock；唯一非重入锁 `_refresh_state_lock`（`AppRefresh.py:49`）已核实其临界区内无自调用（`:67-69` 有显式警告）。

**7.3 释放与 `try/finally`：** 资源"递增"和"释放"必须在同一 `try/finally`，否则异常路径下永久泄漏。
> 案例：`_active_scans` 递增在扫描开始、释放在结束，但不在同一 `try/finally`，扫描抛异常时一次进程池任务永不销毁。
> **✅ 已修**：`AppScanPool.py:113` 在锁内递增、与池装配原子；`:230` 收割线程 `finally` 归还；`:302` 坏池自愈、`:310` 启动期异常显式归还。三条出口（正常 / 异常 / 派发失败）全部闭合。

> 案例（v1.0 新增 · **❌ 未修**）：`_futures_chan_locks`（`AppData.py:1396`）**只增不删**。
> 全项目仅 3 处引用（`:1396` 初始化、`:1701` 读、`:1704` 写），**无任何清理点**；
> `pop_futures_sub_chan`（`:1679`）与 `futures_cache_clear`（`:1654-1665`）都只清缓存不清锁表。
> 后果：每个 `symbol:sub_freq` 永久留一把 RLock。按用户输入键控、无上限，长跑缓慢泄漏。
> 不影响正确性，但违反"锁生命周期 = 资源生命周期"。

**7.4 进程池里的锁无效：** `multiprocessing` 子进程拿到的是父进程的**副本**，父进程持有的 `threading.Lock` 对子进程毫无约束力。跨进程协作必须走 `multiprocessing.Manager` / 队列 / 文件锁。
> chan.py 现状：**无危害残留**。worker 经 `spawn` 起独立进程，进程内 `app_data` 各持一份锁副本——无共享即无需锁；`AppScanStore.py:104-110` 已把"`_init_lock` 跨进程无效、靠时序而非靠锁"登记为已知边界。

## 维度 8：容量与配额 —— 并发体会不会耗尽有限资源？【v1.0 新增】

前面 7 个维度都在问"**会不会错**"，这一个问的是"**够不够用**"。

它容易被忽略，因为这类故障**没有数据竞争、没有死锁、锁全都对，系统就是会越来越慢，而且不报错**。等到用户抱怨"卡"的时候，已经很难归因了。

**8.1 凡是"有限"的都要登记。** 至少包括：线程池/连接池容量、缓存容量与淘汰策略、文件句柄、外部 API 配额、长连接数。

**8.2 长连接与短请求要分开算容量。** 长连接（SSE、WebSocket）会**长期占用**一个执行体，它和"毫秒级的短请求"抢同一个池时，池的有效容量会被长连接吃掉。这类挤兑不会抛异常，只表现为延迟上升。

**8.3 注意"一个逻辑操作消耗 N 份配额"。** 这是最反直觉的一条——配额消耗往往和操作数不成 1:1。

> 案例（chan.py · **❌ 未修**）：股票分析缓存 LRU 上限 50（`AppData.py:1355` `MAX_CACHE_SIZE = 50`）。
> - **双窗一次吃掉 2 个槽**：`_analyze_stock_internal`（`AppEngine.py:311`）在一次调用里建**两个独立的 CChan**（`:684` 先建下窗 `sub_chan`、`:690-707` 再建上窗 `chan`，各自 `step_load()`），分别落 `dual_sub` 与 `dual_main` 两个缓存键（`:354-355`）。
>   所以"双窗 = 1 个 HTTP 请求"只在**请求数**口径成立；在**算力与缓存占用**口径上，它就是两个单窗口。
> - **多用户下颠簸（thrash）**：50 个槽位被 N 个页面争抢，本该命中的请求反复重算。
> - **更糟的是淘汰路径**：`AppData.py:1580-1584` 在**持 `_stocks_cache_lock` 时**执行 `gc.collect()`——
>   一个 stop-the-world 全量 GC 发生在临界区内。淘汰越频繁（多用户场景必然更频繁），
>   所有其他线程在 `_stocks_cache_lock` 上多等的 GC 周期就越多。
> 修法：`gc.collect()` 移出临界区（出锁后异步/条件触发）；上限改为按内存占用而非条目数。

**8.4 交付物：** 容量登记表 —— 资源 / 总量 / 每个操作消耗几份 / 耗尽时的表现（报错？变慢？静默？）。
**"耗尽时的表现"这一列尤其重要**：静默降级的故障最难排查。

Q0. 这份状态是「会话级」还是「进程级」？（维度 0.2）
    └─ 会话级却被放在进程级 → 先改归属，别急着加锁。

    └─ 能 → 消除共享，结束（优先）。
Q3. 共享的是「容器」还是「容器里还活着的对象」？
    └─ 活对象 → 锁必须覆盖读取方全过程，或改发不可变快照（维度 5）。
Q4. 跨进程还是跨线程？

Q5. 操作是读-改-写或遍历+外部修改吗？（维度 4）

Q6. 依赖线程局部/上下文变量吗？

Q8. 获取顺序固定？释放有 try/finally？进程池里没用 threading.Lock？（维度 7）
    └─ 否则补上。
Q9. 它会耗尽什么有限资源吗？耗尽时是报错还是静默变慢？（维度 8）
    └─ 静默变慢的故障最贵，优先登记。
```

## 维度 10：验证方法论 —— 别用信仰代替证据

锁对不对，**靠推理不够，要验证**。

**10.1 用框架源码核实执行体假设。** 不要"框架应该是一连接一线程吧"。去读 `starlette/concurrency.py`、`anyio` 源码确认派发方式（维度 1.3 就是这样推翻 chan.py 的）。

**10.2 确定性交错复现，不靠调度运气。** 用 `threading.Event` 在关键点卡住一方、放行另一方，强制构造竞态，再断言是否抛错/串值。比"跑很多次看会不会崩"可靠 100 倍。

**10.3 静态扫描兜底（v1.0 扩充）。** 不要只靠"肉眼 review"。写一条 `ast` 静态检查：凡是触碰受保护字段的方法，必须出现在持对应锁的代码路径里。

> 教训：chan.py 现有 `Test/test_lock_v5_guards.py` 用计数包装锁，断言"这些入口持锁"——它问的是"这扇门有没有锁"，**没问"是不是所有门都上了锁"**。上面 5 个缺口因此一路溜过去。静态扫描要反向：从"受保护字段"出发，查所有访问点。

**扫描器必须覆盖三种形态**（漏一种就会有系统性盲区，这是 v1.0 补的关键一条）：

| 形态 | 说明 | chan.py 实证 |
|---|---|---|
| **实例字段** | `self._pe` + `with self._锁:` | 现有扫描器只认这一种 |
| **模块级别名** | `_pe_ttm_cache = app_data.pe_cache`，此后绕开 `self.` 直接读写 | `AppRefresh.py:38/42` → `:289` 无锁遍历，**完全逃出现有扫描器** |
| **跨模块守卫方法** | `with app_data.futures_sub_chan_guarded_by_key(key)` | 不被识别为持锁 |

另：chan.py 的 `Test/test_lock_completeness.py` **只扫 `AppData.py` 一个类**（`:159`），
`AppEngine` / `AppRefresh` / `AppScan` / `AppChart` 全在视野外。方向对了（反向扫描），覆盖面太窄。

**10.4 警惕验证脚本自身的假阴性（v1.0 新增）。** 【关键补充】

10.2 讲"要确定性复现"，但没讲一件同样重要的事：**复现脚本本身也可能有 bug，而且它给出的"没发现问题"比"发现问题"更危险**——因为你会信它。

> 实例（本次审计真实踩到的坑）：验证 starlette SSE 是否逐帧换线程时，第一版用 `threading.current_thread().name` 统计：
> ```
> conn0: 帧落线程数=1 跨线程切换=0 线程=['AnyIO worker thread']    ← 假阴性
> conn5: 帧落线程数=1 跨线程切换=0 线程=['AnyIO worker thread']    ← 假阴性
> ```
> 结论是"不换线程"——**错的**。原因：AnyIO 工作线程的 `name` **全都叫 `"AnyIO worker thread"`**，
> 名字不是唯一标识，必须用 `threading.get_ident()`。改用线程 ID 后：
> ```
> conn0: 帧落线程数=6 跨线程切换=11/11                             ← 真阳性
> conn5: 帧落线程数=5 跨线程切换=11/11
> ```

**判据：验证脚本要先自证能检出已知问题。** 具体做法——先构造一个**必然**触发该问题的场景跑一遍，
确认脚本能报出来，再拿它去测未知场景。这一步花不了多少时间，但它能挡住"因为测法错了所以什么都没测出来"。

**10.5 大小相同 ≠ 安全。** `replace_names` 用条数相同的 dict 替换，绕过 CPython 的 `ma_used` 迭代检查，不抛错但**静默串表**。验证要同时检查"不崩"和"值对"。

**10.6 补一层场景级回归（v1.0 新增）。** 单元级和静态扫描都查不出的，是"多用户互相影响"这类问题——因为它的触发条件不在代码里，在**使用方式**里。

建议直接把业务场景写成回归测试：起 N 个并发客户端，分别跑真实的场景组合（如"多页同时开期货 + 一页切走"、"两页同时扫描不同板块"），
断言"前者不断连""后者结果集正确"。这类测试比任何静态扫描都更贴近真正关心的问题，
而且它能兜住维度 0.2（作用域归属）这一整类——那类问题在单用户测试里 100% 表现正常。

## 11. 勘误：v0 中已确认失实的表述

诚实记录比悄悄改掉有用——这三条如果留在 v0 里，下一个人会踩。

**① v0 §9.2 称"`repro_lock_gaps.py` 用此法对 5 个缺口 5/5 确定性命中"。**
核实结果：**该文件不在仓库中**。`Test/` 下现存 `test_lock_completeness.py`、`test_lock_v5_guards.py`、`test_lock_v6_fixes.py`，无 `repro_lock_gaps.py`。
影响：v0 描述的确定性交错复现能力**无法回归**。这句话容易给人"已有复现能力"的错觉，实际没有。
→ 维度 10.2 的方法论依然成立，但**工具需重建**，且重建后要按 10.4 先自证能检出已知问题。

**② v0 全文行号已整体失效。**
原因：后续提交（含 `769e66d 更新 lock`）把 `AppData.py` 的锁块与 `__init__` 大幅前移。
例：裸 property 块从 `1376-1410` 迁至 `1453-1499`。
→ v1.0 全部行号按 HEAD `9cbd85d` 重取。**教训：文档里的行号会腐烂，引用行号时应同时标注 commit。**

**③ v0 称"9 个裸 `@property`"。**
精确数字是 **8 个返回可变容器**（`AppData.py:1466/1470/1474/1478/1482/1486/1494/1498`）；
第 9 个是 `float_mc_loaded`（`:1490`）返回标量 bool，不可变，不构成风险。
