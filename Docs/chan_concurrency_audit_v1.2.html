3.4 层级 ↔ 锁：7 个层级能一一对应到锁吗？v1.1 新增

结论：不能。强行做 1:1 映射是范畴错误——层级和锁是两个正交维度。
指导书 §0.2.1 列的 7 个层级（请求 → 连接 → 任务 → 标签页 → 用户 → 进程 → 主机）描述的是 "这份状态属于谁"（归属）；而锁的类型描述的是 "谁会同时访问它"（并发关系）。两者由完全不同的因素决定，没有理由同步变化。

代码里其实已经写下了正确的说法（AppOrch.py @ L74，SHARED_RESOURCE_REGISTRY 上方注释）：

锁的作用域必须与资源的作用域同级：
   进程内堆对象 → threading.Lock / RLock
   跨进程       → OS 层（SQLite WAL / fcntl / multiprocessing.Lock）
                  ⚠ threading.Lock 跨进程**无效但看起来有效**，是最大陷阱
   事件循环内   → asyncio.Lock，且临界区不得跨 await

注意它说的是「锁的作用域与资源的作用域同级」，不是「层级 → 锁类型」。而且它只分 3 类，对应不了 7 个层级——这本身就是"不能 1:1"的旁证。

① 层级真正决定的是：要不要锁 + 分片键

层级同时几个所有者要不要锁分片键（按什么 key 分）
请求级1（该请求独占）通常不要 优先消灭共享无 —— 压根别共享
连接级1，但可能被多线程访问看访问者 SSE 逐帧换线程 → 要conn_id
任务级N 个任务并存要task_id
标签页级N 个标签页不要 前端 JS 单线程，互斥用不上tab_id（前端只用于取消，非互斥）
用户级N 个用户要user_id
进程级进程内全体要无（全局一把）
主机级机器上所有进程要文件路径 / DB 行

分片键是层级最有用的产物。同样叫"加锁"：进程级是一把全局锁把所有操作串成一行；任务级按 task_id 分片后，两个不同任务互不阻塞。选错层级，性能可能差一个数量级。

② 锁的原语类型由"访问者之间的关系"决定

并发访问者之间的关系该用什么锁典型误用
同进程，不同线程threading.Lock / RLock—
同进程，不同协程通常不需要（单线程调度）；跨 await 的 RMW 才用 asyncio.Lock，且临界区不得跨 await用 threading.Lock 护协程 = 无谓串行
同主机，不同进程OS 文件锁（fcntl.flock / msvcrt.locking）、multiprocessing.Lock、SQLite WAL❌ threading.Lock 无效但看起来有效
不同主机分布式锁（DB 行锁 / Redis / etcd）文件锁（只在单机有效）

两张表正交：一张决定 key，一张决定原语。任何一份共享状态都要各查一次。

③ 一份资源可以同时落在多个层级 → 多层锁必须叠加

这是最反直觉、也最容易出错的一点：层级不是互斥的分类，而是可以叠加的。实测（Windows / msvcrt.locking，脚本 verify_lock_layers.py，4/4 确定性命中）：

用例结果
Q1 持锁时，同进程另一线程用新句柄抢 OS 文件锁没抢到 ✅ 能挡住
Q1b 持锁时，另一个进程抢 OS 文件锁没抢到 ✅ 能挡住
Q2a 只有进程级锁，两进程各做 60 次自增（应得 120）终值 105 ❌ 丢失 15 次更新
Q2b 进程级锁 + 主机级文件锁 叠加终值 120 ✅ 无丢失
  • 主机级锁不能省：Q2a 证明进程级锁跨进程完全无效——threading.Lock 是进程内对象，另一进程持有的是另一个副本。
  • 进程级锁也不能省：Q1 显示文件锁在 Windows 上能挡住同进程异线程，但这是平台行为。POSIX flock 的锁关联 open file description，语义与 msvcrt.locking 不同。依赖它等于把正确性押在 OS 实现细节上。
本项目正例（AppData.py :: save_zxg_blk @ L2495）——两层锁嵌套叠加，不是二选一： 
with self._user_store_lock:               # ① 进程级：挡住本进程内并发的路由线程
    with file_lock(blk_path + ".lock"):   # ② 主机级：挡住独立同步脚本进程

zxg.blk 确实同时落在两个层级：API 进程内的多条路由线程（进程级）+ 独立脚本 Script/ths_sync_to_tdx.py（主机级），所以它必须有两层锁。 锁顺序固定：先进程内、后跨进程（先小作用域后大作用域）——反过来会在"持大锁等小锁"的路径上放大阻塞范围。
反例：_page_index_code（AppScan.py :: _page_index_code @ L100）是任务级状态，却放在进程级、无锁、无分片键。 即使补一把 threading.Lock，也只是让两个页面的扫描串行地互相覆盖——锁的类型选对了，层级错了，结果仍然错。 这正是 §0.2 那句口诀的另一种表述：加锁只是把引信接长，不是拆弹。

3.5 会话隔离作为一种策略：何时该用、何时不能用？v1.2 新增

结论：会话隔离让锁"更局部、更易推理"，但不是"锁消失"。
它把锁从"进程级全局一把"重定域成"会话级每会话一把"，消灭的是跨标签页的数据破坏类 bug（X1 cleanup 核弹、X3 扫描串参数）， 但单会话内部并发、进程级单例资源（行情连接 / 扫描引擎 / zxg.blk）的协调仍在。

会话的载体是标签页，不是请求：一个标签页在生命周期里发起很多请求，它们共享同一份 CChan / chartData，必须属于同一个会话。期货侧 CTqSdkSession 已是"每连接一个会话"，股票侧与扫描侧此前还没这么建模。

四层隔离模型：何时会话化、何时不能

层归属例子（chan.py）协调机制
L1 会话/连接级每标签页一份该页的 CChan + 派生分析每会话一把 RLock，跨标签页不互相阻塞
L2 进程级只读共享全进程、不可变原始 K 线抓取结果、参考数据不可变快照 / 读写锁（copy-on-read）
L3 进程级单例资源全进程、天然唯一行情连接、扫描引擎、zxg.blk进程级锁 / 单所有者 + 发布订阅扇出
L4 主机级跨进程zxg.blk 文件OS 文件锁（见 2.3 / 6.3 / 0.3.2）

L1 就是会话化，价值是把全局锁的"爆炸半径"从全进程缩到单会话。L2 是必须补的底层：若每标签页各存一份 CChan，两页看同一只股票 = 两份相同昂贵解析，多标签页还会把行情源限频打爆——所以 L1 的"会话视图"应架在 L2 进程级只读数据层之上，共享抓取/解析结果，会话只持有自己的可变派生。L3 不能会话化；L4 是 L3 的跨进程兜底。

别只看到好处——会话化新增三件负担：
  1. 内存 / 重算成本：每会话一份可变状态，标签页多时内存线性增长；同代码多标签页重复解析。
  2. 会话生命周期管理（头等公民）：必须有"会话注册表 + 心跳/超时回收"。这恰恰是 X1 当年出事的根因——没有会话概念，清理只能核弹全清。
  3. 进程级单例仍要协调：L3 资源无论怎么会话化，最终都汇聚到一个进程级连接/引擎，那里仍需锁或单所有者扇出。
判据：先问 0.2.1 的"属于谁"。属于某标签页 → L1；全进程且只读 → L2；全进程且唯一 → L3；跨进程 → L4。不要因为"会话化很香"就把 L3 强行拉到 L1。

7对提问的回应

Q0 v1.1：7 个层级（请求/连接/任务/标签页/用户/进程/主机）能一一对应到锁吗？每一级该用什么锁？

不能一一对应。层级描述"状态属于谁"，锁描述"谁会同时访问它"——两者正交，没有理由同步变化。强行 1:1 会得出"_page_index_code 是任务级所以该用任务锁"这种没法落地的结论。

真正能对应的是两样东西：

  • 层级 → 要不要锁 + 分片键。请求级通常不加锁（消灭共享）；进程级是一把全局锁；任务级按 task_id 分片，不同任务互不阻塞。选错层级，性能可能差一个数量级。
  • 访问者关系 → 锁的原语类型。同进程多线程 → threading.Lock；同主机跨进程 → OS 文件锁；跨主机 → 分布式锁；事件循环内 → asyncio.Lock。

还有一个反直觉点：一份资源可以同时落在多个层级，此时多层锁必须叠加，不是二选一。 实测：只有进程级锁时，两进程各自增 60 次得 105（丢 15 次）；叠加文件锁后得 120（无丢失）。 本项目 zxg.blk 就是这么做的——进程内 _user_store_lock + 跨进程 file_lock 嵌套。 完整论证、判据表与实测脚本见 §3.4 与指导书 §0.3。

一个隐含假设需要修正：你说的"多个网页"我按"多标签页"理解了，你确认本意是单页内并发 + 多页间并发两层都要。这两层的技术含义不同——单页内并发不需要第二个用户就能制造竞态（analyze 无 AbortController，快速连点产生飞行中请求，后到覆盖先到），且后端加锁对它完全无效，因为竞态发生在前端共享变量上。

Q2：想法合理吗？

合理，顺序也对（功能清单 → 并发地形 → 锁审计，正是维度 1→2→3 的落地）。但"能否支持"建议拆成四层分别回答：

① 数据正确性
会不会读到错数据 / 写坏文件？
→ 基本达标（12/16 已修）
② 跨页隔离性
A 页操作会不会影响 B 页？
→ 不达标（X1 必然互相破坏）
③ 容量/性能
多页时会不会越来越慢？
→ 按你的意见不在本次讨论范围
④ 语义合理性
多页共用全局状态是否合乎预期？
→ 部分不达标（X3/X6）
Q3：我有更好的建议吗？

有三条（原第 2 条"容量维度"已按你的意见撤下）。它们指向同一件事：这次审计暴露的 P0，指导书 v0 的 9 个维度抓不全。不是维度错了，是覆盖面有盲区。

  1. 补一个维度：作用域归属 —— "这个状态是会话级还是进程级？"
    X1 和 X3 都不是锁问题，是把会话级状态放在了进程级。这其实是维度 0「先消灭共享」的正面表述，但 v0 的写法容易被读成"要不要加锁"的前置判断，而不是"要不要重新设计归属"。v1.0 已把它展开成维度 0.2，并细分为两种错配模式（模式 A：数据放错容器；模式 B：管理动作的作用域大于对象归属）。模式 B 尤其隐蔽——对象设计是对的，错的是清理它的动作。
  2. 把"验证方法论"加一条：警惕验证脚本自身的假阴性。
    我这次实测就踩了坑：用 threading.current_thread().name 统计线程切换，得到"0 次切换"的假阴性——AnyIO 工作线程的名字全都一样，必须用 get_ident()。指导书讲"要确定性复现"，但没讲"复现脚本本身也可能有 bug"。判据：验证脚本要先自证能检出已知问题。（v1.0 已补为维度 8.4）
  3. 把静态扫描的覆盖面问题写进正文。
    现在 test_lock_completeness.py 只扫 AppData.py 一个类、只认 self._field 形态、只认 with self.锁，导致 AppRefresh.py:289 完全在视野外。建议在指导书里明确列出扫描器必须覆盖的三种形态：实例字段 / 模块级别名 / 跨模块守卫方法。（v1.0 已补为维度 8.3 表格）

另外一条流程建议：把"场景判定"环节固化成回归测试——不是测锁，而是测场景： 起 N 个并发客户端分别跑"多页期货 SSE + 一页切走"和"两页同时扫描不同板块"， 断言前者不断连、后者结果集正确。这类测试能直接兜住 X1/X3，而且比任何静态扫描都贴近你真正关心的问题。（v1.0 已补为维度 8.6）
