# 常驻服务进程与两引擎 · 运行架构与设计评估(2026-09-30 讨论整理)

> **一句话摘要**:前端页面只是仪表盘,交易引擎独立于浏览器运行(关页面/Edge 休眠均不影响交易);常驻服务进程是缠论引擎的宿主 + 交易引擎的托管者,同时是两个消费方的共同上游(单点)。与业界主流架构对照,真正的结构性偏离只有一条——**交易关键路径经过常驻服务进程**(交易引擎的 Source 注册表仅 SSE/Replay,信号必须由它供给);其余偏离(文件轮询、同步终判、行情会话按连接复制)在单机规模下自洽、无感。文档末尾汇总待拍板项。

## 1. 术语与角色(对齐后)

术语护栏:引擎只有两个,行文必须写全称——**交易引擎** = `Trading/`(自动下单);**缠论引擎** = `Trading/` 之外的部分(K线/分型/笔/段/中枢/买卖点)。

| 角色 | 是什么 | 不是什么 |
|---|---|---|
| **常驻服务进程** | `FrontAPI`(uvicorn,端口 18081):**缠论引擎的宿主**(行情接入、K线合成、笔段中枢买卖点计算、图表与 SSE 广播)+ **交易引擎的托管者**(`AppTrader`:启停/看护/读落盘) | 不是第三个引擎;是进程载体 |
| **交易引擎** | `Trading/main.py` 子进程,**每品种一个实例**(IF 实例、IM 实例)。订阅缠论广播的 K 线与买卖点,做风控、FOK 报单、离场/锁仓、对账;结果落盘 | 不是页面;不重算缠论(`Trading/` 对缠论主程序零 import) |
| **缠论引擎** | 宿主在常驻服务进程内,为页面图表与 SSE 广播供数 | — |
| **Edge 页面 ×2** | 纯仪表盘:图表(SSE 推流)+ 自动下单动态(Worker 每 5s 轮询)+ 弹窗/系统通知 | 不是引擎;不是交易链路的一环 |
| **快期3** | 同一 CTP 柜台的独立观察端 | — |

### 2.2 消费方模型(三点精化)

1. **是同一个端点、两条独立连接**:交易引擎(`Trading/Source/SSE.py` 的 `SseSource`)与 Edge 页面订阅同一个 SSE 端点(`/api/futures/read/stream`),各持一条独立 HTTP 长连接;服务端"每连接 1 条常驻线程 + 独立会话"(`FrontAPI.py` 文件头自述)。一边休眠/关闭,不影响另一边。
2. **依赖方向**:两个消费方并列、互相不依赖;共同上游 = 常驻服务进程(单点)。
3. **一处不对称**:Edge 比交易引擎多消费一路——自动下单动态(委托/告警/账本/开关)不在缠论推流里,而是交易引擎**落盘**(`state.db` / `events.jsonl` / `gateway.log`)→ 托管层读取 → 页面 Worker 轮询转出。数据流向:缠论引擎 →(SSE)→ {交易引擎, Edge 画图};交易引擎 →(落盘)→ 常驻服务进程 →(轮询接口)→ Edge。

## 3. 运行机制事实(全部经代码核实)

### 3.1 交易引擎与浏览器的解耦(结论:关页面/休眠均不影响交易)

- 交易引擎是常驻服务进程拉起的独立 Python 子进程,启停唯一触发 = `.stop_request` 标志文件(见 §3.3),**代码里不存在"浏览器断开→停引擎"联动**(App/AppTrader.py、App/AppData.py 全量核查无此逻辑);
- 引擎的行情/信号来源是它自己对常驻服务进程的 SSE 连接,与浏览器连接无关;
- 页面关闭/休眠只影响"看":休眠期间图不更新、弹窗不显示;事件已落盘不丢。

### 3.2 上游行情拓扑:**每连接独立会话(扇出复制),不是共享多路复用**

- `App/AppSSE.py` 文件头:"每个 SSE 连接自包含:创建 TqApi → 拉历史 → chan分析 → 推送快照 → 实时循环";
- `CTqSdkSession()` 每连接一个实例,TqApi 在其 `connect()` 内创建;会话绑定经 `DataAPI/TqSdkAPI.py` 的 `_CURRENT_SESSION = threading.local()` + `session_context/session_set/session_clear`(`session_clear` 注明"线程池复用前必须清,防串连");
- 一条会话的范围 = 该连接 URL 参数:单窗 = 1 合约 1 周期;双窗 = 同一合约主/副 2 个周期(同一 TqApi 的两条 kline 序列);
- 因此:页面 IF + IF 引擎同时开 = 天勤侧 **2 个会话**(同一份 IF 15s 行情拉两遍);IM 引擎再 +1。线程 A/B 模型正确,但"天勤侧同一个连接"不成立;
- 关页面 = 该连接的线程与会话整体退出(上游少一份拉数,服务端变轻);引擎连接不受影响;
- 设计动机(代码注释有据):会话隔离、防串连;代价 = 重复订阅。当前规模(约 3-4 个会话)远在天勤限额内。

### 3.3 交易引擎停止触发全清单(仅两项)

1. **`.stop_request` 标志文件**(`Trading/main.py` 的 `_monitor_stop_flag` 每 0.2s 轮询):唯一跨平台触发,只由页面"停止"按钮 → `AppOrch` API → `AppTrader.stop()` 写入;
2. **SIGINT/SIGTERM**(控制台 Ctrl+C)。

`stop()` 全仓库唯一调用点 = AppOrch 的 API;**没有心跳超时、没有"无客户端自动关闭"、没有盘后自动停止**——刻意设计:交易引擎的生死不挂在 UI 是否在线上。SSE 协议层的注释帧(": x")只是传输保活,不是"前端必须证明活着"的契约。

### 3.4 前端关闭后的行为(线程 A/B 模型,确认)

- 线程 A(服务 Edge 的流)随连接断开而退出;线程 B(服务交易引擎的流)继续 → IF 行情照拉、买卖点照算、交易照做;
- 页面重开:F5 后重连,服务端先推 `init` 全量快照,状态从落盘追平;
- 已知边界:前端 `onerror` **只关连接置"● 断开"徽标,不自动重连**(`Frontend/app.js`),回页需手动刷新。

### 3.5 弹窗与通知设计现状(需求⑷⑶均已落地,护边界的待决项也在)

| 通道 | 实现 | 触发条件 | 状态 |
|---|---|---|---|
| 页内 toast | 交易引擎写 state.db 的 toasts 队列 → 前端随状态轮询下发;轻提示 5s 自动消失,严重告警挂到 ack(`Frontend/app.js` toast 组件) | 事件发生 | 已落地(2026-09-18 需求⑷) |
| Win11 右下角系统通知 | **页面自己发**的浏览器 Notification API(`aoNotifyEligible`:仅 `document.hidden || !document.hasFocus()` 且已授权;tag 覆盖防堆积,点击拉回页面;权限在"开启自动下单"手势里申请) | 页面不在前台 | 已落地(2026-09-23 需求⑶);护栏 `Trading/Test/test_p64_ao_bg_notify.py` |
| 后台不卡顿 | 状态轮询在 Web Worker 内(每 5s,不受后台标签页定时器节流);09-23 实盘"通知延迟 60s+"根因 = 主线程被节流,已修;09-24 又修 Worker 内 blob: URL 必须拼绝对 URL 的坑 | — | 已落地 |

**Edge 休眠的直接影响**:休眠冻结整个标签页(主线程 + Worker 一起)→ SSE 断、轮询停 → **页内 toast 与右下角系统通知全停**(后者是页面 JS 发的,不是系统级独立通道)。休眠期间交易引擎照常交易、照写队列;回 F5 后积压补弹(09-24 实测"重开后连弹 5 条积压"),严重告警未 ack 一直挂。**页面切后台但未休眠时**(常态),弹窗/通知链路是通的——这正是需求⑶设计的场景。

### 3.6 Edge 休眠设置实测(本机,2026-09-30 读 `%LOCALAPPDATA%\Microsoft\Edge\User Data\Default\Preferences`)

- `profile.content_settings.exceptions.sleeping_tabs` 已有两条例外:`http://127.0.0.1,*` 与 `http://localhost,*`,setting = **BLOCK = 永不休眠**(模式未写端口 = 匹配任意端口);
- **结论:用 `http://127.0.0.1:18081`(或 localhost)打开的交易页面在"永不休眠"清单里,Edge 不会休眠它们**——全局默认阈值(微软口径 2 小时闲置;本机未改全局键,以 `edge://settings/system` 显示为准)与这两个页面无关;
- 可自行核验:设置页"永不进入休眠状态的网站"清单应能看到这两条;或实测——切走一两个小时,回来徽标仍"● 实时"且数据最新;
- 边界:① 例外只管 Edge 标签页休眠,**Windows 系统睡眠/休眠不豁免**(整机冻结,交易引擎与 CTP 连接全断——真正要防的);② 关 Edge/关标签页仍会让页面通道消失;③ 改用局域网 IP 访问则不在例外里,且 http 非安全上下文无 Notification API(页内 toast 还在)。

## 4. 与业界主流架构对照

### 4.1 同类软件(单人单机、前后端分离的个人程序化交易)的主流组件栈

坐标参照:vnpy(最广为人知的开源参照)= 单进程,行情/交易网关 + EventEngine(进程内队列)+ 策略 + UI 全在一个进程;Web 化的同类把 UI 拆出去,但**行情网关与事件总线始终在交易核心进程内,Web 层是旁路订阅者**。锚点:**UI/Web 服务器必须在交易关键路径之外**。(商业软件内核不公开,不做具体断言。)

| # | 组件 | 主流形态 | 本设计 |
|---|---|---|---|
| 1 | 行情网关 | 交易核心内部持有行情会话 | **偏离 ④**:按连接复制(见 4.3) |
| 2 | 交易网关 | CTP/TqSdk 回调驱动 | 一致(SimNow 经 tqsdk/OTG) |
| 3 | 事件引擎 | 进程内 pub/sub | **偏离 ②**:文件+轮询(outbox 型) |
| 4 | 策略/信号层 | 交易核持有信号计算 | **偏离 ①**:缠论引擎宿主在常驻服务进程 |
| 5 | 风控前置 | 下单前检查 | 一致(`Engine._pre_trade_check`) |
| 6 | 订单/持仓状态机 | 回报驱动 + 看护 | **偏离 ③**:同步终判(部分);看护/三态/跨日规则一致 |
| 7 | 持久化 | 账本落库、重启恢复 | 一致(WAL SQLite + events.jsonl + `_restore`) |
| 8 | 对账 | 簿面 vs 柜台 | 一致且超出(证据门/盲区补) |
| 9 | UI 层 | **旁路** | **偏离 ① 的另一面**:UI 宿主在关键路径上 |

### 4.2 偏离清单(按重要性排序)

1. **交易关键路径经过常驻服务进程(结构性,唯一大条)**:交易引擎的 Source 注册表仅 `SSE`/`Replay`(`Trading/Source/Base.py` 的 `register_source`/`build_source`),无直连行情能力;K 线与买卖点必须由常驻服务进程供给 → 它挂了交易引擎不会死,但会"聋"(无新信号、无新 K 线)。业界锚点是反的(UI 在旁路)。现实风险低(本机常驻 + 单人),但结构单点成立;且托管层与信号供给同进程,加重单点。
2. **进程间状态交换 = 文件 + 轮询(outbox 型)**:业界为进程内总线或本地 pub/sub。本设计换审计/崩溃安全,自洽;详见 §5。
3. **报单成交判定 = 同步终判**:业界为回报回调驱动的委托状态机。submit 阻塞等终态(5s 窗 + watchdog)当场出结论——2026-09-30 P6 事故即此模式固有风险点,已根修(`_p6_is_filled`,详见《P6成交判定误判_根因分析_20260930.md》);Reconcile 兜底仍在。15s bar + FOK 节奏下可接受,记档。
4. **行情会话按连接复制**:业界一个网关会话内部扇出;这里页面+引擎各一份。单机无感,实例/页面多了先撞天勤会话限额。
5. **本地明文 HTTP、无鉴权**:单人单机合理简化;不对局域网开放即可。

### 4.3 收敛优先级(若未来要动)

**1(信号供给独立化,见 §6)> 2(tail+relay,见 §5.4)> 3(异步终判)> 4(共享行情会话)。** 其中 1、3 是需拍板的大动作;2 是小改动。当前建议:**记账不动**——单机单人用法下实际风险低,等"服务进程搬家/上局域网/加实例"时一并评估。

## 5. 轮询 vs 订阅:评估与建议

### 5.1 量级校准

- `state.db` 是 WAL 模式(`-wal`/`-shm` 在):读写互不阻塞;本地 SQLite 查几行 = 微秒~毫秒级,5s 一次成本≈0——**"浪费资源"在本场景不成立**;
- 真实代价只有"不及时"(上界 ≈ 5s + 渲染),且只影响"人看到的提醒":交易决策在交易引擎内部由 K 线闭合驱动,从不经过这条读路径;09-23 的 60s+ 延迟根因是浏览器后台节流(已用 Worker 修),不是轮询设计。

### 5.2 业界对照:两种都是主流,成熟系统两个一起用

- **"写库 + 轮询读"** = transactional **outbox** 模式(事件先落库、中继转发),以可靠著称;红利 = 审计与崩溃安全免费(events.jsonl 就是审计日志,state.db 就是事实源)。推送注定是"加一层",不是"换掉"。
- **订阅/推送**(事件总线)在跨进程/低延迟/多消费方场景是主流;代价 = 送达保证、顺序、背压、重连,轮询天然免疫。

### 5.3 概念澄清(需求⑵之问)

"订阅/推送(事件总线)"是**模式名**;"消息总线"是该模式的**重实现档位**(引入独立中间件:Redis pub/sub / ZeroMQ / gRPC stream)。**是同一个东西的两种说法**——Level 谱系:进程内回调 → tail 日志转发(Level 2,无中间件)→ 独立中间件(Level 3)。

### 5.4 建议阶梯(原则:交易引擎下单路径零改动)

| 级别 | 内容 | 建议 |
|---|---|---|
| Level 0 | 现状:文件 + 5s 轮询 | 单人单机够用,**可不动** |
| Level 1 | 自适应轮询:有页面连着且自动下单运行中 → 0.5~1s;否则回 5s | 便宜,改动只在服务进程读侧 |
| **Level 2(甜点)** | 服务进程 **tail `events.jsonl`**(append-only 追加日志,天然"日志即事件流";业界 Filebeat/Kafka 同源思想),带读偏移,新事件即刻经**已有 SSE 通道**推页面。引擎写路径零改动,延迟亚秒;文件仍是 SSOT/审计 | 嫌慢就直接做这个。前提:交易事件相关 kind 收紧 flush(`Trading/Infra/EventLog.py` 现为每秒/每 64 条,设计容忍丢最后 1 秒) |
| Level 3 | 独立消息中间件(Redis/ZeroMQ/gRPC) | 仅当拆机器部署/多消费方才值得;现在上是复杂度负资产 |

## 6. 信号供给独立化(需求:交易引擎要的是缠论信号,不只是行情)

命题的准确表述:**不是"直连行情",而是"交易引擎的信号供给从常驻服务进程剥离"**——缠论引擎目前宿主在常驻服务进程,信号必须经过它,这就是 §4.2 偏离①的根源。三条形态:

| 方案 | 形态 | 代价/约束 | 判断 |
|---|---|---|---|
| 甲 | 交易引擎内嵌缠论计算(自拉行情、自算买卖点) | 违背既有拍板"Trading/ 对缠论主程序零 import";两引擎焊回一个进程;多实例重复计算 | **不建议** |
| 乙 | 缠论引擎独立成第三进程(信号服务):常驻服务进程(画图/托管)与各交易引擎实例都订阅它 | 多一个进程要运维;需定义信号服务重启期间交易引擎的等待/恢复语义;与"零 import"拍板不冲突(仍零 import,信号经 SSE 进) | **对齐主流 Web 化同类的路**(交易核持有行情+策略,Web 旁路);需要拍板 |
| 丙 | 维持现状 | 常驻服务进程保持为信号单点;靠本机常驻 + 重启恢复 + 对账兜底 | 单机单人下风险可控 |
