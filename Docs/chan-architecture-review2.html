1 · 总体判断

这套代码处在一种很典型的「重构中途态」：分层命名、目录切分、锁策略登记表、迁移映射表、 21 个回归组件，都做得很认真，甚至比多数同类项目认真。但分层是被文档和管理脚本维持的，不是被代码结构维持的。 真正决定系统行为的三条暗线（全局 set_data 注入、核心引擎反向 import App、前端单闭包共享状态） 把所有名义上的边界都穿透了。

1根因缺陷：全局可变状态传参（CTdxAPI.set_data）
2处依赖倒置：核心引擎 import 应用层
39处已核实死代码 / 不可达分支
17处注释与代码事实不符
6个并发 / 正确性风险
7797行单文件前端（1 个 IIFE）
一句话结论：架构的「形」（目录、命名、锁登记表、映射表）已经做到位， 但架构的「体」（数据流所有权、依赖方向、并发边界、前端封装）没有跟上。 当前最该做的不是继续加守护用例，而是把 K 线数据从全局变量改成显式传参—— 这一个改动能同时解开全局锁、时序约定、核心引擎反向依赖三个死结。

2.2 实际依赖（穿透边界的三条暗线）

暗线 ① —— 数据靠全局变量带外传递，抽象是假的

CChan 的构造签名看起来是「给我一个数据源类」：

# App/AppEngine.py
CTdxAPI.set_data(records)                       # ← 写类级全局
chan = CChan(code=..., data_src="custom:TdxAPI.CTdxAPI", lv_list=..., ...)
for _snapshot in chan.step_load(): pass

# Chan.py:102
def get_load_stock_iter(self, stockapi_cls, lv):
    stockapi_instance = stockapi_cls(code=self.code, k_type=lv, ...)   # ← 不传数据
    return self.load_stock_data(stockapi_instance, lv)

# DataAPI/TdxAPI.py:1364
def _get_records(self):
    return CTdxAPI._tdx_data          # ← 从类级全局读回来

也就是说：K 线数据不是参数，是全局副作用。"set_data → 构造 → step_load"这三步必须原子执行， 于是全局锁就从"可选优化"变成了"正确性刚需"。这是整个系统并发能力的天花板，也是下面这一串连锁反应的源头：

  • 必须存在 _stock_analysis_lock（AppEngine:294）与 _ENGINE_LOCK（AppChart:43）两把全局锁；
  • 双窗下窗 CChan 无法作为参数传给上窗，只能塞进 app_data.stocks_sub_cache；
  • 下窗周期还要靠猴补丁属性 chan._stocks_dual_sub_freq（AppEngine:723）告诉引擎去哪儿找；
  • 于是产生「先下后上」这条没有任何机制保证、只靠注释约定的时序契约。

暗线 ② —— 核心引擎反向依赖应用层

# BuySellPoint/BSPointList.py:698   ← 这是"第三方缠论引擎"目录
from App.AppData import app_data
sub_chan = app_data.stocks_sub_cache_get(parent.code, sub_freq)

# BuySellPoint/BSPointList.py:725
from App.AppData import app_data
sub_chan = app_data.futures_cache_get(cache_key)
用户把 BuySellPoint/ 归为"来自第三方、不优化"的目录，但这个文件已经被改造成依赖 App 层单例了。 它不是一个可替换的第三方库，而是一个"半个应用层"——它知道缓存键格式、知道运行时缓存的存在、 还在缓存 miss 时静默改变计算结果（return True # 按子级别背驰处理）。 这既破坏了依赖方向，也让"引擎可独立复用/可独立测试"这件事彻底不成立。

3 · 我认为的最优架构

先说立场：对个人使用的本地分析工具（单用户、单进程、本地数据）， "最优"不是微服务、不是 DDD 六边形、不是前后端分离到极致。最优应该满足四条：

  1. 数据所有权显式——任何计算的输入都是参数，不是全局变量；
  2. 临界区 = 不可再分的最小段——I/O 绝不在锁内；
  3. 依赖方向由 import 图强制——而不是由文档和守护脚本维持；
  4. 一个功能一条链路——同一语义不要有 A/B 两条实现。

3.1 目标分层

L0  引擎内核（Bi/ KLine/ ZS/ Seg/ Combiner/ Math/ BuySellPoint/ …）
    · 纯计算：输入 K 线序列 → 输出笔/段/中枢/买卖点
    · 硬约束：禁止 import App / DataAPI / FrontAPI，禁止读任何进程级缓存
    · 下窗数据通过【注入式 SubLevelProvider 协议】获取，而不是直接 import app_data

L1  数据源 DataAPI/
    · 无状态 reader： (market, code, freq, 区间) → list[record]
    · 不得持有"请求态"：CTdxAPI._tdx_data / CTqSdkAPI._records_by_symbol 必须消失
    · 可选能力（tqsdk / akshare / eltdx / pytdx）统一成 capibility 探测 + 显式注入

L2  领域服务 App/
    · 每个用例一个类/闭包：Analysis / SelectPoint / RedRange / Realtime / Scan /
      Refresh / Download / MarketAmount / Annotation
    · 依赖经构造函数注入（cache、provider、config），不 import 单例
    · 唯一允许持锁的地方，且锁只包"引擎构造"这一件事

L3  API FrontAPI.py
    · 路由 = 参数校验 + 调 use case + 响应组装，无业务逻辑
    · 领域异常 → HTTP 状态码的统一映射

L4  前端 Frontend/
    · ES Module 真模块（浏览器原生 import，零构建，符合项目"零构建"约束）
    · 单一状态容器 + 显式 render(state)，杜绝闭包隐式共享

3.2 最关键的一个改造：把 set_data 换成显式传参

这是唯一必须动到引擎内核边界的改动，但改动面很小，且不需要改缠论算法：

# 在 App 层加一层隔离适配器（不动 Chan.py 的算法，只改调用方式）
# App/chan_runner.py
@contextmanager
def _critical():
    """引擎构造临界区：只包 '注入→构造→drain'，不包任何 I/O"""
    with _ENGINE_LOCK:
        yield

def build_chan(records, lv_list, market_type, code) -> CChan:
    CTdxAPI.set_data(records)               # 全局写入仍在，但被关进最小临界区
    try:
        chan = CChan(code=code, data_src="custom:TdxAPI.CTdxAPI",
                     lv_list=lv_list, config=_make_chan_config(),
                     autype=AUTYPE.NONE, market_type=market_type)
        for _ in chan.step_load():
            pass
        return chan
    finally:
        CTdxAPI.set_data(None)              # 立即释放，避免长生命周期引用
收益：① 临界区从「读盘 + 前复权（可能走网络取 xdxr）+ 分析」缩到「仅构造」， 交互延迟与并发度立刻改善一个数量级；② 锁策略不再需要 SERIAL/SCAN/RAW 三分类的人工登记， 因为"谁碰全局"这件事被收敛到一个函数里；③ 后续若引擎支持构造参数传数据， 只需改这一个函数，上层零感知。

不变量落地手段

5.2 不可达的条件分支（是真实缺陷，不只是冗余）1 项

# App/AppEngine.py:513-522
matched_fmt = None
for fmt in ["%Y/%m/%d %H:%M:%S", "%Y/%m/%d %H:%M", "%Y/%m/%d"]:
    try:
        datetime.strptime(end_date, fmt); matched_fmt = fmt; break
    except ValueError:
        continue
if matched_fmt == "%Y-%m-%d" and freq in INTRADAY_FREQS:     # ← 永假
    target_dt = target_dt.replace(hour=23, minute=59, second=59)
matched_fmt 的取值域只有那三个用斜杠的格式，"%Y-%m-%d"（连字符）不在其中， 条件恒假 → 分支永不执行。

后果不是"代码冗余"而是功能错误：复盘到某日且周期是 30m/5m 时， target_dt 为当日 00:00，records = [r for r in full_records if r["dt"] <= target_dt] 会把当天的所有分钟 K 线全部滤掉。用户复盘到今天，看到的却是昨天收盘的样子。

正确的写法应是判断"传入的 end_date 是否只含日期不含时间"（如 matched_fmt == "%Y/%m/%d"）， 而不是拿一个根本不在候选列表里的格式去比较。

7 · 正确性与并发风险

7.1 P0 并发批量扫描会互相取消

# App/AppScanPool.py
_pool = None                                   # 全局单例

def _monitor_task(task_id, futures):
    ...
    destroy_pool()                             # ← 任一任务结束就销毁"全局"池

def destroy_pool():
    _pool.shutdown(wait=False, cancel_futures=True)   # ← 取消未开始的 future

任务 A、B 并存（两个浏览器标签 / 前端重提交）时，先完成的 A 会 shutdown 共享池， cancel_futures=True 把 B 尚未开始的票全部取消；B 的收割线程 fut.result() 抛 CancelledError，被兜底写成 error 行—— 用户看到 B 的任务"完成了"，但一多半是"基础设施故障"，且无从区分。 修复方向：改引用计数（有活跃任务才销毁），或按 task_id 建池。

7.2 P0 close_all() 无超时等待

# DataAPI/TqSdkCSSESource.py:83-87
for src in sources:
    src._api_closed.wait()          # ← 无 timeout

若生成器尚在 init_chan_symbol（拉历史、建 CChan，可达数十秒）而没进入 wait_update 循环，_closed 标志不会被检查，_api_closed 也不会置位。 而 POST /api/futures/cleanup 直接 await run_in_threadpool(close_all) → 该 HTTP 请求会一直挂起到建链完成。应加超时（如 3s）后降级返回。

7.3 P1 刷新状态可能永久卡死

# App/AppRefresh.py:414
if _refresh_status["running"]: return
_refresh_status["running"] = True
...
# 434-617 行：无 try/finally

中途异常逃逸 → running 永久为 True → 后续所有刷新请求返回 {"status":"already_running"}，只能重启进程。

7.4 P1 配置两套实现行为分叉

# App/AppConfig.py
_FIELD_TYPES = {..., "SSE_DEBUG": bool, ...}      # 缺 FORWARD_ADJUST_ENABLED / FULL_DATA_MODE
...
setattr(self, key.lower(), caster(raw))           # bool("False") == True ！
装了 pydantic-settings 与没装，是两套不同的配置行为：
· 降级路径下 FORWARD_ADJUST_ENABLED、FULL_DATA_MODE、SCAN_FANGLIANG_WINDOW_BARS 以及两个 *_LOOKBACK_CONFIG（dict）都无法被 env/.env 覆盖；

8.1 主要问题：大量断言打在"源码文本"上，而不是"行为"上

# test_phase3_guards.py:135
src = inspect.getsource(fn)
holds = "with _ENGINE_LOCK:" in src          # ← 检查源码里有没有这串字符

# test_phase3_guards.py:164-167
for pat in FORBIDDEN_ENGINE_CALLS:
    for i, line in enumerate(src.splitlines(), 1):
        if pat in line and not line.strip().startswith("#"):   # ← 逐行文本匹配

# test_phase3_guards.py:245
if current != baseline: ...                   # ← 路由集合快照全等
  • 把 with _ENGINE_LOCK: 抽成 helper（with engine_lock():）→ 文本断言立刻失败， 但行为完全正确；反过来，换个写法持锁而文本不含该串 → 断言通过但可能根本没锁。两个方向都会误判。
  • FORBIDDEN_ENGINE_CALLS 只扫 FrontAPI.py 一个文件， AppSSE / AppScan / AppRefresh 直连引擎不受约束。
  • 路由集合全等快照意味着：每加/删一个路由都要"重冻基线"。它冻结的是结构， 因此无法发现"路由存在但没人调用"（/api/futures/read/config 与 /status 就是这么活下来的）。
  • 分层方向检查只列了 AppData / AppConfig / AppOrch 三个文件， 恰好漏掉了唯一的真实违规 BuySellPoint/BSPointList.py。
