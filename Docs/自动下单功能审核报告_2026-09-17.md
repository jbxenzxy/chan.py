## 0. 原始需求原文（一字不改存档）

> ⑵ 从K线页面手工开启"自动下单功能"时，先判断K线页面所展示的期货品种，是否在白名单中？只有在白名单中的品种才支持自动下单，否则弹窗提示不支持

> ⑼ 报单时不要判断是否会被期货公司或交易所拒绝（代码中不再需要涨跌停价），直接报单即可，如果被拒绝，有拒绝码，弹窗提示用户就好，让用户去处理

## 3. 逐条核对详情

### 3.1 ⑴ 加载页面时默认关闭 —— 符合

引擎不是常驻的。后台服务启动时**不会**自动把交易引擎拉起来，只有用户在页面上把"自动下单"开关拨到开，才会启动。页面上的开关亮不亮，问的是后台"引擎进程在不在跑 + 开关状态"，两者都是"否"，所以刚打开页面时它一定是关的。

补充一个对用户友好的细节：就算上一轮用过、引擎状态库里还记着"开"，只要进程没在跑，页面显示的也是关。用户重新拨一次开关才真正开。

**【复核补记】** 剥注释复核时更正了一处表述精度：引擎内部记开关的字段初始值其实是"开"（Engine.py 第 262 行）。这不影响结论——"默认关闭"真正靠的是两层代码事实：① 前端初始化函数里没有任何启动引擎的调用，页面加载不会拉起引擎；② 开关控件在 HTML 里没写 `checked` 属性，浏览器语义就是默认不选中。引擎字段那个默认值只在"进程已在跑、库被手工清过"的边缘场景才起作用，且有启动期对账护栏兜底。

证据位置：前端 Frontend/app.js（开关状态每 5 秒问一次后台）；应用层 App/AppTrader.py（引擎子进程的启动、停止、状态查询，全仓库搜索不到任何"服务启动时自动拉起引擎"的代码路径）。

### 3.2 ⑵ 开启前查白名单，不支持就弹窗 —— 符合

用户拨开关"开"的时候，前端先问后台一个"这个品种能不能自动下单"的接口；后台用**全系统唯一的一份白名单**来判定。不在名单里：开关弹回"关"、屏幕弹出"不支持交易"加原因说明、启动请求根本不会发出去。

白名单目前是 **8 个品种**：股指 IF、IH、IC、IM，沪金 AU、沪银 AG、沪铜 CU、PTA（TA）。能**看行情**的品种有 16 个——看和做是两码事，代码里明确把这两件事分开了。

另外多做了一步体验优化：切到一个不支持的品种时，开关直接变灰、悬停显示"该品种不支持自动下单"，让用户在点之前就知道。这一步只是提示，真正的安全把关还是在"点开"那一刻和引擎启动那一刻（两处用的是同一份白名单，不会出现"前端说能开、引擎不让开"的打架）。

证据位置：前端 Frontend/app.js（开启前的检查 + 弹窗 + 置灰）；App/AppTrader.py（品种检查接口、启动前置拦截）；Trading/Infra/Product.py（白名单唯一实现，8 个品种）。

### 3.3 ⑶ 开着的时候不许切周期/切品种 —— 符合

引擎一跑起来，前端就记着"运行中"。此时用户点周期按钮 → 弹窗"自动下单引擎运行中，请先关闭自动下单，再切换周期"；用户换品种 → 弹窗"请先关闭自动下单，再切换合约"。两条路都被堵死，只能先关再切。

为什么这么设计：引擎绑定了开启那一刻的品种和行情流，切走会导致引擎账本和新页面看到的对不上，所以必须先关。

证据位置：前端 Frontend/app.js 的两个切换入口（切周期、切品种）各自开头都有"运行中拦截 + 弹窗"。

### 3.4 ⑷ 关闭时：今仓锁仓 / 跨日仓平掉 —— 符合

用户拨开关"关"时，引擎做的事：

1. 立刻拒收一切新买卖点信号；
2. 如果手里有仓（运行态），按**最后一笔仓单是哪天建的**分流：
   - **今天的仓** → 走品种执行策略表第 1 列：大多数品种做"反向开一笔对冲仓"把盈亏锁死（不付平今的高手续费）；少数品种（沪金、沪银、沪铜）直接"平今"清掉；
   - **跨日的仓** → 直接平仓（平昨，费率低）。
3. 处理完按三种结局各发一条明确提示：清干净了（放心）；停在锁仓态（盈亏已锁定，不是危险状态，可以手工平或下次开了再拆）；没清掉还有净敞口（**红色严重警告**，让用户去柜台人工处理——离场单被拒时会出现这种情况）。

"是否支持平今"不看交易所名字拍脑袋，完全由那张品种表说了算（表里第 1 列填什么就走什么，填错的责任在人不在代码——这是用户自己拍板的设计法律）。

证据位置：Trading/Engine/Engine.py 的"自动下单关闭"一节；Trading/Infra/Product.py（品种执行策略表：IF/IH/IC/IM/TA 走反向开仓，AU/AG/CU 走平今）。

### 3.5 ⑸ 三态/两态状态机 + 最低手续费 —— 符合

引擎心里始终记着账户处于三种状态之一：**空仓、锁仓、运行**（有净敞口）。

买卖点信号来了之后怎么动，全部写在一张转移表里，一共五种转移：

- 空仓 + 信号 → 开新仓（转移一）；
- 当天建的锁仓 + 信号 → 再开一笔（不动锁仓那笔）（转移二）；
- 跨日建的锁仓 + 对向信号 → 平掉对冲的那笔（拆锁，转移三）；
- 运行态 + 今日仓要离场 → 反向开仓锁仓，或（按品种表）平今（转移四）；
- 运行态 + 跨日仓要离场 → 平昨（转移五）。

"两态"是怎么回事：对沪金/沪银/沪铜这类走"平今"的品种，运行态的仓**必然**是当天建的、平完就回空仓，锁仓态在结构上就到不了——所以它们实际只有"空仓/运行"两个状态，代码里有一条专门的守卫断言保证这一点不会破。

"最低手续费"是怎么保证的：期货平今仓的手续费可能是平昨的十几倍。这套系统的做法是——今日仓离场默认**反向开仓锁仓**，一分平今费都不付；等这仓跨了日，再走便宜的平昨。只有品种表里明确写了"平今"的品种（沪金沪银沪铜，这类平今反而划算或有别的考虑）才直接平今。手续费标准本身也是从配置表生成的，不是代码里写死的。

证据位置：Trading/Engine/Engine.py（三态判定只集中在一个方法、转移表只在两个决策方法里）；Trading/Strategy/Exit.py；Trading/Infra/Product.py（品种表 + 费率生成区块）。

### 3.6 ⑹ 一个信号只报一笔；运行态不再收信号 —— 符合

- **一个信号一笔**：每个信号带唯一编号，处理过一次就记账，重复收到直接丢弃（防重放）。开仓手数 = 品种表第 3 列"一笔挂几手"（比如股指挂 2 手），一笔委托直接挂 N 手，**没有任何拆单逻辑**（想拆成 N 笔 1 手的代码根本不存在，这是刻意的设计）。
- **运行态不收信号**：信号进来第一件事看状态——只要账户在"运行态"（手里有净敞口），信号直接标记为"运行态忽略"然后跳过，连决策都不会进。此时此刻，唯一能触发离场的是止盈止损（见下）。
- **止盈止损 L1-L3**：运行态每一根 K 线都要过一遍三层离场检查——L1 用开仓时的风险基准定止损底线，L2 按市场波动（ATR）调整宽度，L3 在浮盈够多后启动跟踪锁利（浮盈回吐就下场）。触发后走的还是同一张转移表（今仓锁仓/平今、跨日仓平昨），和关闭按钮殊途同归。

证据位置：Trading/Engine/Engine.py（信号入口的状态检查 + "运行态忽略"；止盈止损判定每根 K 线执行）；Trading/Strategy/Exit.py（L1-L3 三层，全仓库只有这一套出场策略）。

### 3.7 ⑺ 按品种统计、不区分账户 —— 符合（按 2026-09-17 更正口径）

需求原文括号里"SimNow和实盘账户分开保存"八个字是笔误，正确口径（需求方 2026-09-17 亲自更正）：**统计只认品种、不认账户**——比如 IF 品种，不管这笔成交是 SimNow 仿真账户跑出来的还是实盘账户跑出来的，盈亏都归并到 IF 名下一起算。照这个口径核对，代码行为与需求完全一致：

- **每个信号一笔成交都记档**：每笔平仓完成的交易都记录在账本库里，记账那一刻就写好了"属于哪个品种"，同一品种的不同合约月份自动归到一起（比如 IF2609、IF2612 都算 IF），也和周期无关；
- **账户自动归并**：账本库本身不区分账户，统计时把扫到的所有账本合并计算——SimNow 的记录和实盘的记录天然汇入同一个品种的统计，正是更正后口径要的效果；
- **页面"统计"按钮**点开，显示的正是要求的三样：**历史累积盈亏曲线**（画图）+ **实际胜率** + **盈亏比**，外加总净盈亏等辅助数字；涨红跌绿按国内习惯；
- **统计读库是只读的**，读哪个库、读到几条、读失败了都会明说，不会把"读不出来"伪装成"没有成交"。

两个给接手人的提示（不是缺陷）：

1. **合并的边界是"目录扫描"**：统计扫的是约定位置下的账本目录。如果哪天想让 SimNow 和实盘各记一套账（比如想分开复盘），把账本目录配成两个、放在约定命名规则内即可，两边仍会被扫到并合并——想看"某一个账户单独的成绩"目前没有界面入口，需要人工看各库的成交明细。这与更正后的口径不冲突，属于顺带说明；
2. 账本库里**没有**"这笔成交来自哪个账户"的标记列。按更正口径这是不需要的；但若将来又想分账户统计，就得从记录层加起，不只是界面的事。

证据位置：Trading/Infra/TradeStats.py（按品种键过滤 + 多库合并 + 汇总计算，文件头明确写着"账户无关：simnow/实盘天然合并"）；App/AppTrader.py（统计接口，扫描全部账本目录合并）；Frontend/app.js（统计请求固定带"合并"参数；面板渲染曲线/胜率/盈亏比）。

### 3.8 ⑻ 品种参数只读配置 —— 符合

### 3.9 ⑼ 不预判拒单，被拒就弹窗 —— 符合

- 全仓库搜索：涨跌停价、涨跌停区间的任何校验代码**一条都没有**（2026-09-17 改造时整体删除，配置档案里只留了个"涨跌停幅度"的纯记录字段，不参与任何判断）；
- 报单就是直接把限价单发出去（挂比对手价让利几个最小变动价位的价格，保证立即成交），发出前不做"交易所会不会拒"的预测；
- 被拒之后：系统会从柜台返回的拒绝信息里识别类别（资金不足 / 非交易时段或无权限 / 仓位对不上 / 价格没成），按类别弹出提示，严重程度分级——不会自己好的弹红色警告框（要人处理），一过性的弹轻提示。拒绝原因的原文会带到弹窗里，用户拿去对照处理即可。

一点说明（不是违反，是避免误会）：报单前引擎有一道"自家账本核对"（比如"要平的仓在账上真的存在吗""平今的目标真是今仓吗"）。这拦的是自己系统内部的糊涂账，不是替交易所预测拒单，与本条"不要预判交易所拒绝"的本意不冲突。

证据位置：全仓无涨跌停校验（关键词搜索零命中）；Trading/Broker/Base.py（拒单分类）；Trading/Engine/Engine.py（拒单→告警分级表、弹窗通道）；Trading/Broker/SimNow.py（报单直接发出，拒绝信息透传）。

### 3.10 ⑽ 入场失败等下个信号；离场失败立即重试 3 次 —— 符合

**入场（信号触发的开新仓 / 拆锁平仓）**：报单不追价——一次不成就不成，拒绝原因弹窗给用户看，然后什么都不做，**等下一个信号**。设计理由写在代码注释里：入场没成功最多是不赚钱，不会亏钱，犯不着追。

**离场（止盈止损触发 / 关闭按钮触发）**：必须追着成交——
1. 报出第一笔，等终态回报；没成交（比如被全额撤销）→ **收到不成功响应后立即重报**（不等待、不睡觉），价格自动朝能成交的方向重新让利；
2. 这样立刻重报最多 **3 轮**（默认配置 3，可调）；
3. 3 轮跑满还没成 → 弹**红色严重警告**："离场追价跑满 3 轮仍未成交，净敞口没变，请人工处理"；
4. 一个贴心的例外：如果是"资金不足""非交易时段"这类**追了也白追**的拒绝，第一轮就停下并弹窗，不会傻追满 3 次（避免无效报单还占用报单流量额度）。

证据位置：Trading/Broker/SimNow.py（入场不追价、离场立即重报共 3 轮、追价无用场景提前停）；Trading/Engine/Engine.py（"追价跑满"严重告警）；Trading/Config.py（3 轮的默认值）。

**【2026-09-17 16:40 改判补记】** 需求 ⑽ 本身的实现符合原文；但代码在 3 轮追价失败弹窗之后还多做了一层"自动兜底"（冷却重试 + 幻影仓自动清簿），这与需求方同日拍板的**总原则**（发现例外→弹窗→用户干预，引擎不自动兜底，否则隐藏 bug 永远暴露不了）相抵触。据此 ⑽ 改判为"**需求本身符合、超出范围的部分待整改**"，拆除范围与代码触点见 §4.3。

### 4.6 【FAQ】两个容易误解的设计点（2026-09-17 需求方质询后补，证据见 §1.5）

**问一：离场失败后的"冷却 5 根 K 线、连续 20 次判幻影仓"是怎么回事？**

【2026-09-17 16:40 更新：已拍板拆除，此问答留作设计背景】这两层是原实现里"弹窗之后引擎不躺平"的兜底：3 轮追价失败弹窗后，每冷却 5 根 K 线再试一轮；连续 20 次被拒且柜台明确说"没这个仓"时自动清簿。原设计动机是"用户没看到弹窗时仓位不裸奔、账本不永久失真"。

需求方复核后裁定此动机**不成立**：自动兜底会把隐藏 bug 一直掩盖下去（引擎每次都替问题"擦屁股"，异常就永远暴露不了），正确做法是发现例外→弹窗把问题描述清楚→用户干预。据此这两层连同"卡单二次确认复核"一起列入 §4.3 整改清单（卡单复核为**整段删除**——FOK/FAK 笔笔有终态，"无终态挂死"场景不存在，见 §4.3 拆除项 3）；拆除后引擎对例外的全部动作就是：把问题弹窗说清楚，然后停手等人。

**问二：引擎内部开关字段初始值为什么是 True？什么时候置 False？默认不该是 False 吗？**

先回答生命周期（全部是代码事实）：**用户打开开关 → 置 True**（后台启动/开启流程显式写入）；**用户关闭开关 → 置 False**（引擎关闭入口第一行就置 False，停止流程的收尾也置 False）。所以 True/False 跟随用户的开关动作，你理解的方向没错。

再说为什么字段默认值是 True 而不是 False——关键是这个字段**不是页面开关本身**：

1. **页面开关的权威载体是"引擎进程在不在跑"**。引擎子进程只可能被用户拨"开"的动作拉起，进程不存在 = 页面显示关。这个字段的职责范围是"**一个已经在跑的引擎**要不要继续收新信号"，而引擎在跑这件事本身就意味着用户刚表达过"我要交易"。
2. **默认值只在极端场景被读到**：状态库里有持久化记录时以记录为准；只有库被清空/损坏、读不到记录时才用默认值兜底——而正常启动流程无论如何都会显式写入 True。所以这个默认值几乎不影响实际行为，选 True 还是 False 都"能跑"。
3. **选 True 的理由是避开一个更危险的状态**：若默认 False，极端场景下会出现"引擎进程在跑、却静默不收信号"的僵尸状态——页面灯亮着、引擎活着、就是不干活，这种不一致最难发现。默认 True 下，"进程在跑"恒等于"在收信号"，状态永远自洽；真要停，走的是显式的置 False 路径，而且置 False 后引擎也不是躺平——它会把运行态持仓强制离场（不走新开仓），只是不再接新信号。
4. 换个角度说：**把默认改成 False 并不会更安全**，因为真正的安全闸门是"进程没被拉起"（⑴），而不是这个字段的兜底值。字段默认 True 是"进程存在即有效"这个设计原则的自然推论。

**问三：告警弹窗有几种形式？关闭行为分别是什么？（2026-09-17 17:03 补）**

引擎侧的 `alert()`（Engine.py 第 1855 行）不是弹窗本身，是**告警登记口**：写进告警队列（同原因未确认时合并计数、不新增条目）、落盘（重启不丢）、随状态接口每 5 秒下发前端。真正显示给用户的弹窗形式有两种：

1. **严重级（severe）→ 浏览器原生阻塞弹窗**：必须点"确定"才关闭，**不会自动消失**；同批多条严重告警合并编号一次弹出，重复发生的会附"已重复 N 次"。关闭后前端调确认接口，后台移除该条——故障若还在，下次产生新记录会再弹（这就是"故障还在"的提醒节奏）。
2. **一般级（warn）→ 角落轻提示（toast）**：**5 秒后自动淡出**，也可点击提前关闭；同屏最多 5 条，超出丢最早的。

另有三层防刷屏节流：前端同一原因 5 分钟冷却（不重复弹）、已处理水位去重、后端合并计数。自动下单链路上没有第三种弹窗形式（无 confirm/自定义模态框）；页面各处还有约二十个操作报错用的原生 `alert()`（加载失败、切换失败等），属页面操作反馈，不在自动下单告警体系内，关闭行为同为"点确定才关"。

**问四：对账把柜台账单同步到本地后，引擎会检查状态机吗？状态不对会主动修正吗？比如锁仓态被用户在快期3平掉空单，只剩多单，状态机会变运行态吗？（2026-09-17 18:07 补）**

分两半回答：

**状态机一定会变对——这是结构保证，不是靠"检查修正"。** 账户三态（空仓/锁仓/运行）在代码里**不是存起来的状态，是每次现算的派生值**（Engine.py:281 `account_state`，全系统唯一判定点）：净敞口≠0→运行态；账本空→空仓态；其余（多空互存）→锁仓态。对账删掉空单后，账本里只剩多单，下一次任何代码问"现在什么态"，答案自动就是运行态——不存在"状态留在锁仓没改过来"这回事。对账路径收口处会同步刷新投影状态（Reconcile.py:112/135 → `_sync_state`），且每根 K 线的固定顺序就是"先对账、再按当前三态分派"（Engine.py:838-846）。

**但"接管剩下那笔多单的止盈止损"——不会自动恢复，会弹严重告警叫人。** 原因：L1-L3 管的是"一段带风控锚的持仓"（锚=进场价+止损止盈计划）。锁仓形成时净敞口归零，锚已按设计收掉；用户在快期3拆掉空单后，敞口从 0 变非 0，但锚没了——引擎**不会猜一个止损价自动重建锚**（代码注释明说：猜出来的止损价可能比裸奔更危险）。实际行为是发 severe 弹窗（Engine.py:584 `_check_run_anchor`）："净敞口≠0 但没有风控锚，L1-L3 已失效，当前敞口处于无止损状态，请人工核对柜台持仓并考虑手动平仓"；且此状态下重启引擎会被启动闸门（G2）拒绝，直到问题解决。

一句话：**状态机的"态"自动变对（锁仓→运行），但运行态的"管"需要风控锚，外部拆单把锚拆没了，引擎按你 16:40 拍板的总原则——弹窗说清问题、停下等人，不自作聪明兜底。** 另注意与正常路径的区别：引擎自己拆锁（转移③）时锚是保留的，拆完无缝继续管；只有"外部手工拆单"才会丢锚触发告警。

**问四补充：什么叫"重启引擎"？"启动闸门 G2"是什么？（2026-09-17 18:20 补）**

- **重启引擎 = 页面上把"自动下单"开关关掉再打开**。这是引擎唯一的生命周期入口：打开 = 后台用子进程方式拉起引擎（AppTrader.start → Popen，引擎进程自己登录 SimNow）；关闭 = 结束该子进程。没有别的"重启"按钮或命令。
- **G2 = 引擎每次启动时过的一道"恢复自检闸门"**（代码里 `_restore_run`，Engine.py:704；G1/G2/G5 是注释里给几道启动闸门编的号，不是配置项）。引擎启动第一步是从 state.db 恢复上次的持仓和运行记录，恢复时校验自洽性：**账本有净敞口、却没有风控锚（run）记录 → 直接抛错拒绝启动**（Engine.py:759 起，错误文本自带处理提示）；锚的方向与净敞口矛盾 → 同样拒；有锚无敞口 → 判为残留清掉（正常）。
- **拒绝启动时用户看到什么**：引擎子进程启动即抛错退出（秒退），后台检测到进程没起来，页面显示引擎未运行；引擎日志（gateway.log）里有完整错误原文和"处理：确认账户无未了结持仓后，删除 Trading/State/state.db 再启动"这类操作指引。
- **"直到问题解决"的具体出路**（外部拆单场景）：先在快期3把柜台持仓人工处理掉（平掉或补齐）→ 再重启引擎 → 启动时的对账会把账本同步成与柜台一致（账本清空/自洽后 G2 自然放行）→ 恢复正常。设计逻辑：带净敞口又没有止损锚地跑 = 裸奔，宁可不开机，也不带病运行。

## 5. 给接手人的系统速览（大白话）

**整个功能分三层：**

1. **前端**（Frontend/app.js）：K 线页上的"自动下单"开关 + 每 5 秒一次的状态轮询 + 各类弹窗。前端自己不做任何交易决定，只负责"问"和"显示"。
2. **应用层**（App/）：后台服务。负责拉起/停止引擎子进程、把引擎状态和告警转给前端、提供品种检查和成交统计接口。
3. **交易引擎**（Trading/）：一个独立子进程，自己登录 SimNow。里面最核心的三个概念：
   - **三态**：空仓 / 锁仓 / 运行，全系统只在一个地方判定；
   - **转移表**：五种转移覆盖所有情况（见 §3.5），全部报单都从唯一出口出去，出口上挂着一道账本核对；
   - **品种执行策略表**：每个品种一行，三个格子——今仓离场走哪条路（反向开仓/平今）、用什么报单方式、一笔挂几手。**想改行为先改表，不改代码。**

**账本与记录都在哪**：引擎的状态、持仓、成交记录、告警队列全落在"状态目录"下的一个数据库文件里；关闭/重启不丢，恢复启动时原样接回（恢复时会做账本与柜台的核对）。

**告警怎么到用户眼前**：引擎把需要人管的事写进告警队列（同一原因自动合并计数，不会连弹几十个框）→ 前端轮询拿到 → 严重级弹阻塞框、一般级弹轻提示 → 用户确认后不再重复弹。引擎异常退出时前端还会贴出日志尾部。

## 6. 一个完整交易日的场景走查（用户视角）

1. 打开期货品种 K 线页 → 自动下单开关是灰的/关的（⑴）。
2. 切到白名单品种（如 IF）→ 开关可点；切到非白名单品种（如 RB 螺纹）→ 开关变灰 + 悬停提示（⑵）。
3. 点开开关 → 后台检查白名单 → 拉起引擎子进程登录 SimNow → 开关亮灯，悬停显示账户状态（空仓）（⑴⑵）。
4. 此时切周期/切品种 → 弹窗拦截（⑶）。
5. K 线闭合出现买卖点 → 引擎按转移表报一笔（挂品种表的手数）→ 成交后进入"运行态"，悬停可见止损止盈位（⑸⑹）。
6. 运行态中再有信号 → 被忽略；价格触发 L1-L3 → 离场（今仓锁仓/平今、跨日仓平昨）（⑹⑸）。
7. 离场单被柜台拒了 → 立即重报，最多 3 轮，仍败 → 红色弹窗（⑽）。
8. 点"统计" → 看该品种历史累积盈亏曲线、胜率、盈亏比——SimNow 和实盘的记录自动归并到同一品种一起算（⑺）。
9. 点关开关 → 今仓锁仓/平今、跨日仓平昨 → 三种结局各有一条明确提示（⑷）。停在锁仓态的话，下次开了等对向信号拆锁或手工平（§4.4）。
10. 报单被交易所/期货公司拒 → 拒绝原因弹窗，用户自己处理（⑼）。

## 8. 术语小字典（大白话）

- **交易引擎 vs 缠论引擎（2026-09-17 拍板，全文按此用词）**：光说"引擎"容易歧义。**交易引擎** = `Trading/` 目录，即自动下单功能（登录柜台、管账本、报单、止盈止损）；**缠论引擎** = `Trading/` 目录之外的部分（K 线合成、分型笔段、买卖点识别）。本文档里说"引擎"，除特别注明外均指**交易引擎**。
- **锁仓**：手里同时持有同品种的多单和空单，数量一样，涨跌都不亏不赚，等于把盈亏"锁死"。本系统用它来躲避平今高手续费。
- **运行态**：手里有没对冲掉的净仓位，盈亏随行情跳动。
- **平今 / 平昨**：平掉今天建的仓 / 平掉以前建的仓。很多品种平今费率是平昨的十几倍，所以系统尽量不平今。
- **反向开仓（锁仓式离场）**：不平仓，而是朝反方向开一笔同样数量的仓，效果等同锁仓。
- **追价**：第一笔没成交，立刻用更让利的价格再报，直到成交。
- **FOK 全撤**：一种"要么全成交、要么全撤销"的报单方式，本系统报单的默认方式；"全撤"就是没成交的信号，追价循环由此触发。
- **三态/两态**：账户的三种状态（空仓/锁仓/运行）；某些品种锁仓态结构上到不了，只剩两种，故称两态。
- **L1-L3**：三层止盈止损——定底线、按波动调宽窄、浮盈够多后跟踪锁利。
- **幻影仓**：账本里记着、柜台实际已经没有的仓。（2026-09-17 拍板：自动清理兜底列入拆除清单，见 §4.3——发现后弹窗说清，由用户核对处理，引擎不再自动清簿。）
