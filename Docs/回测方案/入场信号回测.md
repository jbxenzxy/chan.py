## 1. 数据前提（唯一铁律）

> **回测的 K 线必须与页面逐根相同。** 页面会有前复权、会选点，两者直接决定笔/段/买卖点。

页面/实盘链路（`App/AppEngine._analyze_stock_internal`）读的是**通达信本地 vipdoc**，
并在取数阶段做**自实现前复权**：

```
CTdxAPI.fetch_main_level(market, code, freq)            DataAPI/TdxAPI.py
  ├ w          ← 由前复权【日线】合成（_resample_day_to_week）
  ├ 30m / 15m  ← 由前复权【5m】合成
  └ d / 5m     ← 直接读 vipdoc 的 .day / .lc5
  → _forward_adjust(records, market, code, end_date)
  → tdx_data_context(records)
  → CChan(data_src="custom:TdxAPI.CTdxAPI", autype=AUTYPE.NONE, config=CChanConfig())
```

本流水线**唯一允许**的取数入口是 `common/tdx_source.py`，它直接调同一个
`CTdxAPI.fetch_main_level`。`CChan` 的构造参数（`autype=AUTYPE.NONE` + `CChanConfig()` 全默认）
由 `Backtest/Test/test_bt02_config_contract.py` 钉住 —— **与页面逐字段相等**。

**但"调同一个函数"还不够**：页面喂给 `CChan` 的**不是 vipdoc 全量**，而是再裁一刀之后的
序列（`AppEngine._analyze_stock_internal` 的非复盘分支）。这一刀没裁对，同源就是假的 ——
见 §1.2。

### 1.1 不用它会怎样（实测，`common/data_parity.py`）

曾用腾讯/新浪外部链路取数，**与页面不是同一条序列**（`common/data_parity.py`，抽 20 只）：

| 项 | 通达信 vipdoc | 旧外部链路 | 后果 |
|---|---|---|---|

| 周K 根数 | **294**（由日线合成） | 526 中位（腾讯**原生周线**，最多 800） | 笔数差中位 **+19**（范围 [+0,+47]）；重叠日收盘价差 >1% 占 **9.7%** |
| 分钟线复权 | **前复权** | 新浪**不复权** | 跨分红日多一次跳空 |
| 20 只标的里笔数 / 买卖点完全一致 | — | — | 只有 **1/20**（笔）、**4/20**（点） |

### 1.2 页面加载窗口（"第二刀"）

**页面显示的序列 ≠ vipdoc 全量。** `AppEngine._analyze_stock_internal` 在把 `records`
交给 `CChan` 之前，还有一段裁剪逻辑（非复盘分支）：

| 优先级 | 条件 | 作用 |
|---|---|---|
| ① | `App/double_click_dt.csv` 里该 `(code, freq)` 列有值（= 页面**双击选点**） | 取 `dt >= 选点`，**且不再按根数截断** |

本机实测（`AppConfig` 现读）：`FULL_DATA_MODE = False`；
`STOCKS_LOOKBACK_CONFIG = {w: 0(不限制), d: 500, 30m: 800, 15m: 960, 5m: 960}`。

`common/tdx_source.py` 的 `page_window()` 复刻这一刀，**上限与选点都现读 App 层**（不抄数字）。

> ⇒ 整条笔/段/买卖点全变。**2026-10-07 之前只调了 `fetch_main_level`、没复刻窗口的那版结果，
> 日K 用 1 393 根、分钟用全量，全部作废**（见 §9 勘误 ②）。

**选点这一支**（双击选点 → `double_click_dt.csv`）：

- 链路：页面双击某根 K 线 → `AppData.save_point_time()` 写 CSV → 下次分析时
  `AppEngine` 用 `get_saved_point_time(code, col)` 读回当左边界。
- **本机当前该 CSV 只有 7 行、全是指数、且只填了 `w` 一列**
  （`sh000001/sz399001/sh000300/sh000905/sh000852/sz399006/sh000688`，值 2024/09/13 或 2024/08/23）。
  股票池（4420 只，全为 `sh6*` / `sz0*` 个股）与这 7 只**没有交集**
  ⇒ **对本次全部结果的影响 = 0**。
- 但它**不是摆设**，一旦给个股设了选点，回测必须跟着变。已用副本验证：
  给 `sz000158` 的 `w` 填 `2025/01/03` ⇒ 周K 由 294 根变 **91 根**；
  给 `sh600519` 的 `d` 填 `2026/01/05` ⇒ 日K 由末尾 500 根变 **181 根**（选点**压过**根数上限）。
  复现：`EXP_SAVED_POINT_FILE=<副本> python common/tdx_source.py --code sh600519 --coverage 0`
  （只读指向副本，**不要**拿它去改生产 CSV）。

> **口径边界（必须知道，不是缺陷）**：本层复刻的是页面上"**当前这一条序列**"，
> 与仓库自己的回测入口 `App/AppBacktest.py` 同一口径（"所见即所测"）。
> 它**不是**"每个时点重新取一次滚动窗口"的走查仿真。周K 不限制根数 ⇒ 两种口径等价；
> 日K/分钟周期上，越靠近窗口左端的信号，其"上游历史"比真实实盘**更短**（冷启动伪影）。
> 读结论时按此打折。
>
> 附带效应：窗口化之后分钟周期便宜了 12~24 倍，因此**五个周期第一次统一成 800 只股票池**

### 1.3 xdxr 快照

前复权要 `get_xdxr_data()`，那是 **eltdx 网络调用**（通达信 7709 端口），被全局锁串行化、
单只约 0.4s、**实测偶发无限挂起**。做法是**一次性抓下来冻结到磁盘**：

```bash
python Backtest/Exp/common/tdx_source.py --xdxr 900     # 断点续跑，已抓的跳过
```

落到 `common/.kcache_tdx/xdxr/<code>.pkl`（900 只 / **3.7MB**，不入库，`.gitignore` 已忽略）。

**"磁盘快照"到底是什么意思**（用户会问，这里说清）：

- `get_xdxr_data(market, code)` 在仓库里**只有一个实现**：eltdx 的网络调用
  （通达信 7709 端口 / 0x000f 命令），被 `_xdxr_lock` **全局串行化**，单只 0.4~0.5s，
  且实测**偶发无限挂起**（无超时兜底）。4400 只 = 半小时，进程池下每个子进程还要重来一遍。
- 快照 = 把**它当时返回的那个 `pandas.DataFrame` 原样 pickle 下来**（列：
  `date / fenhong / peigu / peigujia / songgu / zhuanzeng`），之后所有进程改成**读本地文件**。
- 替换点是 **`DataAPI.TdxAPI` 的模块属性** `get_xdxr_data`
  （`TdxAPI.py` 里有 `from DataAPI.ElTdxAPI import get_xdxr_data` 把它绑定成模块属性 ⇒
  必须替换这个属性，改 `ElTdxAPI` 侧无效）。代码见 `tdx_source.install_xdxr()`。

**它和"实盘现问 eltdx"是不是同一个答案？有实测证据**（`common/xdxr_parity.py`）：

| 检查 | 结果 |
|---|---|
| A 覆盖：800 只股票池每只都有快照文件吗 | **800/800，缺文件 0**（791 只有除权记录、9 只确实无除权；事件条数中位 10、最大 38） |

## 2. 三个口径

同一个信号，可以用三种方式问"它好不好"。**三者的可交易性完全不同**，混用是最大的坑。

| 口径 | 判据 | 回答的问题 | 可交易？ |
|---|---|---|---|
| **一 · 结构** | 入场后先「走出反向笔」还是「原笔延伸」 | 这个买点有没有立刻被否定 | 否 —— 定义里就用了未来 |
| **二 · 事件研究** | 信号 `ret_H` − 同标的随机入场收益（配对） | 信号比"随便买"强多少 | 半可交易（含未来信息的部分已单列） |
| **三 · 确认后入场** | 等反向笔确认后再进场，从**确认那根**起算 | 用"迟到"换"确定性"值不值 | 是 |

**口径一的两个结果词**：

- **走出反向笔**（成功）＝ 入场后先形成一笔方向相反的笔 ⇒ 买点至少推动了价格。
- **原笔延伸**（失败）＝ 反向笔还没成形，价格就跌破（买点）／突破（卖点）了信号所依据的分型极值。
  即**入场前提当场破裂**。
- 窗口 = 30 根；超时未定 = 窗口内既没确认反向笔、也没破极值
  （周K 2.4%、日K 1.8%、分钟 0.8%~4.5%，量级可忽略但不为零）。

**超额 Δ 的统一算法**（口径二与口径三同式）：

```
Δ = ret_H(信号) − sg × baseline(同标的、同周期、同一段 K 线的全样本前瞻均值)
sg = +1（买点/做多）或 −1（卖点/做空）  ⇒ 卖点的对照是【随机做空】，不是"拿卖点收益减做多基准"
```

显著性统一用**按标的**的配对 bootstrap（10 000 次，seed 7）；标注 `*** p<0.001 / ** p<0.01 / * p<0.05 / n.s.`。
H = 30 根，与口径一的窗口一致。

### 7.2 并行化：必须用进程池

`Runner.run()` 与 `signal_quality.py` 的扫描都是**纯 Python CPU 活**，
CPython 的 GIL 让 `ThreadPoolExecutor` 在这类活上**退化成串行**。实测
（`common/bench_pool.py`，160 只 × 周K × 1 方案，20 逻辑核）：

| 并发方式 | 墙钟 | 相对 1 线程 |
|---|---|---|
| 线程 1 个 | 20.6s | 1.00× |
| 线程 12 个 | 22.1s | **1.07×（更慢）** |
| 进程 8 个 | **6.8s** | **3.05×**（逐笔结果一致 ✔） |
| 进程 16 个 | 7.9s | 2.78×（核多≠更快） |

⇒ **甜点 8~10 个进程**。或设环境变量 `EXP_PROCS=8`。**取数（I/O）继续用线程池** —— 那里线程是对的。

> ⚠ 进程池有一个**会静默出错**的坑：`spawn` 出来的子进程**不继承**父进程的模块属性覆盖。
> 入场侧 `signal_quality.py` 不受影响（它不 patch 策略），但**出场侧的 A/B 会静默跑成基线值**，
> 见《出场策略回测.md》§6.3。
