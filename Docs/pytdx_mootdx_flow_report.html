发现 1 — 组2 vs 组2b：pytdx 缺得「冤枉」

组2 里本地 block_*.dat 全都在，need_download 为空，pytdx 一个接口都不会被调用。 但 :1288 的 import 写在「读本地文件」之前，所以 pytdx 缺失时函数在 :1290-1291 直接 return {} —— 把本来完全能工作的本地解析也一起废掉了。 1110 只 → 0 只，只留一条 ERROR。这是「无关依赖绑架整条兜底」，而不是「缺依赖所以功能不可用」。

发现 2 — 400 截断是服务端造成的，不是解析器

直接读二进制验证：block_gn.dat（269 板块）/ block_zs.dat（117）/ block_fg.dat（161）/ block.dat（100）里， 声明成分股数最大就是 400，没有任何板块超过 400。

记录步长 2800 字节 ÷ 每股 7 字节 = 400 只（解析器 :1545 pos = block_stock_begin + 2800）
实测 block_gn.dat 269 个板块中，26 个板块恰好 400 只（其余都 <400）
组3 从真实服务器重新下载后，结果依然是 400 ⇒ 上限焊死在数据源侧

所以 Step4 不只是「备胎」，它在被用到时会静默返回不完整数据：同一板块 infoharbor 给 1102 只，block_*.dat 只给 400 只，缺口 702 只（63.7%），且扫描照常进行、不报错。

六、依赖清单该怎么放？

问题答案
项目现在声明了吗？ requirements.txt:17 把 pytdx>=1.72 放在 「一、运行必需」段；mootdx 未声明（与 0 处调用一致，正确）。
缺 pytdx 服务能起来吗？ 能。实测屏蔽 pytdx 后 import DataAPI.TdxAPI 成功， sys.modules 里没有 pytdx。app_config 启动路径不受影响。
缺 pytdx 什么功能没了？ ① 「刷新」按钮的板块文件下载彻底失效（5 个 .dat 都不更新，仅 WARNING）； ② 880xxx 兜底成分股查询返回 0 只。两者都不报错、不崩溃。
该不该留在「运行必需」？ 留，但建议改归位到「引擎可选数据源」并注明「未装则刷新按钮的板块文件不更新」。 理由是它与同段的 fastapi / numpy / pandas 语义不同：那些缺了直接起不来，pytdx 缺了只是功能静默降级。 若产品上认定「板块文件必须能刷新」，那它就该加启动期显式校验（见下），而不是靠清单位置暗示。
能删掉 pytdx 吗？ 不能。refresh_block_files 是前端刷新按钮的唯一实现， 删除会让 T0002/hq_cache 下 5 个板块文件永久停留在旧版本。 要下线必须先有替代下载通道（eltdx 或其它）。

七、建议的修复项（按性价比排序）

P0 — 把 import 挪到真正需要它之前（改 2 行，消掉「无关依赖绑架」）

TdxAPI.py:1288 的 from pytdx.hq import TdxHq_API 移到 :1332 if need_download: 分支内部。这样当本地 block_*.dat 齐全时， 没装 pytdx 也能拿到 400 只，而不是 0 只。实测组2 与组2b 的差距就是这 2 行。

P1 — 把 400 截断从 WARNING 升级为显式标记

:1736 目前只在 len(stocks) >= 400 时打 WARNING 就照常 return。 建议：在返回结构里加 truncated: true 或把日志升为 ERROR， 让「扫描池从 1102 缩到 400」这件事不可能被忽略——这比报错危险得多，因为结果看起来是正常的。

P1 — 修正 Docs/data_source_inventory.md 两处口径

:9 与 :20 的「注释保留」改为「已于 2026-09 整体删除，现为 eltdx 单源」， 并在 880xxx 行补注「block_*.dat 兜底仅 400 只上限、仅覆盖 2 个独有板块」。 顺带把头部 commit 标注更新到 fde4a1d。

P2 — 刷新流程增加 pytdx 可用性前置校验

AppRefresh._refresh_stock_names 在调 refresh_block_files 前， 先探测 pytdx 是否可导入；不可用则把 _set_refresh_status(error=...) 置为可见错误， 而不是只写一条后端 WARNING —— 目前前端刷新进度条会「顺利完成」，用户不知道板块文件根本没更新。
