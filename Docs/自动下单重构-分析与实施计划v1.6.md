## 1. 结论摘要与决策拍板记录

### 1.1 一句话结论

你的判断是对的，而且比想的更彻底：**当前实现里的 `LOCK`（锁仓）与 `UNLOCK`（解锁）不是两个独立操作，它们分别是 `OPEN` 和 `CLOSE` 在特定状态下的马甲。**

证据在 `Trading/Broker/Base.py:44-55` 的 `INTENT_TO_OFFSET`：

| 现有 intent | 实际 CTP 报文 | 等价于 |
|---|---|---|
| `OPEN` | `OPEN` | **OPEN** |
| `LOCK` | `OPEN`（方向相反） | **OPEN**（只是方向取反） |
| `UNLOCK` | `CLOSE` | **CLOSE** |
| `CLOSE` | `CLOSE` | **CLOSE** |

**下单一层早就没有"锁仓/解锁"这回事了，多出来的两个名字纯粹是引擎状态机的记账标签。** 围着这两个标签长出来的 `PositionOrigin`（185 处）、`lock_pair_id`（118 处）、`ExitMode`、`_unlock_position` / `_book_lock_pair` / `_upgrade_lock_pair`（约 300 行）才是"绕"的来源。删掉后，判定从"这笔仓什么出身"变成"净敞口是多少"——正是你 ⑴ 的口径。

## 2. 领域术语表（接手者必读）

本重构涉及的概念在代码里名字混乱（`origin` / `mode` / `intent` / `lock` 等），这张表是**唯一口径**。实施时代码注释与命名应逐步向此表对齐。

| 术语 | 英文/字段名 | 定义 | 常见误解 |
|---|---|---|---|
| **净敞口** | `net_volume` / `net` | `Σ(side.sign × volume)`，多 = +，空 = − | 不是"持仓总手数"，是**代数和** |
| **空仓态** | `AccountState.FLAT` | `net == 0` 且簿内**无**仓单 | 与"锁仓态"区别在**有没有仓单**，不在净敞口 |
| **锁仓态** | `AccountState.LOCKED` | `net == 0` 且簿内**有**仓单 | 不是一种操作，是**净敞口为 0 的自然结果** |
| **运行态** | `AccountState.RUNNING` | `net != 0` | 唯一响应止盈止损的状态 |
| **运行段** | `run_anchor` / `run_date` / `run_plan` | 净敞口从 0 变非 0 起、到重新归零止的一段风控上下文 | 不是某一笔仓单，是**净敞口的投影** |
| **风控锚** | `run_anchor` | L1-L3 的基准价 = 进入运行段那次**成交价** | 与"会计锚"（被平那笔的 `entry_price`）**不同**，两者分离是有意的 |
| **会计锚** | `Position.entry_price` | 记 `Trade` 盈亏用的历史开仓价 | 对账用，不参与风控 |
| **仓单 / 笔** | `Position` | 一次报单的产物，含 N 手 | 交易所没有"笔"的概念（只有手 + 今昨），"笔"是本地为 FIFO 保留的时序索引 |
| **N** | `cfg.risk.max_volume`（现默认 2） | 每次报单的手数 | 假设**恒定**；若可变，一次 CLOSE 会跨笔（见 §8 风险 R4） |
| **D_last** | `latest().entry_date` | 簿内最近一笔仓单的建仓交易日 | 等价于"簿内任一笔的日期"（证明见附录 A.3） |
| **对冲目标** | `oldest_opposite(side)` | 反向仓中 `entry_bar_seq` 最小的一笔 | 即 FIFO：平掉反向**最早**那一撮 |
| **今日单 / 跨日单** | `entry_date == today` / `< today` | 建仓交易日是否等于当前交易日 | 决定性判据，一旦判错会触发平今费/废单 |
| **交易日** | `trading_day_of_ms()` | 北京时间 hour ≥ 20 归属次一自然日 | 夜盘 21:00 的成交属于**次日**交易日 |

## 3. 核心设计决策（已拍板部分）

### 3.1 D1 —— 风控锚（✅ 已拍板）

删掉 `lock_pair_id` 后，"解锁平掉 B 仓，谁来接止盈止损"这个问题失去了答案。你 ⑶ 里问的"场景 X 与 Y 是否执行结果一模一样"，本质就是问锚怎么取。

**方案：引入"当前运行段"（run position）—— 净敞口的投影，而不是簿内某笔仓单。**

引擎额外持久化三个字段，在**净敞口从 0 变为非 0 的那一刻**写入，在净敞口归零时清空：

| 字段 | 含义 | 写入时机与取值 |
|---|---|---|
| `run_anchor` | L1-L3 的风控基准价 | = 该次 OPEN/CLOSE 的**成交价** |
| `run_date` | 运行段的建仓交易日 | = 该次操作后簿内最近一笔的 `entry_date` |
| `run_plan` | 该段的 L1-L3 出场计划 | = `exit_policy.plan(sig, anchor=run_anchor)` |

于是：

- **场景 X（空仓做多）**：买开成交 P₀ → `run_anchor = P₀`
- **场景 Y（锁仓跨日做多）**：买平成交 P₂ → `run_anchor = P₂`

两者同一信号、同一参考价、同一超价规则、同一时刻报单 → **P₀ 与 P₂ 同分布（通常相等）→ L1-L3 结果一致**。这正好回答了你的 ⑶：**一致，而且是由构造保证的，不是巧合。**

对比现状：现在靠 `_upgrade_lock_pair` 拿 `lock_pair_id` 找到配对仓、传 `anchor=unlock_price` 重算 `ExitPlan`（`Engine.py:1465-1467`），目标相同，路径绕了一大圈。

**这个方案还顺带消掉了 4 类复杂度：**
- 不用找配对仓 → `lock_pair_id` 及 5 个防御分支全删
- 不用改仓单的 `origin` → 仓单落簿后**只读**（除被平掉时移除）
- 止盈止损从"逐笔判定"变成"对当前运行段判定一次" → `_settle_positions` 的 FIFO 批次逻辑可大幅简化
- 不需要"缺口补开"逻辑 → `unlock_no_new_open` 配置项退役

> ⚠️ **需要保持的分离**：`Trade` 的会计锚是**被平那笔仓的 `entry_price`**（历史价 P₀/P_B），风控锚是 `run_anchor`。两者分离是有意的（对账用会计锚、风控用风控锚）。保持分离，`Trade` 记账逻辑可基本不动。

### 3.2 D2 —— `max_open_positions` 删除（✅ 已拍板）

### 3.3 D3 —— 关闭自动下单 = "冻结"语义（✅ 已拍板保留）

**先解释"锁对无自动出口"是什么意思**（这是对 `Engine.py:1528-1537` 注释的转述）：

关闭自动下单时（`shutdown_and_lock_all`），引擎按规则 ⑸ 处理未了结持仓：
- 今日单 → 反向 OPEN 锁住（净敞口归 0）
- 跨日单 → CLOSE 平掉

处理完后账户停在**锁仓态**（净敞口 0，但还有成对的多空仓单）。此时：

| 路径 | 是否可用 | 说明 |
|---|---|---|
| 继续等止盈止损 | ❌ | 运行态才有 L1-L3；锁仓态 `net==0`，不响应 |
| 等交易信号 | ❌ | `on_signal` 顶部 `if not auto_order_enabled: return` |
| 引擎自己清仓 | ❌ | 没有这条代码路径，也不打算加 |
| **重新开启自动下单 + 出现交易信号** | ✅ | 走转移表 3（跨日 → CLOSE）或 2（今日 → OPEN）→ 进运行态 → 止盈止损接管 → 逐层拆锁 |
| **人工在柜台平掉** | ✅ | 唯一不依赖引擎的出口 |

**所以"无自动出口"的准确含义是**：关闭期间引擎不会动它，**不是永久死锁**。它是"有意选择的行为，不是遗漏"（原注释原文）—— 理由是关闭往往意味着"人要看一眼再说"，自动清仓反而危险。为了让它在运维侧可见而非静默，关闭时若留下锁仓单会写一条 `account_frozen` 事件（`Engine.py:1587-1598`）。

**保留这个语义，新模型下的改写点只有一处**：把"按 `origin` 统计锁仓笔数"改成"按净敞口统计"：

```python
# 现状（Engine.py:1547-1548, 1577-1581）
remaining = [p for p in positions if p.origin is not PositionOrigin.SOFT_EXIT_LOCK]
locked_n  = sum(1 for p in positions if p.origin is PositionOrigin.SOFT_EXIT_LOCK)

# 新模型
#   关闭时只需处理"净敞口 != 0"的运行段：net!=0 → 按规则 ⑸ 离场一笔
#   net==0（空仓/锁仓）→ 无事可做，直接 return
if self.positions.net_volume() == 0:
    return
```

⚠️ **一个需要你知道的运维约束**（现状也有，不是新引入的）：关闭动作**必须在交易时段内发生**。收盘后（15:00 之后、或 20:00 之后已翻篇的非交易时段）调 `shutdown_and_lock_all` 会尝试报单并全部失败，账户就停在"未了结 + 已关闭"的更糟状态。建议在文档与前端都标注这一点，二期可加一条"非交易时段拒绝关闭、改为仅持久化"的护栏。

### 3.4 D4 —— 成本口径保持不变

`CLOSE` 恒按平昨费率（0.0023%）计，前提是"规则保证 CLOSE 只用于跨日单"。新状态机里 `CLOSE` 的两个出口（转移 3 和 5）都要求 `D_last != today`，前提成立，**这个约束比现状更硬**。现有的 `closetoday_first` / `cost_points` 逻辑不用动。

> 补充（`InstrumentSpec.py:40-44` 已更正过的注释）：`closetoday_first` **不是**"平仓优先平今"，它只是"是否允许把今仓判成平今费率"的成本开关。规则 ⑸ 下正常流程恒走平昨费率。

## 4. 目标模型（把你的规则形式化）

### 4.1 三态：全部由净敞口派生

| 状态 | 判据 | 含义 |
|---|---|---|
| **空仓 FLAT** | `net == 0` 且簿内**无**仓单 | 无仓单，盈亏恒 0 |
| **锁仓 LOCKED** | `net == 0` 且簿内**有**仓单 | 多空互锁，盈亏锁定 |
| **运行 RUNNING** | `net != 0` | 有真实敞口，盈亏实时变动 |

```python
def account_state(self) -> AccountState:
    poss = self.positions.positions
    if not poss:                return AccountState.FLAT
    if self.net_volume() == 0:  return AccountState.LOCKED
    return AccountState.RUNNING
```

### 4.2 两种操作

| 操作 | 买信号 | 卖信号 | CTP 报文 |
|---|---|---|---|
| **OPEN** | 买开（BUY+Open） | 卖开（SELL+Open） | `direction` 由信号方向定，`offset=OPEN` |
| **CLOSE** | 买平（BUY+Close） | 卖平（SELL+Close） | `direction` 由信号方向定，`offset=CLOSE` |

方向**永远由触发源决定，不由"这是第几笔仓"决定**：
- 交易信号触发 → 方向 = 信号方向
- 止盈止损触发 → 方向 = 当前净敞口的**反向**

### 4.3 完整状态转移表

记 `D_last` = 簿内**最近一笔**（`entry_bar_seq` 最大）仓单的 `entry_date`，`today` = 当前交易日。

> 为什么只需看最近一笔 → 附录 A.3：运行态/锁仓态下簿内仓单必然"全今日"或"全跨日"，不存在混合。

| # | 当前态 | 触发 | 条件 | 操作 | 转移后 |
|---|---|---|---|---|---|
| 1 | FLAT | 交易信号（方向 s） | — | OPEN N 手 @s | RUNNING |
| 2 | LOCKED | 交易信号（方向 s） | `D_last == today` | OPEN N 手 @s | RUNNING |
| 3 | LOCKED | 交易信号（方向 s） | `D_last != today` | CLOSE N 手 @s（对冲反向最早一笔） | RUNNING |
| 4 | RUNNING | 止盈止损 L1-L3 | `D_last == today` | OPEN N 手 @(−net 方向) | LOCKED |
| 5 | RUNNING | 止盈止损 L1-L3 | `D_last != today` | CLOSE N 手 @(−net 方向)（对冲反向最早一笔） | LOCKED 或 FLAT |

> 转移 4/5 中的 D6 开关（Phase 10 已落地）：若品种配置了 `prefer_lock_over_closetoday = False` 且交易所支持平今（SHFE/INE），转移 4 改为直接 **CLOSETODAY**（付平今费、直接回空仓态）；否则走反向 OPEN 锁仓（现状）。见 §5.4。

**"最近一笔"的取值规则**（每次操作后自然成立，无需额外维护）：
- OPEN → 新仓就是最新的 → `D_last = today`
- CLOSE → 平掉的是**最早的**反向仓，剩余仓单的最近一笔日期不变 → `D_last` 保持原值

### 4.4 不变量（写成断言 / 契约测试）

1. `net != 0` 时 `|net| == N` —— 因为每次只从 `net==0` 出发开/平 N 手
2. 簿内不存在"部分今日、部分跨日"的混合（附录 A.3）
3. RUNNING ⇔ `net != 0`；LOCKED ⇔ `net == 0` 且非空
4. 一次触发 = 一次报单 = 一笔成交，不留部分成交
5. 状态转移表无第 6 种情况；出现即视为代码缺陷。⚠️ **v1.0 更正**：护栏是**构建期 AST 闸门**（`p33` 断言 `transition=` 的常量集合恰为 {1,2,3,4,5}），**不是**运行时事件 —— 全仓**不存在** `state_machine_violation` 这个事件，旧版本此处写"写 `state_machine_violation` 事件"是文档错误，以代码为准（见 附录 D.2）
6. **CLOSE 的目标必须是跨日仓**（`target.entry_date < today`）—— 这是全交易所安全性的硬约束，见 §5.3

### 4.5 原文举例的逐帧推演（验证状态机自洽）

把需求原文的 A→B→C→D / E→F 例子逐帧过一遍转移表。设 N = 2 手，信号恒为**买信号**，记 `+` 为多、`−` 为空。

**第 1 日（`today = D1`，初始 FLAT）**

| 步 | 触发 | 前置状态 | `D_last` | 操作（走哪条转移） | 仓单序列（按时间） | net | 后置状态 |
|---|---|---|---|---|---|---|---|
| **A** | 买信号 #1 | FLAT | — | **OPEN 买开 2**（转移 1） | `[A:+2]` | +2 | RUNNING |
| **B** | L1-L3 | RUNNING | D1 = 今日 | **OPEN 卖开 2**（转移 4，反向） | `[A:+2, B:−2]` | 0 | **LOCKED（1 锁）** |
| **C** | 买信号 #2 | LOCKED | D1 = 今日 | **OPEN 买开 2**（转移 2） | `[A:+2, B:−2, C:+2]` | +2 | RUNNING |
| **D** | L1-L3 | RUNNING | D1 = 今日 | **OPEN 卖开 2**（转移 4，反向） | `[A:+2, B:−2, C:+2, D:−2]` | 0 | **LOCKED（2 锁）** |

✅ 收盘停在 **LOCKED 2 锁**，与原文一致。**全程只需要"净敞口 + D_last"，没有用到任何配对关系** —— A 与 B、C 与 D 从未被绑定。

**第 M 日（`today = DM`，M ≥ 2，初始 LOCKED 2 锁，全部仓单 `entry_date = D1 < DM`）**

| 步 | 触发 | 前置状态 | `D_last` | 操作 | 对冲目标（反向最早） | 平仓后仓单序列 | net | 后置状态 |
|---|---|---|---|---|---|---|---|---|
| **E** | 买信号 #1 | LOCKED | D1 ≠ 今日 | **CLOSE 买平 2**（转移 3） | `B`（最早的空单） | `[A:+2, C:+2, D:−2]` | +2 | RUNNING |
| **F** | L1-L3 | RUNNING | D 仍为 D1 ≠ 今日 | **CLOSE 卖平 2**（转移 5） | `A`（最早的多单） | `[C:+2, D:−2]` | 0 | **LOCKED（1 锁）** |
| **E2** | 买信号 #2 | LOCKED | D1 ≠ 今日 | **CLOSE 买平 2**（转移 3） | `D`（最早的空单） | `[C:+2]` | +2 | RUNNING |
| **F2** | L1-L3 | RUNNING | C 仍为 D1 ≠ 今日 | **CLOSE 卖平 2**（转移 5） | `C` | `[]` | 0 | **FLAT（0 锁）** |
| **G** | 买信号 #3 | FLAT | — | **OPEN 买开 2**（转移 1） | — | `[G:+2]` | +2 | RUNNING |

> 第 2 次信号的两笔原文未命名，此处记作 E2/F2；第 3 次信号的 OPEN 原文记作 **G**。

✅ **与原文逐字对上**：E 平 B、F 平 A（2 锁 → 1 锁）；E2 平 D、F2 平 C（1 锁 → 空仓）；第 3 次信号回到空仓态才 OPEN。

**值得写进注释的两点**：

1. **F 的判据为什么还是"跨日"**：E 之后剩 `[A, C, D]`，最近一笔是 **D**，`D.entry_date = D1 ≠ today` → 走 CLOSE。**平掉最早的一笔不会改变"最近一笔"的日期**，所以 `D_last` 在整个拆锁过程中保持不变，不需要每步重算。
2. **"今日单不会退化成跨日单"**：第 1 日建的 A/B/C/D 在第 M 日整体变跨日，是一次性跃迁；跃迁之后只能走 CLOSE，直到清空。**这正是"全今日 / 全跨日不混合"（附录 A.3）的具体体现。**

### 4.6 原文"另外⑵"：按笔还是按手记录？

**两个层次都要，且现状做法就是对的**——不是二选一：

| 层 | 记录单位 | 为什么 |
|---|---|---|
| **交易所 / CTP 柜台** | **手** | 柜台的持仓聚合维度是「合约 + 方向 + 今/昨」，**没有"笔"这个概念**。你报一次平仓，它只从对应桶里减手数，不关心你心里想着平哪一笔 |
| **本地 `PositionBook`** | **笔**（每笔 N 手） | 要回答"下一笔 CLOSE 对冲谁"，必须有时序。这个 FIFO 顺序**交易所不替你记**（见 §5.3 与 R9），只能本地记 |
| **前提** | **N 恒定** | 当前 `RiskConfig.max_volume = 2`。若 N 可变，一次 CLOSE 可能跨多笔，本地簿面与柜台对不上 → 见 §8 R4 |

> 所以原文的直觉（"应该按手记录"）在**柜台视角**是对的；而本地多记一层"笔"，是为了 FIFO 对冲能成立。两者不冲突，是同一件事的两个投影。

### 4.7 原文"另外⑶"：场景 X vs 场景 Y 逐项对比

**场景 X** = 空仓态做多（买入**开**新仓）；**场景 Y** = 锁仓态且跨日时做多（买入**平**旧空仓）。

| 维度 | 场景 X | 场景 Y | 是否一致 |
|---|---|---|---|
| 触发源 | 买点交易信号 | 买点交易信号 | ✅ 相同 |
| 前置状态 | FLAT | LOCKED 且 `D_last != today` | —（定义使然） |
| **操作 / CTP 报文** | **OPEN**：`BUY + OPEN` | **CLOSE**：`BUY + CLOSE` | ❌ **必然不同**（这是唯一的操作差异） |
| 对冲目标 | 无（新建仓） | 反向最早的一笔空单（FIFO） | — |
| 成交价 | P₀ | P₂ | ✅ **同分布**（同一时刻、同一超价规则、同为对手价 ± 超价 tick） |
| 净敞口变化 | 0 → +N | 0 → +N | ✅ 相同 |
| 转入状态 | RUNNING | RUNNING | ✅ 相同 |
| **风控锚 `run_anchor`** | = P₀ | = P₂ | ✅ 由 D1 **构造保证**一致（不是巧合） |
| L1 止损价 / R 值 | `base = P₀` | `base = P₂` | ✅ 相同（`Exit.py:144`：`base = anchor if anchor is not None else entry_price`） |
| 保本线 / 跟踪止损触发价 | 由 `run_plan` 决定 | 由 `run_plan` 决定 | ✅ 相同 |
| 手续费（中金所期指） | 开仓 0.0023% | **平昨 0.0023%** | ✅ **相等**（中金所开仓费率 == 平昨费率；平今才是 0.0345%） |
| 滑点 / 超价 | 同一套超价规则 | 同一套超价规则 | ✅ 相同 |
| 离场方式 | L1-L3 → 反向 OPEN（今日）或 CLOSE（跨日） | 同 | ✅ 相同 |
| **`Trade` 会计锚** | 无（新开仓，本笔即起点） | 被平那笔空单的 `entry_price`（历史价） | ❌ **必然不同**（会计口径，不参与风控） |

**结论**：原文的直觉（"执行结果应该一模一样"）**成立** —— 除 **① 报单 offset** 与 **② `Trade` 会计锚** 这两项"必然不同"之外，L1-L3 的**全部行为一致**，且总盈亏 Σ net_points 相同。

> 会计锚不同是**有意的**：锁仓期间浮盈挂在原仓单上不兑现（这是锁仓的定义），所以场景 Y 的 `Trade` 记的是"原空单从开仓到被平"的完整盈亏，而 X 记的是"新多单从开仓到离场"。两者切片不同，但端到端总和一致。

## 5. 全品种适用性分析（你问的 ⑴）

### 5.1 结论先行

**状态机本身 —— 三态 + OPEN/CLOSE + `D_last` 判据 —— 与交易所、品种、夜盘完全无关，5 家期货交易所通用。**

理由很直接：它只依赖两个量 —— **净敞口**（交易所无关）和**建仓交易日**（交易所无关）。没有任何一步需要判断"这是哪个交易所"。

而且有个**意外的好处**：你的"今日单永不 CLOSE"这条规则，恰好让整个系统**永远不需要 `CLOSETODAY` 指令**，从而天然绕开了 5 家交易所最大的平今/平昨指令差异。这是这套设计最有价值的地方，建议写进代码注释 —— 后人很容易以为"没实现平今"是遗漏。

**但要真正跑通全品种，有 6 个适配点需要额外处理（都在状态机之外）。** 见 §5.4。

### 5.2 交易所差异矩阵

#### 表 A：平今 / 平昨指令（决定 CLOSE 会不会被废单）

| 交易所 | 有无独立"平今指令" | 报 CLOSE 时交易所怎么处理 | 我们的设计是否安全 |
|---|---|---|---|
| **中金所 CFFEX**（IF/IH/IC/IM、TS/TF/T/TL） | ❌ 无 | 统一按 CLOSE 处理；**同时有今仓和昨仓时默认先平今仓**（按平今费率收费） | ✅ 安全（我们只在全跨日时 CLOSE，没有今仓） |
| **上期所 SHFE** | ✅ 有（`CLOSE` / `CLOSETODAY` 必须区分） | CLOSE = 平昨；**昨仓不足会废单** | ✅ 安全（同上） |
| **能源中心 INE** | ✅ 有 | 同上 | ✅ 安全 |
| **大商所 DCE** | ❌ 无 | 统一 CLOSE，先开先平 | ✅ 安全 |
| **郑商所 CZCE** | ❌ 无 | 统一 CLOSE，先开先平 | ✅ 安全 |
| **广期所 GFEX** | ❌ 无 | 统一 CLOSE，先开先平 | ✅ 安全 |

**推论**：只要不变量 6（CLOSE 的目标必为跨日仓）成立，**六家都不会废单、都不会误收平今费**。这条不变量应写成硬断言 + 契约测试，不是注释。

#### 表 B：单向大边保证金（决定"锁 N 层"要压多少钱）

| 交易所 | 盘中是否实时生效 | 生效范围 | 取消优惠的时点 |
|---|---|---|---|
| **中金所 CFFEX** | ✅ **盘中实时** | 同品种（2014-10-27 起）；国债跨品种（2015-07-10）；股指 IF/IH/IC/IM 跨品种（2019-06-03） | 国债：交割月前一交易日收盘后 |

**设计影响**：锁仓资金成本随交易所翻倍（DCE/CZCE 盘中双边，锁 N 层占 2N 手），但**不引入锁层数上限**（D9）：程序按状态机自由开/平仓，资金不足 → D10 立即停追 + D11 弹窗提示用户手工干预（加保证金）。

#### 5.2.1 Q4 保证金差异：对当前软件到底有什么影响？（2026-09-11 追加）

**先回答"我感觉软件没有涉及保证金的代码逻辑"—— 你是对的，一处都没有。**

全仓 grep「保证金 / margin / 可用资金 / balance」，`Trading/` 下**零命中**（唯一命中的 `margin` 是前端 CSS 的 `margin-left`）。而且这不是遗漏，是**主动删掉的**：

**引擎现有的拒单处理（已核实）**：

| 场景 | 现状行为 | 代码位置 |
|---|---|---|

| **平仓被拒** | 保留持仓，**下一根 K 线再试** | `Engine.py:1068-1082` |
| 平仓连续被拒 | 写 `close_repeatedly_rejected` 事件 | `Engine.py:1075-1082` |

#### 5.2.2 反向开仓被拒时会发生什么（R10 的准确表述 · 2026-09-11 修正）

> ⚠️ **本节是对初版 R10 的修正。** 初版写成"卡在运行态的死循环"，**表述错误**，已更正。

**先澄清一个极易误解的点：反向开仓被拒后，引擎不会"卡死"，它在持续重试离场。**

规则⑶ 拦截的是**新交易信号**（运行态不准再开新仓），**不拦截离场动作**。运行态下 L1-L3 本就持续触发：

```
运行态 → L1-L3 触发 → 转移 4 反向 OPEN
      → broker 内部追价 close_max_chase 轮（SimNow.py:807-859）
      → 轮数用尽仍不成交 → 返回 rejected
      → 引擎保留持仓，下一根 K 线再触发 L1-L3 → 再来一轮追价
      → ……直到离场成功
```

**所以"每根 K 线重试一次"不是故障，是设计**。真要哪天"追价被运行态拦截"了，那才是灾难 —— 就没人负责离场了。`_submit_lock` 的 docstring（`SimNow.py:811`）把这个理由写得很清楚：「锁仓本质也是离场（软离场），**卡单必须追价，否则浮亏扩大、浮盈变浮亏**」。

**真正的风险不是"死锁"，而是下面两条：**

**① 资金不足的拒单与 FOK 全撤走同一条追价循环 —— 白追。**

| 拒单原因 | 追价有没有意义 | 现状行为 |
|---|---|---|
| FOK 全撤（对手盘深度不够） | ✅ **有** —— 价格会动，超价能吃 | 追价，正确 |
| **资金不足** | ❌ **没有** —— 再追 100 次还是资金不足 | **同样追价**（错误） |
| 非交易时段 / 集合竞价 | ❌ **没有** —— 永远不可能成交 | **同样追价**（错误） |

`_finalize`（`SimNow.py:874-910`）**完全不对拒单原因分类**，`last_msg` 只是原样塞进日志与 `Order.meta`。后果：资金不足时白耗 `close_max_chase × chase_interval` 秒、白吃报单额度（代码 `SimNow.py:854` 自己就在担心"报撤单频率超限 / FOK 撤单计数爆量"），而这整段等待期间**敞口继续裸奔**。

> **这是可修的**：CTP 原始错误信息**带错误码**（代码里已有先例 —— `SimNowSmoke.py:15` 记录过"被 CFFEX 涨跌停风控拒单（错误码 50）"）。技术上完全能识别"资金不足"，只是现在没做。

**② 三条拒单原因里，只有一条能用"资金充足"规避。**

| 原因 | 用户确保资金充足能否规避 |
|---|---|
| 资金不足（双边收交易所上更易触发） | ✅ 能 |
| FOK 全撤（深度不够 / 涨跌停板） | ❌ 不能 —— 但追价通常最终能成，代价是滑点变差 |
| **非交易时段 / 集合竞价报单** | ❌ **不能，且追价 100% 无用** —— 见 §5.4 阻塞点 6；`_lock_remaining_positions` 这条关闭路径绕过了"有 K 线才触发"的隐式规避 |

**关于"由用户确保资金充足来规避"（需求方观点）**：在**只跑中金所期指**的前提下基本成立 —— 中金所单向大边**盘中实时生效**，且规则明确"可用资金为正但不足开一手时，仍允许反向开仓"，所以资金不足这一条**几乎不会触发**。这**正是"一期只跑中金所"（D5）能成立的前提之一**。

两点补充：

1. **"资金充足"在双边收交易所下是个容易被低估的数**（但**不写进代码**，见 D9 修订）。锁仓层数会累积（同日信号密集可锁多层），每层双边占 2N 手。中金所单边收时"够开一手的钱"就够锁；大商所/郑商所需要的量级是 **2 × 预期最大同日锁层数 × N 手** —— 这个数**由用户在入金时自行判断**，代码不设阈值、不拦报单，只在真的被拒时弹窗告诉他。
2. **反过来说：一旦二期上大商所/郑商所（盘中双边收），①的"白追"就从理论问题变成现实问题** —— 那时**不是**要加 `max_lock_layers`，而是 D10 的"资金不足 → 立即停追 + 弹窗"会变得**频繁触发**。弹窗通道（D11）在二期是必需品，不是可选品。

#### 5.2.3 "非交易时段报单"到底什么场景会发生（需求方追问 ⑵）

**先说结论：正常行情驱动路径下确实几乎不会发生，因为系统靠"没有新 K 线就不触发"隐式规避。但存在 4 个真实入口。**

> ⚠️ **一个被忽略的事实**：`Trading/Config.py:281` 的注释写着「已删除：原五道硬闸门（**`enforce_session`** / `no_open_after` / `max_trades_per_day` / …）」——
> **交易时段闸门曾经存在，被删掉了**。所以现在**没有任何代码检查"现在能不能下单"**。

| # | 场景 | 为什么会发生在非交易时段 | 现实概率 |
|---|---|---|---|
| **1** | **用户点"关闭自动下单"按钮**（`shutdown_and_lock_all`） | 这条路径**由前端按钮直接触发，完全绕过了"有 K 线才触发"**。收盘后点 → 报单全废。§3.3 已标注这条运维约束 | **高** —— 这是最现实的一个 |
| **2** | **追价循环跨过收盘时点** | 14:59:50 触发 → 每轮 `sleep(chase_interval)` 重报 → 跑到 15:00 之后仍在报单。追价循环内部**不检查时间** | 中 —— 收盘前的信号必然踩到 |
| **3** | **最后一根 K 线延迟到达** | 15:00 收盘那根 K 线可能因 SSE 推送延迟在 15:00:00 之后才到 → 触发信号 → 报单 | 中 |
| **4** | **夜盘结束到次日开盘的空档 / 集合竞价** | 01:00（或 02:30）夜盘结束到 08:55 之间、`today` 已翻篇但非交易时段；集合竞价（如 9:25-9:30）有行情但**禁止报单** | 低（夜盘品种才有） |

**另外两个"不是非交易时段但表现一样"的情况**，D10 应一并覆盖：

- **涨跌停板**：对手价在停板价 → FOK 必然全撤，追价也追不动（价格出不去）
- **平仓量超过持仓量**（CTP 错误码 30）：本地簿面与柜台不同步时会触发

> **所以 D10 的分类器不该只认两类**，建议三类：`资金不足`（31）、`不可报单`（非交易时段 / 集合竞价 / 合约不能交易）、`价格不可达`（涨跌停）。前两类立即停追，第三类继续追（价格会动）。

### 5.3 逐条核对你的规则

| 你的规则 | 全品种是否成立 | 说明 |
|---|---|---|
| ⑴ 三态由净敞口派生 | ✅ | 纯本地概念，与交易所无关 |
| ⑵ 只有 OPEN / CLOSE 两种操作 | ✅ | 六家交易所都支持 Open 与 Close（平昨） |
| ⑶ 只在空仓/锁仓态响应信号 | ✅ | 纯本地 |
| ⑷ 一次信号 = 一次报单 = N 手 | ✅ | 需保证 N ≤ 交易所单笔限价单上限（中金所 20 手；各所不同，见 §5.4 阻塞点 5） |
| ⑸ 空仓态信号 → OPEN | ✅ | 六家都支持开仓 |
| ⑹ 情况1：今日单 → 反向 OPEN 锁仓 | ✅ | 六家都允许反向开仓；资金上依赖单向大边（§5.2 表 B） |
| ⑹ 情况2：跨日单 → CLOSE 平昨 | ✅ | 六家都支持平昨；安全性由不变量 6 保证 |
| ⑺ 锁仓态信号 → OPEN 或 CLOSE | ✅ | 同上 |
| 附录：无 LOCK/UNLOCK 概念 | ✅ | 报单层本就只有 OPEN/CLOSE |
| 附录：无配对，FIFO 对冲 | ⚠️ **基本成立，但有一个偏差** | 见下 |

**关于 FIFO 的偏差（重要，但不影响正确性）**：

本地按"反向最早一笔"选择对冲目标，但交易所的减仓顺序由它自己的规则决定：
- CFFEX / DCE / CZCE / GFEX：先开先平（**与我们的 FIFO 一致**）
- SHFE / INE：我们显式报"平昨"，交易所从昨仓里减 —— 但**减的是哪一撮昨仓不由我们指定**

所以本地簿面的"被平掉的那笔"可能与柜台实际减的那笔**不是同一笔**。影响：
- **手数总量、资金、净敞口**：完全一致，无影响
- **手续费**：无影响（昨仓之间费率相同；平昨 vs 平今的差别才影响费率，而我们已经规避了平今）
- **会计锚**：`Trade` 记的 `entry_price` 可能对应柜台的另一撮 → **单笔盈亏数字会与柜台对账单有出入，但总和一致**

→ **建议**：对账模块按"累计净额"核对，不要逐笔比对 `entry_price`。这不是新引入的问题（现状同样存在），但以前只跑中金所，影响小；全品种后要显式处理。

### 5.4 真正的 6 个阻塞点（状态机之外，需要额外代码）

| # | 阻塞点 | 影响 | 建议方案 |
|---|---|---|---|
| **1** | **郑商所不支持 FOK** | 不变量 4（全成或全撤）在 **FAK 多手**下失效 → 可能部分成交，簿面与柜台对不上 | 按交易所选指令属性：支持 FOK 的用 FOK（1 笔挂 N 手，N=`risk.max_volume`）；**CZCE 用 FAK 且单笔钉死 1 手**（1 笔挂 1 手，FAK(1)≡FOK(1) → 无"剩余"可撤，不变量 4 与不拆单设计同时保住，无需补簿、无需扩展状态机） |
| **2** | **DCE/CZCE 盘中双边收保证金** | 锁仓层数被资金卡死 | **不加锁层上限（D9）**：程序按状态机自由开/平仓；资金不足 → D10 立即停追 + D11 弹窗提示手工加保证金（弹窗通道在二期是必需品，见 §5.2.3） |
| **3** | **平今的经济性因品种而异** | 对"平今免收/平今便宜"的品种（如部分农产品、原油 SC 平今免收），"锁仓再跨日平"反而更贵（多一次开仓费 + 多一次跨日平仓费） | **Phase 10 已落地**：品种开关 `prefer_lock_over_closetoday`（D6，默认 True = 现状）。为 False 时转移 4 改走 CLOSETODAY → 需 broker 支持第三种 offset，且**仅对 SHFE/INE 可用**（其余四家 DCE/CZCE/CFFEX/GFEX 传平今会报错） |
| **4** | **交割月 / 最后交易日** | 上期所最后交易日前第 5 日取消单向大边；临近交割月交易所提保、限仓、个人户不得持仓进入交割月 | 新增"合约生命周期"护栏：禁止在临近交割月开新仓 + 到期前 N 日强制清仓到空仓态（不走锁仓）。**这是当前完全没有的功能**，中金所期指是现金交割所以可以一直滚，商品不行 |
| **5** | **单笔报单上限 / 最小变动价位 / 涨跌停** | 中金所限价单 20 手；各品种上限不同。涨跌停板上反向开仓可以，但**对手价可能在停板价导致 FOK 全撤** | `InstrumentSpec` 新增 `max_order_volume` / `limit_up_pct` / `exchange` 字段（**这些字段的"值"二期改为从行情自动获取，见 §5.9 / D20**）；连续 N 次全撤要有兜底（告警 or 转平今）。注意引擎不会"卡死"（追价与跨 K 线重试都在跑），风险是敞口长时间裸奔 —— 见 R10 |
| **6** | **非交易时段 / 集合竞价报单** | 日盘 15:00 后、夜盘 21:00 前的空档，以及集合竞价时段报单会失败或被拒 | 新增交易时段护栏（`InstrumentSpec` 或独立 `TradingCalendar`）：非连续交易时段不报单。现状依赖"有 K 线才触发"隐式规避，但 `_lock_remaining_positions` 这条关闭路径绕过了它（见 §3.3 的运维约束） |

**建议分两期**：
- **一期（本轮重构）**：只做与交易所无关的状态机重构（§6 Phase 1-7），保持只跑中金所的现状，**但把上面 6 个点的扩展位留出来**（不写死 `exchange`、不写死 FOK、不写死费率口径）。
- **二期（全品种）**：按 §5.4 逐项落地 + **§5.9 品种参数自动获取**，每落地一个品种跑一次仿真验证。实施纲要见 **§6.2（Phase 8~12）**。

### 5.5 夜盘：现有实现是对的（附推导）

`trading_day_of_ms()`（`Types.py:63-85`）用 **20:00 分界**：`hour >= 20 → 归属次一自然日`。

**为什么这与期货的"交易日"定义一致**（这是夜盘品种正确性的核心依据，值得写进注释）：

期货的一个交易日 = **前一自然日夜盘 + 当日日盘**。例如：

| 时点 | 属于哪个交易日 |
|---|---|
| 周一 21:00 夜盘 | **周二**交易日 |
| 周二 09:00-15:00 日盘 | **周二**交易日 |
| 周二 21:00 夜盘 | **周三**交易日 |

用 20:00 分界验证两个方向：

1. **周一 14:00 日盘开仓 A**（`entry_date = 周一`）。周一 21:00 夜盘时 `today = 周二` → `A.entry_date < today` → 判跨日 → CLOSE 平昨。
   → 柜台视角：周一 15:00 已日终结算，A 确实是昨仓。**✅ 正确。**
2. **周二 21:00 夜盘开仓 B**（`entry_date = 周三`）。周三 10:00 日盘 `today = 周三` → 判今日 → 反向 OPEN 锁仓。
   → 柜台视角：B 是周三交易日的今仓，此时发 CLOSE 平昨会被 SHFE 废单、被 CFFEX 按平今收费。**✅ 锁仓是对的。**

**20:00 这个分界点对所有夜盘时段都安全：**

| 交易所 | 夜盘时段 | 20:00 分界是否覆盖 |
|---|---|---|
| 上期所（铜铝锌等） | 21:00 - 次日 01:00 | ✅ |
| 上期所（金银） | 21:00 - 次日 02:30 | ✅ |
| 大商所 / 郑商所 | 21:00 - 23:00 | ✅ |
| 能源中心 | 21:00 - 次日 02:30 | ✅ |
| 中金所 | **无夜盘** | 不受影响 |

**周末/节假日不做精确交易日历是有意的，且正确**：周五夜盘 → 周六，与下周一不等 → 判跨日。而事实上周五夜盘的仓到下周一确实是昨仓。**只要"是否同一交易日"的判定一致，口径自洽就行**（`Types.py:75-78` 注释已说明）。

**三个夜盘特有的坑**（都建议加护栏，不阻断一期）：

1. **日盘收盘（15:00）到 20:00 之间的 5 小时**：`today` 仍是当日。若此时引擎仍在跑（如收到 15:00 最后一根 K 线后触发结算），会判"今日" → 尝试反向 OPEN 锁仓 → 但已收盘，报单失败。**需要交易时段护栏（阻塞点 6）。**
2. **夜盘与日盘之间的空档（01:00/02:30 到 08:55）**：`today` 已是下一交易日，同样是非交易时段。同上。
3. **CTP 日切时点**：柜台在 15:00 之后（约 15:30-16:00）才完成日切并更新"今/昨"标记。如果在 20:00-21:00 之间报 CLOSE 平昨，理论上柜台可能尚未完成日切。实务上各期货公司时点不一，**建议避免在这个窗口做跨日平仓**（可以简单地把夜盘开盘前 10 分钟设为"静默期"）。

### 5.6 品种层面：`InstrumentSpec` 参数化现状

### 5.7 一期范围与二期架构兼容性论证（2026-09-11 拍板）

#### 5.7.1 一期范围（D5）

- **做**：状态机重构（§6 Phase 1-7），**只跑中金所期指**（IF/IH/IC/IM；国债 TS/TF/T/TL 同规则，亦可）。
- **不做**：全品种适配（Q1）、平今开关（Q2）、交割月护栏（Q3）、保证金计算（Q4）。
- **一句话边界**：**一期只碰"与交易所无关"的部分。凡是需要知道"这是哪个交易所"才能写对的逻辑，一律留给二期。**

#### 5.7.2 为什么 Q1/Q2/Q3 放二期不会改架构（逐条论证）

| 问题 | 二期要加什么 | 会不会动一期架构 | 论证 |
|---|---|---|---|
| **Q1 全品种** | `InstrumentSpec` 加 `exchange` / `max_order_volume` / `limit_up_pct` / `last_trade_date` / `night_session`；**这五个字段的值从行情自动获取**（§5.9）；broker 按交易所选指令属性；交易时段护栏 | **不会** | 状态机的全部输入只有两个：**净敞口**（交易所无关）与**建仓交易日**（交易所无关）。转移表 1-5 里没有任何一步需要判断交易所。二期加的是"下单前的参数校验"和"broker 指令属性选择"，都在状态机**之外** |
| **Q2 平今开关** | `OrderIntent` 加第三个值 `CLOSETODAY`；转移表 4 多一条分支 | **不会**（前提是 **A1** 成立） | 转移表若集中在一个决策函数里，Q2 就只是"多返回一种 intent"；broker 的 `INTENT_TO_OFFSET` 是 dict，加一项即可 |
| **Q3 交割月护栏** | 下单前校验链加一条规则 | **不会**（前提是 **A3** 成立） | 护栏回答"能不能下单"，与"下什么单"正交。放进 `_pre_trade_check()` 就是加一个 item |
| **Q4 保证金** | ~~保证金计算 + 动态 `max_lock_layers`~~ **已作废（D9）**：不引入锁层数概念 | **不会** | 程序按状态机自由开/平仓，资金不足 → D10 立即停追 + D11 弹窗手工加保证金（一期已落地） |

**一句话结论**：Q1/Q2/Q3 全部落在「参数化 + 加分支」层面，**没有一条要求修改三态判定或转移表结构**。所以可以放心放二期。

#### 5.7.3 一期必须遵守的 5 条架构约束（A1–A5）· D7

> ⚠️ **这是 §5.7 最重要的部分。** 一期违反其中任何一条，二期就会退化成二次重构。

| # | 约束 | 具体要求 | 违反的后果 |

#### 5.8.3 三个「SimNow 永远测不到」的盲区（最高优先级）

**盲区① —— FOK 全撤（深度不足）在 SimNow 上几乎不发生，追价循环从未被真正验证。**

SimNow **不撮合**：只要价格合适（与对手价比较）就**全部成交**，不会部分成交、不会全撤。
而实盘 FOK 要求**盘口挂单量 ≥ 委托手数**，否则整笔全撤。

后果：`_submit_lock` 的追价循环（`close_max_chase=20` 轮 × `chase_interval=1.0s`）、
`_finalize` 的全撤分支、以及"部分成交"处理 —— **这三条在 SimNow 上基本跑不到**，
即"SimNow 全绿"对它们没有任何证据力。

> 对策：用 **FakeApi 契约测试**覆盖（沿用 `test_p23_fok.py` 已有的 fake 手法：
> 让 `insert_order` 返回全撤 / 部分成交），新增 **p37**（见 §7.3）。

**盲区② —— 7x24 环境不结算，昨仓恒定，跨日 CLOSE 逻辑测不出来。**

SimNow 第二套（7x24）环境官方说明：**"不提供结算等其它服务"**，账户 / 钱 / 仓与上一交易日保持一致。
而转移 5 / 转移 7 的核心判据是"最近一笔的日期是否今日"，其正确性**依赖昨仓真的存在且真的能被平掉**。

> 对策：跨日路径必须在**第一套环境**（服务时间与生产一致、有结算）或实盘小资金验证；
> 并在 `Tool/SimNow/` 下补一个"跨日仓构造 + 平昨"探针（记入 Phase 7）。
> ✅ **已落地（2026-09-13）**：`Trading/Tool/SimNow/CrossDayProbe.py` ——
> `--phase arm`（第 1 日开 1 手造今仓）/ `--phase check`（第 2 日断言昨仓 ≥ 1，
> 发 1 手 CLOSE 并断言**昨仓下降、今仓不变**）/ `--phase cleanup`（清仓收尾）；
> 另有 `--self-test` 离线自检 9 项（不连柜台即可验证两条平昨判据）。
> 它走的是**生产同一条路径**（`build_broker` + `SimNowBroker.submit`），
> 不是另写一遍判据。⚠️ 7x24 环境无日切，`--phase check` 必然报"昨仓=0" —— 这是盲区本身。

**盲区③ —— 报撤单监管与收费只在实盘存在，且 FOK 撤单被计入统计。**

中金所监管标准明确：**因 FOK / FAK 形成的撤单计入"频繁报撤单"次数统计，普通限价单撤单不计入**。
本系统四类报单全部是 `advanced="FOK"`，意味着**每一次全撤都在累加监管计数**（单日单合约 500 次触发）。
正常行情远达不到，但"资金不足 / 非交易时段"这类**追价 100% 无用**的场景会白追满 20 轮 ——
这正是 **D10 拒单分类器**除"可追溯"之外的**合规层面理由**。

> 对策：D10 分类器（已并进 Phase 3）+ 实盘后监控每日撤单计数（记入 §5.8.4）。

**本轮修正（2026-09-13）—— `SimNow` 侧的判据原先"看不见今/昨之分"：**

原 `_wait_position_ok` 的判据是 `pos_*_today + pos_*_his >= volume`，而
`_verify_position_delta` 只校验**总量**增量。两者都**看不出**成交落在今仓还是昨仓，
于是 §5.8.4 第 4 项（"平昨 CLOSE 是否真的减昨仓"）在代码里**既无实现也无测试**：

```
今仓 2 手 + 昨仓 0 手  ──▶  总量判据放行
                            └─▶ 中金所撮合默认先平今 ⇒ 要么走平今费率（≈平昨 15 倍），
```

今仓下降判 False 并发 P4/P5 诊断 —— 那说明柜台把 CLOSE 撮合到了今仓）。
OPEN 路径**一行未动**（它看总量是对的），故对开仓无任何行为影响。

#### 5.9.1 现状：手工配置，且换品种会静默用错 tick（结论 + 隐患）

#### 5.9.3 优先级语义（**需求方 2026-09-11 已定方向：fail-closed → A′**）

`dry_run` / `replay` 没有行情连接，**必须有兜底值**；但**实盘用"错误的兜底值"下单 == 主动踩坑**。
需求方 2026-09-11 明确：**只有从行情自动获取到正确值才允许交易**，否则宁可不下单。故定为 **A′**：

| 方案 | 语义 | 换品种成本 | 风险 |
|---|---|---|---|
| **A′（已定）** | **行情为准 + fail-closed**：实盘必须**成功取到并校验通过** `price_tick` / `volume_multiple` / 上下限，否则**拒绝进入可下单状态**（不报单 + 严重告警）；配置值**只在离线模式**（`dry_run` / `replay`）生效，且必须显式标注来源 | **零配置** | 行情 / 合约不可用会**挡住下单** —— 这是刻意的：被挡住的是"用错参数交易"这类**不可逆**错误 |
| A | 行情优先、配置兜底（无差别回退） | 零配置 | **兜底值错误时会被静默采用** → 需求方 2026-09-11 否决：这正是踩坑本身 |
| B | 配置优先、行情兜底（仅配置留空才用行情） | 仍需手填 | 行为可预测，但解决不了"每上一个品种都要查表"的痛点 |
| C | 只校验、不自动改（启动时对账，不一致报错） | 仍需手填 | 改动最小，但仍是手工 |

> **降级档收敛（需求方 2026-09-11 拍板）**：开关**只保留 `strict`（默认）/ `off` 两档，删除宽容档 `prefer`**
> —— `prefer` 就是上表 A 案的可执行形态，留着"早晚有人误开"。
> 且 **`off` 仅允许在 `dry_run` / `replay` 下生效；实盘配 `off` → 拒绝下单 + 严重告警**（与 A′ 同口径）。
> **任何"拿未校验的配置值做实盘"的路径都必须被堵死，包括调试开关本身。**

**A′ 的四条硬规则（缺一不可）**

1. **实盘 fail-closed**：`SimNow` 在首次下单前必须完成"行情取值 + 校验"；任一环节失败 → `Engine._pre_trade_check()` 拒单（`Engine.py:884`）+ 严重告警（`Engine.alert`，沿用 D11 通道），**绝不静默回退到配置值**。
2. **离线显式降级**：`dry_run` / `replay` 无行情 → 用配置值，但来源标记 `CONFIG_OFFLINE`，启动横幅 + WARN 写明"tick / 乘数取自配置，可能与交易所口径不符，**回测结果不可直接外推实盘**"。
3. **取值即冻结**：首次取到并校验通过后冻结，全进程不再变（避免盘中换月 / 异常推送导致同一批持仓的**限价口径漂移**）。
4. **降级开关自己也 fail-closed**：`off` 只对 `dry_run` / `replay` 生效；实盘检测到 `off` → **拒绝下单 + 严重告警**，**不允许用调试开关绕过 A′**。

**校验清单**（任一不过 → 走 fail-closed）

| 校验 | 判据 | 为什么必须 |
|---|---|---|
| 非空 / 非 nan | `math.isfinite(v) and v > 0` | tqsdk 取不到的字段返回 **nan 而不是 None**，而 `not nan` 是 `False`（nan 是 truthy）→ 用 `if not v` 判空会**漏过** nan，随后 `round_price()` 在 `math.ceil(nan)` 上直接抛 `ValueError`。现成反例：`SimNow.py:618` / `:897` 已在用 `math.isnan` |
| 取自**真实月份合约** | 读 `self._quote`（其订阅目标是 `trade_symbol`），**不是**主连 `KQ.m@...` | 主连是虚拟合约，静态字段（tick / 乘数 / 涨跌停）多为 nan |
| 涨跌停自洽 | `lower_limit <= 最新价 <= upper_limit` 且区间 > 0 | 挡"合约已异常 / 停板锁死" |
| 与配置差异 | 不一致 → WARN（两个值都打出来） | 让"配置过时"可见，但**以行情值为准**、不阻断 |
| 未知品种 | 无 `ProductProfile` → WARN | `parse_product("KQ.m@CZCE.TA")` = `"TA"` → `PRODUCT_PROFILES.get()` 返回 `None`，品种档案字段**不会注入**，WARN（不阻断）后沿用配置值（IF 基线）。**2026-09-13 更新**：原 `profile_for()` 包装已删（O-5 死代码清理），Config 直用 `PRODUCT_PROFILES.get()`；且 B-3 修复后初始加载为 user-explicit-wins —— 用户显式写的字段连档案值都不会被覆盖，WARN 是唯一的可见性提示 |

> **但行情不是全部真值 —— A′ 通过只是必要条件，不是充分条件。**
> `order_advanced`（**郑商所只支持 FAK、不支持 FOK**）、平今 / 平昨可用性、交割月限仓、
> 保证金口径这些**交易所规则类**参数**不在 quote 里**，只能由「按 `exchange` 的静态档案」提供
> + 启动期硬校验（§5.4 阻塞点 1 / §5.6）。所以：**tick 自动取对了，照样可能被拒单。**
> **上第一个非中金所品种前，交易所档案必须与 A′ 同时就位**，不能只做参数自动获取。

> **一句话**：行情值是**唯一可信真值**；拿不到就**不交易**，而不是拿一个可能错的值去交易。

#### ⚠️ 本阶段挖出的真问题：Phase 4 重写时**静默丢掉了两个行为**

`close_retry_bars` / `close_max_streak` 两个配置项在 Phase 4 之后**没有任何消费方**
（只在 `__init__` 赋值，判定逻辑随旧 `_close_positions` 一起被删）：

| 丢掉的 | 原语义 | 后果 |
|---|---|---|
| **CLOSE 冷却** | 一笔 CLOSE 被拒后 `close_retry_bars` 根 bar 内不再重试 | broker 内部一笔 CLOSE 已追 `close_max_chase`(**20**) 轮；引擎再无冷却后**每根 bar 都补一笔** → 15s 周期约每分钟 80 组报撤单，直接顶中金所「频繁报撤单」监管计数（**R13**） |
| **连续被拒兜底** | 连续 `close_max_streak` 次被拒 → 认定幻影仓、从簿中清除 | 簿面永远留着柜台不存在的仓，后续信号全被"运行态不响应信号"挡掉，**没有出口** |

**这是"配置项还在、行为没了"这一类最危险的漏迁** —— 它不报错、不留事件，只有逐行读代码
才发现。**教训：重写时删一个方法，必须回头查它的配置项还有没有消费方**（已记入 **R18**）。

修法：判定按新分层重新落地在 `Engine._execute`（A3 唯一报单出口）上，而不是去恢复旧的
`_close_positions`。两处口径差异**有意保留**：

- **`force=True` 豁免**：关闭自动下单的收尾路径不走冷却（旧实现不豁免 —— 刚被拒过一次
  平仓时点"关闭"，引擎会什么都不做）。用户当面点下的动作不该排队等冷却。
- **清仓范围收窄**：旧版一次清整批目标仓；新版**只清转移 ⑤ 的目标那一笔**（新模型一次
  只平一笔）。清得少一点，错了波及面就小一点；同一根 bar 的 `_reconcile_positions`
  也会独立判一遍幻影，两条路互为兜底。

#### D11 通道的两个设计要点

1. **不新增 IPC**（**D18**）：告警生产者是引擎**子进程**，消费者是 API 进程，两者不共享
   内存。队列走 state.db 已有的 kv 通道即可，两侧都以它为唯一事实源。
2. **过滤放在读取侧**：`AppTrader._read_engine_switch` 按水位过滤后才下发。引擎可能正卡在
   一次长 `wait_update` 里没落盘；读取侧过滤能保证"用户已确认的告警立刻不再下发"，不依赖
   子进程醒来。

触发源与"**不**触发"的边界（自验 `[3]` 段逐条钉死）：

| 触发 | code | 级别 |
|---|---|---|
| 资金 / 保证金不足（D10 `funds`，错误码 31） | `ctp_reject_funds` | severe |
| 非交易时段 / 无权限 / 合约不能交易（D10 `not_tradable`，错误码 17/28） | `ctp_reject_not_tradable` | severe |
| **可平持仓不足 / 平仓量超过持仓量**（D10 `position`，错误码 30/50/51）—— **v1.0 补入**：v3.13 把分类器由三类扩为四类时漏了本表这一行 | `ctp_reject_position` | severe |
| 离场追价跑满 `close_max_chase`（D10 `price` + attempt 跑满 + `is_exit`） | `close_chase_exhausted` | severe |
| CLOSE 连续被拒达上限 **且类别 = `position`**（柜台说没这笔仓 → 清幻影仓） | `close_repeatedly_rejected` | severe |
| CLOSE 连续被拒达上限 **但类别 ≠ `position`**（**不清仓**，只进冷却 —— 拒单恰恰说明柜台有这笔仓） | `close_streak_not_phantom` | warn |
| 建锚时缺成交价 / 信号（L1-L3 对本段失效） | `run_start_incomplete` | severe |

| **不触发**：价格不可达（FOK 全撤 / 涨跌停）**且**追价未跑满 | — | — |

- 初始（FLAT→OPEN）只有 1 笔，日期 = 今日 → 全今日
- 全今日 + 止盈止损 → 表 4 反向 OPEN，新仓日期 = 今日 → 仍全今日
- 全今日 + 信号 → 表 2 OPEN，新仓日期 = 今日 → 仍全今日
- 跨日之后（新交易日），所有仓单 `entry_date` 都 < today → 全跨日

#### D.2 AST 级「已删符号无活引用」护栏

**为什么需要**：一期漏改的具体形态就是"**代码删了符号，某个角落还在引用它**" —— `smoke_simnow_phase_g.py` 引用 Phase 1 已删的 `OrderIntent.UNLOCK`，语法上不报错、`grep` 不做语义匹配也容易漏，只有**真的执行到那一行**才炸。而它是"真连冒烟"，不在契约门禁内，所以这个缺陷在整整两轮评审里都没被发现（本轮 A/B 对照才暴露出来）。

**实现**（`Trading/Test/test_p43_audit_fixes.py` 第 [6] 段）：用 `ast` 解析全仓 `Trading/`（含 `Test/` 子目录，跳过缓存与依赖目录）的 `*.py`，匹配**属性访问**（`OrderIntent.LOCK` / `OrderIntent.UNLOCK` / `PositionOrigin` / `ExitMode`）与**裸名赋值**，命中即失败。配套两条自检保证护栏**自身**有效：
- `[6c]` **正向**：往内存里的样本源码注入 4 处引用 → 必须恰好命中 4 处（防止"扫描器其实没在工作"）；
- `[6d]` **反向**：注释与字符串里出现同样字样 → 必须**0 命中**（防止误伤，也防止"拿注释交差"）。

> 这条护栏在下一轮就回本了：`p15b` 我改动时它在全量跑批里恰好把 `UNLOCK` 残留拦在了门禁内。
