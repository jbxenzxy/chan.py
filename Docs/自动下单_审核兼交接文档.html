§2 · 维度一：功能正确性逐条

以下每条先说"你原本想要什么"，再说"代码实际怎么做的"，然后是"怎么验"。取证位置给的是文件名加行号，方便你自己对着看。

§2.1 ⑴ 加载 K 线页面时，自动下单默认关闭

你要的是：打开某个期货品种的 K 线，不能自己就开始下单，必须我亲手打开。

代码实际怎么做的：这里要分清"三层开关"。

  • 页面上那个勾选框：写在页面静态文件里，没有被默认勾上，也就是每次刷新页面都是"关"。
  • 下单引擎这个进程：它不是服务一启动就在跑的，而是你点了开关之后，后端才去新建一个独立子进程。不点 = 没有进程 = 不可能下单。
  • 持久记忆：你关掉之后，"已关闭"这个状态会被存进状态库；就算服务重启、进程重拉，它仍然是关的，不会自己复活。

所以从你作为使用者的角度看，这一条完全达标。

一个建议改掉的细节（不影响明天） 引擎内部的"默认"是开着的。也就是说：如果有人绕开页面、直接用一个全新的、从来没写过那把开关的状态库去拉起引擎，它会认为自己是被允许下单的。现在之所以安全，是因为上层在点开关时一定会先写一次状态作为约定。
为什么值得改：这是"靠约定"而不是"靠硬默认"。约定会随重构被稀释，硬默认不会。建议把引擎内部的初值改成"关"，让它天然 fail-safe。属于低风险、低收益的一致性修补。
取证：Trading/Engine/Engine.py:276（内部初值）、:564（读取时的兜底值）；App/AppTrader.py:941-953（上层启动前显式置"开"的程序）与 :484 / :224（关闭时写"关"的程序）

§2.2 ⑵ 白名单内的品种才支持；不在清单要弹框提示

你要的是：只让我在白名单品种上能开；点了不支持的品种要弹框告诉我。

代码实际怎么做的：白名单由后端一张"品种策略表"决定，当前是 8 个品种：

品种今仓怎么离场报单属性一次挂几手走哪套状态机
IF / IH / IC / IM反向开仓（锁仓）全成或全撤2 手三态：空仓 / 运行 / 锁仓
AU / AG / CU直接平今全成或全撤2 手两态：空仓 / 运行
TA反向开仓（锁仓）成交即止（余量撤）1 手三态：空仓 / 运行 / 锁仓

三层防护，一层比一层硬：

  1. 点之前：打开页面时前端会先问后端"这个品种能不能下单"。不能的话，开关直接变灰、点不动；鼠标悬上去能看到原因，以及当前支持哪些品种。
  2. 点下去的那一刻：即使上面那步被打岔（网络抖动、多标签页状态过期），真正要开之前还会再问一次后端；不支持就弹框提示 + 勾选框自动弹回 + 一个启动请求都不发。
  3. 进入引擎：万一被直接调用，引擎启动时会做断言，不在清单就直接报错终止，不会带着参数跑起来。
一个做得很对的细节 前端没有自己抄一份白名单。置灰用的提示和"能不能开"的判断，走的是同一个后端接口。这意味着将来加品种只需要动一个地方，界面不会和规则走散。这比很多系统的做法干净。
一个要注意的默认行为 那个"能不能下单"的查询接口如果挂了（比如后端临时没响应），前端的处理是按"能下单"放行，让引擎自身的闸门兜底。这是有意的取舍：宁可让引擎报错拦住，也不因为一个查询接口挂掉就彻底开不了。
对你的影响：明天如果看到某个你以为不支持的品种开关居然没变灰，别急着交易 —— 先确认那个查询接口是不是活的。
取证：Frontend/app.js:7622-7679（置灰逻辑）、:7857-7893（开启前二次校验 + 弹框 + 回弹）、:4220-4221（前端不抄名单的注释）；App/AppTrader.py:615-665（后端同一来源）；Trading/Infra/Product.py:240-249（8 品种表）

§2.3 ⑶ 切换周期或品种前，必须先手工关闭自动下单

你要的是：开着的时候不许我换周期或换品种，避免状态和画面不是同一个东西。

代码实际怎么做的：在两个入口都设了卡口 —— 切换周期的入口和切换合约的入口。只要引擎在跑，就弹框提示"请先关闭自动下单"并直接取消这次切换，什么都不做。

换品种的所有路径最终都汇到"加载合约"这一个函数：搜索框敲回车、点历史记录、点搜索下拉项、点收藏，全都要过它。所以没有漏网的跳转路径。

两点提醒 ① 卡口只在前端。后端服务本身并没有"引擎跑着就不许订阅别的合约"的二次校验。正常使用碰不到，但如果你以后开了多标签页、或者有人直接调接口，理论上能绕过。可接受，但要知情。
② 判断依据是轮询来的。"引擎是否在跑"这个状态每 5 秒刷新一次。刚点完开关的极短时间内状态可能还没同步到位。实际影响很小，不用管。
取证：Frontend/app.js:3537-3544（切周期卡口）、:4197-4205（切合约卡口）、:4415-4418 / :4115-4117 / :5908 / :6802（各跳转变体最终都汇到同一个入口）

§2.4 ⑷ 关闭时，运行态的持仓怎么处理

你要的是：我关掉自动下单时，如果有持仓在跑，要按"是今天的还是隔夜的、这个品种能不能平今"来决定 —— 是做一个反向仓把它锁住，还是直接平掉。

代码实际怎么做的：判断顺序是这样的。

用大白话说：

  • 这笔仓是今天开的 → 去查品种表里这个品种的"今仓怎么离场"那一列。表里写平今，就平今；表里写反向开仓，就朝反方向再开一笔把它锁住。
  • 这笔仓是隔夜的 → 不用纠结，直接平掉（在代码里这叫"平昨"）。
本轮刚补好的一件重要的事（值得单独说） 以前关掉自动下单之后有三种结局，但只有"停在锁仓"会通知你：如果顺利清干净了，界面一声不响，你没法确认到底清没清；如果平仓没做成（被拒单、没成交），账户会带着仓留到第二天，而没有任何提示。
本轮已经修好：现在三种结局都必然给结论 ——"已清仓无残留"（普通提示）、"停在锁仓"（普通提示，说明需要人工平或重新开启后等信号拆锁）、"仍有净敞口、离场没成功"（严重告警，明确告诉你英国的持仓笔数和手数，要求人工处理）。这是防止"带着仓过夜你还不知道"的关键补丁。
取证：Trading/Engine/Engine.py:1055-1091（两条离场路线的决策）、:1795-1860（关闭流程与三种终局结论）；Trading/Test/test_p58_handover_items.py（本轮新增的 477 行契约测试，含三种结局各一条）
还有一个容易被忽略的行为 关掉之后如果还有净敞口，引擎会在每根 K 线上再试一次离场（这是有意的：生怕一次没平掉就永远平不掉）。好处是顽强，坏处是如果一直被拒会反复重试。现在因为有了上面那条款的告警，你能在第一时间知道，不会被它默默反复打扰而不知道原因。
取证：Trading/Engine/Engine.py:864-870

§2.5 ⑸ 出现买卖点信号后进入三态 / 两态状态机，且按最低手续费操作

你要的是：信号一来（不管信号来自哪个周期）就进状态机；状态机要保证手续费最低。

先看状态机本身 —— 两套，按品种自动走：

三条不同的开呼叫仔细看：

当前状态触发动作
空仓来一个买卖点信号朝信号方向建一个仓（这是最常见的路径）
锁仓来信号，且最近那笔是今天开的朝信号方向再开一个新仓（不动原来的锁仓部分）
锁仓来信号，且最近那笔是隔夜的平掉反向的最早那一笔（按整笔平，不拆）

运行止损止盈触发 / 你手动关闭按 §2.4 那张图走
这一条里唯一需要纠正口径的地方：「最低手续费」不是程序算的 你原文写的是"状态机确保按最低手续费操作"。代码里现在没有一段按费率做比较、自动挑便宜那条路的逻辑 —— 这是有意为之的演进结果。

现在的做法是：这张品种表就是权威。每个品种的"今仓怎么离场"那一列，是人先算清楚"平今便宜还是反手便宜"，然后把结论写进表里。程序运行时只查表、不算账。

这样做的好处：规则看得见、改得起、不会被隐藏的费用公式带偏；加一个新品种只要在表里加一行，不用改任何逻辑。
这样做的代价：如果表里填错了，程序不会发现，也不会救你。"最低手续费"的正确性从代码责任变成了填表责任。

§2.6 ⑹ 一次信号只允许报 1 笔；运行态不再接收信号

你要的是：一个信号 = 一笔单（N 手）。一旦有持仓在跑，新的买卖点信号就不许再进场，交给止损止盈管。

代码实际怎么做的：

  • 运行态直接拒收：决策函数第一件事就是判断"现在是不是运行态"，是的话立刻返回"不动作"。而且这个丢弃会被记账（写一条流水），将来查"为什么这个信号没成交"能查到原因。
  • 一笔单数抉择：一次信号只产生一个动作、一笔单，手数从品种表里取，代码的注释里明确写了"没有任何拆单逻辑，也不允许存在"。
  • 接管关系：一旦有了净敞口，之后的出场由"止损止盈 L1-L3"负责，走的就是 §2.4 的离场路线。
  • 幂等：同一个信号就算重复送来（比如断线重连后重发），也只会被处理一次。
一个设计上的诚实交代（不是 bug，是刻意） "一次信号一笔单"意味着这套系统没有加仓、没有分批建仓、也没有分批止盈。这符合你当初的定义，但它同时也是个限制：如果你想将来做"分两笔进、第一笔先走一半"这类打法，那是新功能，不是改个数字的事。
另外注意平仓不受手数限制：开仓一次只开表里写的那么多，但平仓一定是把目标仓位平满 —— 这个口径是当前代码刻意定的。

SimNow 与实盘分开保存否没有分开。见下方详述

于是：今天先用仿真跑、过几天切实盘跑，两个账户的盈亏会混在同一条曲线里，胜负率和盈亏比也是混合值。

真正能分开的做法只有一条：给成交记录加"账户"这一列（写入时记下当时走的是哪个通道），统计时按它过滤。动的是记录表结构，工作量不大，但要在切实盘之前拍板一次。

明天的做法：记录目录保持默认、别动。仿真期本来就只有仿真这一个通道在记，混不起来（若之前用离线模拟试跑过，那个目录里可能已经存着模拟成交；想要干净起点，把 Trading/State 整个挪走即可）。现阶段先把注意力放在功能验证上。

阈值自校验有品种表在构造时就自校验（第三列只能填两种值、第四列只能填两种值、手数范围、某条件下手数必须为 1），错了直接启动报错，不会带着错值跑
本轮刚刚补上的两处（明显提升运维体验） ① 拒单变得可见了：以前只有"柜台那边明确拒了"才会提示；而"程序自己检查就没通过"的那种拒单是完全静默的 —— 你只能看到"一会儿没成交"。现在全部会提示，并且同一原因连续多次会自动升级成阻塞弹窗（避免偶发一次就调皮性打扰，也不会让真卡死变为无声）。
② 关闭时必须给终局结论：以前只有"停在锁仓"会通知；"清干净了"和"没清干净"都不说话。现在三种结局都必然给结论，重点是把"带着仓过夜还不自知"这个口子堵上了。

这两条合起来是一句话：系统的安全底线没有降低，但不允许出现"账户安静卡住、你完全不知道为什么"。
还缺的定位手段（建议但不是必须）
  • 没有"一键打包诊断信息"：现在要查问题得自己去找流水账、状态库、日志三个地方。可以做一个小脚本，把最近 N 条流水 + 当前状态 + 日志尾部打成一个压缩包。
  • 拒单原因没有直接出现在开关的悬停提示里：现在要弹框或者翻流水。加一行"上次拒单原因"会更省事。
  • 界面上看不到"下一次刷新时间"之类的健康信号：行情断了、推送挂了，现在只能从"很久没动"间接发现。

§4.4 ⑷ 从软件设计角度还要补充什么

  1. 【优先级最高】给"账户三态"的双实现加一个一致性契约测试。便宜、防的是真实且隐蔽的分叉。（见 §4.2 债 2）
  2. 把默认值的方向改成"默认关闭"。现在是"上层先写'开'"，改成"内部默认关，由上层显式开" —— 安全上等价，但少一层约定成本。（见 §2.1）
  3. 前端按模块切分。先切交易开关 / 告警 / 统计面板这三块独立性最高的，不要一次性重写。
  4. 给记录的统计分析加"账户维度" —— 这是唯一真能把两个账户分开的办法。现在记录里没有账户字段。注意换记录目录没用：目录名落在 Trading/State* 的会被自动扫回来合并，指到别处又会整个漏掉。所以要在记录里加一列账户标识，统计时按它过滤。
  5. 把空的风控目录处理掉（补说明或删掉），避免误读。
  6. 给"品种快照一致性"做常态化校验：主连代码与具体月份合约的对应关系、"多了个品种缺少概要"这类问题，已经有入门级别的测试，建议再加一个"启动时自检 + 告警"，而不是只在测试里。

§6.4 明天测不到的东西（别把"仿真全绿"当成"实盘 OK"）

  • 真实的撮合过程：SimNow 不真撮合，价格合适就直接全成。所以"盘口深度不足导致整笔被撤、然后追价重报"这条路明天走不到。
  • 资金不足被拒单的场景与后续处理。
  • 流控 / 限速：真实柜台有限流，明天感受不到。
  • 每日结算单确认：真实环境通常要求每个交易日确认一次结算结果才能下单，仿真环境可能根本不结算。这是实盘首日必验项。
  • 夜盘：做 IF/IH/IC/IM 无影响；做 AU/AG/CU 则夜盘对账会被跳过。
  • 跨日仓 / 平昨：取决于你那个 SimNow 账号落在哪套环境。这套环境不由代码决定，而是由 SimNow 平台按你的账号归属路由。如果账号属于"7x24 那套"，它不做日切，你就造不出隔夜仓，也就测不到"跨日仓平昨"这条路。这一点必须真跨一个交易日才能验。

§7 · SimNow 跑顺之后，切创元期货实盘前要做什么

§7.1 先谈一个好消息：代码层面基本不用改

我特意核实了"实盘通道到底存不存在"。结论是存在，而且路由做得挺细：

  • 实盘的下单实现类就写在仿真类的同一个文件末尾，共享全部核心逻辑（超价、追价、成交判定、各种保护），只有名字不同。
  • 决定"走仿真还是走实盘"的不是类名，而是一个叫市场名的配置：填"simnow"走仿真，填期货公司名（这里是"创元期货"）就走实盘。两条路最终汇聚到同一个登录处理。
  • 有双重安全闸门：要切实盘必须同时满足"市场名填了期货公司名"和"显式打开实盘确认开关"。只填一个会在启动时报错拒绝。这个防的是"以为自己在仿真、其实在实盘"。
  • 账户与密码是分开的两套：仿真用一组环境变量，实盘用另一组；天勤账号两组共用。密码只从环境变量取，不与配置文件混。

§7.3 必须做的测试（按真实资金从小到大排）

顺序测试通过标准
1登录与账户查询（不下单）能连上创元的柜台、能查到真实资金和持仓。常见坑：默认连的是期货公司主席，可能要切换席位；另外 AppID 需要已经和你的资金账号绑定
2结算单确认确认一次当天的结算结果，然后试着下一次单。不确认的话每天的第一单可能被拒。这是实盘特有的，仿真根本测不到

4今日仓的离场路线当天开的仓离场时，走的确实是你在表里填的那条路（平今 / 反向开仓），且实际扣的手续费和你算的一致

6夜盘（只针对 AU/AG/CU）夜盘建的仓会被正确归属到下一个交易日；日盘再看时它应该已经是"昨仓"
7拒单恢复故意制造一次拒单（比如超出当日许可），确认能看到明确提示（现在有告警了），而不是安静卡住
8断网 / 服务中断后重启重启后先从你的真实账户拉一次实际持仓再开始工作，不会把"已经被平掉的仓"当成真仓继续等
9手动紧急干预明白"强制平仓"工具怎么用、"紧急平仓"指令怎么落地。这个必须提前练一次，不要等出事才第一次用
10持续跑一段时间连跑数个交易日，观察有没有累积性的偏差（账户净值对不上、手续费扣得不一致这类）

§7.4 必须向期货公司确认 / 报备的事

这是本份文档里最"非技术"、但最不能跳过的一节 下面的事项全是代码解决不了的，全部是由"你在谁家开户、由谁监管"决定的。建议直接联系你的客户经理，逐条确认，最好留书面答复。
事项性质要确认什么
程序化交易报备监管必需未报备即交易会违规。我方程序是自动报单的，属于程序化交易范畴，须向期货公司报备（并由公司向交易所报告）。这是上线前的合规前置，不是可选
CTP 接入方式必须确认这套代码走的是天勤中继接入（登录时传"期货公司名"的方式）。确认创元期货在天勤支持列表里。如果只给直连资格，接法要改（届时需要另一个直连库和不同的连接层）
AppID 与账号绑定必须确认常见报错"客户端认证失败"就是因为 AppID 没和你的资金账号绑定。需要期货公司协助绑定
交易席位必须确认常见报错"不合法登录"是因为默认连的是主席，需确认是否可以/需要切换席位
实际手续费（含平今）必须确认品种表里"今仓怎么离场"那列是照着费率算出来的。要拿到你户上的实际费率（不是交易所标准费率）：开仓、平昨、平今三档分别多少。然后重新算一遍再填表
保证金收取方式建议确认反向开仓"锁仓"之后保证金怎么压：是按单向大边（只压一边）还是双边？期货公司往往会在交易所基础上再加收。这直接影响你"够不够钱"的判断
结算单是否须每日确认建议确认确认贵方要求：是每个交易日都要手动确认一次，还是自动。不确认会导致当天第一单被拒
报撤单流控阈值建议确认问清前置的限流上限（通常按"报单+撤单合并计"的每秒次数）。另外中金所对频繁报撤单有专门的监管口径，高通损/全成或全撤策略形成的撤单也会被计数，建议心里有数
是否支持你要下的报单属性建议确认程序用的是"全成或全撤"和"成交即止"两种属性，且必须配限价。确认你交易的品种合约支持（不同交易所规则不一）
夜盘 / 交割月规则的执行口径建议确认临近交割月系统自己会拦住不许开新仓；问一下公司对"个人客户何时必须平掉交割月仓"的具体执行口径
建议的上线节奏 仿真跑顺 → ① 完成报备与 AppID 绑定 → ② 只用最小资金 + 单品种（建议先用你最熟悉的那个）跑若干个完整交易日 → ③ 确认实际手续费与表内的预期一致 → ④ 再考虑加品种 / 加资金。
不要一上来就用大资金。理由不是"策略可能不准"，而是这套系统里有很多只有在真实环境下才暴露的东西（结算、流控、席位、实际费率），这些只有小额实跑才能发现。

§8.1 接手的人必须知道的 8 件事

  1. "怎么下单"的所有差异，都来自一张表。每个品种三列：今仓怎么离场、报单属性、一次挂几手。改表就是改行为，不需要改代码。
  2. "最低手续费"是表填出来的，不是算出来的。程序只查表，不算费率。表里填错，程序不会救你。
  3. 改表之前必须先清空持仓。手数列在有持仓时被改动，会导致账实不符并被拒单，届时连"关闭自动下单"都解不开。
  4. "取不到合约参数就绝不交易"是刻意的安全底线。非交易时段一直拒单是预期行为；它现在会明确告警告诉你，不再是静默卡住。
  5. 账号密码只走环境变量，绝不写进配置文件（配置文件会进版本库）。
  6. 只运行一个服务实例。多实例会各自拉起下单进程同时交易。
  7. 收工时先关自动下单开关，并且一定要等到那条"收尾结论"。看到"仍有净敞口"的严重告警，必须人工处理，不能放着过夜。
  8. 有那个（全项目中文术语）护栏测试。新增日志文案、注释、断言描述时容易踩到禁用词，改完必须跑那个测试 —— 只跑你改的那个文件是看不出来的。
