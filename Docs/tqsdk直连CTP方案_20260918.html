1. 结论摘要

推荐路线改为两级（P68 评审后重定位）：① TqCtp 直连为候选——改动只有 SimNowBroker._connect 抽构造钩子 + 装包 + 配置外接参数，技术侧 ≈1.5 人日；② 若 TqCtp 在实环境暴露问题（柜台特性不支持等），再走本文档的全量重写方案（≈18~21 人日，备选保留）。但两件事必须拆开：天勤官方对企业版直连的量化口径是「交易延迟平均减少 10ms 左右」（《TqSdk 企业版》页原文），与本项目要治理的 25~55 秒回报滞后相差三个数量级——直连解决的是对中继的长期依赖，不是本项目的滞后主因；滞后治理见 §1.1 步骤①与 §1.2 零成本先行项，直连立项与否以那里的结论为准。

3. 核心判断（按 09-18 调研修正）

3.1 业界项目怎么连——GitHub 生态证据：vn.py（vnpy_ctp 网关直连期货公司 CTP 柜台，官网明确「直连期货公司的 CTP 期货柜台」）、kungfu（开源版仅提供 CTP/XTP 柜台直连实现，主打低延迟）、wondertrader（C++ 底层直连 CTP/CTPMini/飞马）、PandoraTrader、ctpwrapper 等，均为程序直连 CTP API。经云网关中转的只有 tqsdk 系（信易 otg / openctp 的 relay 类方案），属便利性取舍，非延迟敏感项目的主流选择。方案 B 深度评审收格（2026-09-19，N7）：① northstar 实为 dromara/northstar（591 star，Java，非 Python 项目）、redtorch 为 0 star——二者只作「直连是主流」的旁证，不作 Python 侧证据；② openctp 须拆两类：「CTPAPI 兼容接口 + TTS 模拟柜台」与原生绑定包 openctp-ctp（无框架依赖、BSD-3、唯一有 cp314 win wheel 的 pip 候选，见 §4）；③ 主流结论分两层：「直连 CTP」是主流（vnpy 45.4k star 及上列 C++ 项目），但「自写薄适配」不是主流——Python 侧主流做法是连同框架一起用（vnpy add_gateway，回报队列由框架提供），纯绑定小项目 star 仅 100~600 且有停更先例（lovelylain/pyctp 2017、nicai0609/Python-CTPAPI 2021）。本项目因 Broker 层单向依赖与 1656 行（现行）SimNowBroker 保障逻辑不可能整体迁入 vnpy，选 B 属明知非主流而选之：代价按「自建 + 自担绑定库生命周期」计（R9），不按「大家都这么干」计。

3.2 延迟问题的归属——用户假设「若主流都走中继则延迟不该是问题」：调研结论相反，主流是直连，中继确实多一跳。但量化级差很关键：otg 中继固有开销为毫秒~百毫秒级，本项目 25~55 秒的滞后比它大两个数量级以上，不能用「otg 线路慢」解释。tqsdk 官方文档对 wait_update 的定义是「每次调用时：实际发出网络数据包、尝试从服务器接收数据包并更新内存业务截面」——回报到达本地后若 wait_update 不被调用，数据就一直躺在缓冲区。因此两个假设并列待验证、不预先加权（P68e 评审 N6 勘误：本句原写「大头大概率在消费节奏」系预先加权，且与 §1/§1.1 口径互斥，属旧版残留）：假设甲 = 消费节奏（我们代码的泵），P61 on_idle 泵先消掉甲的可解释部分；假设乙 = 链路段本身。otg_latency 是合成值、只在下单终判落盘，只能提供总滞后的量级、给不出两段分解，定论靠 §1.1 步骤①的上界法（消费段上界 ≈0.2~0.3s 为已知量）。

3.3 去 otg 不必去 tqsdk（修正初版判断）——tqsdk 开源版已提供 TqCtp 直连类：传入 front_broker/front_url/app_id/auth_code（向期货公司申请程序化外接取得；SimNow 有公开测试参数），底层由本地 otg_adapter 进程（tqsdk_zq_otg 包）直连 CTP 前置，绕开信易云网关。API 语义（wait_update/get_position/insert_order/trade_records）完全不变，即 SimNowBroker 内 1647 行的保障逻辑一行不用重写。全量重写方案降级为备选（仅当 TqCtp 实环境受阻时启用）。

3.4 约束收敛与方案决策（2026-09-19 会话补充）

术语：绑定（binding）——CTP 本身是中国期货市场提供的 C++ 原生 API（核心类 CThostFtdcTraderApi / CThostFtdcMdApi + 回调 CThostFtdcTraderSpi，随 C++ 头文件与 .dll/.so 发布）。Python 不能直接 import 一个 C++ 库，必须有一层把这套 C++ 类暴露成 Python 可调用对象——这层即「绑定」，通常由 SWIG / pybind11 / ctypes 生成。由此分两类：纯绑定类（openctp-ctp / ctp-python / ctpwrapper）只做 CTP C++ API → Python 的 1:1 映射，你拿到裸 API（TdApi/MdApi、自己子类化 SPI 实现 OnRspUserLogin/OnRtnTrade/OnRtnOrder、RegisterFront()/ReqOrderInsert()），事件循环 / 订单管理 / 持仓跟踪 / 策略框架全要自写——这「全自写」的部分即方案 B 的「自写薄适配」；框架插件类（vnpy_ctp）底层也封装同一套 C++ API，但额外捆进 vnpy 整套引擎（MainEngine + 事件引擎 + gateway 生命周期 + CtaTemplate 策略基类），import vnpy_ctp 即触发 requires_dist=vnpy>=3.0.0、把整个 vnpy 拉起，无法当 import ctp 那样只取裸 API。

先澄清一个新增事实：现状（tqsdk 路径）的下单子进程数据面是单线程的——tqsdk 在调用 wait_update 的那条 Python 线程里跑自己的事件循环，回报消费与交易引擎逻辑同线程交替执行；唯一的例外是 Trading/main.py:397 的 gw-stop-monitor 看护线程（daemon，只盯 stop_flag 触发优雅退出，不碰任何数据面状态），不构成第二个数据调度单位。而 CTP 是 C++ SDK：调用 Init() 后它会在进程内创建自己的网络工作线程（真正的操作系统调度单位），OnRtnOrder/OnRtnTrade 等 Spi 回调由该线程触发（P68f 六轮 N7：此为通用事实且系本节论证支点，待以上期技术（CTP）官方 API 文档核对后落地——P68 八轮 N7：原「SEE」为多余笔误字符、「落实施」疑漏字，已改）——此时同一进程内出现两个数据面调度单位（主线程 + SDK 线程）。这是直连方案新引入的并发事实；回调进入 Python 层仍受 GIL 约束，SDK 内部的 C++ 网络收发不受 GIL 约束。（P68 评审勘误：原稿「单线程」未提看护线程，已补充；本节后半段的「两个调度单位」论证属方案 B 范围。）

CTP 的 Spi 回调在 SDK 自己的线程触发，与 tqsdk「单线程 wait_update」不同。适配层用「回调入队、主线程消费」桥接：Spi 回调只做入队（SDK 线程不碰任何交易引擎状态），pulse() 在交易引擎主线程把队列消费进本地镜像/订单表；所有 _wait/_wait_finished 谓词改为查消费后的本地状态。这样交易引擎侧时序语义与现在完全一致，不引入跨线程访问——这也是生产环境写 CTP 的标准做法。
