1. 结论摘要

2026-09-18 二次调研修正：GitHub 主流期货自动下单项目（vnpy_ctp、kungfu、wondertrader、openctp、PandoraTrader、redtorch、northstar 等）绝大多数直连 CTP 前置，经云网关中转的 tqsdk 属于便利性路线的少数派（P68f 六轮 N7：本条为 2026-09-18 Web 检索调研结论，项目名未逐一附 URL——引用时可按名检索核对）。同时发现 tqsdk 开源版已提供直连类 TqCtp（源码 tqsdk/tradeable/otg/tqctp.py，装 tqsdk_zq_otg 包后由本地适配进程直连期货公司 CTP 前置，绕开信易云网关）——本文档初版「开源 tqsdk 无直连模式」的判断已过时并修正。

推荐路线改为两级（P68 评审后重定位）：① TqCtp 直连为候选——改动只有 SimNowBroker._connect 抽构造钩子 + 装包 + 配置外接参数，技术侧 ≈1.5 人日；② 若 TqCtp 在实环境暴露问题（柜台特性不支持等），再走本文档的全量重写方案（≈18~21 人日，备选保留）。但两件事必须拆开：天勤官方对企业版直连的量化口径是「交易延迟平均减少 10ms 左右」（《TqSdk 企业版》页原文），与本项目要治理的 25~55 秒回报滞后相差三个数量级——直连解决的是对中继的长期依赖，不是本项目的滞后主因；滞后治理见 §1.1 步骤①与 §1.2 零成本先行项，直连立项与否以那里的结论为准。

⚠ 费用确认（2026-09-18 三次查证，P68 评审补代码闸门证据）：TqCtp 直连属于 TqSdk 付费功能——企业版。官方文档原文（P68c 三轮评审逐字核实并补出处）：tqsdk2 快速入门「直连模式需要购买企业版权限才能使用」（doc.shinnytech.com/tqsdk2/master/quickstart.html）；《TqSdk 企业版》页「企业版和专业版相比的主要区别是柜台支持上的区别，企业版支持直连 CTP/融航/杰宜斯等柜台，专业版只能通过中继的方式去进行连接」「交易指令直达期货公司，省去中继服务器路径，交易延迟平均减少10ms左右」「点击个人中心申请15天试用或购买」（doc.shinnytech.com/tqsdk/master/enterprise.html）。代码侧同一道闸门：tqsdk/api.py:3636-3637 的 _check_account_auth 校验失败即 raise Exception("您的账户不支持…需要购买后才能使用。")，tqctp.py:52 声明的正是 feature: "tq_direct"。即：tqsdk_zq_otg 包可以免费安装，但运行时经 TqAuth 快期账户鉴权，直连 CTP 需企业版授权（可申请 15 天试用）。报价（P68b 二轮评审已升级为官方出处、独立核实）：信易官方商店页「企业版 ¥30000（原价 50000）/年」「支持直连任何期货公司, 3个账户」；官方论坛对比页另载「限时优惠 30000 元/年……超过账户 8000 元/年/个」——30000 为限时优惠价，采购前仍以正式报价为准。这改变了 B' 的成本结构：≈1.5 人日技术工作量不变，但新增持续性授权费 + 账户数约束（超出 8000 元/年/个）；而方案 B（vnpy_ctp / ctp-python 全量重写）的绑定库均为开源免费、无授权费。决策时需把「1.5 人日 + 企业版年费」与「18~21 人日 + 0 授权费」放在一起比较。五分钟前置验证：tqsdk_zq_otg 已在 .venv 就位，登录后看 api._auth._grants["features"] 是否含 tq_direct 即知闸门状态，比任何估算都早地暴露真实瓶颈。

延迟归属的推理链（基于调研修正，P68 评审后两假设并列）：otg 云中继的正常开销是毫秒~百毫秒级；本项目 gateway.log 观察到的 25~55 秒回报滞后远超中继固有延迟的量级，不能用「otg 线路慢」解释。tqsdk 官方文档明确：只有调用 wait_update 时才会收包并更新内存截面——回报到达本地后若 wait_update 不被调用，数据就一直躺在缓冲区。因此存在两个并列假设，不预先加权：假设甲 = 消费节奏（bar 级泵间隙；P61 on_idle 泵即为此修）；假设乙 = 链路段本身（评审指出 SimNow.py:1252-1255 的观察①「连续泵 5 秒回报仍未到、而交易所侧毫秒级成交」与纯消费假设存在张力）。两段归属用 §1.1 步骤①的上界法当天定论。

3. 核心判断（按 09-18 调研修正）

3.1 业界项目怎么连——GitHub 生态证据：vn.py（vnpy_ctp 网关直连期货公司 CTP 柜台，官网明确「直连期货公司的 CTP 期货柜台」）、kungfu（开源版仅提供 CTP/XTP 柜台直连实现，主打低延迟）、wondertrader（C++ 底层直连 CTP/CTPMini/飞马）、openctp（CTPAPI 兼容接口直连各柜台 + TTS 模拟）、PandoraTrader、redtorch、northstar、ctpwrapper 等，均为程序直连 CTP API。经云网关中转的只有 tqsdk 系（信易 otg / openctp 的 relay 类方案），属便利性取舍，非延迟敏感项目的主流选择。

3.2 延迟问题的归属——用户假设「若主流都走中继则延迟不该是问题」：调研结论相反，主流是直连，中继确实多一跳。但量化级差很关键：otg 中继固有开销为毫秒~百毫秒级，本项目 25~55 秒的滞后比它大两个数量级以上，不能用「otg 线路慢」解释。tqsdk 官方文档对 wait_update 的定义是「每次调用时：实际发出网络数据包、尝试从服务器接收数据包并更新内存业务截面」——回报到达本地后若 wait_update 不被调用，数据就一直躺在缓冲区。因此两个假设并列待验证、不预先加权（P68e 评审 N6 勘误：本句原写「大头大概率在消费节奏」系预先加权，且与 §1/§1.1 口径互斥，属旧版残留）：假设甲 = 消费节奏（我们代码的泵），P61 on_idle 泵先消掉甲的可解释部分；假设乙 = 链路段本身。otg_latency 是合成值、只在下单终判落盘，只能提供总滞后的量级、给不出两段分解，定论靠 §1.1 步骤①的上界法（消费段上界 ≈0.2~0.3s 为已知量）。

3.3 去 otg 不必去 tqsdk（修正初版判断）——tqsdk 开源版已提供 TqCtp 直连类：传入 front_broker/front_url/app_id/auth_code（向期货公司申请程序化外接取得；SimNow 有公开测试参数），底层由本地 otg_adapter 进程（tqsdk_zq_otg 包）直连 CTP 前置，绕开信易云网关。API 语义（wait_update/get_position/insert_order/trade_records）完全不变，即 SimNowBroker 内 1647 行的保障逻辑一行不用重写。全量重写方案降级为备选（仅当 TqCtp 实环境受阻时启用）。

先澄清一个新增事实：现状（tqsdk 路径）的下单子进程数据面是单线程的——tqsdk 在调用 wait_update 的那条 Python 线程里跑自己的事件循环，回报消费与交易引擎逻辑同线程交替执行；唯一的例外是 Trading/main.py:397 的 gw-stop-monitor 看护线程（daemon，只盯 stop_flag 触发优雅退出，不碰任何数据面状态），不构成第二个数据调度单位。而 CTP 是 C++ SDK：调用 Init() 后它会在进程内创建自己的网络工作线程（真正的操作系统调度单位），OnRtnOrder/OnRtnTrade 等 Spi 回调由该线程触发（P68f 六轮 N7：此为通用事实且系本节论证支点，待以上期技术（CTP）官方 API 文档核对后落地——P68 八轮 N7：原「SEE」为多余笔误字符、「落实施」疑漏字，已改）——此时同一进程内出现两个数据面调度单位（主线程 + SDK 线程）。这是直连方案新引入的并发事实；回调进入 Python 层仍受 GIL 约束，SDK 内部的 C++ 网络收发不受 GIL 约束。（P68 评审勘误：原稿「单线程」未提看护线程，已补充；本节后半段的「两个调度单位」论证属方案 B 范围。）

CTP 的 Spi 回调在 SDK 自己的线程触发，与 tqsdk「单线程 wait_update」不同。适配层用「回调入队、主线程消费」桥接：Spi 回调只做入队（SDK 线程不碰任何交易引擎状态），pulse() 在交易引擎主线程把队列消费进本地镜像/订单表；所有 _wait/_wait_finished 谓词改为查消费后的本地状态。这样交易引擎侧时序语义与现在完全一致，不引入跨线程访问——这也是生产环境写 CTP 的标准做法。
