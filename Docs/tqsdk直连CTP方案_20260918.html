1. 结论摘要

2026-09-18 二次调研修正：GitHub 主流期货自动下单项目（vnpy_ctp、kungfu、wondertrader、openctp、PandoraTrader、redtorch、northstar 等）绝大多数直连 CTP 前置，经云网关中转的 tqsdk 属于便利性路线的少数派。同时发现 tqsdk 开源版已提供直连类 TqCtp（源码 tqsdk/tradeable/otg/tqctp.py，装 tqsdk_zq_otg 包后由本地适配进程直连期货公司 CTP 前置，绕开信易云网关）——本文档初版「开源 tqsdk 无直连模式」的判断已过时并修正。

推荐路线改为两级：① 首选 TqCtp 直连——改动只有 SimNowBroker._connect 换账户类 + 装包 + 配置外接参数，技术侧 ≈1.5 人日，瓶颈是非技术的「期货公司程序化外接申请」；② 若 TqCtp 在实环境暴露问题（如包版本锁死、柜台特性不支持），再走本文档的全量重写方案（≈18 人日，备选保留）。

延迟归属的推理链（基于调研修正）：otg 云中继的正常开销是毫秒~百毫秒级；本项目实测 25~55 秒的回报滞后远超中继固有延迟的量级，更可能是「回报已到本地缓冲、但 wait_update 未被及时调用消费」（tqsdk 官方文档明确：只有调用 wait_update 时才会收包并更新内存截面）。P61 的 on_idle 泵正是针对此，otg_latency 数据可分解两段归属后再决定是否动直连。

1.1 行动路线（2026-09-18 用户拍板，原文）

「① 先跑几个交易日 otg_latency 定延迟归属；② 同时用 SimNow 直连参数把 TqCtp 路线在沙盒验证通；③ 若消费段已收紧、残余滞后仍在，TqCtp 一刀切过去」

3. 核心判断（按 09-18 调研修正）

3.1 业界项目怎么连——GitHub 生态证据：vn.py（vnpy_ctp 网关直连期货公司 CTP 柜台，官网明确「直连期货公司的 CTP 期货柜台」）、kungfu（开源版仅提供 CTP/XTP 柜台直连实现，主打低延迟）、wondertrader（C++ 底层直连 CTP/CTPMini/飞马）、openctp（CTPAPI 兼容接口直连各柜台 + TTS 模拟）、PandoraTrader、redtorch、northstar、ctpwrapper 等，均为程序直连 CTP API。经云网关中转的只有 tqsdk 系（信易 otg / openctp 的 relay 类方案），属便利性取舍，非延迟敏感项目的主流选择。

3.2 延迟问题的归属——用户假设「若主流都走中继则延迟不该是问题」：调研结论相反，主流是直连，中继确实多一跳。但量化级差很关键：otg 中继固有开销为毫秒~百毫秒级，本项目 25~55 秒的滞后比它大两个数量级以上，不能用「otg 线路慢」解释。tqsdk 官方文档对 wait_update 的定义是「每次调用时：实际发出网络数据包、尝试从服务器接收数据包并更新内存业务截面」——回报到达本地后若 wait_update 不被调用，数据就一直躺在缓冲区。因此滞后大头大概率在消费节奏（我们代码的泵），P61 on_idle 泵即为此修；otg_latency（交易所时间戳→本地终判）跑出数据即可定论。

3.3 去 otg 不必去 tqsdk（修正初版判断）——tqsdk 开源版已提供 TqCtp 直连类：传入 front_broker/front_url/app_id/auth_code（向期货公司申请程序化外接取得；SimNow 有公开测试参数），底层由本地 otg_adapter 进程（tqsdk_zq_otg 包）直连 CTP 前置，绕开信易云网关。API 语义（wait_update/get_position/insert_order/trade_records）完全不变，即 SimNowBroker 内 1647 行的保障逻辑一行不用重写。全量重写方案降级为备选（仅当 TqCtp 实环境受阻时启用）。

5.2 线程模型

先澄清一个新增事实：现状（tqsdk 路径）的下单子进程是单线程的——tqsdk 在调用 wait_update 的那条 Python 线程里跑自己的事件循环，没有额外调度单位（此前架构讨论的结论对现状成立）。而 CTP 是 C++ SDK：调用 Init() 后它会在进程内创建自己的网络工作线程（真正的操作系统调度单位），OnRtnOrder/OnRtnTrade 等 Spi 回调由该线程触发——此时同一进程内出现两个调度单位（主线程 + SDK 线程）。这是直连方案新引入的并发事实，不是现有架构本来就有的；回调进入 Python 层仍受 GIL 约束，SDK 内部的 C++ 网络收发不受 GIL 约束。

CTP 的 Spi 回调在 SDK 自己的线程触发，与 tqsdk「单线程 wait_update」不同。适配层用「回调入队、主线程消费」桥接：Spi 回调只做入队（SDK 线程不碰任何引擎状态），pulse() 在引擎主线程把队列消费进本地镜像/订单表；所有 _wait/_wait_finished 谓词改为查消费后的本地状态。这样引擎侧时序语义与现在完全一致，不引入跨线程访问——这也是生产环境写 CTP 的标准做法。
