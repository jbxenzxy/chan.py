AppData vs DataAPI · 职责边界 单一事实源阶段 4 数据层

澄清「业务数据层 AppData.py」与「数据源抽象层 DataAPI/」的职责分工 · 归档本次架构评审结论

1职责判定规则

判断一个数据相关功能该归 AppData.py 还是 DataAPI/，不依结果形态（"几支股票"还是"几根K线"），而依数据所有权与是否构成应用长期状态：

DataAPI · 外部适配器
只从外部读取、用完即释放（不构成应用长期业务状态）→ DataAPI/
AppData · 业务数据层
管理应用方承担持有/管理职责的数据（自有数据 · 缓存化/持久化的外部数据 · 计算产物）→ App/AppData.py

要点：本规则的「掌握应用长期业务状态」是关键判据。外部源原始数据经应用决定缓存并写盘后，其"持有"职责转入 AppData（如股票名称、PE-TTM）；DataAPI 内部的模块级缓存（如 _INFOHARBOR_BLOCK_CACHE）只是避免重复拉取的获取侧优化，不转移职责，仍属 DataAPI。

2两大层职责定义

AppData.py · 业务数据层

问题：数据存哪、怎么存、归谁管、谁长期持有

职责：缓存、持久化、标注、自选股、行业映射、计算产物缓存

数据所有权：应用一方

生命周期：长期持有 · 可靠写盘 · 原子操作

典型能力：LRU 缓存、CSV/JSON 持久化、CRUD、标注去重

DataAPI/ · 数据源适配器

问题：数据从哪拿、外部格式如何转内部结构

职责：通达信文件、AKShare、深交所官网、TqSdk、取K线

数据所有权：外部源

生命周期：瞬时拉取 · 用完释放（仅保留拉取侧优化缓存）

典型能力：网络/盘面适配、格式解析、行情获取

依赖方向：FrontAPI → AppOrch → AppData → AppConfig；AppData 与 DataAPI 互不依赖（设计 4.4）。两者各自"自含属于自己的读取"，这是边界正确结果而非重复缺陷。

3决策流程

功能触发读数据
  ├─ 读的是外部源、app 不长期持有 → DataAPI
  └─ app 自有 / 决定持有（缓存+持久化）/ 计算产物
        ├─ 数据获取发生在 DataAPI → 读毕
        └─ 是否要 app 长期持有？
            ├─ 是 → 归 AppData（如名称/PE 缓存）
            └─ 否 → 留在 DataAPI（如成分股瞬时拉取）

6本规则的边界与例外

.blk 解析为何存在两份（非缺陷）

AppData 解析它自己的 zxg.blk（自选股，应用自有）→ 合法归 AppData；DataAPI 需要解析通达信外部下发的 .blk 板块（服务指数成分读取）→ 合法归 DataAPI。两份解析各自自含"属于自己的那份"，是边界正确结果，而非重复缺陷——此前试图用顶层中立模块强并它们违背了本规则。

「用完即释放」应读作「不构成应用长期业务状态」

DataAPI 内部的模块级缓存仅作获取侧优化、不转移职责；真正分界的唯一判据是：应用是否承担对这一数据的长期持有/管理。
