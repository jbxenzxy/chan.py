## 0. 一句话结论

把底部的 `_showVolume` / `_subShowVolume` 两个**布尔**换成 `_bottomSlots` / `_subBottomSlots` 两个**字符串 id 数组**；槽数由窗口模式决定（**单窗 2 槽、双窗 1 槽**）；每个槽带一条 14px 标签行（内含一个可点的指标 chip，点击在候选集内循环）；RSI(12) **数据由后端算、随 SSE 逐根下发**（新增 `App/AppUtils.calculate_rsi`，口径照抄 `Math/RSI.py`；前端只读 `k.rsi` —— **与 MACD 展示侧完全同构，前端零计算**），前端**只负责绘制**（值域 / 绘制 / 纵轴 / 标签 / 翻转照前端 MACD 指标那一套，见 §2.4.1；翻转下 **「0」的语义与 MACD 不同** —— MACD 的 0 是**值域内插的零线**、RSI 的 0 是**值域端点**（中位是 50），见 §2.4.3）；单窗 `volRatio` **翻倍到 `0.40`**（= `2 × VOL_RATIO`）—— 即**底部区总高 ×2、每槽与现在的单槽逐像素相同**。 **算法侧**核心 `cal_rsi` **已定打开**（`rsi_cycle=12`）、**展示侧**由 App 层另算并下发（见 §1.3 / §6.1-E1 / §6.1-E2）。

**代价与收益**：单窗主图从 601.6px 降到 451.2px（**−25%**），换到两个各 **136.4px** 的指标槽 —— **与现在的单槽逐像素完全相同**，不是「把两槽挤进原来的一格」。

### 1.3 RSI 数据从哪来（含 2026-10-09 新问与 v6 定论）

**先澄清一个前提：真正的 MACD 指标有「两套」，分别在两层算。**（下表第三行名字里也带 MACD，但那**既不是 MACD 指标、也与本文 RSI 的参照对象无关** —— 它是 `vol` 槽自己的一种显示模式，列在这里只为避免接手人把它误当成第三套 MACD。）

| 指标 | 算法在哪 | 谁消费 | 数据怎么到前端 |

> ⚠️ **概念区分（用户 2026-10-09 澄清）**：上表第三行的「类MACD」**不是** MACD 指标的第三套实现 —— 它是**成交量指标自己的一种显示模式**（`_volDisplayMode = 'bar' | 'macd'`，设置抽屉里那个单选项），做法是把指标输入从 `close` 换成 `成交额/量` 后套 MACD 算法，**与 `k.dif/dea/macd` 这条 MACD 指标链路毫无关系**。真正的 MACD 指标只有上表前两行（算法侧 / 展示侧）。
> **本文讨论 RSI 的参照对象时完全不涉及它** —— 请把「成交额/量只有默认（柱状）显示」当作既定前提：RSI 的显示处理照的是 **MACD 指标**那一套（§2.4.1），与 `vol` 槽用什么显示模式无关。第三行列在此处**只为说明它不是 MACD 指标**（防接手人混淆），不是 RSI 的参照。
>
> **实测：两套 MACD 是同源的** —— 同一 201 根样本上 `CMACD` 与 `calculate_macd` 逐点最大绝对差 **7.4e-14**（浮点级一致；`CMACD` 的 `(2v+(n−1)p)/(n+1)` 与 `ema()` 的 `k = 2/(n+1)` 是同一个递推）。
> 所以目前**不会**出现「图上 MACD 与买卖点背驰不一致」，但**架构上确实是两份实现** —— 这正是下面 RSI 要处理的同一个问题。

| 用途 | 该放哪 | 依据 |
|---|---|---|

> 换句话说：**「像 MACD 一样」在两层都成立，且两层都在后端** —— 算法侧照 `Math/MACD.py` → `Math/RSI.py`（进核心，只差开关）；展示侧照 `AppUtils.calculate_macd` → `AppUtils.calculate_rsi`（App 层另算 + SSE 下发）。**MACD 两层都在后端，RSI 照办后两层也都在后端**（这正是 v9 反转 v6/v8「前端自算」的依据）。

**E2 采纳：展示也从后端下发**（v9 反转；本段即 E2 的落地清单）：`AppUtils` 加 `calculate_rsi` → `AppEngine.py:947/952-960` 加字段 → `AppSSE._apply_rsi_*` 及其调用点加 RSI 状态 → 预览 bar 同族继承（详见 §3.3）。代价是改到实时流路径（原「前端自算」方案正是为躲开它而提，**已按用户口径放弃**）；收益是**前端零计算、与 MACD 单一参照**。

**口径细节（App 层 `calculate_rsi` 必须逐字照抄核心 `Math/RSI.py`，避免两套打架）** —— `Math/RSI.py:10-38`：

```
add(close):
  第 1 根            → 返回 50.0
  diff 长度 < period → 用全历史 diff 的简单平均（不是最近 period 根）
  diff 长度 ≥ period → Wilder 平滑：up = (up_prev*(p-1) + upval)/p
  down == 0          → 返回 100.0（up>0）或 0.0
  否则               → 100 - 100/(1 + up/down)
```

> 注意第 3 行的既有口径：**前 `period−1` 根用简单平均**（标准 Wilder 是"前 period 根 SMA 做种子"）。
> App 层 `calculate_rsi` 必须逐字照抄这个分支，否则展示值会与核心 `klu.rsi` 对不上（与 MACD 的 `CMACD` ↔ `calculate_macd` 同款问题，靠 §4.3-2 护栏钉住）。

### 1.4 高度：**每槽与标签行都不变，代价全部由主图承担**（双槽口径已改为「翻倍」）

> **勘误（2026-10-09，两轮）**：
> ① 最早我说「指标绘图窗与标签行高度都不变、几何函数一行不用改」—— 那只在**单槽**前提下成立。
> ② 随后我给的方案是「把现有底部区**等分**给两槽」（`volRatio = 0.30`，每槽 98.8px）—— **那不是你的口径**。
> ③ 你的口径是「把现有单槽**翻倍**」：底部区总高 ×2（`volRatio = 0.40`），每槽 = 现在的单槽。
> 本文已按 ③ 定稿：**每槽绘图窗 136.4px、标签行 14px 都与现在完全相同**，高度代价全部落在主图（−25%）。

实测（`tools/measure_canvas.py`，1600×900 视口，本机 Chrome，股票 D 线快照）：

```
单窗：canvas H = 820      （窗口 900 高，顶部占用 48 + 容器 820 + 余 32）
      netH = 820-20-36-12 = 752
      主图 = 752×0.80 = 601.6
      底部区合计 = 752×0.20 = 150.4   （其中标签行 14，指标绘图窗 136.4）

双窗：每窗 H = 410        （container.clientHeight/2，见 app.js）
      netH = 410-10-30-4 = 366
      主图 = 366×0.70 = 256.2
      底部区合计 = 366×0.30 = 109.8   （其中标签行 14，指标绘图窗 95.8）
```

**「翻倍」的定义**（③ 与 ② 的唯一差别就在这一行）：

```
底部区总高 = 槽数 × (标签行 + 每槽绘图窗)        ← 「翻倍」的定义
           = 2 × (14 + 136.4) = 300.8           ← 单窗；正好是现状 150.4 的两倍
⇒ volRatio = 300.8 / netH = 300.8 / 752 = 0.40 = 2 × VOL_RATIO
⇒ 每槽绘图窗 = 300.8 / 2 − 14 = 136.4 = 现状单槽（逐像素相同）
```

一般式（`n` = 槽数）：`volRatioFor(n) = n × VOL_RATIO`
⇒ **`每槽绘图窗(n) = netH × VOL_RATIO − 14`，与 n 无关**。
这是本次设计最硬的一条不变式：**槽位数量不影响每槽的高度**，只影响底部区总高与主图。

**单窗放两个槽，取不同 `volRatio` 时各段高度**（`netH = 752`）：

| 单窗 volRatio | 底部区合计 | 主图 | **每槽绘图窗** | 对比：现单槽 136.4 |
|---|---|---|---|---|
| 0.20（现状，两槽挤一格） | 150.4 | 601.6 | 61.2 | −55% ✗ 必糊 |
| 0.30（**等分**方案 · 已否） | 225.6 | 526.4 | 98.8 | −28% |
| 0.36 | 270.7 | 481.3 | 121.4 | −11% |
| **0.40（= 2 × `VOL_RATIO` · 翻倍 · 已定）** | **300.8** | **451.2** | **136.4** | **0%（逐像素相同）** ✓ |

**定为 `volRatio = 0.40`（= `2 × VOL_RATIO`）** —— 只有取到 2 倍，每槽才**恰好等于现在的单槽**：读数密度、柱宽口径、DIF/DEA 双线的可辨度全部不变，验收可以直接拿现有截图逐像素比对（§5-3b）。这是「翻倍」相对「等分」唯一的、也是决定性的好处。

主图代价随窗口高度线性（单窗 `netH = H − 68`，各窗口下**恒为 −25%**）：

| 单窗 canvas H | netH | 主图（0.40） | 每槽绘图窗 |
|---|---|---|---|
| 700 | 632 | 379.2 | 112.4 |
| 768 | 700 | 420.0 | 126.0 |
| **820（本机实测基准）** | **752** | **451.2** | **136.4** |
| 900 | 832 | 499.2 | 152.4 |
| 1080 | 1012 | 607.2 | 188.4 |

⇒ 每槽高度随窗口等比缩放；窗口越矮，主图越吃紧（`H=700` 时主图 379.2px）。§6.1 的 D 项（主图保底）已由用户 ⑷ 拍板**不做** —— 保持「每槽逐像素相同」这条可验收的不变式。

- **每槽绘图窗高度：不变**（单窗 H=820 时仍 **136.4px**）—— 因为 `每槽绘图窗 = netH × VOL_RATIO − 14` **与槽数无关**；双窗单槽也仍是 95.8px（其 `volRatio` 走 `DUAL_LAYOUT` 的 0.30）。
- **标签行高度：不变，仍是 14px**。`MACD_TEXT_HEIGHT`（`app.js::MACD_TEXT_HEIGHT`）不动 ⇒ `Test/test_vol_macd_mode.py:447` 的几何常量护栏继续有效。变的是**条数**：单窗 2 条、双窗 1 条。
- **变的只有两样**：① 底部区**总高**（单窗 150.4 → 300.8，即 ×2）；② 主图（−25%）。
- **双窗：几何一行不改**（仍单槽，仍 `DUAL_LAYOUT`）。注意 `DUAL_LAYOUT.volRatio = 0.30` **不是** `2 × VOL_RATIO` —— 它是双窗为抵消「每窗高度减半」单独调的占比，与单窗的翻倍无关；两套参数各服务自己的窗口模式，**不要合并**。

### 1.5 双击：可以删，但**不能只删那 3 行**

底带那段双击代码**同时承担命中拦截职责**。若只删 `_showVolume = !_showVolume; saveOverlaySettings(); render();` 而把 `return` 一起删掉，双击指标区会**落到底下的「双击空白处」分支**：

- 单窗 `app.js`「默认：恢复全视图」→ `viewCount = VIEW_COUNT` —— **双击指标区会把缩放视图弹回全视图**
- 双窗下窗 `app.js`「默认：恢复下面窗口全视图」→ 同理

正确删法是**保留拦截、只删切换动作**（单窗 `app.js`、双窗下窗 `app.js`）：

```js
// 底部指标区：切换入口已改为标签行 chip（见 getBottomSlotChipRect），
// 这里只做命中拦截 —— 不得落到底下的「双击空白处 → 恢复全视图」
if (clickX >= area.x && clickX <= area.x + area.w &&
    clickY >= bottomTop && clickY <= bottomBottom) {
    return;
}
```

顺带一个 1px 边界：单窗 step 1（`app.js::clickY`）用的是 `clickY > area.y + area.h` 才 return，而底带起点恰好 `=== area.y + area.h`（因为 `getMacdTextArea().y === getChartArea().y + getChartArea().h`，见 `app.js`）。现在底带块先接住了它；删掉切换后建议把 `>` 改成 `>=`，否则那一行像素会去参与 K 线命中测试。

### 1.6 槽位方案：**折中已拍板**（用户 ⑴），且是**唯一**在双窗下不牺牲主图的解

| 方案 | 单窗 | 双窗 | 判定 |
|---|---|---|---|
| 单槽（现状） | 每槽 136.4px | 每槽 95.8px | 做不到「同屏看背离」 |
| 双槽 + 底部区**等分** | 每槽 98.8px（volRatio 0.30） | 每槽 **40.9px**（(109.8−2×14)/2） | 单窗偏小；**双窗不可用**（40.9px 画 MACD 双线+柱必糊） |

| **折中（已拍板）** | **2 槽 · 翻倍（每槽 136.4px）** | **1 槽 · 几何不动（每槽 95.8px）** | ✅ 用户 ⑴ 确认 |

## 2. 设计

### 2.1 状态模型

```js
// 底部指标区槽位（单窗 2 槽 / 双窗 1 槽）；元素为 BOTTOM_INDICATORS 的 id
let _bottomSlots    = ['macd', 'rsi'];  // 上窗 / 单窗
let _subBottomSlots = ['macd'];         // 双窗下窗（独立，不与上窗联动）
```

**为什么用数组而不是 `_bottomIdx: number`**：数组天然就是"多槽位"的输入，`slotCount` 只决定**取前几个**。单窗配好的 `['macd','rsi']`，切双窗时只渲染 `_bottomSlots[0]`，切回单窗自动恢复第 2 槽 —— 无需额外状态。

**槽位次序**：`slots[0]` 在上、`slots[1]` 在下（固定，不做拖拽调序）。

**是否允许两槽选同一指标**：**不做判断**（允许重复 —— 用户 ⑶ 拍板，代码里不写互斥分支）。默认给不同指标即可。

**候选集**（顺序即 chip 循环顺序）：

### 2.2 槽位几何（新增/改写 3 个函数）

现状（`app.js 的 `getVolArea` / `getMacdTextArea`（改造前，本轮已删）`）两个函数**不接参数**，只算「唯一那个槽」：

```js
getVolArea()      → { y: L.top + chartH + 14, h: netH*volRatio - 14 }   // 绘图窗
getMacdTextArea() → { y: L.top + chartH,       h: 14 }                  // 标签行
```

改为**按槽索引**（`i ∈ [0, slotCount)`），并让**每个槽与现在的单槽等高**（等价于底部区总高按槽数翻倍）：

```js
const SLOT_COUNT   = () => (isDualWindow ? 1 : 2);
const SLOT_GAP     = 0;      // 槽间像素（0 = 靠标签行视觉分隔）

function getBottomSlotLabelArea(i) {      // 第 i 槽的标签行
    const L = getLayoutParams();
    const netH = canvas.clientHeight - L.top - L.bottom - L.gap;
    const chartH = netH * (1 - L.volRatio);
    const total = netH * L.volRatio;                       // 底部区总高 = 槽数 × 现底部区（volRatioFor 已按槽数翻倍，见下）
    const n = SLOT_COUNT();
    const slotH = (total - n * MACD_TEXT_HEIGHT - (n - 1) * SLOT_GAP) / n;
    const y = L.top + chartH + i * (MACD_TEXT_HEIGHT + slotH + SLOT_GAP);
    return { x: PADDING.left, y, w: totalW - rightGap, h: MACD_TEXT_HEIGHT };
}

function getBottomSlotPlotArea(i) {       // 第 i 槽的绘图窗
    const label = getBottomSlotLabelArea(i);
    const L = getLayoutParams();
    const netH = canvas.clientHeight - L.top - L.bottom - L.gap;
    const total = netH * L.volRatio;
    const n = SLOT_COUNT();
    const slotH = (total - n * MACD_TEXT_HEIGHT - (n - 1) * SLOT_GAP) / n;
    return { x: label.x, y: label.y + MACD_TEXT_HEIGHT, w: label.w, h: slotH };
}

// 整个底部区的下沿（十字光标竖线、日期轴的定位基准）
function getBottomAreaBottomY() {
    const L = getLayoutParams();
    const netH = canvas.clientHeight - L.top - L.bottom - L.gap;
    return L.top + netH;      // ≡ top + chartH + total，与改造前的 volArea.y + volArea.h 同值
}
```

**几何不变式（护栏要钉住这个）**：

- **每槽高度与槽数无关**：`slotH(n) = netH × VOL_RATIO − MACD_TEXT_HEIGHT`（因 `volRatioFor(n) = n × VOL_RATIO`）⇒ 单窗双槽的**每个槽都逐像素等于今天的单槽**（H=820 时 136.4px），双窗单槽仍 95.8px
- `n = 1` 时两函数**逐像素等价于**现在的 `getVolArea()` / `getMacdTextArea()` ⇒ **双窗零回归**（成立条件：`slotH = total - 14`，代入上式即得）
- `n = 2` 时 `label(0) ∪ plot(0) ∪ label(1) ∪ plot(1)` 恰好铺满 `[L.top + chartH, L.top + chartH + total]`，无重叠无空隙
- 最后一个槽的下沿 = `L.top + chartH + total` = `L.top + netH*(1-volRatio) + netH*volRatio` = `L.top + netH` ⇒ 与原 `volArea.y + volArea.h` 一致

**`getChartArea()` 一行不改**（`app.js::getChartArea`）：它的 `chartH = netH*(1-volRatio)` 在双槽后仍是主图高度，只是 `volRatio` 从 0.2 变 0.40（`n = 2`）。

**底部区占比 `volRatio`：按槽数翻倍**（`app.js` `const VOL_RATIO = 0.2, GAP = 12;`）：

```js
// 底部区总高 = 槽数 × 现在的底部区（即「翻倍」）。
// 每槽固定 = 一条 14px 标签行 + 一个与现在同高的绘图窗；槽数变了就让总高跟着变，
// 否则两槽只能各分一半 —— 那正是被否掉的「等分」方案。
// 取 n × VOL_RATIO 是唯一的解：它使 每槽绘图窗 = netH×VOL_RATIO − 14，与 n 无关
//   ⇒ 单窗双槽的每个槽，与今天单窗单槽逐像素相同（H=820 时 136.4px）。
// n = 1 时恒等于 VOL_RATIO（单窗 0.2；双窗走 DUAL_LAYOUT 的 0.3）⇒ 零回归。
function volRatioFor(slotCount) { return VOL_RATIO * slotCount; }
```

> ⚠️ 不要把它写成「取一个更大的常数」（`0.30` / `0.36` / `0.40` 硬编码都算）：那样「每槽高度」会随窗口模式与槽数漂移，
> 就没法再用「与现单槽逐像素相同」来做验收了。`n × VOL_RATIO` 是**唯一**保住该不变式的式子。
> ⚠️ 也不要顺手改 `DUAL_LAYOUT.volRatio`（0.30）：它是双窗专用参数，改动会破坏「双窗零回归」。

**连带要改的两处「按底部区下沿定位」**：

| 位置 | 现状 | 改为 |
|---|---|---|
| `app.js::drawCrosshair` `drawCrosshair` | `const crosshairEndY = volArea.y + volArea.h;` | 用**整个底部区下沿**（`getBottomAreaBottomY()`），十字竖线要贯穿所有槽 |
| `app.js::drawDateAxis` `drawDateAxis` | `const dateY = volArea.y + volArea.h + 28;` | 同上 |

> 顺带：`drawCrosshair` 的第 7 个形参 `macdTextArea`（`app.js::drawCrosshair`）**函数体内从未使用**（死参数），可一并清理。

| 翻转视图 | **支持**（需求 F，用户 2026-10-09 明确要求）—— Y 轴翻转 + 纵轴标签上下互换，见 §2.4.2 |
| 标签 | `RSI(12): 58.32`（跟随 hover 的 K 线，规则同 `drawMacdLabel`） |
| 数据 | **后端下发**：前端只读 `k.rsi`（取值函数 `rsiOf(k)`）；后端由新增的 `App/AppUtils.calculate_rsi` 算好、随 SSE 逐根下发（§3.3）。**前端零计算** —— 与 MACD 读 `k.dif/dea/macd` 同构；**显示处理照前端 MACD 指标**，见 §2.4.1 |

#### 2.4.1 落地形态：与前端 MACD 指标**完全同构**（数据同样来自后端）

用户口径「**只考虑 MACD 指标；MACD 只有后端处理、传给前端；RSI 就类似处理即可**」= RSI 的**全链路**照 MACD：**后端算 → SSE 逐根下发 → 前端只取值/绘制**。RSI 与 MACD 的**唯一差别是指标定义本身**（单线 0~100，而非 `dif/dea/macd` 三序列），处理环节一一对应（下表）。

| 环节 | 前端 MACD 指标现状（照抄对象） | RSI 照办 |
|---|---|---|
| 数据来源 | 后端 `calculate_macd` → SSE 下发 → 前端读 `k.dif/k.dea/k.macd`（`app.js::getVals` `getVals` 缺省返回 `k`） | 后端**新增** `calculate_rsi` → SSE 下发 → 前端读 `k.rsi`（取值函数 `rsiOf(k)`）。**同构、同样零前端计算** |
| 值域 | `getMacdRange`（`app.js::getMacdRange`）：从 `k.macd/dif/dea` 算 min/max + 10% margin，全 0 兜底 `{min:-1,max:1}` | `getRsiRange`：**随可见窗口自适应**（与 `getMacdRange` 同机制：只吃 `getVisibleKlines()` 那一刀切出来的 klines），上下各 5% 余量，**再夹回 `[0,100]`**（RSI 是有界量，刻度落在定义域外一定是错的 —— 实测窗口含 `RSI=0` 时下沿被留白算成 −4.76）；空窗 / 整窗缺值回落 `{min:0,max:100}`。**不是固定 `[0,100]`** —— 固定值域会让缩放/滚动对 RSI 曲线毫无影响（放大后被压成一条直线） |
| 绘制 | `drawMacd`：`macdToY(v)` 带翻转分支 + `zeroY = macdToY(0)` + 柱（`isUp = macd >= 0`，翻转换色） + dif/dea 双线 | `drawRsi`：同式 `rsiToY(v)`（`min/max` 由上一行的 `getRsiRange` 给出，**不再假定是 0/100**），中轴取 `rsiToY(50)`；**单线**（无柱、无 dif/dea），颜色 `COLORS.rsi` |
| 纵轴 | `drawMacdAxis`：`topVal = _isMirrorMode ? min : max`、`botVal` 反之 | `drawRsiAxis`：**不是三段式** —— 印 `RSI_AXIS_LEVELS`（= `RSI_REF_VALUES` 排序）里**落在当前值域内**的档位（典型 `80 / 50 / 20`）；一档都不在窗内时退化为值域上下沿（两位小数），纵轴不留白 |
| 标签 | `drawMacdLabel`（改造前）：hover 命中 → 否则末根兜底；左标签「指标名 + 各值」（真 MACD 分支） | `drawRsiLabel`：同一套「hover 命中 / 末根兜底」规则；文案 `RSI(12): 58.32`；单值 ⇒ 无 BAR 换色分支 |
| 翻转视图 | `_isMirrorMode` 在 `macdToY` / BAR 颜色 / 轴值三处生效 | 同款（Y 翻转 + 轴值换位）；**单线单色 ⇒ 只翻 Y 位置，不改颜色**，见 §2.4.2 |
| 预览 bar | 后端 `App/AppUtils.py::_inherit_metrics_for_preview_bar`：**末根继承前一根**，不重算 | **同一口径、同样在后端**：`_inherit_*_for_preview_bar` 顺手把 `rsi` 也继承（或新增 `_inherit_rsi_for_preview_bar`）。**前端无需任何预览判据** —— 它读到的 `k.rsi` 已是后端处理好的值 |

> 值得注意：`drawMacd` 本身已带 `valOf` 注入参数（`drawMacd` 的形参表里就有），已支持"换取值来源、复用画法"，说明「照 MACD 的**画法 / 口径**、只换数据来源」是这个文件既有的做法 —— RSI 因形态不同（单线、无柱）不直接复用 `drawMacd`，而是照它的**口径**另写 `drawRsi` / `drawRsiAxis` / `drawRsiLabel`。

> ℹ️ **预览 bar 不再需要前端判据**（v9）：末根继承既然与 MACD 一样由**后端**做（§3.3），前端读到的 `k.rsi` 已是处理好的值。原「前端自算」方案里那条「末根 `k.vol <= 0` 形态判据」及其「停牌 K 线被误判」的副作用**整段作废**（那是前端自算才需要解决的问题）。

> **前端实现要求**（v9 后只剩「消费」）：**取值同源** —— 绘制 / 纵轴 / 标签三处都走 `rsiOf(k)`，而 `rsiOf(k) = k.rsi`；`k.rsi` 缺失时按「不画该点」处理（与 `k.dif` 缺失时 `ZERO_MACD_VALS` 兜底同思路）。**无须全序列计算、无须惰性 Map、无须抽段标记** —— 那些都是「前端自算」才需要的，已随 E2 反转一并去掉。

#### 2.4.2 翻转视图（右键菜单 · 需求 F）

链路已核实：菜单项 `app.html::annotation-menu-mirror` `onclick="toggleMirrorMode()"` → 全局开关 `_isMirrorMode`（`app.js::_isMirrorMode`）→ 切换 `toggleMirrorMode()`（`app.js::toggleMirrorMode`，菜单文字在同一处同步）。原理是**纯视图变换（Y 轴翻转），不改数据**（`_renderChart` 的翻转注释），每个 draw 函数**自行按 `_isMirrorMode` 处理**。

RSI 与 MACD 同属「有中轴、有方向语义」的一类，**照 `drawMacd` / `drawMacdAxis` 写**：

| 元素 | MACD 现状（照抄对象） | RSI 照办 |
|---|---|---|
| 值 → Y | `drawMacd` 的 `macdToY = (v) => _isMirrorMode ? (顶→底) : (底→顶)` | `rsiToY(v)` 同式；`min/max` 取自 `getRsiRange`（**自适应**），断言里**别假定它是 `[0,100]`** |
| 中轴 / 参考线 | `zeroY = macdToY(0)` —— 0 是**值域内插的零线**（MACD 的 min/max 由数据推，0 通常不在端点） | 中轴 `rsiToY(50)` + 参考线 `rsiToY(80)` / `rsiToY(20)`（超买 / 超卖） —— **三条都必须走同一个 `rsiToY`**；翻转后 80 ↔ 20 **互换**（80 落到下方 = 做空视角）。**0 在 RSI 里是值域端点、不是中轴** —— 见 §2.4.3。⚠ v10 曾写「50 恒在正中、是不动点」，那是**固定值域 `[0,100]`** 下的结论；值域改自适应后，`rsiToY(50)` 只在值域恰为 `[0,100]` 时才落在绘图窗正中 —— **别把它当不变式写进断言** |
| 纵轴上下值 | `drawMacdAxis` `topVal = _isMirrorMode ? min : max`（`botVal` 反之） | `drawRsiAxis`：**没有** `topVal` / `botVal` 概念 —— 按 `RSI_AXIS_LEVELS` 过滤出窗内档位，翻转只改 Y 方向、不改档位集合 |
| 轴标签顺序 | 随 `topVal/botVal` 自动换位 | 同上 |
| 颜色 / 数值语义 | BAR 颜色在翻转下对调（`drawMacd` 的柱色分支 / `drawMacdLabel` 的 BAR 换色） | **不适用**：RSI 单线单色、数值含义不随视角变 ⇒ **只翻 Y 位置，不改颜色、不改数值** |

> 别照 `drawVolume`：成交量柱恒正，它选择「不翻柱方向、只翻颜色」，`drawVolumeAxis` 也不换位。RSI **不属于**这一类 —— 它有 50 中轴与 80/20 阈值语义，必须与 MACD 同款（轴值换位 + 线/参考线整体镜像）。

#### 2.4.3 翻转下「0」的语义差异：MACD 的**零线** ≠ RSI 的**端点**（本轮新增防护）

> **用户 2026-10-09 追问**：「MACD 指标，翻转视图后，0 轴变化的问题（之前踩过坑），RSI 是否也同样考虑了？」

**先说踩过的那个坑是什么**（仓库里有留痕）：MACD 的 0 轴在**两处**被画出来 —— `drawMacd` 画**线**（`zeroY = macdToY(0)`，、`drawMacdAxis` 画**刻度文字** ，注释  明写「0 标签位置也随 Y 轴翻转」）。两处算的是同一个 0，但**用的是两个式子**：前者 `macdToY(0)`，后者手写化简式 `area.y + area.h * macdRange.max / range`（非翻转分支）。代数上确实等价（`range + min = max` ⇒ `1 − (0 − min)/range = max/range`），但只要翻转分支里**改了一处、漏了另一处**，就会出现「**刻度 "0" 与零线错位**」。现在由 `Test/test_vol_macd_mode.py:611-637` 两条断言钉死：

1. **零线镜像不变式**：未翻转零线 y ＋ 翻转零线 y ≡ 指标区上下沿之和（`zn + zf == vol_top + vol_bot`，容差 4px）—— 该和**与 range 内 max/min 取值无关**；
2. **刻度与零线同位**：轴上 `"0"` 文字的 y 与实测零线 y 差 ≤ 4px（`textBaseline: alphabetic` 的基线偏移）。

**RSI 的关键差别 —— 不能照抄 `drawMacdAxis` 的 `topVal` / `zeroY` / `botVal` 三段式**：

| 项 | MACD | RSI |
|---|---|---|
| 值域 | 数据驱动（`getMacdRange` 由 `k.macd/dif/dea` 推 min/max + 10% margin，**不对称**） | **随可见窗口自适应**（`getRsiRange`：窗口内 `rsi` 的 min/max + 上下 5% 余量）+ **夹回 `[0,100]`**；空窗 / 整窗无 `rsi` 回落 `[0,100]` |
| 「0」的角色 | **零线**：值域**内插**的第三条刻度，位置由 `macdToY(0)` 决定、**随数据变** | **值域端点**：0 是 RSI 定义域的下沿、**不是中位**；与 100 构成两端 —— 这正是照抄 `zeroY` 会出错的根因 |
| 中位 | 0 自身（若 `min < 0 < max`，零线恰在中位附近） | **50**（与 0 无关系）；`rsiToY(50)` 的位置随值域变，**值域恰为 `[0,100]` 时才居中** |
| 纵轴档位 | `[max][0][min]` —— 中间那条是**内插零线** | 印 `RSI_AXIS_LEVELS`（= `RSI_REF_VALUES` 排序）里**落在值域内**的档位（典型 `[80][50][20]`）；一档都不在窗内 ⇒ 退化为值域上下沿（两位小数），纵轴不留白 |
| 翻转后档位 | `[min][0][max]`，0 的 y 按 `macdToY(0)` 镜像（**位置随数据变**） | 档位集合不变，Y 由 `rsiToY` 镜像（`80` 落到下方） |
| 额外水平线 | 无 | **80 / 20 参考线**（细点虚线），翻转后互换 |

⇒ **照抄 `drawMacdAxis` 会犯两个错**（值域含 0 / 100 端点时最明显）：

- 中间那档刻度会写成 `"0"`（MACD 的零线位置），而 RSI 的中位是 **50**；
- 又因 `rsiToY(0)` 落在下沿，按 `zeroY` 式子算出的 y 与 `botVal` 的位置**重合** ⇒ `"0"` 会被画**两遍**、中间**缺 `"50"`**。

**⇒ 落点要求**（已写进 §4.3-4 护栏）：

1. `drawRsiAxis` 印 `RSI_AXIS_LEVELS` 过滤后的档位（典型 `80 / 50 / 20`），**中间那条走 `rsiToY(50)`、文案恒 `"50"`**；变量**不得沿用 `zeroY`** 命名（该名承载 MACD 的零线语义，容易把两套口径又混起来）；
2. **单源映射**：折线 / 50 中轴 / 80·20 参考线 / 档位刻度 —— **全部 y 从同一个 `rsiToY(v)` 出**，**禁止**手写 `area.h * 0.8` / `* 0.2` / `* 0.5` 之类相对比例（MACD 那个坑的成因正是「两套式子算同一个 0」）；
3. **镜像不变式对任意一条水平线都成立**：`rsiToY(v)` 翻转前 ＋ `rsiToY(v)` 翻转后 ≡ `2 × area.y + area.h`。`v = 50` **只在值域为 `[0,100]` 时**是不动点；`v = 80 / 20` **互换**；
4. **像素探针要适配**：现有 `PIXEL_STATS_JS` 的零线探测（`:366-380`）是启发式 —— 找「整行多数像素为 `rgba(255,255,255,0.2)` 叠底后的灰、且 `zeroRatio ≥ 0.35`」。RSI 的参考线是 `rgba(255,255,255,0.15)` **虚线**、中轴另色 ⇒ **同一探针会把 RSI 的线误认成零线（或漏掉）**。RSI 的护栏应改用「**按已知 `rsiToY(v)` 反查该行**」或「按目标颜色分类统计」，**不要复用 MACD 的启发式**。

### 2.6 持久化与迁移

```js
// saveOverlaySettings (app.js)
bottomSlots: _bottomSlots,
subBottomSlots: _subBottomSlots,
// 旧键 showVolume / showSubVolume 不再写出（读侧保留迁移）

// loadOverlaySettings (app.js)
if (Array.isArray(s.bottomSlots)) {
    const valid = s.bottomSlots.filter(id => BOTTOM_INDICATORS[id]).slice(0, 2);
    _bottomSlots = valid;
} else if (typeof s.showVolume === 'boolean') {          // 旧键迁移
    _bottomSlots = [s.showVolume ? 'vol' : 'macd', 'rsi'];
}
if (Array.isArray(s.subBottomSlots)) {
    const valid = s.subBottomSlots.filter(id => BOTTOM_INDICATORS[id]).slice(0, 2);
    _subBottomSlots = valid;
} else if (typeof s.showSubVolume === 'boolean') {
    _subBottomSlots = [s.showSubVolume ? 'vol' : 'macd'];
}
```

**迁移规则**：旧用户保留第 1 槽的原有选择（`showVolume=false → 'macd'`、`true → 'vol'`），第 2 槽补 `'rsi'`。⇒ 升级后"原来在看的那个指标还在原位"，同时直接获得新能力，符合上一轮定下的"升级无感"原则。

**新用户默认**：`_bottomSlots = ['macd', 'rsi']`（你的 ⑶ 明确要求：上 MACD、下 RSI），`_subBottomSlots = ['macd']`（双窗默认 MACD）。

**兜底**：`_bottomSlots` 为空数组时，渲染层回落到 `['macd']`（避免"标签行空了、指标窗无内容"的空状态）。
