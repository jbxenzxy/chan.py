## 一、铁律（无条件遵守，违反会出事）

1. **绝不直接改用户项目目录**（`C:\my_chan_project` 等）。改动只写在沙盒
   `C:\Users\river\WorkBuddy\<session>\sandbox\`；交付 = zip 包，合并永远由用户自己做。
   `cp`/`rsync` 指向真实项目 = 违规，即使"为了方便复验"——复验一律解压到独立临时目录。
2. **交付格式**：每阶段完成后把改动文件**按仓库原目录层级**打包 zip，**不出 patch/diff**。
   细则（diff 双禁令 / 清 `__pycache__` 与运行时产物 / 打包后解压复验 / **`.md` 一律不进 zip** /
   **实验脚本默认不发**）全文在 `memory-workflow.md` §交付格式 第 1-10 条，动手前先读它。
3. **Bash PATH 常损坏**（`ls` / `dirname: command not found`）→ 每条命令开头加
   `export PATH="/usr/bin:/bin:/usr/local/bin:$PATH"`；管道也会挂，截断输出就在 Python 里做。
   **打包/解压一律用 Python `zipfile`** —— PowerShell `Compress-Archive` 在本机静默失败过 3 次。
4. **同一文件多处改动必须串行 Edit**（一条消息一个 Edit）：并行会因 EBUSY 静默丢改动，
   改完用 Grep 确认无残留旧符号。CRLF 仓库整块替换会失配 → 用 Python 脚本 + 断言命中次数。
5. **改 chan.py 任何文件前先读 `memory-chanpy.md` 的术语护栏**（禁用词：腿/双仓/丢仓/leg/legs…）；
   新增日志/注释/断言描述最容易撞，改完必须重跑 `test_p26_terminology_guard.py`。
5.5 **改完代码必验（2026-09-23 拍板；用户不必记，他说"验一下"即全跑）**：
   `Trading/` 任何改动后**必跑门禁** `<项目venv>\Scripts\python.exe Test/run_all.py`（cwd=仓库根），
   **退出码 0/1 即判决**；**新写的测试不会自动进门禁**（要手动加 `COMPONENTS` 一行）；
   **写完测试 / 拉远端合并后 / Phase 收尾前**再跑**发现式** `run_all_tests.py` 看差集（查"写了没人跑"）。
   命令、判读、常见坑见 `memory-chanpy.md` §1。
6. **断言"代码里没有 X 能力"之前必须先 grep**（≥2 组关键字 + 文件:行证据），给不出证据就写"待确认"。
6.5 **只认代码、注释不算证据**：核对/断言任何行为必须分析源代码，结论落到可执行分支 +
   文件:行号；注释、docstring、日志字符串只当线索、不当证据。需求与注释冲突时先跟需求方确认口径。
   **对评审自己同样生效**：自检①"这行是可执行语句吗"②"行号指向该行真正做的事吗"
   ③"外部数字附官方 URL 了吗"；贴语义标签前先看该行所属函数的分工，**全称量词（所有/唯一/恒）
   给出前先穷举**。三条硬检查 + 反面实例全文见 `memory-workflow.md` §评审自检。
6.6 **报问题先给背景**：指出任何"问题/缺陷/风险"时，**第一句必须是"什么条件下
   才会发生"** —— 触发条件 + 可达路径 + 是否属设计已明示不支持的异常流程，再谈后果与严重度；
   **给不出可达路径的不许当缺陷报**（只能标"不可达 / 仅理论推演"）。严重度按**可达性**定，
   不按后果画面感定。**先问"这在正常流程里怎么发生"，判完可达性再决定报不报**；
   反例（B1/B2 初报只写"少记账、统计失真"看着严重，补背景才发现要"簿面被外部改动"才可达）
   与三条判定链全文见 `memory-workflow.md` §报问题先给背景。
7. **新规则写在靠前位置，不要 append 到末尾** —— 末尾会被截断，等于没记。
   本文件超过 ~4,500 字符就再拆一次。
8. **开工前置检查**：接到任务先过第二节索引表，命中主题词就
   **先 Read/Grep 对应 `memory-*.md` 再动手**，不许凭印象干；**子文件不会自动注入，不读 = 不存在**，
   但**同一会话内已读过的子文件不重读**（跨会话新任务再读）。
9. **引用即注明**：凡是读过子文件记忆，回复里必须写明
   「读了 `memory-xx.md` 的哪节」，让用户能一眼看出我查没查、漏没漏。
10. **交付 HTML / MD 文档须确保用户能下载到本地、图与表都能正常显示**：
    `present_files` 只是预览/卡片，用户最终要落本地（覆盖目标目录）→ 交付前确认：① 内联图（SVG /
    Base64）与表格在**无网络、本地双击打开**时都能正常渲染；② 不依赖会过期的外链 / CDN；
    ③ 回复里**明确给出文件本地路径**。纯 SVG 文档自包含，但仍要走"给路径 + 可下载"这一步。
    ④ **交付配对按内容类型分流（默认契约）**：
    - 含生成式可视化（手绘/数据驱动 SVG、图表、由数据生成的表）的 HTML → 交 **HTML + JSON 两文件**（JSON 为 SSOT，HTML 为渲染产物；MD 不需，因 MD 无法忠实承载内联 SVG）；修改时改 JSON 再生 HTML，禁止仅凭 HTML 反推。
    - 纯散文（仅文字/表格/代码块、无生成式图） → 交 **MD 单文件即可，不需 HTML**（MD 可 100% 表达其内容且为 SSOT，随时可转 HTML/PDF）。
    - 用户**显式指定格式**（如「要个漂亮 HTML」）时以用户要求为准，不受上述分流限制。
    - 无论哪种，回复中**显式给出文件本地路径**。

11. **新增 / 修改文件前两套前置对齐**：
   - **分层与单向依赖**：不得破坏既有分层架构与单向依赖。动手前先找出该仓库分层约定
     （架构文档 / 目录职责注释 / import 守卫测试）确认「谁能 import 谁」；实现后逐条核对：
     不新增反向依赖（下层 import 上层）、不跨层直连、不把上层专属类型/常量塞进下层。
     宁可多绕一层（**下层定义 SSOT，上层适配**），也不图省事反向引用。
   - **命名**：动手建文件**之前**先 `ls` 目标目录 + 看隔壁同类文件，**照抄它的大小写风格与词法**，
     不许自创风格。判据 = **同目录/同类既有文件的多数派**，不是通用社区惯例（PEP8 不适用）。
   - 既有文件是违例（异类命名）→ **报告 + 问是否连带改名**，不擅自 rename（上游 pull 冲突成本 +
     已交付包/文档里的路径引用会失效）。改名交付多一步：zip 只有新路径，**用户仓库旧文件不会随
     覆盖解压消失**，必须明确让他手动 `del`（不删 = 留个无人 import 的死模块）。项目级规范与反例
     （trade_stats→TradeStats）见 `memory-chanpy.md` §3。

12. **回答风格 · 不写开场白/结尾**：除非用户明确要求，不加"我来看看…""以上就是我做的
   改动…"这类开场白/结尾，直接给结论、改动、证据。
13. **回答风格 · 不加代码解释摘要**：不额外附一段"代码说明/改动摘要"复述已列内容。
14. **回答风格 · 不写"我犯了错/如何改进"类过程叙述**：绝不输出自我检讨 / 排查过程 /
   纠错经过（"误用 X、一度怀疑 Y、重跑即恢复"），证据只留结论性事实（"回归 43/48，与基线一致"），
   原因压成一句结论。铁律 12/13 同理。
15. **新功能先调研、不自造轮子**：接到"实现新功能 / 新对接"任务，**动手前先去 GitHub +
   官方文档搜同类项目**，看主流做法、选现成库/类，并在方案文档里给出调研证据；禁止凭印象设计。
   反例：P67 凭旧认知断言"开源 tqsdk 无直连"差点产出 18 人日方案，一轮搜索发现官方 `TqCtp`（1.5 人日）。
16. **因果正序：正确性决定改不改，改动面不决定**：判断某处修改"正确"就坚决执行，
   **不许拿"改动面大 / 牵连多"当不做的理由**（那是因果颠倒）；面大 = 多花时间 + 多补护栏 +
   更严格执行交付闭环，不是"所以先算了"。例：`-1` 哨兵收敛成 `None`，3 → 9 文件。
