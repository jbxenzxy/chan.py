## 工作安全偏好（重要）
- **不要直接修改用户的项目目录**（如 `C:\my_chan_project\`）。所有代码/文档改动先在**沙盒目录**暂存，完成后**打包（zip）交给用户自行合并**。
- 触发背景：用户在 2026-08-31 发现我此前在 Agent/craft 模式下直接写盘到其项目目录，明确表示不希望这样，要求以后在沙盒中修改、改完打包给他自己合并。
- 沙盒目录约定：`C:\Users\river\WorkBuddy\<session-id>\sandbox\`（按会话建子目录）。
- 机制说明：本环境文件编辑工具（Write/Edit）默认写**真实文件系统**，没有按目录的自动沙盒隔离；只有 `Desktop/Downloads/Documents/Home` 等受 `personal_files_safety` 策略保护。因此"沙盒"必须**由我主动把改动写到独立目录**来实现，而非依赖工具自带隔离。
- 例外：用户明确授权直接改的文件/目录（如 WorkBuddy 自身的输出目录、`output/`）除外。
  **用户点名要求"同步更新 XX 文档/文件"也算显式授权**，可以就地改。
  ⚠️ 就地改之后要不要出"可比对物"，**以 2026-09-15 用户裁决为准**（见下节）：默认**不补丁**，
  只按目录层级打包改动后的完整文件。仅在用户明确要 diff 时才补。
- **交付变更优先"单可替换单元"，避免全仓库 refactor**：用户极其在意**变更波及面可控、可一键回退**。与其为整洁去重构整个仓库（动 Docs + 根目录结构），不如把改动收口在**一个可整体替换的目录**（如只给 `trader_gateway/` 一个 zip 直接覆盖），其余核心代码一行不动。文档修正**单独打包**（`Docs_updates.zip`），与代码改动解耦，每个改动独立可还原。每次交付后务必从 zip 解压到干净目录**复验**（跑测试/冒烟）再交付。


## ✅ 交付格式（2026-09-15 用户拍板，最高优先级，覆盖此前的"必须出补丁"要求）
- **每个阶段完成后：把改动过的文件按原目录层级打包成 zip 交付即可，不要产出 unified diff / patch 文件。**
- 具体要求：
  1. zip 内**保持仓库原始目录结构**（如根下直接是 `Trading/…`、`Docs/…`），让用户可以直接覆盖到项目目录；
     不要平铺、不要加 `changed/` 之类的额外层。
  2. 只放**改动后的完整文件**（整份覆盖语义），不放 `.patch` / `.diff` / `patches/` 目录 —— 除非用户当次明确要。
  3. 报告/证据类产物（评审报告、测试日志、探针输出）可以放在 zip 内**独立的 `reports/` `evidence/`** 目录，
     与可覆盖的代码/文档解耦，用户自己挑。
  4. 打包前必须清 `__pycache__/`、运行时产物（`_verify_A/`、`state.db` 等），否则混入交付包。
  5. 打完包仍要**解压到干净目录复验**（跑测试 / grep 新标记存在、旧标记消失），这一步不因"不出补丁"而省略。
  6. **"不出补丁"包含两件事，缺一即违规（2026-09-15 二次拍板）**：
     - **不加附件**：交付时（含 `present_files` 的附件列表）只给 **zip + 报告**，不得顺手附 `.diff` / `diff_all.txt`；
     - **不让 diff 进包**：diff 产物**不能放在 `reports/` 里** —— 打包规则会把整个 `reports/` 装进 zip，
       用户解压覆盖时会把这些 `.diff` 落进仓库目录树。diff 一律放**交付区之外**（本会话约定 `internal/`）。
  7. **修复姿势**：已经泄漏的用**重打包脚本（带断言）**收口，不要手改 zip；脚本要断言"包内无 `.diff`/`diff_all`
     /`__pycache__`/`state.db`、且路径分段不以 `_verify_` 开头"，再解压做 md5 往返校验比对**已跑过测试的那棵树** ——
     md5 相等即可免重跑回归。
  8. **注意断言自身会误伤**：`' _verify_ ' in path` 的朴素写法会把 `regress_verify_from_zip.json` 判成违规；
     要按**路径分段**判断，并尽量让文件名不撞护栏关键词。
     ⚠️ **2026-09-15 实测第二次踩到**：`BANNED_SEG` 里放了 `deliver`，结果合法测试文件
     `Trading/Test/test_p53_delivery_guard.py`（文件名含 "deliver"）被判违规、拒绝打包。
     **正确姿势：禁用词只匹配目录段（`for s in segs[:-1]`），文件名只判扩展名。**
  8b. **"残留符号"扫描必须先剥 docstring（2026-09-15 实测）**：
     断言「旧符号 `.spec` 已无实代码引用」时，只跳过行首 `#` 不够 ——
     「原 `instrument.spec` 兼容别名**已删除**」这类**docstring 散文**会被当成残留（本轮首跑误报 4 处）。
     做法：先用正则把 `"""…"""` / `'''…'''` 按**等长空白**替换（保持行号不变），再逐行匹配实代码；
     这样既保住"该符号确实没了"的护栏，又不会把留档说明算成违规。
     （与 §「删除字段类改动的测试改写套路」同源：**注释/docstring 里的"已删除"不算实引用**。）
  9. **`.md` 一律不进 zip（2026-09-15 三次强化）**：
     - zip 只装**要按仓库目录层级覆盖进仓库的东西**（代码 / 配置 / 测试）；
     - `.md` 报告与设计文档**只作为独立附件给**（`present_files`），**不要重复放两份**；
     - 触发背景：上一轮把设计 md 同时打进 zip 又单独发一次 → 用户反馈"会重复"，且解压覆盖会把 md 落进仓库树；
     - 纯文档轮次（无代码改动）**不打 zip**，只给 md 附件。
   10. **实验脚本默认不发（2026-09-15 四次强化）**：
      - 范围：为**验证 / 对照 / 计数 / 派生 / 探针**而写的一次性脚本 —— `exp_*.py`、`derive_*.py`、
        `verify_*.py`、`audit_*.py`、临时探针片段等。它们是**取证手段，不是交付物**。
      - 默认动作：**既不进 zip，也不挂 `present_files` 附件**，连 `reports/` 归档也**不必单发**。
        只交付 **结论 + 文档**；回复末尾用一句话交代「脚本在沙盒 `sandbox/`，需要随时说」。
      - 用户明确索要时（"把脚本发我"）才单独给 —— 此时也**只走 `present_files` 附件，不进 zip**。
      - 触发背景：前几轮交付把实验脚本一起列进 `present_files`，用户反馈这些他并不需要。
- 用户原话：「以后每个阶段完成后，把修改的文件，按目录层级，打包给我就行，无需出补丁」。
- **存储位置 = `C:\Users\river\.workbuddy\MEMORY.md`（本机、按 Windows 用户目录，不按登录账号）**。
  实测 `~/.workbuddy/` 下 `MEMORY.md`/`skills/` 全是平铺单一路径，`settings.json` 的 `claw.users`
  虽有 3 个账号 ID 但**没有任何按账号分目录的配置** → 换 WorkBuddy 登录账号**仍有效**；
  换机器或换 Windows 用户才失效（需迁移，见「技能库位置与迁移」节）。
- 推论：评审/分析类结论仍要写在报告里，但**交付物 = 文件包**，不是补丁包。

## 沙盒与真实项目同步方法（2026-09-05 教训，会话内写盘不可靠）
本环境文件编辑工具（Write/Edit）落盘动作**在会话内可能不可靠**——曾出现过"会话上下文说已写 E3.2 改动到沙盒 tg/sizing.py/risk.py/engine.py"但磁盘上文件 mtime 全是 Sep 4、所有 E3.2 标记 grep 不到（完全空白）的情况。

**根因猜测**：上次会话结束前 Write/Edit 写到一半被打断、没 flush；或文件落到了别的工作区但消息系统没正确同步。

**恢复 SOP**（用户指示"拉取 custom-dev 最新代码"）：
1. 用 `cp -ru <真实项目>/trader_gateway/. <沙盒>/trader_gateway/` 同步真实项目到沙盒
2. cp -ru **不排除 __pycache__**，打 zip 前必须 `find . -type d -name "__pycache__" -exec rm -rf {} +`
3. 跑全套回归确认基线绿（沙盒同步完后）
4. 在沙盒里做新 phase（Edit/Write 工具实际生效）
5. **每个 phase 完成后立即** `py_compile + pytest + grep -rE "新标记" tg/` 确认落盘
6. 打 zip（PowerShell Compress-Archive）+ Expand-Archive 解压复验

**沙盒内 Phase 工作流**（适用于任何含 tg/ 子目录的项目）：
- 用户说"开始做 X" → 不要假设前置 phase 在沙盒里 → `ls <sandbox>/tg/` + `grep -lE "<phase 标记>" <sandbox>/tg/*.py` 确认状态
- 若状态缺失 → 询问用户"是 cp 同步真实项目、还是从零重做"


## 交付验证 SOP：证明"交付 zip ≠ 本地旧结构"（2026-09-08 固化）
- 用户多次质疑"你给的 zip 跟我本地一模一样，修改没体现"。根因是会话内 Write/Edit 没落盘，导致上一轮 zip 实际 == 本地旧结构。
- **交付前/后必做三件事**：
  1. **从 zip 内读回关键 token 校验**：`zipfile` 打开交付包，读回每个关键文件，断言新标记存在（如 `entry_params`/`exit_params`）、旧标记消失（`*PolicyConfig`/`DefaultExitPolicy`/`@register_exit`/`build_*`/`*_POLICIES` 等），且只应作为「已删除」的注释出现。
  2. **双向 grep 证明差异**：对交付目录 grep 旧 marker 应空（仅注释提及删除）；对**用户真实项目目录** grep 同一批旧 marker 应非空（旧结构仍在）→ 直接证明「zip 已改、本地未改」。
  3. **跑全套测试**：`Test/*.py` 多为独立脚本（`check()`+`sys.exit(1)`），用 `my_chan_project/.venv/Scripts/python.exe` + `PYTHONPATH=<sandbox>` 逐个跑，确认全绿。
- 注意区分「注释/docstring 中'已删除'的解释性字样」与「真实代码引用」——后者才算未删净。引擎实例属性 `self.entry_policy`/`self.exit_policy` 合法，不等于 Config 的 `entry_policy`/`exit_policy` 选择器字段。

## 设计文档在实施后刷新的套路（2026-09-22 固化）
- 场景：设计文档写于实施前、实施后代码整体位移 → 文档里几十处行号批量失效。**分区处理，别一刀切**：
  ① **问题陈述章节**（"现状 / 背景"，描述的是实施前形态）→ **保留实施前坐标**，加粗警示 + 指向对照表。
     把它改成实施后坐标会让陈述变假（如"此处不写 Trade"在实施后已不成立，却指着已改写的新行）。
  ② **设计 / 评审章节**（指向同一批代码实体、只是坐标变了）→ **就地更新为实施后坐标**，旁注"（实施前 :XXXX）"便于追溯。
  ③ 新增一节 **「实施后坐标对照」**：漂移表（old→new + 影响章节）+ **未漂移清单**（同样重要，证明逐条复核过）+ 本次刷新摘要 + 未决项表。
- 刷新前必须**逐条 grep 核实**，不能照抄评审报告的映射——报告里也会有 ±1、路径错。
  （2026-09-22 实例：报告写 `main.py:343-346`，实测是 **`Trading/main.py`**，仓库根另有一个 88 行的同名 `main.py`。）
- 计数类断言（"测试 X/Y 通过"）要**实跑复核**，不要沿用文档旧值（本次 54/54 → 实测 63/63）。


## 长中文文档写完后必须扫乱码（2026-09-17 实测，当日踩到 22 处）
- 现象：模型写**长篇中文**交付文档（HTML/MD）时，正文里会混进乱码片段，肉眼看不出来：
  西里尔字母（`срещу`）、法语词（`sécurité`/`confirme`）、孤立英文单词
  （`Nitration` / `Land` / `github split` / `urchin` / `Closeout` / `workflow` / `liabilities`）、
  纯数字串（`1278990;`）、以及**分词器占位符**。
- **占位符的真身是 `<｜hy_place▁holder▁no▁813｜>`**：外层还有**一对尖括号**，
  中间是 `U+FF5C` 全角竖线 + `U+2581` 下横块。只按 `▁` 或 `hy_place` 去匹配会**命中 0 次**（我为此错了两轮）。
- **必做的两步扫描**（写完立刻跑）：
  1. 非中文非 ASCII 白名单扫描：正则取 `[\u0400-\u04FF\u0370-\u03FF\u3040-\u30FF\uAC00-\uD7AF\u00C0-\u00FF]`
     排除掉合法的 `§ · × ｜ ①②③ ⑴-⑻`，其余逐个看；
  2. 中文行里的英文词聚合去重后**人工判读**（HTML 属性 / 文件路径 / 技术术语是合法的，其余多半是乱码）。
- 修复脚本纪律：每条替换显式写"期望命中次数"，`count != 期望` 就**打印并退出、不写盘**
  （首次写盘失败很正常，改对再跑）。一次写 20+ 条也只跑一轮。
- 占位符被替换掉的中文要**按上下文回译**（如"夜盘对账 ▁▁▁ 判定"→"跨交易日判定"，3 个 token 对应 3 个占位）。


## 断言"改配置能达成某效果"前，必须同时看定义方与消费方（2026-09-17 教训）
- 场景：我照抄 `.env.example` 的注释"换目录 = 换一套账本"就写进交付文档，
  结果消费方 `App/AppTrader.py:_discover_state_dbs()` 会 `glob(Trading/State*)`

## 不许断言"用户本地不入库的东西"的当前值（2026-09-17 教训，同一天被问倒两次）

## 出补丁前必须复查"基线是否已被用户推进"（2026-09-14 实测）
- 场景：上一轮交付补丁后，用户**中途已合入** → 本轮再取 GitHub 原始版时 HEAD 已变
  （`c6fc454b80` → `199ee31c7a`），我的工作树仍基于旧 HEAD。
- 风险：直接 `git diff` 可能把用户已合入的内容**反向回退**，或产生大量无关 hunk。
- **必做两步**：
  1. `curl -k -sL https://api.github.com/repos/<owner>/<repo>/compare/<旧HEAD>...<新HEAD>`
     看两次之间改了哪些文件（确认是否就是我上一轮交付的那几个）；
  2. `git diff` 后逐文件扫一遍 hunk，确认没有"意外回退"（尤其被删字段又出现）。
- 顺带：本轮工作树与"新 HEAD + 补丁"结果逐字节一致时，清房复验可直接在
  （工作树副本 → 还原改动文件为 HEAD 原版 → `git apply`）上跑，比重新拉全仓快得多。

## 方案设计：不要往用户规则上套"通用风控旋钮"（2026-09-09，同一错误犯两次）
- 用户明确偏好：**顺其自然，不限制、不干预、不增加代码复杂度**。资金/交易所会拦的事，代码不要再拦一次。
- 反面案例（连砍两次）：先提议 `max_lock_layers`（锁层数上限）→ 用户"没感觉到哪个场景需要它"；
  再退守 `max_book_legs`（总笔数上限）+ `max_new_trades_per_day`（熔断）→ 用户"不要限制，钱不够自然开不成功，
  消化速度错配不要考虑，没你想得那么严重"。
- **两条具体禁令**：
  ① 别把"现有实现有个 int 字段（如容器容量）"当成"必须设上限"的理由 —— 字段可以表达"不限"（None/0）。
  ② 别做"XX 速度错配 → 会雪球 → 所以要限"这类**基于自己假想场景**的建模，除非用户提出该场景。
- **意外收获模式**：很多"容量/截断类"缺陷（抛错崩溃、静默丢数据、恢复截断）在"取消上限"后**自动消失** ——
  遇到这类缺陷时先问"能不能直接去掉这个限制"，而不是"如何把限制设得合理"。
- 但要区分：**去掉上限 ≠ 功能可用**。硬编码的多仓闸门（如单仓兼容层守护、多仓一律 skip 的 early return）
  属于"功能未完工"，必须逐条列出并说明它们与"要不要限"无关。


## 方案设计：不要给"不存在的自由度"写规则（2026-09-09）
- 典型翻车：用户规则里"平旧仓要平哪一笔持仓"，我写了"混合日期时优先平昨仓"。
  用户一句"昨仓没拆完就不会开新仓，哪来的今日锁"直接戳穿。
- **两条自检**：
  ① 先把状态机推演一遍（M 日 / M+1 日逐日走），能排除的场景就**不要写规则**；
  ② 问一句"这个选择权真的存在吗？" —— 很多"优先级规则"其实是伪选择：
     本例中平哪一笔持仓由**信号方向**唯一决定（必须平反向仓），日期只决定"这笔持仓能不能平"，没有挑选余地。
- 收敛后的正确形态通常是**一行判定式**（如 `反向仓最老一笔 entry_date < today → UNLOCK 否则 OPEN`），
  而不是额外分支。

1. **净敞口取值域**：`Engine.account_state()` 唯一实现 —— `Engine.py:259-263`（`!= 0` → RUNNING；

## 评审自检：给出证据前的三条硬检查（2026-09-18 实测，同日自己犯两次）

14. **频率型改动（把某回调从"每帧数据"改到"每帧"/调换挂点位置）的判据是两个数的比较**（2026-09-18 P68k 改动审新增）。

     不比较就等于只验证了"改完还会不会被调用"，那只覆盖了补丁声称的一半。
   - 反面实例（P68k「空闲泵挂点前移」）：挂点从"每帧数据之后"挪到"每帧（含心跳）之前"，机械上确实修好了
     （A/B 实测：只喂 5 帧心跳，旧版 `on_idle` 调用 **0** 次、新版 **5** 次）。但泵的代价上界 = `keepalive_wait`
     = **0.2 s/次**（`Config.py:474` → `SimNow.py:643` → tqsdk `api.py:2106/2108` + `_fetch_msg:4126-4132`
     「等到非空业务数据包」），而上游心跳的间隔上界 ≈ **0.1 s**（`AppSSE.py:440` 的 100 ms 窗口 + `:452` 每轮无条件发）
     → 消费 5 帧/s < 生产 10 帧/s，积压落在 `SSE.py:42/50-52` 的 `buf`（无上限、不再 `read1`、**不自愈**）
     → 治回报滞后反而造出行情滞后。**新增的挂点与最大阻塞代价落在同一个状态**（上游没数据 ⇒ 才只发心跳；
     同一市场交易侧也没数据 ⇒ 泵等满窗口）—— 这一点必须写进评审，不能只看"更频繁地调用了好回调"。
   - **反证陷阱**：不能拿"系统平时跑得动"否掉上一条。要看**旧挂点本来命中的是哪个状态**：P68k 里 K 线未走完的
     tick 推送分支（`AppSSE.py:523-553`）同一轮会连发 heartbeat+update，旧挂点在那状态下本来就在以同样帧率调泵
     —— 但那正是交易侧有行情、`wait_update` 早早返回、单次代价很小的状态。
   - **另两条判据**：① 挂点位置换了 → 事件交付顺序也换了（本次从"帧后"变"帧前"，本帧事件被推迟 ≤0.2 s）；
     ② "A 组没有、B 组有"不够，**还要看 A 组什么时候有**（旧挂点调 2 次/新版 5 次的差别，才是这次的风险来源）。
     - 落地技巧：这类改动可以用"**假上游 + 真模块**"做 A/B（换掉 `urlopen`，其余代码一行不动），
     无需引擎与网络；细节见技能 `chanpy-trading-engine-verify` §5.3。**顺手一条**：全树哈希比对沙盒 vs 用户项目要
     先做"仅换行差异"归一化，否则 49/51 个文件会被误报成内容差异。

15. **凡是"用 `deadline` / `timeout` / `wait` 参数把等待改成不等待"的修复，判据必须再下沉一层：单次调用"放行多少单位工作"**
   （2026-09-18 P68k v2 复核新增）。第 14 条只算到"单次代价从 0.2 s 降到 ~0"，这在**被等待方是有队列的服务者**时不够：
   代价趋零 ≠ 吞吐够用，还要问"这一次调用把上游队列推进了几格"。
   - 反面实例（P68k `pulse(0)`）：实测空转代价确有改善（`deadline=now` **0.0001–0.0012 s**、事件循环 generation **1**；
     `now+0.2` → **0.2034–0.2087 s**、generation **57699**）。但 tqsdk 的 ws 收包循环
     （`connect.py:187-191`）每收一包前 `await self._api._wait_until_idle()`，而 `_run_until_idle`（`baseApi.py:96-98`）
     **每次只 pop 一个** `_wait_idle_list` future（`probe_pops.py` 实测：预置 1/5/50 个 future，`pulse(0)` 恒 pop **1**；
     0.2 s 窗口能把预置量弹满）→ **一次 `pulse(0)` 只放行 ≤1 个 ws 报文**，且 md 与 trade 共用同一条 md ws
     （`api.py:3720` → `multiaccount.py:132-144` 串行下发）→ **整连接吞吐上界 ≈ 帧率**（AppSSE `:440` 100 ms 窗口 ≈10/s）。
     结论不是"v2 错了"，而是"v2 少测了一个维度"：报文速率 / `_ws_md_recv_chan.qsize()` / `otg_latency` 三选二必须实测。
   - **推广判据（三个问题，缺一即未验证）**：① 这次调用**把服务方队列推进几格**？② 那个计数是**每次调用固定值**还是
     **按剩余量弹满**（决定"够不够"能不能靠提高调用频率补）？③ 服务方是**独占**还是**多消费者共用**（共用时单消费者
     的频率上界 = 全局上界）。
   - **顺手记一条本机坑（Windows + asyncio 实测类探针必踩）**：`asyncio.new_event_loop()` 在 Windows 返回
     **`ProactorEventLoop`**，其 `_loop_self_reading` 靠 future 回调自续，每次 `stop()` 都 `_event_rev+1` →
     tqsdk `_run_until_idle` 的 `while _check_rev != _event_rev` **永不收敛**（实测 `deadline=now+0.2` 空转 57699 次、
     `deadline=now` 直接卡死，`faulthandler` 抓到 `_check_rev=5999/_event_rev=6003`）。**探针里必须显式
     `asyncio.SelectorEventLoop()`**（与 `baseApi.py:25` 一致），否则测出来的"慢"是本机 loop 的假象。

     cp314 的 numpy 会 `ImportError: numpy._core._multiarray_umath`。
