## 二、铁律（一句话版；完整版见 `memory-rules.md` 同编号）

1. **绝不直接改用户项目目录** —— 改动写沙盒，交付用 zip，合并永远用户自己做。
2. **交付 = zip**（按仓库原目录层级），不出 patch/diff；细则见 `memory-workflow.md` §交付格式。
3. **Bash 每条命令开头加** `export PATH="/usr/bin:/bin:/usr/local/bin:$PATH"`；**打包一律用 Python `zipfile`**；**含反引号的内容别走 shell**（会被命令替换吃掉且退出码仍 0）。
4. **同一文件多处改动串行 Edit**（一条消息一个）；改完用 Grep 确认无残留旧符号。
5. **改 chan.py 前先读 `memory-chanpy.md` 术语护栏**，改完重跑 `test_p26_terminology_guard.py`。
5.5. **改完代码必跑门禁 `Test/run_all.py`**（退出码 0/1 即判决）；新写的测试不会自动进门禁。
6. **断言"代码里没有 X"之前先 grep**（≥2 组关键字 + 文件:行证据），给不出证据就写"待确认"。
6.5. **只认代码、注释不算证据**；结论落到可执行分支 + 文件:行号。
6.6. **报问题先给背景** —— 第一句写"什么条件下才会发生"；给不出可达路径不许当缺陷报。
7. **新规则插靠前，绝不 append**；**本文件 ≥4,500 字符立刻再拆**；**加铁律前先量字符数**。
8. **开工前置检查** —— 接到任务先过第一节索引表再动手。
9. **引用即注明** —— 读过哪个子文件，在回复里写明读了哪节。
10. **交付文档必须能下载到本地**（内联图/表离线可渲染）；含生成式图 → HTML+JSON，纯散文 → MD 单文件。
11. **新增/改文件前两套对齐**：分层单向依赖（下层定义 SSOT）+ 命名照抄同目录多数派。
12. **不写开场白/结尾**，直接给结论、改动、证据。
13. **不加代码解释摘要**，不复述已列内容。
14. **不写"我犯了错/如何改进"类过程叙述**，只留结论性事实。
15. **新功能先调研**（GitHub + 官方文档），方案里给调研证据，禁止凭印象设计。
16. **因果正序**：正确性决定改不改，**不许拿"改动面大/牵连多"当不做的理由**。

> 每条的**理由、反例、落点**都在 `memory-rules.md` 同编号条目下 —— 别只凭这一句话执行。
