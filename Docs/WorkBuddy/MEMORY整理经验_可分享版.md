# 让 AI 真的"记住"：MEMORY 文件的三层整理法

> 一份实操记录：741 行 / 42 KB 的长期记忆 → 压到 54 行 → 12 天后涨回 104 行 → **二次拆分后 58 行 / 2,433 字符**。
> 内容一个字没删，能被 AI 看见的比例从 11% 提到 100%。
>
> 环境：WorkBuddy / Claude Code 这类"带持久记忆文件"的 AI 助手。
> 其他助手只要也有"每轮自动读取一个记忆文件"的机制，道理完全一样。
>
> ⚠️ **2026-09-27 复查**：拆完第 12 天回涨到 104 行 / 4,944 字符，**再次被截断**，
> 连索引表都没进上下文；**当天已按 §5 的方法二次拆分修好**（见 §5.1）。
> 文内 09-15 的数字均为整理当天快照；阈值口径、维护节奏、**主文件形态**均已按复查结果修订。

---

## 0. 一句话

**记忆文件不是"写得越多越有用"，而是"前 N 个字符才有用"。**
所以正确的形态不是一本越写越厚的笔记，而是**一张短到能读完的索引 + 一堆按需查阅的专题文件**。

---

## 1. 问题：你记的东西，AI 可能根本没看到

我实测到的情况（WorkBuddy，`~/.workbuddy/MEMORY.md`，**2026-09-15 当天实测**）：

| 项 | 数值 |
|---|---|
| 磁盘上的记忆文件 | 741 行 / 42,129 字符 |
| 每轮真正注入 AI 上下文的 | **前 4,733 字符**（约 11%） |
| 被静默丢弃的 | **89%，32 个章节** |

三个要命的特征：

1. **静默截断，不报错**。AI 那边看到的是一份"完整文件"，它不知道后面还有内容 —— 所以你不能指望它说"我的记忆被截断了"。
2. **从尾部砍**。越晚写进文件的东西，越早消失。
3. **每轮全量注入**。它不像技能/文档那样"用时才读"，而是每轮硬塞一次，所以必须短。

**推论（最反直觉的一点）**：
如果你习惯把新经验**追加到文件末尾**，那等于**写进黑洞** —— 我过去半年犯的就是这个错，新规则全在最后 500 行里，一条都没生效过。

---

## 2. 前提：先分清"自动注入"和"按需加载"

整理之前，先搞清楚你的 AI 在哪几层放东西，因为它们的触发方式完全不同：

| 层 | 怎么进上下文 | 要不要你提醒 AI |
|---|---|---|
| 记忆文件**主体** | 每轮自动全量注入 | 不需要，100% 生效 |
| 记忆**子文件** / 项目记忆 | **不自动注入**，要 AI 主动去读 | 需要索引提示，可能漏 |
| 历史对话检索 | AI 主动调工具才查 | 需要你说"上次那个 XX" |
| 技能 / Skill | 描述常驻，**正文按需加载** | 不需要你打命令 |

**关键区别**：记忆是"塞"，技能是"取"。
所以**长内容应该做成技能（按需加载）**，而不是塞进记忆；记忆里只放"必须每轮都知道"的东西。

---

## 3. 做法：铁律 + 索引 + 子文件

### 3.1 主文件只留三样东西（**顺序不能变**）

1. **索引表**（一张表，**必须放在最前面**）—— "命中什么主题词 → 读哪个子文件"。
2. **铁律**（**一句话版**）—— 违反就会出事的硬约束，每条只留**可执行动作**；
   理由 / 反例 / 落点搬到子文件，主文件标 `→ 见 xxx.md 同编号`（具体做法见 §5.1）。
3. **分层说明**（3~4 行）—— 以后新东西该往哪儿写。

**为什么索引表必须排在铁律前面**：铁律会越加越多（我 12 天从 7 条涨到 16 条），
而截断是从尾部砍的 —— 索引表一旦排在后面，就是**整套方法的触发机制自己先被砍掉**（见 §5）。

**判断标准**：主文件压到注入预算的一半以内 —— 但**别真按"一半"来规划**，
要按回涨速度留余量（见 §5，我用"一半"这个标准，12 天就破了）。

⚠️ **口径：一律数字符，不要数 KB。**
中文 UTF-8 下 1 字符 ≈ 3 字节，用 KB 判断会把"刚超预算"看成"还很宽裕"：
这份现在 4,944 字符（已超 4,733 预算），按字节算是 9.67 KB，
看着像"离 4.7 KB 预算还差得远"——正好相反。
整理当天我自己在两个地方记下 2.3 KB 和 3.4K 字符两个数，就是被这个口径坑的。

### 3.2 索引表模板（可直接抄）

```markdown
| 命中什么 | 读哪个文件 |
|---|---|
| **铁律的完整版**（理由 / 反例 / 落点） | `memory-rules.md` |
| 交付 / 评审 / 方案设计 | `memory-workflow.md` |
| 本机环境坑：Shell、编辑器、打包 | `memory-env.md` |
| Git 拉取、diff、代码评审 | `memory-github.md` |
| 某个业务域的专业规则 | `memory-domain.md` |
```

配套一句硬话，写在文件最开头：

> 命中主题词时**必须**先 Read 对应子文件再动手，不许凭印象作答。
> 子文件不会自动注入，不读 = 这条记忆不存在。

还有一句（09-27 补）：**索引表要放在主文件第一节，别排在铁律后面**。
位置这事儿比内容更容易被忽略，但它决定了后面所有子文件还有没有机会被读到。

### 3.3 子文件怎么分组

按**"什么时候会用到"**分，不要按时间或字母分。我的分法供参考：

| 文件 | 装什么 |
|---|---|
| `memory-workflow.md` | 做事方式：交付规范、评审方法、方案设计禁忌 |
| `memory-env.md` | 环境坑：Shell、编辑器、编码、打包工具的已知故障 |
| `memory-domain*.md` | 业务域专业事实（按领域拆，一个领域一个文件） |
| `memory-projectX.md` | 某个具体项目的现状、基线、目录结构 |

每个子文件开头写一句：**"本文件不常驻上下文，按需读取"** —— 免得后来的自己（或别的 AI）误以为它自动生效。

### 3.4 铁律的写法

三条标准：

- **可验证**：写"每条命令前加 `export PATH=...`"，别写"注意环境问题"。
- **带日期**：`2026-09-15 拍板` —— 以后能判断这条是否已过时。
- **不写废话**：一条铁律一句话讲不完，说明它该进子文件。

## 4. 四条维护纪律（比整理本身更重要）

1. **新规则插在靠前位置，绝不 append 到末尾。**
   这是整套方法里最值钱的一条 —— 前面说的 89% 就是被这个习惯吃掉的。
2. **主文件接近预算就再拆。（修订：阈值取 ≥4,500 字符，别按"预算一半"算）**
   别等它涨到 741 行才动手 —— 我原来按"预算一半"定阈值，12 天就破了（见 §5）。
3. **引用即注明：AI 读了哪个子文件，就在回复里说出来。**
   这条让"漏查"变得可监督 —— 你一看回复就知道它到底查没查。
4. **每次往主文件加东西之前，先量一次字符数。**
   加之前量，不是加之后量 —— 事后再量的人，12 天后总会发现量晚了（见 §5）。

## 5. 拆完还会长回来：12 天实测（2026-09-27 复查）

整理完很容易以为"一劳永逸"。12 天后实测：

| 项 | 整理当天（09-15） | 12 天后（09-27） |
|---|---|---|
| 主文件 | 54 行 / 约 3.4K 字符 | **104 行 / 4,944 字符** |
| 铁律条数 | 7 条 | **16 条**（还冒出 5.5 / 6.5 / 6.6 这种插队编号） |
| 本轮实际注入到 | 全文 | **第 81 行中段（≈4,04x 字符）** |
| 没能进上下文的 | 无 | **索引表（85-92 行）+ 分层说明（94-104 行），整段** |

回涨速度：**约 130 字符/天**，12 天正好吃掉 1.5K 字符的余量。

三个教训：

1. **触发机制自己会被截断。** 整套方法靠"主文件里的索引表提醒 AI 去读子文件"，
   而索引表在主文件偏后位置 —— 一旦长回来，**先被砍的就是它**。
   所以索引表要放在主文件**最靠前**的位置，不能排在铁律后面。
2. **"铁律只留 7~10 条"会被现实碾过去。** 12 天到 16 条，而且每条都在加长
   （带例外、带子条款）。真正该盯的不是条数，是**总字符数**。
3. **插队编号（5.5 / 6.5）是饱和信号。** 它说明"新规则插靠前"这条纪律正在被执行，
   也说明主文件快满了 —— 出现第二个插队编号时就该拆了。

**修订后的阈值**（替代 §3.1 的"预算一半"）：

- 主文件 **≥ 4,500 字符** → 立刻拆，不等；
- 出现**第二个插队编号** → 立刻拆；
- **每加一条铁律前先看一眼当前字符数** —— 这条动作要写进主文件铁律本身，
  否则它自己也会被忘掉。

### 5.1 怎么修的（2026-09-27 当天执行）

上面这套阈值定完当天，我自己就踩线了，于是当场拆了第二次。结果：

| 项 | 触顶时 | 二次拆分后 |
|---|---|---|
| 主文件 | 104 行 / 4,944 字符 | **58 行 / 2,433 字符** |
| 铁律 | 16 条完整正文（约 4,000 字符） | **16 条一句话摘要**；完整原文搬到新子文件 `memory-rules.md`（4,051 字符，零删减） |
| 索引表位置 | 第二节（85-92 行，被截断） | **第一节**，第 140 字符处就出现 |

两个上次没写、这次才摸索出来的做法：

1. **铁律做"摘要 / 详情"分离。**
   铁律天然会膨胀（12 天 7→16 条，正文近 4,000 字符），主文件放不下、又一条都不能删 ——
   那就**主文件只留一句话**（只保留可执行动作，如"每条命令开头加 `export PATH=...`"），
   **完整版（理由、反例、子文件落点）整段搬进 `memory-rules.md`，编号一一对应**。
   主文件按字符数收敛，"为什么这么定"却一条没丢。
2. **索引表提到第一节，排在任何内容之前。**
   §3.1 原来的顺序是"铁律 → 索引表 → 分层"，长回来时先被砍的正是索引表。
   现在它是全文第一个内容块 —— 只要注入没被砍到只剩标题，索引表就一定在。

**顺带修正一个更根本的认知错误**：
我原来把"注入上限"当常数（4,733），所以才敢按"预算一半"规划。
但这次实测只进到 **≈4,04x 字符**（09-15 测的是 4,733）——
**上限会随系统 prompt 开销、会话状态浮动，不是固定值**。
所以"按预算的一半留余量"这个算法本身就不成立；
真正该做的是三件事：**盯实测字符数 + 给一条触发线（≥4,500 就拆）+ 把最关键的那一块放最前面**。

## 6. 我踩过的坑

| 坑 | 后果 |
|---|---|
| 新经验一律追加到文件末尾 | 89% 的内容从未生效 |
| 把长篇操作流程写进记忆 | 挤占预算，且它是"每次都读"，浪费 |
| 子文件不写"不常驻"的提示 | 后来的会话误以为它自动生效，不去读 |
| 拆分后没备份原文 | 无法比对是否丢了内容 |
| 拆完不做关键词抽查 | 搬漏了也不知道 |
| **以为拆一次就一劳永逸** | 12 天回涨 1.5K 字符、再次触顶，索引表被截断（见 §5） |
| **用 KB 而不是字符数判断体积** | 中文下 1 字符≈3 字节，把"已超预算"误判成"还很宽裕" |
| **索引表放在铁律后面** | 长回来时它最先被砍，整套方法的触发机制跟着失效 |
| **以为铁律必须整条写进主文件** | 条数一涨（7→16）正文就撑爆主文件；应做摘要/详情分离（见 §5.1） |
| **把注入上限当固定常数** | 实测 09-15 是 4,733、09-27 是 ≈4,04x —— 按"预算一半"留余量的算法不成立 |

## 7. 怎么验证你整理好了

拆完跑这六个检查，缺一不可：

1. **章节计数**：拆分前后 `## ` 数量要对得上（我这次 47 → 51，多出的 4 个是新加的小节，能对上账）。
2. **关键词抽查**：每个子文件抽查 3~5 个"只可能在这里出现"的硬词（错误码、文件名、配置项），全命中才算搬完。
3. **预算检查（按字符数，不按 KB）**：主文件字符数**明显低于触发线**（我的线 4,500，拆完 2,433）。
   ⚠️ ① 中文 UTF-8 下 1 字符 ≈ 3 字节，用 KB 量会得出完全相反的结论（见 §5）；
   ② **别按"注入上限的一半"算** —— 上限会浮动（两次实测分别是 4,733 和 ≈4,04x），见 §5.1。
4. **备份**：拆之前先复制一份 `MEMORY.full-<日期>.md`，随时可还原比对。
5. **回涨检查（拆完之后每轮都要跑）**：主文件 ≥4,500 字符、或出现第二个插队编号 → 再拆。
   这条是 09-27 复查补的 —— 前四条只保证"拆完那一刻是对的"，不保证一周后还对（见 §5）。
6. **索引表位置检查**：索引表必须在主文件**前 1/3** 内（我这次在第 140 字符处）。
   主文件只有"前 N 字符"有效 —— 位置靠后的索引表，等于没有索引表。
   若铁律做了摘要/详情分离，还要抽查**两侧编号一一对应**（主文件 16 条 ↔ 子文件 16 条）。

## 8. 转述话术

### 30 秒版

> AI 的记忆文件每轮只被读前几千字符，超出部分**静默丢弃、不报错**。
> 所以越往文件末尾写的东西越白写。正确做法是：主文件只留**铁律 + 一张索引表**，
> 详细内容拆成子文件按需查。我这么整理后，记忆文件从 741 行压到 54 行，
> 能被 AI 看到的内容从 11% 变成了 100%。
> 但得补一句实话：**这个 100% 只维持了 12 天** —— 主文件回涨到 4,944 字符又超预算了。
> 于是我又拆了第二次：铁律改成"主文件一句话摘要 + 子文件完整版"，索引表移到最前面，
> 现在 58 行 / 2,433 字符。所以**拆不是一次性的事，是一套要定期跑的维护动作**。

### 3 分钟版（加四个要点）

> 第一个要点：**先分清"塞"和"取"**。
> 记忆文件是每轮硬塞进上下文的，必须短；技能/文档是用的时候才读的，可以长。
> 所以长流程要做成技能，别写进记忆。
>
> 第二个要点：**光拆开还不够，得有触发机制**。
> 子文件不会自动读，靠的是主文件里那张索引表提醒 AI 去查。
> 我加了两条自我纪律：一是接到任务先过一遍索引再动手；
> 二是读过哪个子文件要在回复里注明 —— 这样你一眼就能看出它漏没漏。
>
> 第三个要点（12 天后补的）：**索引表必须放在主文件最靠前的位置**。
> 主文件会长回来，而它偏后的部分先被砍 —— 我这次就是索引表被整段截掉，
> 于是后面 7 个子文件一个都不会被读到：**触发机制自己失效，是最要命的一种失效**。
>
> 第四个要点：**铁律会膨胀到放不下，那就做"摘要 / 详情"分离**。
> 主文件每条只留一句可执行动作，理由、反例、落点整段搬进 `memory-rules.md`，编号对应。
> 既守住了字符数，又一条经验都没丢。顺便修正一个认知：**注入上限不是固定值**
> （我两次实测分别是 4,733 和 ≈4,04x），所以别用"预算的一半"这种算法规划 ——
> 盯实测字符数、给一条触发线（≥4,500 就拆）、把最关键的那块放最前面，比算百分比靠谱。

## 附录：拆分可以脚本化

要点（Python，约 60 行）：

1. 按行首 `## ` 切块，得到 `(标题, 正文行)` 列表；
2. 建一张 `(标题关键词 → 目标文件, 排序号)` 映射表；
3. **未匹配的章节必须 assert 失败并退出**（这条最关键 —— 防止写盘时才知道漏了）；
4. 每个子文件加 header 说明"不常驻、按需读"；
5. 写完后跑关键词抽查，全绿才算完；
6. 第一步永远是 `shutil.copy2` 备份原文。
