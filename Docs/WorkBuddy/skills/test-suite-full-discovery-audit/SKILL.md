# 测试全量发现式审计

面向这类请求：「把 `X/` 和 `Y/` 下所有测试全跑一遍」。核心不是"跑"，而是
**跑完能说清每一条红的性质**，并揪出那些**因为从没被跑过、所以从没人发现**的破损用例。

## 铁律

1. **先问"仓库有没有现成入口、它覆盖多少"，再决定要不要新写脚本。**
   入口名字极其常见但不通用（`run_all.py` / `check.py` / `ci.sh`）——先读它的**注册表**，
   再和"按前缀发现"的结果做**差集**。
2. **别急着把发现式逻辑并进既有门禁脚本。** 注册表里往往有意为之的例外：
   缺陷未修故不注册（注册即恒红）、需要真连外部系统、恒 0 无门禁能力。
   一旦自动发现，`退出码 0 = 门禁绿` 这个契约当场失效，文件里那些"暂不注册"的注释也一起失真。
   正确做法：**门禁脚本不动，另开一个全量发现脚本**，两者分工写清楚。
3. **"在不在注册表里"常常本身是被引用的契约**（其它文件靠"未注册"来标识"这条还不合格"）。
   改之前 grep 一遍 `run_all`/`注册` 之类的自标识注释。
4. **逐文件独立子进程**：这类用例多在顶层改 `sys.path` / `sys.stdout` / monkeypatch，
   同进程连跑会互相污染。别试图用 pytest 收编（先数一下 `import pytest` 有几个）。
5. **相对路径 → 绝对路径**：`--json` 之类的输出参数在 git-bash 风格路径下会被 Windows
   Python 解析失败，报告写不出来。自己把路径规范化。

## 步骤

### 1. 算覆盖差集（回答"能不能只改既有入口"）

```
注册集合 = 解析 run_all 的注册表（正则抓 os.path.join("a","b","c")）
发现集合 = 按前缀 (test_/repro_/smoke_) 遍历目标目录
报出：交集 / 只注册未发现 / 只发现未注册
```

只注册未发现的那些，**名字通常不带前缀**（`*_runner.py` / `*_check.py` / `_mutate_*.py`），
任何自动发现逻辑都扫不到 → 这就是"不能合并"的硬证据。

### 2. 建全量 runner（单文件，放仓库根）

必备件（缺一个就会在真实仓库上翻车）：

| 能力 | 要点 |
|---|---|
| 抽干输出 | `Popen(stdout=PIPE, stderr=STDOUT)` + **独立读线程**。用 `subprocess.run(timeout=)` 会踩下面那个坑 |
| 孤儿管道兜底 | 子进程退了但**孙子进程还握着 stdout** → `communicate()` 等 EOF 永远等不到。子进程退出后再给管道 3 秒，仍不 EOF 就杀进程树（Windows `taskkill /F /T`，POSIX `killpg`）**并继续跑下一条** |
| `stdin=DEVNULL` | 用例不可能卡在等控制台输入 |
| 独立进程组 | Windows `CREATE_NEW_PROCESS_GROUP`；控制台 Ctrl+C 不把用例撕成半截 |
| Ctrl+C 安全 | 捕获 `KeyboardInterrupt` 后照常打印逐条清单 + 汇总 + "还剩几条没跑"，照常落 `--json`，退出码 **130**。旧版一中断，已完成的几十条结果**全部丢失** |
| 凭据隔离 | 默认在子进程环境里清掉真实账号变量（`SN_ACCOUNT`/`TQ_PASSWORD` 之类）。"只想构造对象注 FakeApi"的用例，在凭据齐全的机器上会**真的登录外部系统**。要真连的用例给 `--keep-credentials` |
| 单条超时 | 兜底防某条连网卡死拖住整轮 |
| **子进程 `PYTHONUNBUFFERED=1`** | 管道上 Python 默认**块缓冲**（约 8KB）→ 跑到一半的进度一条都传不上来、被强杀时那几 KB 直接丢。**不设它，后面两条都没意义**（见 2.5） |
| **慢/卡分流** | 心跳附上"子进程最后打印的一行"；超过 `--stall N`（默认 20s）自动**倾倒它当前全部输出一次**；`--diag` 让子进程带 `faulthandler` 打 Python 栈（见 2.5） |
| 前后工作区对比 | 跑前跑后 `git status --porcelain`，把"跑测试新产生的改动"列出来（不是 git 仓库就降级跳过） |

### 2.5 「慢」与「卡死」必须当场分得开（否则用户会误判成"你的脚本挂了"）

**症状**：用户跑全量，卡在某条不动，于是 Ctrl+C，然后来问"是不是这条坏了 / 你的脚本卡死了"。
实际那条只要 1 秒，而且**问题根本不在那条用例上**。

**根因（观测缺陷，不是代码缺陷）**：子进程 stdout 是**管道**，Python 在管道上默认**块缓冲**（约 8KB）。
于是 ① 用例正在跑时进度**一条都传不上来**；② 被强杀 / 超时时缓冲区里那几 KB **直接丢失**，
失败尾部是空的。结果「慢」和「卡死」在控制台上一模一样。

**先算一遍再下结论**（这条算术是排除"卡死"最快的办法）：
把已完成条目的耗时**逐个相加**，与整轮实测总耗时比 —— 如果两者几乎相等
（实测案例：62 条耗时合计 113.4s，整轮 114.1s），说明**最后那条只跑了几分之一秒就被外部中断**，
即人为 Ctrl+C，而不是它卡住。再单独把那条跑一遍（连跑 10 次取耗时区间）即可结案。

**三件套修法**（缺一仍会误判）：

1. 子进程环境强制 `PYTHONUNBUFFERED=1`（**前提**）；
2. 心跳不只报"运行中 Ns"，**附上它最后打印的一行**（没有则明确写「尚无输出」）；
3. 超过 `--stall N` 自动**倾倒它当前的输出** —— 倒出来有多行进度 = 慢；只有一两行 = 卡在下一行。
   `--diag` 再让子进程带 `faulthandler`（在**子进程内部** `faulthandler.enable()` +
   `faulthandler.dump_traceback_later(n, repeat=True)`，用 `runpy.run_path(p, run_name="__main__")`
   保持"直接执行脚本"的语义），到点打印所有线程的 Python 栈 —— 这是"卡在哪一行"的唯一硬证据。

**自测必须用正/负两个样本**（只测"卡"分不出"慢"）：

| 夹具 | 构造 | 期望 |
|---|---|---|
| 慢但有输出 | 每 3s 打一行进度、共 ~21s，**故意不 flush** | `--stall 8` 倾倒出 3 行左右 progress；最终 PASS |
| 真卡住 | 打两行后无输出地 `while True: time.sleep(3600)` | 倾倒**只有那两行**；`--diag` 的栈里应出现夹具文件名 + 死循环所在函数名 |
| 关闭开关 | 慢夹具 + `--stall 0` | 全程**无倾倒块**，只有心跳 |

**坑**：`--diag` 下 faulthandler 会自己打一行 `Timeout (0:00:08)!` —— 它**不是**用例超时，
而是**栈倾倒计时器**到期（秒数 = `--stall`），此时用例还在跑。用例真超时的字样必须另起一种
（如 `[TIMEOUT] <文件> 超过 Ns 被终止（已强杀进程树）`）。两种字样混同，用户会把"打栈"读成"超时"。
这条要写进脚本 docstring。

### 2.6 「幽灵 Ctrl+C」：不是我按的，整轮也会被中断（Windows 专有，极隐蔽）

**症状**：全量跑到**固定某一条**（两次完全一致）就打印"收到 Ctrl+C / 中断信号"，
已完成的 N 条结果保留、后面全没跑；用户坚持"键盘鼠标都没动过"。
**该条用例本身完全正常**（单跑秒级通过），而且日志里**连它的输出都没有**。

**根因**：Windows 上 `signal.CTRL_C_EVENT == 0`，于是**`os.kill(pid, 0)` 根本不是存活探测** ——
CPython 遇到 0/1 会走 `GenerateConsoleCtrlEvent`，实际效果是**给该 pid 所在进程组投一次真实的
Ctrl+C**（`pid == 0` 时**广播整个控制台**）。这句被当成"探活"的调用因此产生了真实副作用。

受害者为什么总是"跑测试的那个进程"：

- runner 是**普通控制台进程（Ctrl+C 启用）** → 收到 KeyboardInterrupt → 整轮中断；
- 触发它的用例是 runner 用 `CREATE_NEW_PROCESS_GROUP` 起的 → **该组 Ctrl+C 是禁用的** →
  事件对它无效 → 它自己照样 PASS，于是"凶手毫发无伤、受害者是跑测试的人"。

**为什么极难复现（我在这一步上白跑了两轮）**：需要同时满足

1. **有真实控制台**（`GetConsoleWindow() != 0`）—— 无控制台时 `GenerateConsoleCtrlEvent`
   直接失败，被 `except OSError` 吞掉，看起来毫无异常；
2. **进程的 Ctrl+C 处于启用态** —— 该状态**会继承**（父进程带 `CREATE_NEW_PROCESS_GROUP`
   时后代全都禁用）。agent/CI 宿主演生的进程树通常是禁用的 → 事件投过来也无人响应。

⇒ **要复现就得自己造"真控制台 + 显式打开 Ctrl+C"**：

```python
# 中间加一层 stage1：先打开 Ctrl+C，再原样跑 runner（runpy.run_path(runner, run_name="__main__")）
ctypes.windll.kernel32.SetConsoleCtrlHandler(None, False)   # 关键一行
# 由外层用 CREATE_NEW_CONSOLE + STARTF_USESHOWWINDOW/SW_HIDE 起这个 stage1
```

**定位手法（决定性，且不靠读代码猜）**：装一个 **C 级** `SetConsoleCtrlHandler` 计数，
再对**同一组输入**跑"原实现 vs 候选修复"，比对事件增量：

| 输入 | `os.kill(pid, 0)` 原实现 | OpenProcess 版 |
|---|---|---|
| 自己的 pid | False（把活着的自己判成死） | True |
| 存活子进程 | True | True |
| **pid = 0** | **True + 控制台事件 +1（广播！）** | False + 0 |
| 不存在的 pid | False | False |

**修法**：Windows 用 `OpenProcess(SYNCHRONIZE)` + `WaitForSingleObject(h, 0) == WAIT_TIMEOUT`
纯查询；`pid <= 0` 直接 False；POSIX 保留 `os.kill(pid, 0)`。**别用 psutil 的
`send_signal(CTRL_C_EVENT)` 替代**——它就是 `os.kill(pid, 0)` 的包装（`psutil/_pswindows.py`）。

**runner 侧加固（把致命事件降级为可观察事件）**：收到信号先打**取证块**（第几次、哪条用例、
进入该条多久、当前进程的 `stdin/out/err isatty` 与 `GetConsoleWindow`），并给
`--on-sigint continue`：当前用例记 `[SIG]`、继续跑完，N 秒内第二次才真中止。
**默认仍保持 abort**（不改旧行为）。

**验证必须做 A/B 最小对照**：同一条用例、同一真控制台，只换被测文件 →
"原版 rc=130 / 中断" vs "补丁版 rc=0 / 通过"，再补一次全量（原版中断于该条、补丁版跑完全部）。

### 3. 非零退出四分类（这一步才是价值所在）

| 类别 | 判据 | 处理 |
|---|---|---|
| **设计如此** | 文件头/docstring 写明"需要真实连接""命中即退出 1，故不注册" | 不改，写进报告 |
| **环境缺依赖** | 缺包 → 秒退 `ModuleNotFoundError`；有包 → 真连外部系统 | 靠凭据隔离 + `--keep-credentials` 分开 |
| **行尾假红** | 断言"文本里找到标记"，目标文件是 CRLF（见第 4 节） | 修行尾敏感的**匹配**，不要改目标文件行尾 |
| **输入耦合假红** | 快照/基线用例整片红，diff 是**成千上万个派生值**，而代码没动 | **先别 `--update`**，按 4.5 隔离输入再说 |
| **真缺陷** | 下面这些特征 | 最小修复 + 回归 |

**"从未被跑过"的典型特征**（一命中就是真缺陷）：

- `py_compile` 都过不去（少括号、缩进坏）→ 说明它连一次都没被执行过
- 同目录 N 个兄弟都有 `sys.path` 引导，**只有它没有** → 命令行跑必红 `No module named '<顶层包>'`
- 断言数字是"某个历史点"的，现在早已漂移

**量化"修好了多少"**：修前统计"打勾 N 行就崩、无汇总行"，修后统计"结果: X 通过 / 0 失败"，
直接给出**回补了多少条从未执行过的检查**。

### 4. 整行锚定正则 × CRLF 的静默失效审计（顺带做，一次就够）

失效组合**只有一个**：**读盘时用 `newline=""`（保留原始换行）+ 正则用 `^…$` 配 `re.M`**。
`$` 在 MULTILINE 下匹配 `\n` 之前，而 CRLF 里 `\n` 之前是 `\r` → 整行失配。

- 为什么"只有这一处"说得通：**默认 `open(path, encoding="utf-8")`（通用换行）会把 CRLF 翻成 LF**，
  所以绝大多数守卫天然免疫。会中招的必然是"必须保留原始行尾"的地方（生成器要沿用量到的 `\r\n`，
  否则会把 CRLF 文件改写成 LF）。
- 后果**双向**：断言"找到标记"→ **假红**；断言"零命中"→ **假绿**（更危险）。
- 顺带发现：这类生成器**自己也是坏的**——同一个正则被用来定位区块做替换，CRLF 文件上直接
  `ValueError("缺少标记")`，表现为"生成器跑不了但没人发现"。

**修法（关键细节）**：把 `[ \t]*$` 改成 `[ \t]*(?=\r?$)`（**前瞻**）。

- ❌ 别写成 `[ \t]*\r?$`：它会把 `\r` 吃进 match，`m.end()` 偏移右移一格，
  之后 `head + nl` 就拼出 `\r\r\n`。
- ✅ 前瞻不消费字符，`m.start()/m.end()` 偏移与 LF 场景完全一致，替换后文件仍是 CRLF。

**验证（必须逐字节）**：取真实 CRLF 文本与它的 LF 版本各跑一次"用原文区块重建"，
断言**产物与原文本逐字节相同**、行尾不变；再断言 `text[m1.end():m1.end()+3] == '\r\n'`。
最后跑一次真 CLI 的校验模式（`--check` → rc=0），并用"篡改一个数字 → rc=1"证明护栏真会咬人。

审计扫描法：`grep -n "re\.M\b|re\.MULTILINE"` 找多行正则，`grep -rn 'r"[^"]*\$"\s*[,)]'` 找
`$` 收尾字面量，两集合求交 → 逐个确认它扫的是哪个文件、那个文件是什么行尾、怎么读的。

### 4.5 快照 / 金标准基线：先隔离「运行时可调输入」，再谈刷基线

**症状**：一串快照用例整片红，diff 里是**成千上万个派生值**（K 线字段 / 索引 / 笔端点全变），
看起来像算法被改坏了。**这时最危险的动作就是 `--update`** —— 盲刷会把真漂移一起冻成基线。

第一步不是问"算法哪里变了"，而是问"**输入是不是运行时可调的**"：

- 这类输入的共同特征：**界面上可调 / 默认值随版本变 / 能被环境变量覆盖**。
  典型：回看窗口条数、分页大小、超时、阈值。
- 判据是**读出它的定义处与读取处**（模块级全局 vs 启动时注入），确认它真的改变了被快照的数据窗口。
- **反例警告**：别按配置名猜作用点。本会话我按名字写了 `m.FUTURES_LOOKBACK_CONFIG = {}`，
  可该符号**根本不在那个模块的命名空间**（由启动时经 setter 注入到下层）——典型**死代码**，
  只因外面套了 `if getattr(m, NAME, None) is not None` 才没报错。改完必须用"实测值真的变了"
  （如 K 线根数 500→472）自证生效，而不是"我改了、它应该生效"。

**决定性实验（判定"输入变了"还是"算法变了"）**：把该输入**钉回旧值**再跑一遍，看能否**逐值复现旧基线**。

- 能复现（只剩本次有意新增的字段差异）⇒ **纯输入变化**，可以放心重冻。这句话就是交付说明里
  最有分量的一条证据，比读代码争论快得多。
- 不能复现 ⇒ 真有行为漂移，**别刷基线**，先查。

**修法：让基线跑在「测试自己拥有」的输入上**，而不是"宿主机当前配置"。

- 采集期把该输入置为"不约束"（如窗口置空=不截断），用毕还原；夹具即窗口。
- 为什么非改不可：基线一旦与"可调默认值 / 环境变量"绑定，**同一份代码在不同机器上就产出不同快照**
  —— 这是比"红"更糟的假红 / 假绿。
- 仓库里若**已有另一个入口**这么做，两个入口必须统一口径（本会话 `test_trigger_step_replay`
  早就写了 `= {}`，而 `snapshot_runner` 没有 —— 同源数据两套政策，正是要收口的地方）。
- **把代价说清**：重冻后基线会**一次性质变**（数据窗口变了），此后只在算法变时才动；
  被换掉的是"该输入自身行为"的覆盖 —— 若它在别处没被覆盖，要么补一条直接断言，要么
  明确告知"这条覆盖换成了确定性"。

**两个必带细节**：

- 刷基线前先修 `json.dump` 的 `newline`：Windows 上不写 `newline="\n"` 会把整份文件翻成 CRLF，
  下次 `--update` 就产出"整份都变了"的假 diff。幂等验证 = 连刷两次字节不变。
- **网络 / 日期相关的展示性字段**（名称、PE、指数归属、公告标记）**不能顺手刷原始值**，
  要**打桩成确定值**再刷 —— 否则换台机器、隔天、断网就变。
- 多个入口各自复制一份"参考数据注入"函数，就是"同一个展示性字段这处刷了、那处漏刷"的成因：
  **合并成单一来源**（后者 `import` 前者），以后新增字段不会再只修一半。

### 5. 打包交付

- 以**用户仓库的原始字节**为基线做定点替换（断言"命中且仅命中一次"），**保留该文件自己的行尾**——
  同一个仓库里 CRLF/LF 是混的，沙盒副本的行尾经常与用户仓库不一致。
- zip 内按**仓库原目录层级**，不出 patch/diff，不放 `.md` / `__pycache__` / 运行时产物。
- 打包后**解压到独立临时目录**逐字节复验：md5 + 行尾 + 语法编译。
- 覆盖方式写清楚：解压到仓库根直接覆盖。
- 全量回归对比要能回答"**除预期条目外，其余逐条退出码不变**"。

## 报告模板

```
## 三处缺陷（都在用户仓库实测复现，非沙盒假象）
① 文件:行 —— 现象 / 根因 / 性质 / 改法（附修复后输出）
## 修复前后覆盖量对比        （打勾 N → X 通过 / 0 失败）
## 全量回归（112 条）        （通过数、非零数、超时、孤儿管道；退出码变化的只有这 N 条）
## 仍非 0 的条目定性          （设计如此 / 环境 / 未决）
## 中断或"卡住"的定性          （已完成耗时算术 → 是外部 Ctrl+C 还是真卡；慢用例单独重跑耗时区间）
## 顺带审计结论              （CRLF 盲区只剩这一处 + 为什么只有这一处）
## 覆盖方式                  （zip 清单 + md5 + 自验命令）

```

## 坑

- `/tmp` 在 git-bash 下与原生 Windows Python 看到的路径**不是同一个**，临时文件用显式 Windows 路径。
- 探测脚本自身也会出错（如 `py_compile(cfile=os.devnull)` 在 Windows 不被接受）——把探测当成会错的代码来写，异常里要能看出是"探测工具坏了"而不是"被测对象坏了"。
- 别把"我没跑起来"报成"它坏了"：先在**用户仓库 + 用户解释器**下复现一次再下结论。
- 用户报"卡在 X 了"时，**先算耗时算术再查 X**（见 2.5）。多数情况 X 无辜，
  真正的问题是"进度看不见"；把观测补上比去改 X 有用得多。
- 用户报"**我没按 Ctrl+C，它却收到 Ctrl+C**"时，别急着归因为"用户误触"（我这么判过一次，
  被下一份日志直接推翻）。先看是不是**每次都在同一条**——那是确定性触发，去查被测代码里的
  `os.kill(pid, 0)`（见 2.6）。**"我这边复跑不复现"很可能只是因为我的环境收不到控制台事件**，
  不代表用户那边不是真 bug；把复现条件（真控制台 + Ctrl+C 启用）补齐再下结论。
- 定性出"**查询动作夹带副作用**"这类缺陷后，收口动作是**补一条能自证的护栏**，不是只写进
  交付说明 —— 见 `side-effect-invariant-guard`（AST 平台分支划分 + 调用计数桩 +
  源码/运行时双重变异自证）。注意**只看返回值抓不到这类 bug**：旧实现在真控制台里
  返回值也是对的，只是顺带投了一次 Ctrl+C。
- **"交付形态复验"要连 runner 本体一起放进临时树**：只解压交付文件、基底树里又漏拷
  `run_all_tests.py` 时，子进程会以 `rc=2`（python 找不到脚本）返回 —— 那是**假红**，
  不是用例失败。判据：`rc=2` + 输出里没有任何逐条结果 ⇒ 先检查"脚本在不在"。
- **全量 runner 必须用"依赖齐全的那个解释器"启动**（子进程继承它）。本会话先用缺 `fastapi`
  的解释器跑，`test_api_integration` / `phase2_guards` / `phase3_guards` 三条秒退报
  `ModuleNotFoundError` —— 那是**环境缺依赖**（上表第 2 类），与用例好坏无关。
  开跑前先 `python -c "import pandas, fastapi, tqsdk"` 探一遍，别把这类红算进结论。
- 结论性的"K 线根数 / 窗口长度"这类数字，**用实测值说话**（改前 472、改后 500），
  不要只写"已隔离该配置"—— 后者无法证伪。
