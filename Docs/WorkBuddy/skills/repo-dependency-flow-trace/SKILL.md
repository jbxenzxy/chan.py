# 第三方库调用链路溯源

用户问「哪个流程用到 X」时，**要的不是 grep 结果列表，而是「哪条业务流程会真的走到它」**。
一个 `import X` 出现在 5 个文件里，可能只有 1 处是活的，另外 4 处在注释里。
所以必须做三层收敛：**grep 撒网 → 死活判定 → 沿调用者上溯到用户入口**。

## 铁律

1. **区分"提到"和"调用"**。注释、docstring、`.md`/`.html` 文档、requirements.txt 都不算调用。
   判定一行是否活着：`not line.lstrip().startswith('#')` —— 但**还要排除 docstring 内**，
   否则会把大段说明文字当成代码（本方法在 chan.py 上实测：5 行"未注释"里 5 行全是 docstring）。
   最可靠的是 `ast.parse` + 遍历真正的 Import 节点。
2. **懒导入必须报出来**。`import X` 写在函数体内 vs 模块顶层，行为完全不同：
   - 顶层 → 缺 X 直接 ImportError，服务起不来；
   - 函数内 → 缺 X 只是该功能静默降级，**启动毫无异常**。
   这是"该不该进运行必需依赖清单"的关键判据。
3. **上溯到用户可感知的入口为止**。停在 `TdxAPI.xxx()` 不算答案，
   要一路走到 `前端按钮 → HTTP 路由 → App 编排层 → DataAPI → 库`。
4. **必须做缺失依赖实证**。在没装该库的环境里把入口函数真跑一遍，
   记录它**是抛错还是静默返回空**。静默降级是最危险的形态，必须写清。
5. **检查 import 语句相对「分支出入口」的位置 —— 这是最隐蔽的一类缺陷。**
   懒导入只解决了「模块能否 import」，没解决「函数会不会白跑」。若写法是
   ```
   try: from X import Y          # ← 在本地缓存/短路分支之前
   except ImportError: return {}  # ← 直接放弃整个函数
   ...读本地文件，压根不需要 Y...
   if need_download: ...用 Y...
   ```
   则缺 X 时**连不用 X 的那半段功能也一起废掉**。chan.py 实测：
   `block_*.dat` 全在本地、`need_download` 为空、X 一个接口都不会被调用，
   但缺 X 仍让结果从 400 只变 0 只。**要判据是「import 行号 vs 该库第一次真正被用到的行号」**
   —— 两者之间有「不依赖该库的可用路径」就是缺陷，修法是把这个 import 下移到真正需要的分支内。

## 流程

### ⓵ 拉取最新代码（GitHub 通道）

`git clone` 在部分 Windows 机器上因 schannel 报 `CRYPT_E_NO_REVOCATION_CHECK` 而失败，
tarball 通道（codeload）经常卡死 + 不支持 Range 续传。**首选 API + raw 逐 blob**：

```python
# 1. 定位最新 commit
GET https://api.github.com/repos/<o>/<r>/commits?sha=<branch>&per_page=10
# 2. 拿全仓清单（含 path/size/sha）
GET https://api.github.com/repos/<o>/<r>/git/trees/<branch>?recursive=1
# 3. 逐 blob 下载
https://raw.githubusercontent.com/<o>/<r>/<branch>/<urllib.parse.quote(path)>
```

三个必做的细节：
- **跳过资源目录**（`Image/` 等），只取文本扩展名 → 328 blob/61MB 可收敛到 282 文件/1.5 分钟。
  （2026-09-11 复测：chan.py 330 blob/64.9MB → 284 文件，**284/284 成功、0 失败**，约 1 分钟。）
- **用 size 做幂等跳过**：`if os.path.exists(dst) and os.path.getsize(dst) == size: continue`，
  中断后重跑即可续传。
- **中文文件名必须 `urllib.parse.quote(path)`**，且**只编码 path 不编码整个 URL**。
  否则 `'ascii' codec can't encode characters` 整批失败（chan.py 的 `Docs/止盈止损/*` 17 个文件）。
- 先 `GET /commits?sha=<branch>&per_page=15` 拿时间戳定位"合到哪个 commit"——
  chan.py 的 commit message 全是「更新」，**只能靠时间戳对齐**。
  顺手把 sha 写进交付报告，用户才知道你看的是哪一版。

### ⓵′ Bash 环境先自检

Windows 上 Bash 工具的 PATH 可能整体没注入，表现为 `shim/shell-runtime-bash-env.sh: dirname: command not found`
+ 所有命令 `command not found`（exit 127）。**先试最省事的绕法**：

```bash
export PATH="/usr/bin:/bin:/c/Windows/System32:$PATH"; ...
```

一行即可恢复 `ls/head/curl/python`。若仍不行，改用 managed Python 绝对路径 + 把 shell 活写进 .py。
另注：PowerShell 工具可能 exit 0 但 stdout 全空，**别在 PowerShell 上反复重试**。

### ⓶ 死活判定（AST，不信肉眼）

```python
import ast
tree = ast.parse(src)
for node in ast.walk(tree):
    if isinstance(node, (ast.Import, ast.ImportFrom)):
        ...  # 这才是真 import
```
再补一遍动态导入（`__import__` / `importlib.import_module`）——字符串拼出来的库名 grep 不到。

同时按"行是否在注释里"做一次快速分类，把**纯注释块**标为死代码候选。

### ⓷ 上溯调用者到用户入口

对每个活的调用点，用 `Grep` 反查谁调这个函数，逐层向上，直到命中：
`前端 fetch/按钮` → `FastAPI/Flask 路由` → `App 编排层` → `DataAPI/适配层` → `库`。

记录**关键行号**（函数定义行 + import 行 + 实例化行），因为函数名可能重名，
行号是唯一能对齐用户阅读位置的锚点。

顺手确认"前置分支"：很多调用是**兜底路径**（如 `Step4: infoharbor 不可用时才走`），
必须写清**触发条件**，否则用户会以为它每次都在跑。

### ⓸ 缺失依赖实证（不可省）

```
<python> -c "import sys; import <模块>; print('<lib>' in sys.modules)"
```
1. 先证 **import 该模块不会拉起库**（懒导入证据）；
2. 再真调入口函数，看是抛错还是静默返回空；
3. 记录 WARNING 日志原文。

### ⓹ 用户说「这段兜底是无效的，删掉吧」时 —— 必须逐文件核验，不能顺着同意

用户常见的推理是：「上游流程 A 已经取了 X，如果失败，下游兜底也取不到 X，所以兜底无效」。
**这个推理经常不成立**，因为兜底读的往往是**另一个文件 / 另一种查法**。逐项核验：

1. **两个数据源是不是同一个文件？** 逐个列出来源文件的真实路径。
2. **查法是否相同？** 常见陷阱：一个**按代码**命中（`map[code]`），另一个**按名称**命中
   （`cfg[code]` → name → `map[name]`）。查法不同 ⇒ 覆盖度不同 ⇒ 互不替代。
3. **上游失败是否真的传导？** 看刷新/写入是**逐文件独立**（每个文件单独返回 True/False、循环继续），
   还是整体事务。独立 ⇒ 不存在传导。
4. **失败时是否保留旧数据？** 若写盘是「校验通过才原子替换、失败保留旧文件」，
   则下游读的是**上次成功快照**，「今天失败」完全不影响它。
5. **服务端可得性是否独立？** 直连探测每个文件的 size，别假设「都从同一台服务器来就同生共死」。

**结论可能是「不该删」，但顺手往往能挖出真缺陷**——例如兜底的旧格式有硬上限
（固定记录长度 ÷ 每项字节数 = 2800 ÷ 7 = 400），于是降级会**静默返回截断数据**：
同一板块主路径给 1102 只、兜底只给 400 只，只打一条 WARNING 然后照常 return。
这比报错危险得多。此时正确建议是「保留兜底 + 把截断升级为 ERROR/标记」，
而不是删除。

⚠️ **截断要分清是「本地解析器砍的」还是「服务端就只给这么多」**——两者修法完全不同。
chan.py 本轮实测：直接读二进制，四个 `block_*.dat` 里**声明成分数最大就是 400，无一超过**；
从真实服务器重新下载后结果**仍是 400**。⇒ 上限焊死在数据源侧，
改本地解析器（把 2800 步长算得更细）**一点用都没有**。判据：
把文件里每条记录的 `declared_count` 逐条 dump 出来看最大值，比看解析器算术可靠得多。

**同时要用两个口径给兜底定规模**，否则结论会失真：
- 「兜底独有覆盖」= 主路径取不到、只有兜底能给的条目（chan.py 实测仅 **2/472 = 0.4%**）⇒ 日常几乎不是活路径；
- 「主路径全挂时的兜底覆盖面」= 主数据源缺失时能顶上的条目（chan.py 实测 **370/472 = 78%**）。
只看前者会误判成"可删"，只看后者会误判成"每次都在跑"。**两个数都要报给用户。**

#### 删除决策三问（报完数还不够，要给出决策依据）

用户看到「独有覆盖 0.4%」后很自然会跳到「那就删了吧」。**别顺着答，先补三个数**：

1. **净损失的构成**：删掉后失去的条目里，多少是**完整数据**、多少是**截断数据**？
   chan.py 实测：删 Step4 影响 2 个板块 / 712 条，其中 **312 条（`880524 含可转债`）
   是未触顶的完整数据**，只有 400 条是截断的 —— 「删掉的都是坏数据」是错的论断。
2. **删除后失败变响亮还是变安静？** 最容易漏的一问。现状至少有一条
   `log.warning("可能受 400 只上限影响")`；删掉兜底后同一输入返回 `[]`，
   前端「扫描出 0 只」**不报错、不提示**。⇒ **删除把"有告警的部分数据"换成了
   "无告警的零数据"，可观测性不升反降**，与"消除误导"的目标背道而驰
   （0 只同样会被误读成"这个板块没有成分股"）。**要删就必须同时补一条显式告警。**
3. **入口可达性**：兜底覆盖的对象，用户**能不能在 UI 上碰到**？
   查法：这些标的的行情数据是否本地存在（chan.py 实测 `sh880524.day` / `sh880735.day`
   均在，652 个 880xxx 板块指数都有日 K）⇒ 用户能在图表里打开并勾选「成分股」
   ⇒ 不是"碰不到的路径"。查出来确实不可达，删的论证才真正成立。

**往往能给出比"删 / 不删"更好的第三条路**：chan.py 里兜底的**联网下载段**与
「刷新」按钮的 `refresh_block_files` 完全重复（同样下那 4 个文件、同样写 hq_cache），
而**本地解析段**才有独立价值 ⇒ 只删联网段（~67 行）、保留本地解析：
读取路径变成**零第三方库依赖**（顺带消掉一处 import 位置 bug），又保住那 312 条完整数据。
**先检查"这段兜底内部能不能再切一刀"，再决定整体删留。**

### ⓺ 对照实验：搭假环境直接驱动代码路径

判断「某条分支到底会不会产出数据」不能只读代码，要**搭出最小可运行环境**：

1. 造出代码期望的目录结构（如 `<tmp>/vipdoc` + `<tmp>/T0002/hq_cache/`）；
2. 把**真实下载的**数据文件放进去（别造假数据，否则解析结果不可信）；
3. **优选用「内存 monkeypatch 屏蔽高优先级分支」来强制走到目标分支**，
   而不是合成配置文件映射输入。例如要验 Step4 兜底，就把 Step3 的函数替换成
   `T._read_infoharbor_sector_stocks = lambda code: []` —— 比自造 cfg 精确得多，
   且**零风险**（不改仓库文件、不碰真实数据），也绕开了"合成标识符撞真实条目"的老坑。
   合成 cfg 只在「想验配置解析本身」时才用。
4. 设好全局配置入口（`set_tdx_config(...)`）并**在每次调用前重置所有相关 cache 全局量**
   ——否则第二次调用会命中缓存，测出假结果。
   典型要清的一对：`_XXX_CACHE = None; _XXX_CACHE_LOADED = False`。
5. **屏蔽第三方库用 `sys.meta_path` 插一个 `find_spec` 抛 ImportError 的 finder**，
   比卸载/改环境干净得多，也便于同一进程内交替开关做 A/B：
   ```python
   class BlockPytdx:
       def find_spec(self, name, path=None, target=None):
           if name == "pytdx" or name.startswith("pytdx."):
               raise ImportError("BLOCKED-BY-EXPERIMENT: %s" % name)
           return None
   ```
   开关前记得 `del sys.modules[pytdx...]`，否则已缓存模块不会被拦。
6. 逐组对照：A=正常路径 / B=只有兜底覆盖的输入 / C=移走主数据源模拟故障。
   三组都拿到数据 ⇒ 兜底有独立价值；C 组数量显著低于 A ⇒ 存在降级失真。

⚠️ **合成标识符必须先查占用**：自造的"假代码"（如 `880901`）极可能**恰好撞上真实条目**
（本例撞上了真实板块"信息安全"），导致实验静默测错分支、数据完全失真。
**造之前先用真实数据 `assert fake_id not in real_data`。**

⚠️ **样本必须按「兜底路径实际使用的查表键」来选，不是按主路径的键。** 
chan.py 实测踩坑：infoharbor 里 `880904` 叫**「智能机器」**，而 `tdxzs.cfg` 里同一个 code 叫
**「机器人概念」**；兜底按 `tdxzs[code] → name → block[name]` 查表，于是选的样本
在 block 里**根本不存在**，B 组静默返回 0，看起来像"兜底失效"其实是**选错样本**。
**选完样本必须断言它在兜底数据源里真能查到**（如 `assert tdxzs[code] in allblk`），
否则整轮实验结论作废、且不会报错。

### ⓻ 交付

- 一张**汇合图**：两条（或多条）上游流程 → 各自的适配层函数 → 唯一交汇的库调用点 → 落地产物。
  图里要标出「唯一真实调用点」和「已注释 = 死代码」。
- 表格：`调用点文件:行 ← 上游函数 ← 用户入口`。
- **顺手核对文档口径**：仓库里的 `Docs/*.md` 常写着「X 的旧回退已注释保留」，
  而实际是「已整体删除」。这类**方向相反的描述**必须逐条比对代码后报出来
  （chan.py 实测：`Docs/data_source_inventory.md` 两处说"注释保留"，实为"整体删除"，
  且文件头标注的 commit 已严重过期）。判据：去那个文件里数**有没有被注释掉的可执行代码**，
  只有说明性文字 ≠ "注释保留"。
- 结论要回答：**这条依赖能不能删 / 缺了会怎样 / 该不该放进"运行必需"依赖清单**。
  清单归位建议要指出语义差别：同段里 fastapi/numpy 缺了服务起不来，而懒导入的 X 缺了只是
  功能静默降级——**同在"运行必需"段但语义不同，就该给出改归位或加启动期校验的建议**。
- 用户提出「这段无效，删掉吧」时，交付里必须**明确写出前提错在哪**（附实测数据），
  再给出「不删 + 怎么改」或「要删就删这些 + 代价是什么」两条路，把取舍交回给用户。

## 反模式（都踩过）

- ❌ 只给 grep 结果，不给流程 → 用户还是要自己读代码。
- ❌ 把注释里的调用算成调用 → 得出"三条回退链都活着"的错误结论。
- ❌ 不追到前端 → 用户不知道"从哪个按钮会触发"。
- ❌ 不做缺失实证 → 漏掉"静默降级"这个最致命的事实。
- ❌ 只报调用点不报**触发条件** → 把兜底路径说成主路径。
- ❌ 顺着用户的"这段无效"推理直接删 → 兜底读的是另一个文件，删了会真丢功能。
- ❌ 合成测试标识符不查占用 → 撞上真实条目，实验静默测错对象。
- ❌ 只看"兜底独有覆盖"就下结论 → 漏掉"主数据源全挂时它顶 78%"的事实，误判成可删。
- ❌ 把"服务端只给 400 条"当成"本地解析器的算术上限" → 去改解析器，白改。
- ❌ 只验"缺库时抛不抛错"，不验"该库在这条分支里到底用没用到" →
  漏掉「本地缓存足够、库一个接口都不调，却因缺库整条兜底返回空」这种无关依赖绑架。

## 附：删除大段注释代码时的两个机械坑

1. **分隔线标记可能重复**。`# --------` 这类块尾标记在文件里常出现两次
   （块内小标题 + 真正块尾），用 `str.find(END)` 会**只删掉 9 行、残留 170 行注释**。
   用 `rfind(END)`，并加断言：删除块必须覆盖所有被删符号名、行数落在预期区间、
   块之后必须紧跟预期的下一个 `def`（本例是 `def get_xdxr_data`）。
2. **被注释的代码可能本来就跑不起来**。本例注释块里 `_threading.Thread(...)` 引用的
   `_threading` **从未 import**（文件里是 `import threading`）——说明它被注释后就再没验证过，
   「取消注释即可恢复」是假的。这构成**直接删除**而非「留着备用」的额外理由。
   顺手核对一遍块内所有外部符号是否真的 import 过。
