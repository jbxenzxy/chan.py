# 记忆文件体积治理与结构性重整

**对象**：一切「不常驻上下文、命中索引后按需 Read」的文档 —— `memory-*.md`、`MEMORY.md` 子文件、`SKILL.md`、
长 README / 交接文档。这类文件的成本模型是 **「读一次全量 = 一次昂贵的 Read」**，不是 token 注入。

## 0. 先建立正确的问题认知（否则会做错事）

三条容易做错的地方：

1. **字符数增长 ≠ 冗余增长**。这类文件长起来，多数是**新增了真规则**（新口径、新护栏、新操作清单），
   不是水词。**砍活规则 = 造成真实损失**，比"文件太大"严重得多。
2. **「回到历史某个字符数」是伪目标**。历史上的 3K 是因为当时内容少；现在 16K 是因为规则多了 5 倍。
   目标应是 **「可控的单次读取成本」**。
3. **降读取成本的主力手段是粒度，不是删减**。Read 支持 `offset`/`limit`：把 `##` 拆成 `###` 子节 + 顶部路由表后，
   读一节只要 0.5~1.5K，而不是整份 16K —— **收益 10 倍于删减，且零信息损失**。

→ 所以标准动作 = **移档死重 + 去重 + 分节 + 路由表 + 修正失真自称**；**不做**为了好看而砍活规则。

## 1. 工作流

### 1.1 量化现状（先看数，别凭感觉）
用 Python（不要用 bash 管道，长输出会被截断）统计：总字符、总行数、**每个 `##` / `###` 节的字符数**。

```python
import io, re
s = io.open(path, encoding="utf-8").read()
heads = [(m.start(), m.group(0)) for m in re.finditer(r"^(##|###) .*$", s, re.M)] + [(len(s), "<EOF>")]
for i in range(len(heads)-1):
    print(len(s[heads[i][0]:heads[i+1][0]]), heads[i][1][:60])
```

判读：**单个 `###` 子节 > 1,500 字符 = 该节该拆或该压**；`##` 节 > 4,000 = 该拆 `###`。

### 1.2 备份快照（**破坏性编辑前的强制步骤**）
建立同级 `memory-<topic>.full-YYYY-MM-DD.md`，内容 = **整理前的完整原文，一字不删**，头部写明：
只增不删的审计存档 / 它是哪次重整前的 / 新版里哪些内容被移到这里 / 上游存档链条。
**绝不覆盖已存在的快照**（`assert not os.path.exists(dst)`）。

### 1.3 逐条分类：活规则 / 重复 / 死重
对着每一节问三个问题：

| 类别 | 判据 | 处置 |
|---|---|---|
| **活规则** | 描述**现在该怎么做**（口径、操作清单、护栏、命名规范、禁用词） | **全留**，只压措辞 |
| **重复** | 同一事实在两个以上小节各写一遍（如"定位差异"与"操作清单"、A 问题与 B 问题的**同源**说明） | **合并到一处**，其余留一句指针 |
| **死重** | ① 过期数字（条数、耗时、行号、版本）② 已被取代的旧状态描述（"待拍板""本次未动"但**已修**）③ 明确标注"已不再适用"的备查差异 ④ 纯过程证据（实验读数、负控红了几条） | **移档**（从新版删，归档里已有全文） |

⚠️ **死重最危险的一类是「过期状态」**：文件里写着"处置待拍板"，而现实中已经修掉了。它会让下次读的人
做出错误决策 —— 这种必须当场改成现状（并顺手核对代码/常量验证，别照抄记忆里的数字）。

### 1.4 加顶部导航（本工作流的核心产出）
在标题下加两件东西：

1. **主题词 → 节号 路由表**（表格，6 行以内）：让"命中主题词后只读一节"可执行。
2. **体检块**：当前字符数 / 整理台账（每次重整的 `A → B` 字符）/ **再瘦信号**（什么现象出现时就该再来一轮）/
   移档指向（归档文件名 + "按关键字 Grep 之"）。

**约束：`##` 节号不要重编号** —— 上级索引文件（如 `MEMORY.md` 铁律）往往有 `见 §1` / `见 §3` 之类的引用。
动节号 = 必须同步改上级索引，漏一处就变成新的失真。节内重排（`###` 顺序）安全。

### 1.5 校验没丢东西（**必做，否则不知道砍坏了没有**）
从**旧版**抽一份 **MUST-token 清单**（关键标识符 / 文件:行 / 常量名 / 拍板日期 / 结论关键词），断言它们**全部仍在
新版**里：

```python
miss = [t for t in must if t not in new_text]
print("MUST-MISS:", miss or "none")
```

清单要覆盖每一节，尤其：**结论的反面约束**（"禁止改成 X""不可行""别改回 2""不扫 Docs"）—— 这类最容易被压缩时丢掉，
而丢掉后果最严重。另外断言 **移档内容确实不在新版**（证明真移了，不是白算了半天）。

### 1.6 收尾
- 报告：`旧字符 → 新字符（降幅）`、各节前后字符表、移档清单（移了什么、去了哪）、MUST-MISS = none。
- 把「本次移档了什么」写进归档头部，让下次整理的人知道去哪儿找。
- 更新上级索引（只在**节号或文件名变化**时）与工作区 memory 日志。

## 2. 反面清单（本工作流踩过的坑）

- ❌ **只改措辞、不分类** → 忙半天只降 2%，等于没做。降幅的主要来源是**移档**与**去重**，不是同义改写。
- ❌ **为了「瘦」去砍活规则**（操作清单、护栏索引、禁用词表） → 下次执行任务时出错，损失远大于省下的字符。
- ❌ **移档时删掉结论只留指针** → "指针"必须让人**知道去归档里搜什么**；纯指针会变成"读不到 = 不存在"。
- ❌ **重编号 `##`** → 上级索引里的 `§N` 引用静默失效。
- ❌ **照抄记忆里的数字** → 条数/行号/耗时是最易漂移的；写进新版前**用代码或常量实测一次**（例：`COMPONENTS` 条数
  实际是 120，记忆里还写着 119）。
- ❌ **用 bash 管道统计** → 中文长文件输出会被截断/乱码，一律在 Python 里做汇总。

## 3. 判断"是否需要动手"的闸门

只有命中以下任一条才做重整（否则是 churn）：

- 文件头有**与实际不符的自称**（"已瘦身到 3K"而实际 14K）—— **必改，这是失真**；
- 单个 `###` 子节 > 1,500 字符，或 `##` 节 > 4,000 字符；
- 出现**过期状态描述**（"待拍板"已成往事）—— 这条**随时可修，不必等体积问题**；
- 用户明确提出"读这个文件太贵了"。

**不需要**因为"数字看起来大"就动手：按需读的文件不占注入预算，只要分节粒度够细，16K 也是可接受的。
