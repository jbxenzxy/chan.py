# 代码驱动文档刷新

用户说「按最新代码刷新一下」时，要的**不是润色文字**，而是**把文档里每一条事实重新从代码里取一遍**。
这类文档的腐坏方式很特定：行号漂移、函数改名、分支增删、"注释保留"其实"已删除"。
所以核心动作是 **审计 → 重写 → 断言化核验**，第三步是这份技能的主要增量。

## 适用与不适用

- **适用**：`Docs/` 下的清单/说明类文档，断言密度高、引用大量 `文件:行`。
- **不适用**：只需改 3~5 处 → 用 `large-doc-atomic-multiedit`（保持原文、原子多点改）。
  判据：**要改的内容占比 > 50%** 就整体重写（本技能）；否则散点改（那个技能）。

## 变体：反向核对（文档承诺 → 代码是否落地）· 2026-09-16 新增

用户说「**这些文档里的重构是否全部落地了？**」（而不是「把文档刷新一下」）时，
方向正好相反：**不改文档，先给代码出证据**。流程复用本技能，但产出换成一个核对报告。
实测最有价值的四条：

1. **先钉基线，且必须做 CRLF 归一**。`git-blob sha1`（`sha1(b"blob %d\0" % len + data)`）
   逐文件比对沙盒/工作副本与远端。**不归一就整仓虚警**（实测首次比对报几十个 DIFF，
   全部 +N 字节 = 纯 CRLF 差异，归一后 315/315 一致）。⚠️ tarball/clone 通道常卡住
   （codeload 卡在 7.6MB），基线确认用 API tree + raw 比 sha 就够，**不必真下全量**。
2. **多份文档先盘「取代关系」再逐条核**。同一主题的 3 份设计文档通常是**逐层取代**
   （计划稿 → 治理稿 → 终态表），**只有最新那份是事实源**。核旧稿会得出「代码里还有
   `exchange` 分支 / 费率自动获取」这种反向误判 —— 那些是被取代稿里的承诺，代码里删掉
   才是对的。**报告里必须有那张取代关系图**（实测用 1 张内联 SVG）。
3. **每条承诺给「文件:行 + 现场命令」双证**，别只写「已实现」。
   例：「表第 3 列不取小」→ `Engine.py:979` + 测试；「费率生成式」→
   真跑 `GenFeeTable.py --check` 得 rc=0。**能跑的命令一律真跑**（全量回归 57/57
   是最强的一条，比任何行号引用都硬）。
4. **区分「文档说要、代码没有」与「文档自身落后」—— 后者才是多数**。
   实测落差只有 1 条（且文档自标可选），但文档侧要修的有三类：
   ① 附录坐标表行号全线漂移（13~106 行）+ 函数改名（`_close_mode`→`_today_exit`）；
   ② 头部结论与附录自相矛盾（「未动一行代码」vs 附G/附H 列了改动）；
   ③ 已删字段仍留在同仓 `README.md` 配置示例里（**照抄会报错** —— 这类要单独列一节）。
   结论必须写成「重构本体全部落地 + 文档侧需修 N 项」，不能只说"落地了"。
5. **交付形态**：自包含 HTML 报告（实测 43KB）。自检项固定为
   **外链 0 / `<script>` 0 / `<img>` 0 / `<iframe>` 0 + 标签配平 + SVG 合法**
   （用户要在无网络环境本地双击打开）。探针脚本留沙盒，**不挂附件**（同 `memory-workflow.md`）。

## 变体：从代码**穷举**一份「用户可见清单」（弹窗 / 接口 / 事件 / 提示）· 2026-09-22 新增

用户说「把 XX 功能运行中，所有弹窗列一张表，写清楚何时触发 / 内容是什么 / 几秒自动消失还是点确认消失」
「所有会打扰用户的提示列全」时用这一支。产出 = 一张**可从代码复核**的清单表，
并（若用户要求）追加进既有报告成一节。实测要点：

1. **两侧都要数，只数一侧必漏。** 消费端（前端 `showAlert/showConfirm/showToast` 调用点）
   ＋ **生产端**（后端 `Engine.alert(...)` / `notify(...)` 的每一个产出点）。
   本次：前端 45 个调用点，后端 severe 21 类码 + warn 5 类 + 轻提示 5 类 ——
   只数前端就会漏掉「框里可能出现的正文有哪些」，只数后端会漏掉「同屏还可能弹什么」。
2. **用带断言的正则计数，别手数**；并用脚本把每个调用点的**所属函数**映射出来
   （从行号往上找最近的 `function/window.X = function/对象方法`，**排除 `if/for/catch` 等关键字**，
   否则会得到一堆 `if() @714` 这种无用归属）。映射结果直接当表格的「触发场景」列。
3. **把计数与产出点数量写进正文，并用断言钉住。** 例：「全站共 45 个弹窗调用点
   （23 模态 + 1 问答 + 21 toast），其中与 X 相关 11 个」。脚本里
   `assert (n_alert, n_confirm, n_toast) == (23, 1, 21)` —— 下次代码一动，数字对不上立刻报错。
4. **「怎么消失」必须从实现里读，不能按类型想当然。**
   时长要读到常量（`const TOAST_MS = 5000` + `setTimeout(close, ms || TOAST_MS)` 才叫「5 秒」）；
   **全部出口都要穷举**（本次一个模态框有 4 条出口：确定 / 点框外 / Esc / Enter，
   且「点框外」在 alert 与 confirm 上语义**相反**）。同屏上限、冷却、去重水位这些
   「为什么不会刷屏」的闸门要单列一卡 —— 那是用户真正关心的第二问。
5. **清单类文档不能增量改。** 文案一变必须**整份重算**：本次发现第 1 轮那份弹窗清单里
   8 条文案、时长、消失语义全已过期（改前 `自动下单需要人工介入！`/toast 2 秒/原生 alert 阻塞），
   只改被点名的几行会留下一份自相矛盾的文档。交付时明确说「这份取代了上一份」。
6. **追加进既有报告（而不是新开一份）时，两头都下断言：**
   写盘前 —— 尾部锚点唯一（`assert rep.count(TAIL) == 1`）、关键契约文案在源码里确实存在
   （把要写进表格的原文串逐条 `assert m in src`，防止报告与代码脱节）、计数断言；
   写盘后 —— `<table>/<tr>/<td>` 配平、**外链 0**、关键小节标题在。
   最后用真 Chromium 打开**本地文件**，从**渲染后的 DOM**取：`h2` 节数、每张表 `rows.length`、
   `rowspan` 是否真生效、正文关键字是否可见、内联图 `naturalWidth > 0`、无横向溢出
   （`_shot_report.py` 模式，实测 60/0）。**标签配平 ≠ 渲染正确**，这一步不能省。
7. **与远端比对前先钉基线**：拉到**新目录**再逐文件 md5 diff，**别覆盖自己的工作树**
   （增量拉取的 `skip` 只比 size，同 size 改动会静默漏拉；覆盖还会丢掉「差异是谁造成的」这个信息）。

## 铁律

1. **先钉死代码基线，并把 commit sha 写进文档头。**
   - 远端用 GitHub API + raw 逐 blob 拉（见 `repo-dependency-flow-trace` 技能）。
   - **必须比对本地工作副本与远端是否一致**：`diff -rq --strip-trailing-cr -x __pycache__ ...`。
     只多出 `.env` / `.venv` / 运行产物（`*.json`、`*_run.log`、`State/`）→ 可直接以远端为基线；
     若有源码差异 → **先问用户以哪边为准**，别自己裁决。
2. **行号必须重新取，一个都不许沿用旧文档。** 旧文档里的行号是最先腐坏的东西。
   取行号用 `grep -n "def <名字>"`，把「函数名 + 定义行」成对写入，
   因为**函数名可能重复**，行号是唯一能对齐用户阅读位置的锚点。
3. **文档里每条数字都要能追溯到一条命令。** 「16 台服务器」「400 只上限」
   「覆盖 421 个板块」这类数字，必须现场跑出来，不许从旧文档抄。
4. **旧文档的口径错误要显式留痕。** 在文档末尾加「已知限制与口径提醒」，
   写明「此前版本写的是 X，实为 Y」。否则下一个人会照抄旧错。
5. **绝不直接写用户的项目目录**（`C:\my_chan_project` 等）。
   改在沙盒 `sandbox/out/<原目录层级>/`，再打 zip 交付。

## 流程

### ⓵ 审计：把文档拆成「可验证断言」清单

逐节读旧文档，对**每一格表格 / 每一条说明**问三个问题：

- 这个函数还在吗？还在哪个文件、第几行？（重取）
- 这个数据源地址 / 字段索引 / 常量值还对吗？（重取）
- 这个「消费方」还对吗？（`grep -rn "<函数名>"` 反查）

**顺手做一次死活判定**：旧文档列的适配器/模块，有没有已经 0 处调用的？
有没有**代码里新增但文档完全没提**的？（chan.py 实测：适配器表只列 5 个，
实际 `DataAPI/` 有 13 个文件，漏了 8 个。）

### ⓵·补 比行号更容易腐坏的五种东西（2026-09-15 新增）

只查行号会漏掉一半腐坏。审计时对这五类**逐条**过：

1. **论证依据已消失**（最隐蔽、后果最大）。文档常拿某个值/字段当论据，比如
   「值按来源分两类：经验标定（`min_r_points=3.0`、`r_multiple_tp=2.0`）／交易所事实」。
   若 `min_r_points` **已被删除**，那不只是「这个数字过期」——**整条划分线失去依据**，
   该节的结论要重新判定，而不是换个数字继续用。
   做法：文档里每个**举例用的字段名**都 grep 一次死活（见第 2 条的三态判定）。
   实测：该文档整节的结论因此被推翻，必须标注「本节已被取代」，不能只做数值校准。
2. **「已删除」的三态判定**（别只会 grep 有没有）。同一个已删字段在三处出现，性质完全不同：

   | 形态 | 例子 | 判定 |
   | --- | --- | --- |
   | 实代码引用 | `if min_r_points:` / 构造参数 | **残留，必须改** |
   | 注释 / docstring 留档 | 「`min_r_points` 已于 2026-09-14 删除」 | **是留档，别删** |
   | 负向断言 | `check(..., "min_r_points" in resolved, False)` | **是护栏，别删** |

   所以报告要写成**定量表述**：「命中 34 处 / 8 文件，**逐条定性后 0 处实代码**」。
   用带边界正则 `(?<![A-Za-z0-9_])NAME(?![A-Za-z0-9_])`；
   子串口径与带边界口径会差很多（实测 `trade_symbol` 子串 124 处 vs 带边界 122 处，
   因为 `self._trade_symbol` 这类前缀形式很常见）——**报数字前先声明口径**。
3. **括号里的「理由」会独立过期**。行号对了、数字也对了，但理由错了，例如
   「49 文件 59 处（**`now_cn` 全仓在用**）」——49 文件是 **Types 整体**的消费面，
   `now_cn` 单看只有 14 文件。行号断言抓不到，只能靠**逐个名词回查**。
   这类错误的危害是让**排期决策建立在错理由上**（改动面被估错方向）。
4. **同一文档内自相矛盾**（上轮"校准"只改了一半的指纹）。文档里常有
   「正文 §2.4」+「本轮校准表 §7.2」两处讲同一组数字。上一轮只改了校准表、
   没回填正文 → 读者看到两组数字打架。**判据：同一名词在文档里出现 ≥2 次计数，
   就把每次都 grep 出来逐一对齐**（`grep -n "87 处\|89 处\|124 处\|129 处"`）。
   更一般地：**校准表里写了"实际是 Y"，正文里那个 X 就必须一起改掉**——
   否则校准表反而制造了新的不一致。

5. **方案里的「规则」与仓库里「同名的现成实现」可能不是同一条**（最贵的一种腐坏，
   因为它会诱导实施者**复用错误实现**）。场景：文档提出新规则 R，仓库里已有一个做
   类似判断的现成函数 F。两者**看起来等价** → 文档写「复用 F」，或干脆把实现留成
   `...` → 实施者照 F 抄，把 F 的口径错误继承进新代码，且**测试全绿**。

   chan.py 实测：文档规则 R = 「平今费 ≤ 开仓费 ＋ 平昨费 → 平今」（锁仓路径是
   **两笔**成交 + 两笔滑点），仓库现成的 `evaluate_closetoday_economy` F =
   「平今费 ≤ 平昨费 → 平今」（只比**一笔**）。二者在
   `开仓费 < 平今费 < 2×开仓费` 区间**结论相反**。8 个品种恰好没有一个落在这区间，
   于是两条规则**跑出完全一样的结果**——「回算 8/8 一致」看着是铁证，
   实际是**样本巧合**。

   做法：
   - 对文档里每条**判定式 / 公式 / 阈值**，回查仓库有无现成实现，**逐项对齐三件事**：
     比较对象（比一笔还是两笔？）、边界符号（`<` 还是 `≤`）、失败兜底侧。
     只停在「数值回算一致」= 把巧合当证明。
   - **显式枚举分歧区间**并写进文档：把 A 规则 / B 规则在区间两侧各代一次，
     即使当前样本全落在一侧，也要标注「分歧区间在 X，当前样本未覆盖」。
   - **绝不把「与现值一致」当正确性证据**。现值本身可能是次优或错的；一致只能证明
     「迁移无行为变更」，证不了「现值对」。想证对得**独立算经济账**：
     本例把成交笔数差（2 笔 vs 1 笔）→ 滑点 → 双边保证金占用 叠加进去，
     才看出「恰好相等」那一档该判**另一侧**，从而发现现值不是最优解。
   - **实现别留 `...`**。容易误用的地方把实现**照抄进文档**，并在 docstring 明写
     「不要复用 `XXX`（口径少一笔）」——文档里一句负向指引，抵得上实施者一次踩坑。
   - 顺带：这类"现值不是最优"的发现要写成一个**待拍板项**（行为变更 vs 行为零变更），
     不要静默改掉用户的现有行为。

> 一句话：**行号断言的覆盖面 ≈ 文档腐坏的 60%**。剩下 40%（论据死活 / 理由过期 /
> 内部打架 / 口径声明 / 现成实现不等价）必须靠「逐个名词回查 + 同名词多处对齐」，
> 别指望脚本替你做。

### ⓶ 区分「可达」与「不可达」，别把死路径写成活路径

同名的面可能一个活一个死。chan.py 实测：
`AkshareAPI.fetch_index_cons`（成分股面）是 API 服务的活路径，
而 `CAkshare`（K线面，走 `DATA_SRC.AKSHARE`）只有独立脚本能到。
判据：**找 App 层的装配点**（如 `data_src="custom:TdxAPI.CTdxAPI"`），
凡不在装配点集合里的数据源，都归到「仅独立脚本可达」一节，不要混在主表里。

### ⓷ 重写：结构按「消费方视角」组织

推荐骨架：

```
〇、主数据源（K线/核心链路）      ← 先讲主干，别让读者从支线找起
一、N 类信息的数据源（表）        ← 信息 → 适配器 → 取数函数(定义行) → 真实数据源 → 消费方
二、二级链路（成分股 / 派生数据）  ← 带路由顺序说明
三、刷新/写回链路
附 A：适配器一览（文件 / 行数 / 数据源 / 能力 / 实际消费方）
附 B：仅独立脚本可达的数据源
附 C：依赖可用性与降级行为（缺了会怎样，实测口径）
附 D：已知限制与口径提醒（含旧错修正留痕）
```

每张表都加一句**「说明」**写触发条件与例外——读者最容易误解的就是「这条是不是每次都在跑」。

### ⓸ 断言化核验（核心，不可省）

**写一个脚本，把文档里每条行号引用与事实断言变成可执行检查。** 这是本技能最有价值的产出：
它把「文档是否准确」从人眼复核变成 0/1。

```python
def chk(rel, ln, must, desc):
    """第 ln 行（1-based）必须包含 must 中任一子串"""
    L = open(os.path.join(R, rel), encoding="utf-8", errors="replace").read().split("\n")
    if ln < 1 or ln > len(L):
        fails.append(f"{rel}:{ln} 越界（共 {len(L)} 行） — {desc}"); return
    got = L[ln - 1]
    if not any(m in got for m in must):
        fails.append(f"{rel}:{ln} 期望含 {must} 实际={got.strip()[:90]!r} — {desc}")

def chk_def(rel, ln, name, desc):
    """第 ln 行必须定义名为 name 的函数/类 —— 比 chk 更抗漂移"""
    got = open(os.path.join(R, rel), encoding="utf-8", errors="replace").read().split("\n")[ln-1]
    if not re.match(r"\s*(def|class)\s+%s\b" % re.escape(name), got):
        fails.append(f"{rel}:{ln} 期望定义 {name}，实际={got.strip()[:90]!r} — {desc}")

fails = []
# ... 逐条登记，然后
if fails: print("FAIL", len(fails)); [print("  ✗", f) for f in fails]; sys.exit(1)
print("全部核验通过")
```

要覆盖的断言类型：
- **定义点**：`chk_def("DataAPI/TdxAPI.py", 1665, "get_index_stocks", ...)`
- **调用点**：`chk("App/AppScan.py", 363, ["get_index_stocks"], ...)`
- **常量/字面量**：接口地址、字段索引（`fields[39]`）、枚举集合（`sorted(codes) == [...]`）、
  列表条数（`len(re.findall(r"\(", tb)) == 16`）
- **反断言**：文档说「未声明」→ `assert "mootdx" not in requirements_txt`
- **分段落位置**：`pytdx` 在 requirements 的「运行必需」段而非「可选」段
- **⚠️ 负面断言必须成表（强制）**：凡文档写了「已删除 / 已下线 / 已退场 / 不再使用」，
  就要有一条 `NEGATIVE_ASSERTS` 逐文件 grep 确认**真的搜不到**。这是最容易被忽略、
  也最容易在下一轮重构后静默回潮的一类事实。
  实测清单式：`("pytdx", ["DataAPI/TdxAPI.py", ...])`、`("_download_block_gn_from_network", ...)`、
  `("fetch_float_mc_from_tencent", ...)` —— 一条 token + 一份不该出现的文件列表。
  没有它，「我已删除 X」这类结论就没人守。
- **负面断言要区分「定义」与「docstring 里的历史说明」（用正则，别用子串）**。
  重构时常会刻意在 docstring 留一句「本函数原为 `_refresh_pe_ttm`…」作为迁移说明 ——
  朴素的子串负面断言会把它判成违规，然后你会去删掉本该保留的说明。
  做法：`REGEX_NEGATIVE_ASSERTS`，pattern 锚在**定义形态**上
  （`r"^\s*def\s+_refresh_pe_ttm\b"`、`r"(?<!legacy_)stock_pe_ttm_file"`、`r"^\s*import\s+json\s*$"`）。
  同理「落盘不再写某字段」要断言**赋值形态**（`r"=\s*\{[^\n]*[\"']pe_ttm[\"']"`），
  不要断言 `"pe_ttm":` —— 后者会命中 docstring 里刻意保留的旧格式 JSON 示例。
- **自动解析文档里「所有」`文件:行号` 引用（防漏登记）**。手工维护的 `LINE_ASSERTS` 只覆盖你想到的；
  用正则把文档扫一遍再逐条核对存在性与行号范围，能抓住漏登记的引用：
  ```python
  DOC_REF_PATTERN = re.compile(r"`?((?:[\w.]+/)*[\w.]+\.(?:py|html|js|json|txt|md))`?\s*:\s*(\d+)")
  # 文档常只写 basename（`AppData.py:1230`）→ 需要候选目录解析器：
  CANDIDATE_DIRS = ["", "DataAPI/", "App/", "Test/", "Docs/", "Trading/", "Common/", "KLine/"]
  # 解析不到 = FAIL；解析到但行号越界 = FAIL
  ```
  实测一份 264 行文档自动扫出 **49 条**引用。**好处是行号引用的正确性不再依赖人眼**，
  且新增章节时不会被忘记。
- **⚠️ 不要把「行号 → 期望内容」硬编码进脚本（2026-09-12 教训，已因此重写脚本）**。
  硬编码版一旦遇到上游重构（哪怕只是在文件头部插入 12 行常量）就会**全线假失败**，
  于是它既无法区分「文档过期」和「引用写错」，也彻底失去回归价值 —— 上一版 200+ 条硬编码
  断言正是这样废弃的。**正确做法**：脚本只做机器能判的两件事 ——
  ① 被引用文件是否存在（抓改名/删除）；② 行号是否越界。
  然后把该行内容**打印出来供人工核对语义**（"这行是不是我想引用的那行"是语义判断，
  机器给不出结论，硬编码"期望内容"只是在制造新的漂移源）。
  这样脚本永不因漂移假报，仍能守住真正的破坏性变化。本轮新版：`verify_doc_refs.py`（93 行）。
- **⚠️ 引用核验脚本的三处硬化（2026-09-16 实测，缺一个就误报/漏报）**：
  1. **仓库根路径必须传「Windows 原生路径」**。在 Git Bash 里把 `/c/Users/...` 传给
     Windows 版 Python → `os.path` 解析不到 → **全部引用一次性误报「找不到文件」**
     （实测 157/157 全红，看着像文档全废）。传 `C:\Users\...`（正/反斜杠都行）即可。
     **教训：断言大面积同向失败时，先怀疑「路径/口径」而不是「事实」。**
  2. **只用后缀匹配解析 basename，别让 `os.path.join(root, rel)` 直连优先**。
     文档常只写 basename（`main.py`），直连优先会命中**仓库根**的 `main.py`（88 行），
     于是 `Trading/main.py:108` 被判成「越界」。做法：把 `rel` 当**以 `/` 为边界的后缀**
     去匹配全仓路径；匹配到 >1 个 = **歧义**（单独报，不猜）。
  3. **歧义 basename 要在文档侧消歧，而不是在脚本里猜**。`Base.py`（`Broker/` 与
     `Source/` 各一份）、`main.py`（根与 `Trading/` 各一份）这类，**文档里统一写成带目录的
     `Broker/Base.py:98` / `Trading/main.py:108`**，歧义即归零。
     改法用**精确替换脚本**：每条替换断言**命中数 == 1** 才写盘（命中 0 或 >1 → 整体不写），
     避免 CRLF/多处误替换；顺带把文档里的笔误（实测 `fail_fee_overrides` → `fee_overrides`）一起修掉。
- **内容级锚点抽查：期望值要跟代码对齐，别怪文档**。结构核验（存在性 + 行号范围）之外，
  再对 ~90 个**关键锚点**做一次"该行确实是那个符号"的内容级抽查（如 `Product.py:213` 行内
  必须是 `class ExecPolicy`）。**但抽查脚本自己的期望值也会 off-by-one**：实测期望
  `Product.py:71 = class Fee`，该行实为 `@dataclass(frozen=True)`（`class Fee` 在 `:72`）；
  `Instrument.py:177` 是装饰器行、`:178` 才是 `class EffectiveSpec`。**这类"失败"多半是
  检查器期望值写错，不是文档错** —— 修检查器（或把文档改成引用装饰器所在行），别去改对的文档。
  锚点选择原则：**只挑"一句话就能判对错"的定义行/字面量行**，语义题留给人工。
- **文档正文里的「计数词」要与其它章节交叉一致**。本轮抓到的典型：
  第一节写「**两个**公开取数函数共用分流规则」，附 A 写「**三个**取数函数契约一致」——
  新增了 `fetch_pe_ttm_live` 后只改了后者。这类不一致**跑不出行号断言**，
  要靠「按名词 grep 全文计数」的抽查习惯（`grep -n "两个\|三个" 文档`）。

跑完 **0 失败才允许打包**。实测一份 141 行文档可铺 ~120 条断言，一次抓出 4 处行号错；
另一份 191→220 行的文档铺了 **110 条断言**（含 4 条负面断言、14 条行数断言），抓出 1 处陈旧行号
（`class CTdxAPI` 文档写 985、实为 983 —— 这类"差 2 行"的错正是靠断言而非人眼抓到的）。

**同一脚本要对两棵树各跑一次（本轮最有价值的用法）**：

| 树 | 期望结果 | 说明 |
| --- | --- | --- |
| 已应用本次改动的树 | **0 失败** | 文档与最终代码一致 |
| 未应用改动的**基线树**（用户项目原状） | 失败项**恰好等于本次改动的落点** | 既是复验，也是**「基线未漂移、补丁可干净应用」的证明** |
| **交付包覆盖到干净基线副本**（第三棵） | **0 失败** | 证明「只有这个包」就能把基线变成文档一致状态，不依赖沙盒中间产物 |

第二棵树是关键：若基线树上冒出了**计划外**的失败，说明用户项目已被改动过，
此时直接覆盖交付会出事故 —— 必须先问清。反过来，若基线树的失败项与预期落点完全吻合，
就同时证明了「交付包能干净套在基线上」。

第三棵树（**清房复验**）在交付前做，做法是把交付 zip 解到一个**干净的基线副本**上
（`tar` 排除 `.venv`/`__pycache__` → 覆盖 zip 内容 → 跑脚本）。
本轮实测：覆盖后 **204 项断言 0 失败**。它抓的是「沙盒里改对了、但包里的文件不是那个版本」
这类**交付形态错误** —— 只跑前两棵树永远抓不到。
配套动作：`testzip()` 破损检测 + 逐条目 sha256 与源树比对 + **中文名条目可读性检查**。

### ⓸·补二 三种新断言（入口 README 轮实测 · 2026-09-17）

刷新对象是**仓库入口文档**（`Trading/README.md` 这类"新人第一份要读的东西"）时，
除行号/锚点/负面三类，再加两件 —— 实测 109 引用 + 143 锚点 + 12 负面 + 117 数值 = 全绿才交付：

1. **数值断言：直接 import 项目的包，比 `model_fields[...].default`。**
   文档里"默认值表"最容易抄错（本轮 34 个字段 0 错，但全靠断言证明）。
   ⚠️ 两端都要注意：
   - 必须用**项目自己的 venv**（`<repo>/.venv/Scripts/python.exe`），沙盒 python 没 pydantic；
   - **不要实例化配置对象去读值** —— `TradingConfig()` 会加载仓库根 `.env`，
     读到的是**环境覆盖后的值**（如 `.env` 里 `TRADING_BROKER=simnow`），
     而文档写的是**模型字段默认值**，两者不等 ≠ 文档错。取
     `Model.model_fields[name].default` 才是对的。
   同类可断言：枚举字典（`EXEC_POLICY` 8 行三列）、白名单键集合、周期集合、
   档案参数（`r_multiple_tp` / `price_tick` / `multiplier`）、
   目录树里每个文件的行数（口径 `count("\n")`）、脚本个数（`glob`）。
2. **交付形态自检：Markdown 渲染 + 行尾。**
   固定四项：`![` 图片 0、外链 0（**只允许** localhost 端点如 `http://127.0.0.1:18081`
   —— 它是被描述的配置值不是资源依赖）、**反引号内的裸 `|` 必须写成 `\|`**
   （否则表格被撑破，实测文档里有 `{date}\|{type}\|{B/S}` 这种）、每张表列数恒定。
   加：代码栅栏偶数配平 / 纯 LF / 无 BOM / 结尾有换行 / H2·H3 与正文交叉引用对得上。
   ⚠️ **交叉引用要专门查**：本轮抓到一处悬空 `见 §11 附录 B`（附录只有 A），
   这类错跑不出行号断言，只能靠"把所有 `§X` / `附录 X` 抓出来逐条对目标是否存在"。

**三个坑（本轮实测）：**

- **断言失败时先怀疑断言，再怀疑文档。** 本轮 16 项失败里 **12 项是检查器的期望值写错**
  （期望 `:21` 实际 `:19`；期望含"单向依赖"而那行是"设计约束"），文档本身是对的。
  改之前先把该行原文 `print` 出来看 —— 见本技能「⓹·补」里"内容级锚点抽查"那条。
- **负面断言里"注释"必须一起剔，光剔 docstring 不够。** `code_only()` 只去 docstring 时，
  `#   （原 on_bar 里的 RiskGate.roll_day …随风控五道硬闸门整体删除）` 这类
  **讲旧行为的注释行**会被判成"仍在引用已删符号"。做法：ast 剔 docstring **+** 丢掉
  `L.strip().startswith("#")` 的行。反过来，`("max_volume", "…迁到品种执行策略表")`
  这种**已删键清单里的负向记录**是留档，不是消费点 —— 判据要锚在**定义/消费形态**上
  （`^\s*max_volume\s*:`、`risk\.max_volume`），不要用裸 token 子串。
- **包内文档的引用要双前缀解析。** README 住在 `Trading/` 里，正文写 `Infra/Product.py:414`
  比 `Trading/Infra/Product.py:414` 自然。解析器必须两者都试：
  `for cand in (rel, os.path.join("Trading", rel))`；否则一半引用会误报"文件不存在"。

### ⓸·补 交叉引用一致性（新增章节编号时必查）

刷新时若**新增/删除了带编号的条目**（如附 D 加了 D-5 / D-6），必须回头把**引用它们的地方**一起改 ——
正文里常写着「（附 D-5）」「详见附 D-6」这类前向引用。漏改的后果是读者被指到不存在或错位的条目，
而且**这类错误跑不出断言**（除非专门断言"引用编号 ≤ 实际最大编号"）。

做法：`grep -n "附 [A-Z]-[0-9]\|§[0-9]\|见第[一二三四五六]节" 文档`，
把每个引用与被引目标对一遍。同理，**章节自身的序号**（一/二/三/附 A…）增删后要重排。

### ⓹·补 文档集收敛：**一轮只交一份主文档**（2026-09-15 新增）

**症状**：多轮迭代后，`present_files` 里堆了 3 份 md（旧交接稿 + 新设计稿 + 证据报告），
用户原话是「**让我都晕了，不知道看哪个？**」。这不是用户的问题——是**交付集没收敛**。

**判据**：只要**同一主题**存在 ≥2 份 md，就说明上一轮没做收敛。触发收敛时按下面做：

1. **先盘「谁取代谁」**。用 `grep -n "^#\{1,3\} "` 列出各文档章节树，逐节标注：
   - 只在新文档有 → 保留
   - 只在旧文档有 → **并入新文档**（这步最容易漏！旧稿的"概念澄清/术语锚点"经常是唯一副本）
   - 两边都有 → 留新文档的，旧文档标注「已并入 §X」
2. **产出一份**，并在文档头写清 **`覆盖与删除清单`**（我删了哪些旧文件、内容去了本文哪一节）。
   - 文件名**不带日期后缀**（git 已有版本历史），否则下轮又出现 `_20260915` / `_20260916` 并存。
   - 命名对齐同目录**已有的兄弟文档**风格（实测：`Trading配置架构治理_交接文档.md`
     → 新文档取名 `TradingInfra划分治理_交接文档.md`，一眼看出是同一系列的）。
3. **不为"保留审计快照"而留旧文件**。旧文件在 git 历史里；留着只会再造歧义。
   要留痕就在新文档里写「旧文件 X 的 §Y 已并入本文 §Z」。
4. **证据报告不再单独交付**：关键证据并进主文档的「证据索引」小节
   （`文件:行` 表格）。用户要的不是"证据文件"，是"结论 + 能核对的锚点"。
5. **交付动作**：`present_files` **只给主文档**（`.md` 一律不进 zip，见 `memory-workflow.md`
   §交付格式 第 9 条）。纯文档轮次**不打 zip**。**实验/审计脚本默认不随交付发出** ——
   `exp_*.py`、`audit_*.py`、探针片段等**既不进 zip，也不挂 `present_files` 附件**
   （同文件第 10 条）：文档里给出「证据索引：`文件:行`」表格即可，脚本留在沙盒备查。
6. **回归护栏**：收敛后对主文档跑一次「旧文件名/旧章节号是否还被引用」的检查
   （`grep -n "Infra文件命名治理\|再设计_20260915" 主文档` 应为 0，除"删除清单"那节刻意提及）。
7. **变体：把「已成链的三份」合并成一份（2026-09-16 实测，C→B→A 逐层取代链）**。
   用户说「把这三份合并为一份，按最新代码刷新」时，收敛对象是**整个取代链**，做法：
   - **合并深度先问用户**（用 `AskUserQuestion`）。两档：**精编收敛**（只留现行有效结论 +
     证据索引，废止结论压成「决策考古」附录并标 `已废止`）／**全文合并**（原文全留）。
     实测用户选精编：成品 2251 行 / 1732 非空 / 160KB（略超 1300–1700 行目标但内容完整）。
   - **原始需求原文必须「一字不改」留档**（独立成章，按 一代/二代/三代 分段）。
     这是唯一不能"精编"的部分 —— 需求原文是**追溯决策动机的唯一凭据**，压缩即失真。
   - **替换掉"取代关系图"，改用「废止留档」**：原报告里那张 C→B→A 的 SVG 图，
     合并后不再需要"选哪份读"，改为在附录里留「哪条结论被谁推翻、为什么」的考古记录。
   - **章节骨架按"给接手人看"重排**：怎么用 → 一页速览 → 原文存档 → 术语表 → ADR 总表 →
     各专题（表/费率/Infra/状态机/链路/统计/实盘/测试/坑点）→ 覆盖与删除清单 →
     附录（考古 / 证据索引 / 变更历史）。
   - **交付 + 删除清单一起给**：`present_files` 只给合并后那一份 `.md`（不进 zip），
     回复里明确列出**要删的旧文件清单**；⚠️ 若旧文件不在用户工作副本里（只在仓库快照 `Docs/`），
     要**说明它们在哪儿**，别让用户去自己目录里白找（实测三份源文档只在 `sandbox/chanpy_head/Docs/`）。
   - **拼装用分片再合、合完归一空行**：分 N 段写 `_merge_p*.md` → `re.sub(r"\n{3,}", "\n\n", ...)`
     拼接 → 复核 代码栅栏是否偶数（配平）/ 纯 LF / H2·H3 计数。分片放 `_scratch/`，**不进交付目录**。

**配套**：收敛时顺手把**旧文档里已被推翻的结论**标记为「已废止」而不是删掉——
保留"为什么这条规则不成立"的论证材料，下一个人就不会重新提同一个方案。

## 坑（都踩过）

1. **`str.splitlines()` ≠ `wc -l`**。`splitlines()` 会在结尾无换行时多切出一行，
   且对 `\x0b\x0c\x1c-\x1e\x85\u2028\u2029` 也切分。**行数口径统一用 `content.count("\n")`**
   （等价 `wc -l`），并在文档里声明口径。实测 13 个 py 文件里 7 个两种口径差 1。
2. **校验脚本自身的正则要匹配真实字面**。字典键是 `"forward_adjust_enabled": False`，
   正则写成 `forward_adjust_enabled\s*:` 会**永远匹配失败**，看起来像"事实错了"，
   其实是脚本错了。**断言失败时先怀疑断言，再怀疑事实。**
3. **别把「文档没提」当成「代码没有」**。两者都要报：漏掉的新增模块比过期的旧条目更值得写。
4. **行尾/编码要保持与原文一致**：读 `rb` 探测 CRLF/LF/BOM，回写保持一致，
   否则整份 diff 全红。chan.py 的 `Docs/*.md` 是纯 LF + UTF-8 + 有结尾换行。
5. **别只重写正文**。旧文档头部的「基于 commit `386dd3c` 核查」这种标注必须更新，
   否则刷新后的文档看起来还是旧的。
6. **上游一次重构会让整节行号集体作废 —— 量级要按"整节"预估，不是"几处"**。
   实测 `TdxAPI.py` 从 2355 行重构到 2067 行后，旧文档 §二（成分股路由）与 §三（板块刷新）
   的**每一个行号都失效**，还伴随三条事实变化（pytdx 退场 / Step4 兜底删除 / 板块刷新换通道）。
   所以刷新前先跑 `git diff --stat <旧基线的文件>` 或比对新旧行数：
   **某文件行数变化超过几行 → 直接假定该文件相关的所有引用都作废，全部重取**，
   不要试图只改"看起来变了的那几行"。
7. **新得的事实要回流到"能力边界"类技能**。本轮在刷新文档时确认的一批实测边界
   （`spblock.dat` 不经 `0x06B9`、`finance_batch` 单批上限 80、北交所唯一毒丸 `bj920025` 的隔离修法、
   `infoharbor_block.dat` 547 段经一致性过滤只剩 420 个带代码板块）
   已同步进 `tdx-data-provenance-verify` 的「已知能力边界」表 ——
   **文档刷新常是发现新事实的场合，别让这些事实只留在文档里**。
8. **「只改了注释」照样让整文件行号漂移 —— 判漂移要看行级 diff，不看文件级"改没改"**（2026-09-22 实测）。
   上游把某字段的 5 行注释压成 4 行（纯注释、0 条可执行语句变化），该行以下**全体 -1**：
   文档里 `Instrument.py:424 / :458-459 / :461-486` 三组引用一次性全错。
   正确做法：拿旧基线 + 新 HEAD 两份原文跑 `difflib.SequenceMatcher(a, b).get_opcodes()`，
   建 **old 行号 → new 行号** 映射（`equal` 段逐行平移、`replace` 段标 GONE），再逐条查引用落点；
   **别用"文件 md5 变了没变"当判据，也别只看 diff 的语义描述**。
   顺带两条：① 刷新后**保留"原坐标"列**（本文档 §10.5 的做法），否则下一轮无从追溯；
   ② 文档里的**基线 commit 标注**要跟着新 HEAD 一起改（坑 5 同理）。
