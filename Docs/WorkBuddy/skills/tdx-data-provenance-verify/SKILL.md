# 通达信数据源溯源与可替代性核实

用户问「X 数据能不能用 Y 拿到」时，**要的不是"Y 有没有这个 API"的文档摘录，而是三件事**：
① 现在这份数据实际从哪来（代码事实）② Y 到底能不能拿到（实测）③ 换了之后会变好还是变差（差异清单）。

**文档说能，不等于能。必须起服务器实测。** 本方法在 eltdx 上实测过：文档功能地图里没有成分股条目，
但代码表接口里赫然藏着一个 `category == "index"` 规则含 `sh880/881/999` —— 这是文档不会主动告诉你的能力。

## 铁律

1. **先定位消费链路，再谈替代**。不要一上来就查库的 API。
   正确的第一刀是从用户操作入口（前端按钮 / 菜单项 / API 路由）往下追到实际取数函数，
   追到**最终那个读文件或发请求的语句**。链路没定位，替代方案就是空中楼阁。
   （实测教训：用户说「点某个按钮」，追下去是 `AppScan.py` → `AppData.py` → 一个内嵌 470 条的硬编码字典，
   全程零联网零文件读取 —— 这决定了"换个库"根本解决不了层级问题。）

2. **区分三种"数据来源"，它们的可替代性完全不同**：
   - **协议接口**（7709 命令）：可被等价库替代，只要命令码相同（如 `0x06B9` 文件下载、`0x044d` 代码表）
   - **本地文件**（`T0002/` 下）：能不能替代取决于**这个文件是否在协议的下发清单里**。在 → 可下；不在 → 只能读本地
   - **硬编码常量**（代码里的字典/列表）：任何接口都替代不了，因为它是"抄进代码的快照"，只能用接口去**校验它是否过期**

3. **"拿得到代码"≠"拿得到语义"**。代码表给的是 `code + name`；层级、分类、成分股关系都是**另一套信息**，
   通常不在同一个接口里。必须显式检查：目标字段在返回值里存在吗？不存在就是拿不到，不要靠推断。

## 流程

### 第 1 步：定位消费链路（只读代码）
从前端文案/接口路由反查：
```
grep -rn "<用户看到的按钮文字>" Frontend/ App/         # 找到前端选项文案
grep -rn "<该文案对应的后端 key>" --include=*.py .      # 找到 map 里的分支名
```
拿到后端函数后，继续读它调用的取数函数，直到出现 `open(...)` / `download_file` / 网络请求为止。
**记下确切行号** —— 报告的"代码事实"部分全部靠它。

### 第 2 步：找本地文件在哪（全盘语义搜索，别猜文件名）
想找"藏在哪个文件里"的数据，**不要逐个猜文件名**（`tdxhy.cfg`? `tdxzs.cfg`? `incon.dat`?），
直接**全盘按 GBK 解码搜该领域的中文名称字符串**，按命中数排序：

```python
import os
NEEDLES = ["煤炭开采", "动力煤", "银行", "汽车零部件"]   # 挑该领域独有的词
hits = []
for dp, dn, fn in os.walk(ROOT):
    for f in fn:
        p = os.path.join(dp, f)
        try:
            if os.path.getsize(p) > 60*1024*1024: continue
            t = open(p, 'rb').read().decode('gbk', errors='ignore')
        except Exception:
            continue
        n = sum(1 for s in NEEDLES if s in t)
        if n >= 2: hits.append((n, os.path.relpath(p, ROOT), os.path.getsize(p)))
for h in sorted(hits, reverse=True)[:40]: print(h)
```
通达信文件**几乎全是 GBK**，必须 `decode('gbk', errors='ignore')` 才不会漏。
实测：4 万多个文件里一次命中 `T0002\cloud_cfg\hy_tree.xml`（研究行业树）—— 这是猜文件名永远找不到的。
同时留意 `mtime`：**安装包自带的静态文件不会自动更新**，它的新鲜度要单独论证。

**但名称搜索只是第二选择。先试"按代码前缀扫"——它更可能直接命中映射表本身。**
若已知目标是有编号体系的（如 881 板块指数、880 概念板块），先在**最可能的目录**里
逐文件统计该前缀的出现次数：

```python
import os, re
HQ = os.path.join(ROOT, "T0002", "hq_cache")     # 先扫单层目录就够，不必全盘
for f in sorted(os.listdir(HQ)):
    p = os.path.join(HQ, f)
    if not os.path.isfile(p): continue
    b = open(p, 'rb').read()
    n = len(re.findall(rb'881\d{3}', b))
    if n: print(f"{f:26s} {len(b):>10d}  881 出现 {n}")
```
实测一次扫出 5 个候选（`shs.tnf` 467 / `tdxzs3.cfg` 467 / `tdxzsbase2.cfg` 467 …），
再逐个 dump 前 20 行看格式 —— 其中 `tdxzs3.cfg` 就是**「名称|881代码|…|X代码」的直连映射表**，
比用名称做桥跨源拼接硬得多。**优先找直连映射，找不到才退化为名称桥接。**

### 第 3 步：解析可疑文件（GBK XML 用逐行正则，不要用 xml.etree）
把文件 `decode('gbk')` 成 str 之后再交给 `xml.etree`，**会静默返回空节点树**（本轮实测踩到）。
通达信的 XML 结构简单（`<node caption="..." blockid="...">`），**逐行正则 + 缩进计层级最稳**：

```python
import re
txt = open(path, 'rb').read().decode('gbk', 'ignore')
pat = re.compile(r'^(\s*)<node\s+(.*?)/?>\s*$')
recs = []
for ln in txt.splitlines():
    m = pat.match(ln)
    if not m: continue
    ind, at = m.group(1), m.group(2)
    cap = re.search(r'caption="([^"]*)"', at)
    bid = re.search(r'blockid="([^"]*)"', at)
    if bid: recs.append({'key': bid.group(1), 'name': cap.group(1) if cap else '',
                         'ind': len(ind.expandtabs(4))})
```
缩进档位去重后即为层级，可与编码位数交叉验证（实测两者完全吻合：30 / 127 / 312）。

### 第 4 步：实测协议能力（起服务器，别信文档）
```bash
# eltdx 与 pytdx 可共存于同一个 venv，直接做双库对照
C:/Users/river/.workbuddy/binaries/python/envs/default/Scripts/python.exe your_probe.py
```
- **枚举能力**：把库的命令注册表全列出来（`registry.py` / `grep '"<name>":'`），
  逐条判断哪些跟目标语义相关。结论写成「有 N 个命令，其中相关的只有 X 和 Y」——
  这比「没找到」有说服力得多。
- **能力验证**：对候选接口直接调用，打印**数量 + 样本 + 字段名**。
  空口说"能拿到"没有意义，必须给出「实测 467 个，带名称」这种可复现的数字。
- **反向验证**：改从服务器取，与本地文件取的结果**做集合差**。
  双向缺口都是个位数，才说明两个源等价可用做桥。

### 第 5 步：合成方案与差异清单
当单一来源都不完整时，**用名称做桥跨源拼接**，并量化：
- 命中率（实测 465/469 = 99.1%）
- 未命中清单 + **逐条定性原因**（已下架 / 改名 / 未收录）—— 这一步最有价值，
  它直接暴露了现有实现的问题
- **反向清单**：新方案里有哪些是在现有实现中根本不存在的

最后与现有实现逐条对比，产出**错在哪、错成什么样、影响哪个用户可见行为**：
> 漏 4 个已上线指数 → 用户勾选项时这 4 个不出现
> 留 7 个失效代码 → 扫描返回空
> 1 个名称错位 → 汽车链整体错一格，扫 A 显示 B 的名字

**名称匹配前必须做同义归一化**（`其它`→`其他`、全半角、空格），
否则「其它发电设备 / 其他发电设备」会被误判成缺失。这是最容易漏的一步。

### PE / 市值 的可替代性（2026-09-12 全量实测，可直接引用）

**PE-TTM**：A股 5224 只 vs 腾讯 `[39]` → **完全相同 5099（97.60%）**、差 ≤0.05 98 只、差 >0.05 22 只（仅 7 例相对差 >1%，集中在亏损股/科创板次新/周期股）、eltdx 空 5 只（**全为次新**，`tdxstat` 滞后；其中 2 只腾讯返回 0 而调用方本就过滤 0）。**eltdx 有值 / 腾讯为空 = 0**。
**流通市值**：随机 800 只 A 股 vs 腾讯 `[44]`×1e8 → **纯取整误差（|差| ≤ 50 万元 = 腾讯亿元两位小数的半格）790 只 = 98.75%**；超取整 9 只，其中仅 3 例相对差 >0.5%，最大 4.06%。
**市值差异根因 = 流通股本时效，不是口径错**：逐票拆股/价后确认**价格完全一致**（sz300112 两边都是 9.11），差异 100% 来自 `0x0010` 的流通股本（`updated_date` = 最近财报期，滞后于解禁/增发/转股）。典型：国民技术/成大生物「**总股本两边吻合但 eltdx 流通股本偏少**」（未计新解禁）；万讯自控连总股本也差 3.5%（腾讯整体更新更快）。

> **性能结论**：PE 替换 **13s(27 次 HTTP) → 1.2s(1 次 0x06B9)**；市值用 `finance_batch`+`get_snapshots` 自算 ≈2.6s 全市场（优于 `stock_profile_table` 的 7.7s）。

### ⚠️ `read_stats` 是「整体文件」——取单只与取全市场同耗时（2026-09-12 实测，决定架构）

这是**决定「要不要落盘缓存」的关键事实**，必须先量出来再谈方案：

| 取数规模 | 耗时 | 说明 |
|---|---|---|
| 取 **1 只** A 股 PE | **1.20~1.40s**（三次：1.20 / 1.26 / 1.40） | 与全市场**完全相同** |
| 取**全市场** 8037 只 PE | 同上 | `read_stats()` → `zhb.zip` 内 `tdxstat.cfg` **整包下载后本地解析** |
| 港股 1 只 PE（腾讯 `qt.gtimg.cn`） | ≈0.47s | 单只 HTTP，非整体文件 |

**为什么必须知道**：如果误以为「只取单只会快」，就会设计出「按需单只实时取数 + 不加缓存」的方案
却发现每次仍要 1.2~1.4s 而返工。反之，正因为**取单只 = 取全市场**，
「打开某个标的就取一次」在体验上完全可接受（本软件 K 线读本地 vipdoc、无实时行情，
新鲜度只需对齐「打开这个标的」这一动作）→ **正确决策是不加时间缓存**。
**反过来说：任何「为省时间而只取单只」的优化在该接口上不存在**，别在这条路上花时间。

### ⚠️ 反模式：把「每天变的量」和「季度变的量」塞进同一个缓存文件 + 同一次刷新

2026-09-12 实测的腐坏链（用户实际踩到）：`stock_pettm_index.json` 同时存
**PE-TTM（每日随行情变）** 与 **指数归属（季度调仓才变）**，只在点「刷新」时整体更新；
而实际使用中**不会每天点刷新** → 页面长期显示陈旧 PE。

诊断这类问题的**通用问法**：把每个字段的**真变化周期**写出来，再问「这份缓存/这次刷新的周期是否与之一致」。
不一致就是缺陷，且**会静默存在**（页面照常显示，只是数字是旧的）。

修法（本轮落地，可直接复用）：

1. **按变化周期拆文件** —— PE 不再落盘（实时取），指数归属留在 `stock_index_belong.json`；
2. **改名而非同名换内容**，并为旧文件写**一次性自动迁移**（新文件不存在且旧文件存在 → 读旧字段写新文件，
   **旧文件保留不删**，回退 = 什么都不做）；
3. **把刷新按钮里过期的那个区块删掉**（不要留着"顺便也刷一下"——那会重新引入双时间维度）；
4. **前端同步**：按钮 title 里的过期口径要去掉，否则用户仍以为刷新会更新 PE。

### 实时化的三个必备件（少一个就出事故）

「打开即取」不是把落盘读换成网络调用就完了，必须同时设计：

1. **single-flight 用「非阻塞 acquire」而不是排队等待**。多标签页/多请求并发首开同一标的时，
   抢不到锁的请求**立即返回当前表**（不排队）—— 代价是那一两次页面 PE 为空，
   收益是「一个卡住的网络请求不会把整批请求一起拖住」。若用阻塞锁，一次网络卡顿会放大成整批超时。
2. **失败静默降级，不向上抛**。元数据（PE）取数失败不该让 K 线接口整体 500 ——
   捕获后记 `log.info`、保留旧值、返回 `None`。**与「前复权失败即显著报错」是不同策略**，别一刀切。
3. **保留一个「冻结旗」给快照/回归测试**。实时化最容易打掉的是**测试确定性**——
   若测试直接调点查函数，就会真的联网。做法：留 `_pe_loaded` 这类旗（语义 =「表由外部提供」），
   置真即**短路实时层变纯点查**；快照用例注入内存表 + 置旗即可冻结基线，**零改动通过**。
   要先 grep 测试是怎么注入内存表的（本轮实测 `snapshot_runner.py` / `test_trigger_step_replay.py`
   直接 `_pe = {...}`，**不经 json**）→ 所以「只改填充来源、不动点查接口」就不会破坏它们。

**注入点选择受架构守卫约束，先查守卫再选位置**：本轮 `AppData` 不得 import `DataAPI`
（phase5 守卫防影子双源）→ 取数实现只能**依赖倒置注入**；而 phase4 守卫的数据源白名单
**只放 `AppRefresh`** → 注入点不能挪到 `AppEngine`/`AppOrch`。**顺序是：先跑守卫测试确认合法位置，再写代码**，
否则会写一个"看起来更干净"但被守卫拦下的实现。

### ⚠️ 「归一化到单一数据源」的通用反模式（2026-09-12 教训）

用户提出「把 X 也统一到 Y 库，方便维护」时，**不要只回答能不能**，必须同时回答**故障域**问题：

1. **算清合并后有几个故障域**。实测该库已是前复权 + 板块刷新的**单点**；再把 PE/市值并入 → 一次 7709 不可用会**同时打掉 4 个功能**。原设计刻意保留的「失败即显著报错、不静默降级」在单源化后必须**重新设计降级策略**。
2. **盘后能测，不等于盘中能测**。`tdxstat.cfg` 是**盘后快照**（`stats_date` 是日期，无时刻）；腾讯是实时接口。**周六盘后测出的 97.6% 一致不能外推到盘中** —— 必须在交易日再复测，并把「未验证」写进结论，不要用「一致」掩盖时间口径差异。
3. **单位必须逐项对齐**（本次实测：`resources.read_stats` 的市值单位是元、腾讯是亿元；阈值与缓存文件都是亿元，换算错会静默把预过滤全灭）。
4. **要给出可回退的分档方案**（档1 只归一化最受益的那一项 → 档2 → 档3 全量），而不是「能/不能」的二元答复。用户要的是「变更波及面可控、可一键回退」。
5. **但用户可能明确选择全量档 —— 此时不要再劝，改为"把代价写进交付物 + 交付最小可替换单元"**。
   本轮实测：给出分档建议后用户回复「我就要一次做完，归一化，方便维护」，于是正确做法变成：
   * **不要**再退回分档实现（那是无视明确指令）；
   * 把「缺包/通道故障会同时打掉哪几个功能」**逐条写进交付说明的坑点段**（本轮是 5 个：除权除息 / 前复权 / 板块刷新 / A 股 PE-TTM / A 股流通市值）；
   * **按目录层级交付可覆盖文件集**（而非全仓 patch），使回退 = 删掉新增文件 + 还原被覆盖文件；
   * 用**真实 A/B 对照**证明"零回归"，而不是只说"测试通过"（见下条）。

6. **回归结论必须来自 A/B 双树对照，不能只看改动树的通过数**。
   本轮实测：改动树 44/46 看着"有失败"，但**未改动的基线树同样 44/46 且失败项完全相同** →
   零回归。做法：把仓库复制成两棵**对称补齐资源**的树（缺 `Frontend/`、`Test/fixtures/` 会造成大量
   假失败 —— 本轮初测因只复制 `.py` 而出现 15 个假失败），一棵打补丁一棵不打，逐组件比对 `ok` 标志。
   **判据是"46 个组件的 ok 标志全等"，不是"通过数相同"**（数量相同但失败项不同是完全不同的事）。
   对残余失败要**定性到根因**（本轮 2 个 = 用户自己 auto-order 功能的路由/window API 未登记，与数据源改动无关）。

7. **「按市场分流」≠「按标的类别分流」—— 单源化最隐蔽的漏失**（2026-09-12 实测回归，用户报障才发现）。
   分流规则若只判 `market ∈ {sh,sz,bj}`，就会把**指数**一并送进新源（`sh000001` 的 market 同样是 `sh`）；
   而新源的覆盖范围是按**标的类别**划的（eltdx 统计文件只含沪深股票）→ **指数 PE 静默变空**，
   且它不在涨停/跌停这类"显眼"的地方暴露，只表现为「打开指数没有 PE 数值」。

   **落地前的必做动作**：把旧源的**全部标的类别**列成清单，逐类喂给新源做覆盖性实测，尤其注意
   **与普通股票共享市场前缀**的那几类：`指数`（`sh000xxx`/`sz399xxx`）、板块指数（`sh88xxxx`）、
   ETF、转债、北交所。**只测"普通股票"就等于没测。**

   判据：`_split_by_source` 这类函数必须同时考虑两个维度 —— **市场** *与* **标的类别**。
   本项目已有 `App/utils.py::is_index` 作单一事实源；`DataAPI` 层不能反向 import App，
   故在 `MarketStatsAPI` 内实现 `_is_index_symbol` 并用**全量真实代码**（vipdoc 7955 条）做一致性
   守卫测试锁死两份判定零分歧，而不是靠"记得同步改两处"。

   **一个可复用的自检问句**：*「这个新源的覆盖集合，是不是和旧源的覆盖集合逐类对齐过？」*
   若答不上来，就不算验证过。

### 文档行号会随上游重构整体漂移 → 交付"断言化核验脚本"

凡产出**带行号引用的文档**（数据源清单 / 架构说明 / 接口清单），行号是**最先失效**的部分：
上游一次重构（本轮 `TdxAPI.py` 2355→2067）就让整份文档的行号集体作废，而**失效是静默的**。

做法：把文档里每一条 `文件:行号` 与每个「N 行」声明，写成**可执行断言表**随文档一起交付：

```python
LINE_ASSERTS = [
    # (相对路径, 行号, 该行必须包含的子串, 文档出处)
    ("DataAPI/TdxAPI.py", 1234, "def refresh_block_files", "三 刷新入口"),
    ("DataAPI/ElTdxAPI.py", 324, "def download_block_files_via_eltdx", "三 eltdx 批量下载"),
]
LINE_COUNT_ASSERTS = [("DataAPI/TxAPI.py", 132, "附A 腾讯"), ...]
NEGATIVE_ASSERTS = [("pytdx", "TdxAPI 中不应再有 pytdx 引用", ["DataAPI/TdxAPI.py", ...]), ...]
```

要点：
* **断言"该行含某关键子串"而非"整行相等"** —— 容忍缩进/注释微调，但函数名、关键语句、
  配置项名一漂移就报错。
* **务必包含负面断言**：文档声称「X 已删除/已下线」时，必须真的 grep 不到。
  没有负面断言，"已删除"这类结论就没人守。
* 行号口径与文档对齐（`content.count("\n")`，等价 `wc -l`），避免出现"132 还是 133"的假失败。
* **同时拿脚本跑两棵树**：对**已打补丁的树**应 0 失败；对**未打补丁的基线树**，
  失败项应**恰好等于本次改动的落点** —— 这既是复验，也是"基线未漂移、补丁能干净应用"的证明。
  若基线树上出现**计划外**的失败，说明用户项目已被改动，直接覆盖会出事故。

### `zhb.zip` = 板块 cfg 的下载载体（2026-09-11 实测，关键突破口）

"meta=`size=0` 所以只能读本地"这个结论**只对"按文件名直接下载"成立**。这些文件其实躺在
**`zhb.zip`** 里，而 `zhb.zip` 本身是**可下载**的：

```python
get_block_info_meta("zhb.zip")   # → size=1406899
```

- `zhb.zip` 内含 **46 个条目**，含 `tdxzs3.cfg` / `tdxzs.cfg` / `tdxstat.cfg` /
  `incon.dat` / `ilong.dat` / `nbcomte.dat` 等。
- **客户端解包去向分两处**：`incon.dat` / `ilong.dat` / `nbcomte.dat` → 安装根目录；
  其余 → `T0002/hq_cache/`。所以"磁盘上某个 cfg 来自哪里"可直接从 zip 里反查。
- 意义：即使本地文件损坏/缺失，也能**联网自愈**（下一版可加"板块刷新时拉 zhb.zip 补文件"）。

### 证明某个 cfg 确实随盘后下载更新（三方字节同一法）

不要靠"看 mtime 是今天"下结论 —— 复制/解压都会刷新 mtime。做法是**三方 sha1 对照**：

| 来源 | 取法 |
|---|---|
| 磁盘 | `<TDX>/T0002/hq_cache/<file>` 直接读 |
| 本地 zip | `T0002/hq_cache/zhb.zip`（客户端下载时留下的副本） |
| 服务器 zip | 现下 `zhb.zip` 后解出同名条目 |

三者 sha1 全等（实测 `tdxzs3.cfg` = `d51e0f9e0d6a`）→ 证"盘上这份就是服务器发的最新版，
且本地 zip 是它的原始载体"。
**额外证据**：zip 内部条目的时间戳是**"内容最后变更时间"而非打包时间**（实测跨度
2024-03-29 ~ 2026-09-10，各不相同）。所以 `tdxzs3.cfg` 内部时间 `2026-09-10 17:53:24`
== 磁盘 mtime，直接证明它是**被内容更新驱动**地落盘的，即随盘后下载刷新。

**层级来源之二（次选，需名称桥接）：`<TDX_INSTALL_DIR>/T0002/cloud_cfg/hy_tree.xml`**
安装包自带的静态文件（mtime 常年不变，实测 2024-04），协议下不到，可提供
**名称 + 嵌套层级**（`<node caption="名称" blockid="X编码">`），但**不含 881 代码**，
必须再拿 881 代码表按名称桥接 —— 故 `tdxzs3.cfg` 存在时应优先用后者。
程序化定位：若代码里已有 `_get_hq_cache_dir()` 之类从 `vipdoc_dir` 推 `T0002/hq_cache` 的函数，
`cloud_cfg/` 就在同一层 `T0002/` 下。

## 首选权威源：`T0002/hq_cache/tdxzs3.cfg`（2026-09-11 实测发现）

**这是「研究行业 881 指数 ↔ X 行业码」的直连映射表，本地文件、零联网，取代了所有名称桥接方案。**

```
路径：<TDX_INSTALL_DIR>/T0002/hq_cache/tdxzs3.cfg    （GBK 文本）
格式：名称|881代码|12|1|0|X代码
      ↑field0  ↑field1  ↑f2 ↑f3 ↑f4 ↑field5 = X 行业码
煤炭|881001|12|1|0|X10
煤炭开采|881002|12|1|0|X1001
汽车零部件|881218|12|1|0|X2603
车身附件及饰件|881219|12|1|1|X260301
```
- 解析：`line.split("|")`，取 `[0]` 名称、`[1]` **必须 `fullmatch(r"881\d{3}")`**、
  `[5]` **必须 `match(r"X\d+")`** —— 非 881 行（880 板块指数 / 880 地区）靠这两个正则自然跳过。
- **层级 = `len(X) - 1`**（X+2 一级 / X+4 二级 / X+6 三级）。实测 30 / 128 / 309，与
  `hy_tree.xml` 的嵌套深度完全吻合，互为交叉验证。
- 同批盘后下载的邻居（可互相印证新鲜度）：`tdxhy.cfg`（股票→X）、`tdxzsbase.cfg`、`shs.tnf`。
- **合法性下限必须设**（实测用 300）：文件被截断/损坏时宁可弃用回退，也绝不让"半张表"静默生效 ——
  少一半行业的后果比数据过期严重得多。

**次选：`T0002/hq_cache/shs.tnf`（沪市代码表，含 881 代码 + 名称）**
无表头文档，格式靠实测破解：**50 字节头 + N × 360 字节定长记录**，N = `(size-50)/360`
（实测 27920，与服务器 `get_security_count(1)` 一致）。每条记录：`[0:6]` 为 ASCII 代码，
**名称起始于记录内偏移 31**，GBK，到连续两个 `0x00` 结束：

```python
if r[:6].isdigit():
    off = next(i for i in range(6, REC-1) if r[i] > 0x80)
    end = off
    while end < REC and not (r[end] == 0 and r[end+1] == 0): end += 1
    name = r[off:end].decode('gbk', 'replace').replace('\x00', '').strip()
```

## 核实出"硬编码表已过期"之后怎么修（两层，可分别交付）

这类表的本质是**移动靶的快照** —— 只修数据，下次通达信重构行业树会原样复发，且症状一样隐蔽。
建议拆成两层、各自独立可选：

1. **数据层**：把内嵌表校正到与权威源逐条一致。改动要**两张表对称套用**
   （正向 `X→881` 与反向 `881→X`），改完必须验双向自洽（`rev[fwd[x][1]] == (x, fwd[x][0])`）。
2. **机制层**：加一个**本地权威源优先、缺失即回退**的解析器，替掉原来的"直接返回硬编码"。
   要点（缺一不可）：
   - 解析结果按 `(路径, mtime, size)` 三元组缓存，文件更新自动失效；
   - 用**叶子锁**保护（只护本缓存，持锁期间不取任何其它锁）—— 项目若已有锁设计文档，必须遵守其锁序；
   - 任何异常就地吞掉 + WARNING，**降级不得阻断业务路径**；
   - 设 `MIN_ROWS` 合法性下限，残缺文件宁可回退也不用；
   - 入口选**项目自称的"单一加载点"**（如 `load_tdxhy_mapping`）—— 一处改动可同时修好多条消费路径。

交付时**给两个变体**（完整版 / 仅数据版），因为后者波及面明显更小、可一键回退成前者。
务必从 zip 解压到**干净目录**复验两个变体都工作，再交付。

### 第三层（最彻底）：删掉内嵌快照，改成完全单源

权威源证明会随下载刷新之后，**修数据就是治标** —— 内嵌表是"移动靶的快照"，早删早好。
但要删得干净，**必须同时处理这三件事，缺一件就会出事故**：

1. **启动期的裸调用**。解析器常被插在启动路径里（本项目 `AppEngine.py` 一行裸调用）。
   删表后文件一旦缺失，**启动直接崩**。改为 `try/except` + WARNING，**降级不得阻断启动**。
   —— 先 grep 出所有调用点，别只改那个"看起来是唯一入口"的函数。
2. **测试里的冻结断言**（最隐蔽，本轮就是这么翻车的）。仓库常把行数/内容哈希**写死在测试里**：
   实测 `Test/test_blk_parsing.py` 硬编码 `len(tdxhy2)==125` / `len(tdxhy3)==315`，
   `Test/test_industry_mapping.py` 把 470 行内容 sha256 冻结进 `Test/snapshots/*.json`。
   删表后这些测试**必红，且与你的改动正确与否无关**。
   → **动手前先搜**：`grep -rnE '\b(125|315|470)\b|sha256|hashlib' Test/`，
   把所有"冻结的旧事实"改成"**契约式断言**"（校验"必须从哪个文件读 / 最少多少行 /
   禁止内嵌快照回潮"，而不是校验具体内容哈希）。
3. **前端错误可见性**。单源后"文件缺失"是**可预期的运行时状态**，必须让用户看见。
   实测该项目的 `FrontAPI` 异常处理器把 `RuntimeError` 吞成 `{"detail":"服务器内部错误"}`，
   而前端只读 `errors` 字段 → 用户只看到"0 个候选股"，完全不知道自己缺文件。
   → 正确做法是**沿用项目已有的降级范式**（本项目是 `errors.append(msg)` + WARNING + `continue`，
   与"流通市值缺失/预过滤失败"同款），而不是往外抛异常。

删完的验收标准是**功能零变化**：新单源加载器产出的映射摘要（行数 + 各层级计数 + 逐条 digest）
必须与删表前**完全一致**，同时行数大幅下降（本轮 −858 行 / 文件从 ~2600 行降到 1754 行）。

## 陷阱

- **别假设 eltdx 覆盖港股 —— 它完全不支持**（2026-09-12 实测）。`codes.all("hk")` 抛 `ValueError: invalid market`、
  `stock_profile_table(["hk00700"])` 抛 `ProtocolError: invalid code`，而腾讯 `hk00700` 正常返回 PE/市值。
  这个缺口最容易漏：**只有先把消费链路的代码读完**（发现 `_refresh_pe_ttm` 里赫然写着 `mkt == "hk"` 分支），
  才会意识到「全量替换」会静默丢掉一整类标的。
- **eltdx `0x054C` 批量快照混入北交所会整批抛异常**。单只 `get_snapshots([bj9200xx])` 20/20 成功，
  但 `get_snapshots(bj[i:i+10])` 必现 `ProtocolError: snapshot record marker not found: bj920025`，
  且是**整批失败**（不是跳过单条）。凡走 `stock_profile_table` / `full_quotes`（内部即 `0x054C`）的批量取数，
  候选池含北交所时必须**按市场分批隔离**。
- **`zhb.zip` 里除板块 cfg 外还有 `tdxstat.cfg` / `tdxstat2.cfg`** —— 这是「全市场 PE-TTM / 自由流通股本 /
  涨停统计」的载体，`resources.read_stats()` 已封装。**先看 `zhb.zip` 的条目清单（46 项），再决定要不要找新接口**。
- **对比腾讯行情字段时，先验标签再信标签**。实测腾讯 `[39]` 被文档标为「市盈率-**动态**」，
  但其值与 TDX `tdxstat.cfg` 的**滚动市盈率**浮点严格相等 → 实为 **TTM** 口径。
  做法：拉一条**完整记录**（`q=sh600519` 返回 88 个字段）打印全部字段，而不是只取被引用的那一个。
- **`incon.dat` 是证监会行业分类**（`#ZJHHY`），与通达信研究行业不是一套，别拿它当层级来源。
- **别用 pytdx 枚举全量代码表 —— 会静默漏掉整块，得到假阴性**（本轮实测踩到，代价很大）。
  `pytdx.get_security_list(market, start)` 在**分块边界**上会返回空列表，且**重试 5 次仍为空**、
  不抛异常。实测 `(1, 0)` 与 `(1, 21000)` 都返回空 → 得出"881 只有 323 个"的**错误结论**，
  并写进了交付报告，直到换 eltdx 才发现真相是 467 个。
  **改用 `eltdx` 的 `client.codes.all("sh")` 过滤 `881`**，并用 `get_security_count(market)`
  交叉核对总数。
  教训：**枚举类结论一旦与"应有总数"对不上，先怀疑取数通道，别急着当事实写进报告** ——
  漏取和"确实没有"在返回值上长得一模一样。
- **`hy_tree1_total.xml` 是主题/概念树**，不是行业树。
- **重名检查**：881 代码表里有没有重名行业？（实测 0 个，所以名称可以当唯一键 —— 但必须验，不能假设）。
- **"下架的 881 代码"不一定是空结果 —— 有一半是静默返回残票**（本轮实测，极易误判）。
  `tdxzs3.cfg` 里没有的 X 码，在 `tdxhy.cfg` 里**可能仍挂着 1~2 只股票的旧码行**。
  实测 7 个下架码：3 个真返回空（日志 `❌ 未找到成分股`），4 个静默返回 1~2 只存量残票、**不报错**。
  所以判定"某个 881 已失效"必须**同时查两处**：行业树（`tdxzs3.cfg`）里在不在 + `tdxhy.cfg` 里有几行挂着它。
  只看"返回是否为空"会把 4 个静默错误漏掉。
- **不要动用户项目目录**。核实类任务的产出是**独立报告 + 复现脚本**，不是代码改动。
  若确实要改，先在沙盒改、打包交付。
- **沙盒里补全仓库时，下载脚本会覆盖你已打补丁的文件**（本轮实测踩到）。
  用 GitHub API 批量下载源码时，脚本常见写法是"size 与 tree 不符即重下" —— 打过补丁的文件
  size 必然不符，于是被静默还原成原始版。**必须维护一个 `PROTECTED` 名单跳过它们**，
  或者改完补丁后再下载。踩到后表现为"diff 显示 0 处改动"，很容易误判成"补丁没生效"。
