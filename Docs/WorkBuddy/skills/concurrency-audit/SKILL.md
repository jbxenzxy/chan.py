# 并发安全审计

## 何时用

- "多开几个页面/标签页同时操作会不会出问题"
- "锁设计完备吗""能不能支持并发"
- "两个用户同时做 X 会怎样"
- 用户已有一份并发/锁设计文档，要按它核查代码现状

## 核心立场（先看这条）

**死锁、数据竞争往往不是最大风险。** 实践中真正的 P0 常是：

1. **作用域误用** —— 把"会话级状态"放到了"进程级"。单用户测试 100% 正常，第二个用户出现就炸，且静默。
2. **静默降级** —— 不崩溃、不报错，只是数据错了或系统变慢。
3. **跨用户互相破坏** —— 一个用户的操作干掉另一个用户的会话/缓存。

这三类**都不是加锁能解决的**。如果你的审计结论只是"这里少把锁"，大概率漏了重点。

## 流程

### 0. 拿到代码并确认基线

```bash
# GitHub 直连不通时依次尝试镜像（实测 gh-proxy.com 可用）
git clone --branch <branch> --depth 50 https://gh-proxy.com/https://github.com/<owner>/<repo>.git <dir>

# 若用户本地已有副本，先确认远端与本地是否一致（忽略换行符！）
diff -rq --strip-trailing-cr --exclude='.venv' --exclude='__pycache__' --exclude='.git' <local> <clone>
```

记录 commit hash，**报告中每个行号都要标注属于哪个 commit**。

### 1. 先梳理功能清单（不可跳过）

没有功能清单，并发分析就是空中楼阁。双向取证：后端路由表 × 前端触发点。

- 全部端点：方法 + 路径 + 落在哪类执行体
- 前端每个请求点：`文件:行号` → URL → 触发它的用户操作
- **定时器全清单**（`setInterval`/`setTimeout`）—— 自动持续发请求，是并发压力主源
- **长连接点**（SSE/WebSocket）—— 一个页面能同时开几条？
- 标记：写共享状态？重计算？长连接？支持多窗口？

**务必澄清"多窗口/双窗口"的真实代价**——不要只看请求数：

| 口径 | 要看什么 |
|---|---|
| 请求数 | 一次用户操作发几个 HTTP 请求 |
| 连接数 | 开几条长连接 |
| **算力** | 后端建了几个重量级对象（如独立的分析引擎实例） |
| **缓存占用** | 占几个缓存槽 |

同一个功能在这四个口径上结论可能完全不同。只报"请求数=1"会误导。

### 2. 并发地形图 + 实测执行体假设

**不要相信框架文档对执行体的描述，去读框架源码 + 跑实测。**

重点验证："长连接/SSE 是每连接一条常驻线程吗？" 常见答案是**否**——
很多框架对同步生成器是**每帧一次独立的线程池派发**（如 starlette 的
`concurrency.py:57` 每帧 `anyio.to_thread.run_sync`）。

后果：入口设一次的 thread-local，从第二帧起就失效。

**同时枚举三个并发来源**（很多人只想第一个）：
- 多页并发（多标签页/多浏览器/多机器）
- **单页内并发**（一个页面多个飞行中请求！一个用户就能制造竞态）
- 跨进程并发（生产进程 vs 独立脚本进程）

单页内并发典型形态：请求无取消机制（无 `AbortController`），后到响应覆盖先到。
**后端加锁对它无效**，因为竞态在前端共享变量上。

### 3. 共享资源登记 + 裸出口扫描

按落点分类登记：模块级全局 / 类级静态 / 实例字段 / thread-local / contextvars /
**前端模块级单例**。

裸出口（比"没加锁"更隐蔽）：
- `@property` 直接 `return self._xxx`（xxx 是可变容器）
- 模块级别名：`X = app_data.names`（此后绕开 `self.` 直接读写）
- 函数返回内部活对象（如 `return self._annotations.get(key, [])`）

**用 AST 脚本扫，别靠肉眼。** 检查项目自带的资源登记表是否覆盖了全部条目。

### 4. 锁覆盖度审计

对每个操作问：是读-改-写（RMW）吗？遍历期间会被改吗？

高频缺口模式：
- "取对象 → 锁外改 → 写回"跨锁边界 → 丢失更新
- flag 先置位后填充 → 读者拿到半成品且不再重试
- **锁只护住"取指针"，遍历在锁外**（护容器不护对象图）
- 读者把取到的"缓存"当私有对象改 → 污染共享缓存
- 递增与释放不在同一 `try/finally`
- 进程池/子进程里用 `threading.Lock`（无效，父子进程各持副本）
- 跨进程共享文件用 `threading.Lock` 而非文件锁

### 5. 作用域归属检查（最高价值，最易漏）

#### 先定义"会话"

"进程级"是 OS 概念，边界清晰；但**"会话级"不是 OS 概念，是业务概念——没有默认值，必须自己定义**。

不要抽象地问"什么是会话"，会空转。**反过来问：**

> **"如果两个人同时用，什么东西应该是每人一份的？"**

**这个"每人一份"的载体，就是会话边界。** 边界不是先定义后套用的，是从"什么该隔离"里推出来的。

常见层级（由小到大）：请求级 → 连接级 → 任务级（task_id）→ 标签页级 → 用户级 → **进程级** → 主机级（跨进程/文件）。
判据：**找出"谁的"**——答案是"这台机器上所有人"的，才放进程级。

#### 两种错配模式（形态与修法都不同）

**模式 A：会话级数据，存放在进程级容器里**
> 典型：用户的任务参数存在模块级全局变量（后发起的覆盖先发起的）；单例服务对象持有当前任务上下文。
> 判据：第二个任务/用户进来，会不会覆盖第一个的**参数或数据**？

**模式 B：会话级资源，被进程级操作管理** ← **更隐蔽**
> 对象本身是每会话一份的（**这部分做对了**），但管理它的**清理/重置/遍历动作是进程级的**。
> 典型：每条连接一个 Session 对象（正确），但 `close_all()` 遍历**全局注册表**一次关掉所有连接（错）。
> 判据：清理动作的作用域，是否**大于**被清理对象的生命周期归属？
> **为什么易漏**：审查时看到"每连接一份，没问题"就翻篇了。错的是管理它的动作，不在对象本身。

**这类问题的判据不是"会不会崩"，而是"第二个用户出现时会怎样"。**
它在单用户测试时 100% 正常，只在第二个用户出现时爆炸，且往往静默。

#### 层级 ↔ 锁：不要做 1:1 映射（常见追问）

列出上面 7 个层级后，用户几乎一定会问："每一级对应什么锁？"

**答：不能一一对应，强行映射是范畴错误——层级和锁是两个正交维度。**
- 层级描述"**状态属于谁**"（归属）→ 决定 ①要不要锁 ②**锁的分片键**
- 锁的原语类型由"**谁会同时访问它**"（并发关系）决定

| 层级 | 要不要锁 | 分片键 |
|---|---|---|
| 请求级 | 通常不要（消灭共享） | 无 |
| 连接级 | 看访问者（若逐帧换线程 → 要） | `conn_id` |
| 任务级 | 要 | `task_id` |
| 标签页级 | 不要（前端 JS 单线程） | `tab_id`（只用于**取消**，非互斥） |
| 用户级 | 要 | `user_id` |
| 进程级 | 要 | 无（全局一把） |
| 主机级 | 要 | 文件路径 / DB 行 |

| 访问者关系 | 原语 |
|---|---|
| 同进程不同线程 | `threading.Lock` / `RLock` |
| 同进程不同协程 | 通常不需要；跨 `await` 的 RMW 才用 `asyncio.Lock`（临界区不得跨 `await`） |
| 同主机不同进程 | OS 文件锁 / `multiprocessing.Lock` / SQLite WAL |
| 不同主机 | 分布式锁（DB 行锁 / Redis / etcd） |

**分片键是层级最有用的产物**：进程级全局锁把所有操作串成一行；任务级按 `task_id` 分片后不同任务互不阻塞。选错层级，性能差一个数量级。

#### 一份资源可以同时落在多个层级 → 多层锁必须叠加

层级**不是互斥的分类，而是可叠加的**。这是最反直觉、最易错的点。

实测模板（两进程各自增 N 次，应得 2N）：
- 只有进程级锁 → **丢更新**（实测 105/120）。`threading.Lock` 是进程内对象，另一进程持有的是另一个副本。
- 进程级 + 主机级文件锁**嵌套叠加** → **正确**（120/120）。
- 注意：Windows `msvcrt.locking` 能挡同进程异线程，但这是**平台行为**；POSIX `flock` 关联 open file description，语义不同。**不可依赖 → 进程级锁仍需显式加。**

**锁顺序固定：先进程内、后跨进程（先小作用域后大作用域）。** 反过来会放大阻塞范围。

> 反例：某状态是任务级却放进程级 —— 即使补一把 `threading.Lock`，也只是让两个任务**串行地互相覆盖**。
> **锁类型选对了、层级错了，结果仍然错。** 加锁只是把引信接长，不是拆弹。

### 6. 临界区重量检查（不是容量检查）

**注意区分**：本步骤只查"临界区内做了重活"，这属于锁粒度问题。
**单纯的容量问题（线程池/连接池大小、缓存容量与淘汰策略、配额）不属互斥锁范畴**，
除非用户明确要求，否则不要写进锁审计报告——会稀释主线。

判据：**临界区内只允许做"必须互斥"的那几行。**
凡是可以挪到锁外的（I/O、GC、重计算、日志格式化），都挪出去——
锁的代价不止串行化，还有**阻塞放大**：临界区内每一点工作都被所有等待线程摊上。

> 典型案例：在持锁时执行 `gc.collect()`（stop-the-world GC 发生在临界区内）。

### 7. 场景判定与整改清单

按用户实际关心的场景出判定表（多股票页/多期货页/…），每个功能组标：
安全 / 基本可用 / 有风险 / 不支持。

整改清单按 P0/P1/P2 排，**每条标注性质**：`架构`（改归属/改作用域）/ `加锁` / `契约收口` / `性能` / `清理`。
让用户一眼看出哪些不是"加把锁"能解决的。

## 四个硬教训

### ⚠️ 警惕验证脚本的假阴性

验证脚本本身可能有 bug，而**"没发现问题"比"发现问题"更危险，因为你会信它**。

真实案例：用 `threading.current_thread().name` 统计线程切换，
得到"0 次切换"的假阴性——AnyIO 工作线程的 name **全部相同**
（都是 `"AnyIO worker thread"`）。必须用 `threading.get_ident()`。
改用线程 ID 后真实结果是"11/11 全部切换"。

**判据：验证脚本要先自证能检出已知问题。** 先构造一个必然触发该问题的场景跑一遍，
确认它能报出来，再拿去测未知场景。

### ⚠️ 文档里的行号会腐烂

后续一次提交就可能让全文行号失效（本次：一次"更新 lock"提交让代码整体前移，
裸 property 从 1376 迁到 1466）。

**约定：引用写成 `文件:行号 @ <commit>`，或只引符号名（函数名/字段名）+ 大致区域。**

### ⚠️ 静态扫描器的覆盖面就是盲区

反向扫描（从受保护字段出发查所有访问点）方向正确，但实现常太窄。
**必须覆盖三种形态**，漏一种就有系统性盲区：

| 形态 | 例子 |
|---|---|
| 实例字段 | `self._pe` + `with self._锁:` |
| 模块级别名 | `_pe_ttm_cache = app_data.pe_cache`，此后绕开 `self.` |
| 跨模块守卫方法 | `with app_data.xxx_guarded(key)` |

另检查：扫描器扫了几个文件？（常见只扫核心数据层，业务层全在视野外）

### ⚠️ 别把"容量"塞进锁审计

线程池大小、连接池、缓存容量与淘汰策略、配额——这些影响的是性能与可用性，
**不属于"互斥锁设计"的讨论范围**。混进来会稀释主线，用户也会明确要求拿掉。

**唯一例外**：如果容量问题的**根因在锁上**（如"在持锁时做重活导致阻塞放大"），
那它属于锁粒度问题，应剥离出来单独报，而不是整条归入容量。

先问用户要不要覆盖容量；默认不覆盖。

## 并行化建议

代码量大时，派 3 个后台 agent 并行（用 `run_in_background: true`）：
1. 共享资源登记 + 裸出口扫描
2. 锁覆盖度 + RMW/对象图/生命周期审计
3. 前端功能清单梳理

自己同时做**需要实测的关键验证**（执行体派发、线程池容量）——agent 容易凭注释下结论。

## 交付

生成 HTML 报告（浅色主题），结构：
摘要卡片 → 功能清单 → 并发地形（含实测数据） → 锁审计（已修/未修对照表） →
新发现 → 场景判定矩阵 → 整改清单 → 对用户提问的回应。

**每条结论都必须带 `文件:行号` 证据 + 代码片段**，不采信代码注释
（注释与代码矛盾时要指出，那是误导源）。
