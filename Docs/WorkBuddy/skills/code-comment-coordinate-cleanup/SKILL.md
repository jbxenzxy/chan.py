# 代码注释「过程坐标」清理

和 `code-driven-doc-refresh` 是**同一原则的两个面**：那个清文档，这个清注释。
共同判据：**只在开发过程中才有意义的坐标 → 删；「为什么这么写」 → 留。**

## 适用与不适用

- **适用**：注释/docstring 里堆积了阶段号、工单号、死章节引用、墓碑注释、日期戳。
- **不适用**：注释本身就是**领域数据**（`# 格式: 2021-09-13`、夹具日历）。
  这类必须**显式保护**，见 §3 的安全阀。
- **边界**：若仓库有「不可改模块」约束（如核心算法目录），把它们放进 `CORE_DIRS` 跳过。
  交付时要**明确报告**这些目录里的残留是**规则性跳过**，不是漏网。

## 1. 核心设计：**哨兵标记法**（这是整份技能的关键）

**不要**用「命中 token → 替换成空串」。删完之后你**无法再判断**哪个标点是被删
token 留下的孤儿、哪个是正文，只能靠"孤儿标点"这类过宽规则硬猜，必然误删正文。
实测踩过的坑（每条都是真事故）：

| 天真规则 | 真事故 |
|---|---|
| 孤儿加号 `+` | `200 + status=ok` → `200 status=ok` |
| 孤儿斜杠 `/` | `exchange / last_trade_date` → 两词黏死 |
| 列表连接符 `·`/`—` | `作用域 —— X1（…）` → `作用域 —（…）`（破折号削半） |
| 清空括号（含 ASCII） | `clear()+update()` → `clear+update`（**函数调用括号被吃**） |
| 清空括号（字符类跨括号） | `alert()"）。` → `alert。`（docstring 直接崩） |
| `^[：:]+` 去行首冒号 | 吃掉注释的**刻意缩进** |
| 合并连续分隔符 | `Script/，仓库根` → `Script/仓库根`（`/，` 被当残留） |

**做法**：删除点写成 `SENT = "\x00"`，收尾阶段按「删除点两侧到底是什么」精确判断。

```
① 两个删除点紧邻 → 合一；中间的连接符/连词（· / 与 和 及）一并吃
② **纯列表连接符**（只 `· / ／`）紧跟删除点 → 一并吃
   ⚠️ 绝不含 `，、；` —— 它们是子句分隔，吃掉会断句
      真事故：`口子（原注释）；Phase 10 启用第三项` → `口子（原注释）启用第三项`
③ 括号场景：`（SENT）` 整段删；`\s*SENT\s*[SEPCH]*\s*([）)])` → `\1`（**回填原括号类型**，
   否则 `(` 被换成 `（`—— 实测 5 个文件被串换，靠"全文件括号平衡"才抓出来）
④ 删除点本体：两侧都不是「代码字符」→ 直接删（中文黏合）；
   有一侧是代码字符（`A-Za-z0-9_+\-*/=<>`）→ 补一个空格（否则 `+D6` 黏死）
⑤ 残余标点归一 + 空白归一
```

⚠️ **空白归一必须限定在删除点附近**，不能对整段生效。写成
`re.sub(r'(?<=[\u4e00-\u9fff])\s+(?=[\u4e00-\u9fff])', '', t)` 这种**整段规则**会
把与删除无关的地方也压掉（实测 13 处）：

```
部分成交 契约测试 → 部分成交契约测试      上海/深圳/北京/香港 计数 → …香港计数
```

正确做法：只处理**紧邻哨兵**的空白（`\x00\s+` / `\s+\x00`），以及重复空白；
不要动段落中间原本就存在的单个空格。

实现上，纯 Python 用 `tokenize` 定位 COMMENT 与文档字符串（`ast` 找
`body[0]` 为 `ast.Constant(str)` 的 `Module/FunctionDef/ClassDef` 拿行号区间），
按行号**倒序**回写；docstring 内的多行逐行 `clean_body`。

### 必踩的两个 docstring 坑

1. **单行 docstring 复制成两行**：回写公式
   `lines[first-1:last] = [before+seg[0]] + seg[1:-1] + [seg[-1]+after]`
   在 `len(seg)==1` 时 `seg[0]` 与 `seg[-1]` 是同一元素 → 变两行。
   **必须**给单行单独走 `lines[first-1] = before + seg[0] + after`。
   这个 bug 会把收尾行 `    """` 打成顶格 `"""`，肉眼很难发现，靠不变量校验抓出来。
2. **收尾行缩进回填**：`\n    """` 惯用法下 `seg[-1]` 是空的 `"""`，
   要回填**收尾行自己的缩进**；但若收尾行本身带内容+缩进（`   detail"""`）就不能再补，
   否则缩进翻倍。判据：`if tail and not tail[:1].isspace(): tail = lastindent + tail`。

## 2. 什么删、什么留（判据表）

| 类别 | 处置 | 例子 |
|---|---|---|
| 阶段编号 | 删 | `Phase 8.1（B-1）：` |
| 评审/审计工单号 | 删 | `（审计 P1-4）：`、`（评审 P2-3）` |
| 批次/条目号 | 删 | `（A 批 ⑵+⑶-b）：`、`⑶-d`（**仅带字母后缀或紧跟批次码**；裸 `需求 ⑵` 是语义，留） |
| 死章节引用 `§x.y` | 删（删后成句） | `（交接文档 §4.3 · 2026-09-15 拍板）` → `（交接文档 · 拍板）` |
| 墓碑注释 | **去标记、留名字**（⚠️ **不要整行删**，见 §2.1） | `# 【已删除】_scan_lock` → `# 已删 _scan_lock` |
| 日期戳 | 删（**仅与过程事件绑定时**，见 §3） | `2026-09-11 实测已漂移` → `实测已漂移` |
| 开发轮次 | 删 | `第 3 轮用户点名` |
| **"为什么这么写"叙述** | **留** | `（原 UNLOCK 的值不在白名单 → 已随概念改名）` |
| **迁移/docstring 说明** | **留** | `原 InstrumentSpec 收缩而来` |
| **决策编号（ADR）** | **留** | `D1–D25`、`A′` —— 是已归档文档的锚点，删了就断链 |
| 坐标**夹在句子中间**（它本身是句子成分） | 删，但**必须回读整句** —— 见 §4.4d | `（P2-2 起本工具位于 Script/）` → `（本工具位于 Script/）`，不是 `（起…）` |

### 2.1 墓碑注释**绝不能整行删** —— 会制造「指代悬空」

这是复审才抓到的实质缺陷（第一版就踩了）。墓碑行的**下一行**往往是解释：

```
# 【已删除】_ENGINE_LOCK + engine_section          ← 删掉
# 二者是套在 AppEngine._stock_analysis_lock 外的第二层壳   ← 留着
```

删掉墓碑后，`二者` / `两条` / `它` / `它们` **失去先行词**，"两条都是死别名"却只剩一条 ——
**删了坐标，伤了语义**，比留着工单号更糟。

**正确做法**：`【已删除】` 是过程标记（删），**被删符号名是语义（留）**：

```
# 【已删除】_ENGINE_LOCK + engine_section   →   # 已删 _ENGINE_LOCK + engine_section
```

附带两个好处：① 行数不变 → 不破坏文档里的 `file:line` 引用；② 后文代词仍有主语。

**交付前必须自查**：对每个被整行删掉的注释，看**紧随其后**那 3 行是否含
`二者|两者|两条|两处|它|它们|上述|以上|该|此|其` 等指代/数量词；命中即说明悬空了。

### 「日期 + 动词」要区分**保留动词**与**整体删**

- `删除|已删除|已删|新增|补充|收窄|修复` → **只删日期、保留动词**
  （`2026-09-16 删除：max_volume` → `删除：max_volume`。动词本身承载"这个字段被删了"的事实）
- `插入|评审|审计|复核|改|起` → 与日期**一起整体删**（`2026-09-14 插入）` → ``）

### RULES **不要顺手吃掉尾随冒号**

`# P0-4 修复：删除 X` 与 `# P2-6：关服务…` 是两种情形：前者冒号要留（`修复：`），
后者冒号要删（行首孤儿）。做法：RULES 不含 `[：:]?`，冒号交给
「行首孤儿标点（仅当原本不在行首才删）」+「中文后多余空格」两步处理。

## 3. 日期：**必须有安全阀**，不能无脑删

注释里的日期有两类，**字面完全一样、性质相反**：

- 过程戳：`2026-09-11 实测已漂移 12 处`
- **领域数据**：`# 格式: 2021-09-13`（代码按长度 10 解析日期！）、
  `# 2021-09-13`（`parse_time_column` 的输入示例）、
  `2024-01-02 起连续 5 个交易日`（测试夹具日历）

安全阀 = **「日期后必须紧跟一个过程事件词」才删**：

```python
PROC_AFTER = (拍板|定版|确认|核实|实测|归一|补注册|补充|补|修正|推翻|取代|否决
              |明确|用户|需求方|移入|迁入|新增|删除|收窄|修复|改名|更名|重命名
              |拆分|合并|建立|落地|启用|上线|停用|废弃|更新|重构|精简|收敛|加固
              |统一|对齐|二次|随|立|按|由|把|将|插|改|删|评审|审计|复核|[A-C]\s*批|[：:·])
DATE_PROC = (?<![\w\u4e00-\u9fff])\s*\d{4}-\d{2}-\d{2}\s*(?=PROC_AFTER)
```

**`起` 刻意不算过程词** —— `date 起` = "自某日起"，在两类语义里都携带真实信息。

交付前**必须**对这四类断言「仍在」：

```
OK  # 格式: 2021-09-13 / # 2021-09-13 / # 20210902113000000
OK  交易日历（2024-01-02 起连续 5 个交易日，跳过周末：01-06/07）
```

## 4. 验证：五道闸门，缺一不可

### 4.1 代码零改动 —— **最强不变量**（这一步是技能的核心增量）

对每个 `.py`：剥离注释与 docstring 后，比较**全部 token 的 `(type, string)` 序列**，
要求逐字节相同。**关键**：非 docstring 的字符串字面量要**保留** ——
配置键、事件码是靠字符串使用的，NAME-token 搜索会漏；保留它们才能抓到"误删字符串"。

```python
SKIP = {COMMENT, NL, NEWLINE, ENCODING, ENDMARKER}
# 文档字符串判定：STRING token 且前一个有效 token 是 NEWLINE/INDENT/DEDENT/文件头
```

JS 无标准 tokenize → 用**行级 diff 门禁**：所有 +/- 行去掉前导空白后必须
以 `//`、`*`、`/*`、`*/` 开头。⚠️ 不要写朴素的字符级 JS 扫描器
（正则字面量 `/\d+/`、模板串会让它失同步，产生假失败）。

**原始就不可解析的文件**（故意留的语法坏例）要单独 `try/except` 记为 `SKIP`，
否则会污染结论。

### 4.2 语法 + 括号完整性

- 全仓 `compile()` 逐文件（一条 `SyntaxError` 就回退排查）
- **全角/半角括号平衡**逐个文件与 pristine 比对 —— 专抓"括号类型被串换"

### 4.3 残留清零（**只统计注释区**，真口径）

用 `tokenize` 取 COMMENT + 文档字符串再 grep 坐标 token。
⚠️ **不要对整文件 grep** —— 文件名（`smoke_simnow_phase_g.py`）、代码字符串、
测试常量里的 `Phase`/日期会让数字虚高几十倍，结论不可信。

### 4.4 质量复查（残留标点）

对全部改动点跑正则，**逐项核对**。设计上要接受"一定会有一批假阳性"：

- 「空括号」会命中 `start()` 这类函数调用 → 假阳性
- 「孤立斜杠」会命中 `tick / 乘数` 这类正文 → 假阳性
- 「括号不配对」**行级**判定会命中跨行括号 → 必须**按块/整文件**判，不能按行

### 4.4b 复审（第二遍）该查什么 —— 第一遍查不出来的三类

第一遍的「残留标点 + token 不变量」**都发现不了**语义问题。复审必查：

1. **指代悬空**（见 §2.1）：整行删掉的注释，其后 3 行有没有指代/数量词。
   通用检测：被删片段里的**标识符**在后文完全消失，且后文含
   `它|它们|二者|两条|上述` → 悬空。
2. **误删理由**：对被删片段 grep 强理由词
   `因为|由于|避免|防止|否则|原因|确保|必须|曾|历史|兼容|注意|⚠|前提|约定|契约`。
   命中就要人工判 —— 这些是"为什么"，不该删。
3. **空白/排版副作用**：比对 before/after 里 `中 文`（CJK 间空格）的计数差，
   差值 >0 = 有列举关系被压黏。

### 4.4c 审计脚本自身的两个坑（会让结论全错）

1. **别用 pristine 行号去索引 cleaned 文件** —— 一旦有整行删除/插入，行号整体错位，
   后面每一个断言都是假的。用**锚点内容**定位，并断言命中数 == 1。
2. **别按行号配对两个版本的 token** —— 同样会因删行错位（实测把 5 个文件的偏移
   放大成 1159 个假"字符串被改"）。正确做法：各自用自己的 `ast` 剔除 docstring 后，
   比较**序列**（与行号无关）。

### 4.4d 「删坐标 → 留残句」：**括号失去主语**（第三轮才暴露的一类，最该查）

现象：删掉的是**句子成分的一部分**（不是整行），删完句子读不通 —— 前两轮的五道闸门全放过去了：

```
（审计 P1-1 的根因之一）          →  （的根因之一）          ← 括号首段被删，剩下「的」
出场策略自 2026-09-08 起**只有**…  →  出场策略起**只有**…    ← 剩下「起」
（P2-2 起本工具位于 Script/…）     →  （起本工具位于 Script/…）
原 Phase 9 的「CZCE 钉 1 手」      →  原的「CZCE 钉 1 手」   ← 「原的」不成词
# 这是审计 X1 的关键判据           →  # 这是的关键判据
（…起配置类 frozen=True）          →  （\n起配置类 frozen=True）  ← 括号悬空在行尾
```

检测（两遍，**只在注释 / docstring 行内判**）：

1. **Pass 1（无需基线）**：清理版里以**全角 `（`** 结尾的注释行。
   ⚠️ 必须限定"注释 / docstring 行"（`tokenize` 的 COMMENT token + `ast` 的 docstring 覆盖行）。
   不限定的实测代价：649 处噪声 —— 所有 `foo(\n  a, b)` 多行调用都会被捞进来。
   也别用 ASCII `(` 判，那是代码。
2. **Pass 2（需基线）**：两版做**行级** diff 定位变更行 → 行内**字符级** diff 找删除点 → 判据
   「删除点紧跟全角 `（`」**或**「删除后剩下的首字 ∈ 承接虚词表」。
3. **虚词表要收窄**。`在|由|从|被|把|将|前|时|来` 都能正常起名词短语
   （`（在 CLI 路径闭环…）`、`（前端共享）`、`（来源标记）`），放进表里就是成片假阳性。
   实测：宽表 283 处 → 收窄到 {的,起,后,以来,之后,之前,则,而且,并且,才} 得 37 处，人工过筛后 30 处为真。

修法只有两条，**不许新增事实**：丢掉失去前件的虚词（`（的根因之一）` → `（根因之一）`），
或补「此 / 已」把时间语义接上（`。后 exit_params` → `。此后 exit_params`；`（起不再有…）` → `（不再有…）`）。

⚠️ **收尾必做**：把被删 token 逐个回看一遍 —— 有些"坐标"其实是**语义词**。本轮实测 2 处误删：
`（不是拿第一轮的价格反复报）` 里的「第一轮」指首次报价轮次，不是评审轮次，必须**恢复**。
判据：删掉它之后句子是否出现语法空洞 —— 出现空洞的，先怀疑自己删错了，而不是去补字。

### 4.5 全量回归

⚠️ **先确认工作副本完整**！按体积过滤复制仓库会漏掉大文件
（实测漏了 445KB 的 `Frontend/app.js` 和 3 个 600KB+ 的 `Test/snapshots/*.json`），
导致 2 个测试假失败。复制后**要断言文件总数与源一致**。

**必须覆盖**：`inspect.getsource()` 断言类测试 —— 它们断言函数体源码里**包含某些字符串**
（`.env.example` 必须含 `max_volume`、某个函数必须含 `[5d]` 等），注释改动会让它们红。
用 `grep -rl "getsource" ` 先列出受影响的测试文件，确保回归套件包含它们。
另外别忘**术语护栏测试**（若有禁用词名单）。

### 4.5b 有 FAIL 时：**用 pristine 基线证伪**，别急着回退

老仓库常有**预存的守卫基线漂移**（路由基线表、快照 key、函数归属表没跟上新功能、
夹具 manifest 与生成器脱同步）。这类失败看着吓人，但**与注释无关**。

做法：拿**未清理的 pristine 树**跑**同一个**回归入口，与清理树**逐条比对**：

1. 失败**项数**是否相同；
2. 失败**断言文本**是否**逐字相同**（`:0` / `4 项` / `路由基线外新增: [...]` 这些细节）；
3. 差异**只出现在**"夹具/快照/路由/窗口登记表"这类基线断言上，而不是语法/import/source 断言。

三者都对上 → 判定**预存漂移**，写进报告（附对比表 + 双方原始失败行），
说明"属仓库侧待治理，不在本次范围"。**绝不要**为了凑绿去改这些基线表 ——
那会把"注释清理"这轮污染成"功能改动"。

```bash
# 两侧同入口、同参数，输出到各自文件后 diff 失败项
```

### 4.6 打包与解压复验

- zip **只装"与 pristine 有差异"的文件**（比对前做 **CRLF 归一**，否则整仓虚警），
  按仓库原目录层级；**清 `__pycache__` / `state.db` / 运行时产物**
- ⚠️ **扩展名过滤必须用白名单，不能用黑名单**。黑名单实测漏进 4 个运行时产物：
  `Test/report.json`（测试套件自己写的报告）、`App/double_click_dt.csv`、
  `App/last_code_freq.json`、`App/stock_float_mc.json`。
  这些是在工作副本上**跑过回归之后**才出现的 —— 第一版 zip（跑测试前打的）是干净的，
  跑完再打就混进去了。所以：**只允许 `.py` / `.js` 进 zip**，其余一律排除。
- ⚠️ 对应的，**解压复验脚本也要只比 `.py`/`.js`** —— 否则拿"跑过测试、已被污染的
  工作副本"当基准，会报 4 个假"缺文件/内容不一致"。
- **`.md` 报告不进 zip**（会被解压进仓库树），单独作为附件给
- 复验：解压到干净目录 → 覆盖一份 pristine → 断言结果与已验状态**逐字节一致**。
  这一步同时验证"不漏文件、路径不漏层级、能复现验收状态"。
