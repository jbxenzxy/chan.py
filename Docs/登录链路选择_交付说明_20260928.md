## 2. 设计取舍

### 2.1 为什么走"环境变量注入子进程"而不是新增配置项

自动下单子进程由 `AppTrader.start` 用 `subprocess.Popen` 拉起，环境变量取自 `env = dict(os.environ)`（`App/AppTrader.py`，改前 `:442`）。在此处覆盖那三个键，子进程里的 `Trading/Config.py` 照旧从 env 读 —— **`Trading/` 一行未改**。

备选方案是给 `main.py` 加 `--tq-market` 之类的命令行参数（`--broker` 本来就有，`Trading/main.py:212-213`）。未采用：Config 是配置的唯一入口，再加一套参数通道会让"配置从哪来"分叉。

### 2.2 为什么持久化放 state.db 而不是 localStorage

选择属于**交易侧状态**，与 `auto_order_enabled` 同一条通道（`_engine_store`，kv 读写）。localStorage 换浏览器/清缓存即丢，且"下次默认选哪个"这件事本就该跟交易进程同源。副作用是换状态目录（换账本）后默认项回到 SimNow —— 安全方向，可接受。

### 2.3 为什么实盘仍要 `.env` 里那两个开关

`confirm_live_trading` 是防"以为在仿真、其实在真钱"的最后一道。若界面一键即可切实盘，这道闸门就退化成"点一下"。故保留为**资格总开关**：没配 → 对话框里实盘选项置灰并写明缺什么；配齐 → 界面上再确认一次。两层都还在，界面选择不取代它。

期货公司名属**接入身份**（与账号密码同类），配一次即可，且 `.env` 在 `.gitignore` 里不入库。

### 2.4 为什么前端不复制"实盘能不能选"的判据

可用性只由后端 `AppTrader.link_options` 产出，随状态接口下发（`link_view`）；前端只负责渲染。判据写两处必然漂移（本项目品种白名单一度两处各写一遍，出现过"前端放行、引擎自杀"）。

## 3. 改后数据流

### 3.1 全链路

```
点开关（on）
  → 品种白名单兜底检查（既有）
  → 弹「选择登录方式」对话框（SimNow / 实盘，默认取上次选择）
  → 确认 → POST /api/trader/auto-order/on  {symbol, freq, sse_base, link}
      → AppOrch.call_trader_start(link=…)
      → AppTrader.start(link=…)
          ├─ _resolve_link(cfg, link)：链路 → broker/tq_market/confirm（实盘缺前置则 400）
          ├─ _check_live_gate(cfg, broker, market=…, confirm=…)：按**选定值**复检
          ├─ _write_link_choice(out_dir, link)：持久化到 state.db
          └─ Popen 子进程时 env.update(_link_env(resolved))
  → 子进程 Trading/main.py → Trading/Config.py 从 env 读到 → Broker.build_broker
```

取消 / 点框外 / Esc → `link = null` → 不发请求、开关回弹。

### 3.2 默认值

无上次选择 → SimNow。上次选择不可用时（例如上次选了实盘，但后来把资格开关关了）→ 自动退到第一个可用项，**绝不让禁用项成为默认选中**。

### 3.3 持久化

`state.db` 的 kv 键 `ao_link`（与 `auto_order_enabled` 同库）。读回时只认 `simnow` / `live`，其它值当没有。

### 3.4 子进程实际生效值

| 选择 | `TRADING_BROKER` | `TRADING_BROKER_PARAMS__TQ_MARKET` | `TRADING_BROKER_PARAMS__CONFIRM_LIVE_TRADING` |
|---|---|---|---|
| SimNow | `simnow` | `simnow` | `false` |
| 实盘 | `live` | 配置里的期货公司名 | `true` |

三个键名由 `Test/test_trade_link_choice.py` [4] 组钉死并对 `TradingConfig` 做真实消费验证 —— 键名写错不会报错，只会静默沿用 `.env`，是最难查的一类失效。

### 3.5 取消语义

对话框新增 `choice` 形态，与既有 `confirm` 同出口语义：点「取消」/ 点框外 / 按 Esc → 取消；按 Enter / 点「确定」→ 返回选中值。

### 3.6 当前链路可见

顶栏「自动下单」一组末尾新增徽标 `#auto-order-link`，仅在子进程运行中显示：实盘红字「实盘」、仿真绿字「SimNow」，悬停说明。此前完全看不出跑的是哪条通道。

## 6. 用户操作指南

首次要用实盘，需在 `.env`（或系统环境变量）配一次：

```
TRADING_BROKER_PARAMS__TQ_MARKET=创元期货
TRADING_BROKER_PARAMS__CONFIRM_LIVE_TRADING=true
```

**这两行已配好随交付发出：`交付/env-live-创元期货.txt`**（追加到你仓库根 `.env` 末尾即可；没有 `.env` 就先 `cp .env.example .env`）。追加而非整份替换 —— 你的 `.env` 里可能已有 `TDX_INSTALL_DIR` 等本机配置。文件必须存为 **UTF-8 无 BOM**：中文期货公司名存成 GBK 会读成乱码，进而被实盘闸门当成非法值挡掉。

配置 **追加后需重启后端服务**（`.env` 只在 `Config` 加载时读一次），再点自动下单开关。

该文件的有效性已用真代码验证（不是照配置读一遍，是把两行喂进 `AppTrader._load_cfg()` 后走完整判据）：

| 验证项 | 结果 |
|---|---|
| `cfg.broker_params.tq_market` | `创元期货`（双下划线嵌套键被正确解析，非字符串整体吞掉） |
| `cfg.broker_params.confirm_live_trading` | `True` |
| `link_options()` 实盘项 | `enabled=True`，`hint='实盘 · 创元期货'`（界面不再置灰） |
| `_resolve_link('live')` | `{broker: live, tq_market: 创元期货, confirm: True}` |
| `_link_env()` 注入给子进程的三键 | `TRADING_BROKER=live` / `TQ_MARKET=创元期货` / `CONFIRM_LIVE_TRADING=true` |
| 同配置下 `_resolve_link('simnow')` | `broker=simnow`、`tq_market=simnow`、`confirm=false` —— **不受 `.env` 里期货公司名污染** |

账号密码仍只走环境变量（`SN_*` / `TQ_*` / `LIVE_*`），与改前一致。

之后每次开自动下单：点开关 → 选 SimNow 或实盘 → 确认。选择会被记住为下次默认项。**不再需要为了切换去改 `.env`。**

实盘选项置灰时，把鼠标悬上去会写明缺哪一项（未配期货公司 / 资格开关未开）。

## 7. 已知边界（本次未做，需另行裁决）

> **2026-09-28 二轮裁决**：第 1、2 两条用户已裁决 —— **维持现状，不做**。热切链路仍不支持（需先关再开）；仿真与实盘**就是共用一套账本**，不做拆分。以下保留为设计说明，不是待办。

1. **运行中不能热切链路**（裁决：维持）。切换需先关自动下单再开。两个通道共用一套账本（`TRADING_STATE_DIR`），同时跑一个状态目录没有意义；且 `AppTrader.start` 对"已在运行"直接返回现有进程。
2. **仿真与实盘仍共用一套账本**（裁决：维持）。`.env` 注释称"换目录 = 换一套账本"，但 `App/AppTrader._discover_state_dbs()` 会 `glob(Trading/State*)` 把分出来的目录全部扫回合并 —— 分账本不是"加一行配置"就能安全做到，本次未动。
3. **`dry_run` 不在对话框选项里**（需求只列了 SimNow 与实盘）。离线模拟仍可通过 CLI 直跑或不带 `link` 的调用路径使用。
4. **子进程启动后的凭据缺失**（如没配 `SN_*`）表现为子进程退出、前端展示 `gateway.log` 尾部 —— 与改前一致，未新增前置校验。

## 9. 第三轮（2026-09-28）：交接文档「行号 → 锚点」+ `.env.example`

### 9.1 为什么要做

核对合入时发现 `Docs/股票页「止盈止损」功能_设计兼交接文档_v1.7.md` 的行号引用**已经大面积失真**：按"文档行的语义关键词能否命中源码目标行 ±2 行"批量校验，124 处引用里 **19 处已漂**，其中 `Frontend/app.js` 的止盈止损一批（8554/8579/8601/8641/8695/8726）**统一后移 24 行** —— 正是本次功能插入前端代码造成的。行号是这类文档里最容易腐坏、又最不容易被发现的资产。

### 10.2.1 「回归」术语澄清（回应用户提问）

用户问：`bsp_count 45→53` 是「预期内的算法改动」还是「回归」？「回归」是何意、是否指引入问题？

- **回归 / regression（软件工程义）**：指「一次改动让原本正确/通过的行为变错/变失败」。本质是**「丢掉了曾经能用的行为」**，不只泛指「有 bug」。所以可以说「回归＝引入问题」，**但更精确是「这个改动把原本对的东西弄坏了」**。快照基线本来是绿的，现在对当前代码红了 —— 这正是回归的**形状**，前提是「代码改动是无意的/错的」。
- 但基线红还有第二种成因 —— **基线漂移（baseline drift）**：代码是有意改的（行为本就该变），只是冻结的测试基线没跟着重冻。这时代码没错，是测试工件陈旧。两者处置相反：回归要**修代码**，基线漂移只要**重冻基线**。
- 本批 9 个里可明确分流：
  - **`fractal_high`/`fractal_low` 字段缺失 → 基线漂移，不是回归**。`Test/comparator.py:16` 的注释原话就是「期货 bsps 的 fractal_low/high 就是这么滞后的」——作者明知这批基线因新增展示字段而过期。新增字段来自 `App/AppEngine.py:1201-1202`、`:1528-1529` 与 `App/AppSSE.py:1405-1406`（买卖点输出层为 TP/SL 功能挂上分型高低点），属有意改动。
  - **`bsp_count 45→53`（仅 `multilevel_d_30m*`） → 真正需判定的一项**。`bsp_count = len(bsp_data)`（`App/AppEngine.py:1299`/`:1570`），它只数买卖点**个数**，与展示字段无关；字段新增不会改 count，所以 count 变化来自**买卖点检测/装配层本身**（核心 `BuySellPoint/` 或 `App` 装配），不是显示层副作用。
- **本环境无法最终定性**（sandbox 与 `C:\my_chan_project` 都**不是 git 工作树**，无 blame 可用）。但有可佐证的刻画证据（重冻前/后对比 `multilevel_d_30m` 的 `sub` 买卖点）：

  | | bsp_count | 类型分布 |

  | 旧（stale） | 45 | `{1:34, 0:10, 2:1}` |
  | 新（重冻后） | 53 | `{1:34, 0:15, 2:4}` |

  即新增 8 个买卖点：**type-1 数量完全不变（34→34），只多了 type-0（+5）和 type-2（+3）**。这**不是**「随机重复/垃圾点」（那种会全盘膨胀或产生非法条目），而是真实多出的 0/2 类点 —— 形态上更偏向「有意的算法调整」而非「污染式回归」。
