# 互斥锁设计指导书（初稿 v0）

> 适用场景：当你在写/改一段并发代码，犹豫"这里要不要加锁、加什么锁"时，按顺序过一遍下面的维度。
> 本文不是 API 手册，而是一套**决策维度**。每个维度都附带了在 chan.py 项目中真实暴露出来的反例（标注为 `案例：…`），方便对照理解。
> 状态：初稿，欢迎逐条提修改意见。文中 `【待讨论】` 为作者留给你拍板的点。

---

## 0. 总原则：先消灭共享，再谈锁

锁不是"保护"，是"给并发加约束"——它同时带来复杂度、性能损耗、死锁风险和"看起来安全其实没护住"的错觉。所以第一步永远是问：

> **能不能让这块数据根本不被并发访问？**

能，就别加锁。常见手段：
- 把数据做成**不可变快照**再发布（chan.py 的期货下窗 CChan 若只发布 REST 实际需要的序列，就不会有"发布活对象"问题）。
- 用**每请求/每连接私有实例**替代共享单例。
- 用**消息/队列**串行化，而非共享内存。

只有"共享无法消除"时，才进入下面的维度。

## 维度 1：并发地形图 —— 操作到底在哪个执行体上跑？

你无法判断任何锁的正确性，除非先搞清楚**并发模型**。这一步要画出"执行体 × 操作"的映射。

**1.1 枚举所有执行体。** 常见三类：
- 事件循环线程（asyncio / 单线程跑协程）
- 线程池线程（`run_in_executor` / `anyio.to_thread` / 框架的线程派发）
- 进程池进程（`multiprocessing.Pool`）

**1.2 标注每个请求/任务落在哪类执行体。** 不要靠印象，要追到路由层。在 chan.py 里：`FrontAPI.py` 把股票部分请求直接丢事件循环、部分丢线程池、扫描丢进程池；期货 SSE 走线程池。

**1.3 致命陷阱：执行体的"连续性"假设。**
很多人默认"SSE 一条连接 = 一条常驻线程，全程不换"。**这条假设要实测，不能信文档。** 在 chan.py 里，`FrontAPI.py:9`、`AppSSE.py:315`、`AppOrch.py:127` 都这么写，但实测 starlette 对**同步生成器是每帧一次独立的 `anyio.to_thread.run_sync`**（`starlette/concurrency.py:57`）。结果：6 连接 × 12 帧，4/6 发生跨线程迭代，28 帧读到**别的连接**的线程局部会话。
> 案例：期货下窗的 `session_set(src)` 只在生成器入口设一次 thread-local，但实时循环每根 K 线 `step_load()` 都新建数据源读该线程局部——落在别的线程就串品种，落在没绑定过的线程就回退空缓存。**这是唯一会静默产生错误行情数据的 P0。**

**1.4 交付物：** 一张表 —— 操作名 / 执行体 / 是否跨执行体切换 / 线程局部依赖与否。

## 维度 2：隔离边界 —— 谁和谁真正共享内存？

**2.1 进程级天然隔离。** 进程池的多个进程有各自独立的地址空间，内存数据**完全不共享** → 一般**不需要锁**。

**2.2 线程级天然共享。** 同进程的多线程共享：堆、全局变量、模块级变量、类级/静态变量、导入的单例。**这些才需要锁。**

**2.3 非内存资源要单列。** 文件、socket、外部句柄即使进程隔离，一旦多进程/多线程共享同一物理文件，仍需文件锁。
> 案例：`zxg.blk` 有两条写路径。生产路由走**无锁非原子 append**；另一条在**独立的脚本进程**里持 `threading.Lock` + 原子写。后者这把锁是**进程内锁**，跨进程天然无效——这正是进程间共享文件必须上文件锁（而非 threading.Lock）的典型陷阱。

**2.4 共享池会打破隔离。** 即便"进程隔离"，一旦用了**进程池 + 共享内存 / Manager / 共享队列**，隔离就被打开，需要重新评估。
> 口诀：**进程池默认免锁，共享池才要锁。**

**2.5 交付物：** 隔离边界矩阵 —— 资源 / 是否跨线程 / 是否跨进程 / 是否跨非内存介质。

## 维度 3：数据落点 —— 共享的东西存在哪一层？

同一份"共享数据"，落点不同，保护方式天差地别：

| 落点 | 例子 | 风险 |
|---|---|---|
| 实例字段（堆上） | `self._names` | 若被多个执行体引用，需锁 |
| 模块级全局 | `app_data` 单例 | 几乎一定共享，必须登记 |
| 类级/静态 | `_scan_skip_log` | 所有实例共享 |
| 线程局部 | `threading.local()` 会话 | 仅当前线程可见，但**跨线程失配**（见维度 1.3） |
| `contextvars` | 协程上下文 | **逐帧线程派发下不可靠**（见维度 6） |

**3.1 关键陷阱：裸出口 = 暴露共享对象。**
即便方法内部加了锁，如果还留了 `return self._names` 这种裸 `@property`，下游会把它绑成模块级别名（chan.py 里 `AppEngine:200/220/224/253/293`、`AppRefresh:35/38/42`、`AppScan:50` 全是 `xxx = app_data.names` 这种别名）。这些别名的注释写着"共享同一对象，零漂移"——**零漂移是目的，代价是零保护**，任何线程都能在无锁状态下改它。

**3.2 交付物：** 共享资源登记表（参考 chan.py 的 `AppOrch.py:SHARED_RESOURCE_REGISTRY`）。每条至少含：字段名 / 落点 / 执行体 / 是否 RMW / 谁持锁。

> 案例：`AppData.py:1376-1410` 有 9 个裸 `@property` 直接 `return self._names / self._pe / self._annotations` 等，连锁本身也漏登记。`_scan_skip_log`（`AppScan.py:53`）**整个逃出了登记表**——它不是"加错锁"，是"根本没人管"。

## 维度 4：操作原子性 —— 是不是读-改-写（RMW）？

锁只在"复合操作"上有意义。先把每个操作拆成基本动作：

**4.1 纯单读 / 纯单写：** 若读写方各只有一个执行体，或只读不变，可不加锁（配合不可变快照最佳）。

**4.2 遍历 + 可能外部修改：** 字典/列表迭代期间被 `clear()` 或增删 → `RuntimeError: dictionary changed size during iteration`。
> 案例：`get_annotated_codes`（`AppData.py:2073`）无锁遍历标注表，刷新线程的 `replace_names` 同时 `clear()+update()` → 路由直接 500。

**4.3 先置位后填充（flag 竟态）：** 先把"已加载"标志置 True，再慢慢填数据。读者看到 True 但数据还是 None/半成品，且 flag 已 True，**这一轮不再重试**，永久拿到脏值。
> 案例：`load_pe_ttm_cache`（`AppData.py:1681`）先置位后填充，读者拿到 `None`（文件里明明有 25.3），且 `pe_loaded` 已 True 不再补。

**4.4 缓存条目的 RMW 跨锁边界：** 取出来 → 在锁外修改 → 写回去，两步不在同一把锁内 → 丢失更新。
> 案例：`AppEngine.py:779-786 / 804-811`，两线程各取缓存对象、各自更新、先后写回，最终缓存只剩后写者的 `['records']`，前者的 `chan` 被覆盖。

**4.5 读者直接改共享对象：** 取到的"缓存"其实是共享引用，读者在函数内 `result["sub"]=...` 改的就是缓存本体。
> 案例：`AppEngine.py:353-354`，读者改 `result["sub"]` 改的是缓存里的对象，然后 return 给路由序列化，污染其他读者。

## 维度 5：锁的粒度与覆盖 —— 护容器，还是护对象图？

这是最多人栽的地方：**以为锁了 dict 就万事大吉，其实只护了 dict 的四个瞬间（get/set/del），没护里面那个"还活着的"对象。**

**5.1 容器级锁够不够？** 如果共享的是"一个 dict，value 是不可变标量"，锁 dict 就够。

**5.2 对象图共享：** 如果 value 是**可变对象（CChan、list、嵌套 dict）**，锁只保住"取到指针"这一步，取到后在锁外遍历/修改 `bi_list`、替换 `kl_datas`，就完全无保护。
> 案例：`_futures_cache_lock` 护住 dict 写入（`AppSSE.py:733` 发布），但 REST 侧 `AppChart.py:400`、`BSPointList.py:754` 取到指针出锁，遍历 `bi_list`；而实时循环每根 K 线 `do_init()`（`Chan.py:90`）把 `kl_datas` 整个换成新的空对象。读到的缓存瞬间过期 → "红框内无完整笔""下窗缓存已过期"类报错很可能就是撞这儿。

**5.3 两条正路：**
- （A）**发布不可变快照**：提取下游真正需要的序列（而非活 CChan），发布那一刻 deepcopy/冻结。
- （B）**锁覆盖读取方全过程**：把"取指针 + 遍历 + 使用"整个包进同一把锁（性能差，首选 A）。

## 维度 6：选对并发原语 —— 别用错工具

**6.1 `threading.Lock`：** 线程间互斥，最常用。

**6.2 `threading.RLock`：** 可重入，仅用于"同一线程可能嵌套加锁"的少数场景。**不要默认用 RLock**——它会掩盖锁顺序设计缺陷。

**6.3 文件锁（`fcntl.flock` / `msvcrt.locking` / `portalocker`）：** 跨进程共享文件时**必须**用它，不能用 `threading.Lock`。

**6.4 线程局部 / `contextvars` 的陷阱集：**
- **线程局部只在"绑定线程全程不变"的前提下有效。** 逐帧换线程（维度 1.3）下，入口设一次 = 后面帧读不到。
- **`contextvars` 在 `anyio.to_thread.run_sync` 里不可靠。** 实测：`run_sync` 在调用方上下文的副本里执行，帧内 `set()` 不回传，同一条线程第 2 帧就丢值——会把"偶发失配"变成"必然失配"。**别把线程局部戏法换成 contextvars 了事。**

**6.5 信号量 / 条件变量：** 限流、等待-通知专用，不是互斥锁的替代品。

## 维度 7：死锁、重入、生命周期

**7.1 锁顺序：** 多把锁同时持有时，全局固定获取顺序，否则交叉等待 → 死锁。

**7.2 重入：** 同一执行体递归进入持锁区，`Lock` 会自死锁，`RLock` 不会——据此判断是否真需要 RLock。

**7.3 释放与 `try/finally`：** 资源"递增"和"释放"必须在同一 `try/finally`，否则异常路径下永久泄漏。
> 案例：`_active_scans` 递增在扫描开始、释放在结束，但不在同一 `try/finally`，扫描抛异常时一次进程池任务永不销毁。

**7.4 进程池里的锁无效：** `multiprocessing` 子进程拿到的是父进程的**副本**，父进程持有的 `threading.Lock` 对子进程毫无约束力。跨进程协作必须走 `multiprocessing.Manager` / 队列 / 文件锁。

## 维度 8：决策速查清单（一页）

按此顺序回答，全否 → 不用锁：

```
Q1. 这块数据会被 >1 个执行体访问吗？（线程 or 进程 or 非内存介质）
    └─ 否 → 不用锁，结束。
Q2. 能改成"每执行体私有实例 / 不可变快照"消除共享吗？
    └─ 能 → 消除共享，结束（优先）。
Q3. 共享的是「容器」还是「容器里还活着的对象」？
    └─ 活对象 → 锁必须覆盖读取方全过程，或改发不可变快照（维度 5）。
Q4. 跨进程还是跨线程？
    └─ 跨进程/共享文件 → 文件锁；跨线程 → threading.Lock。
Q5. 操作是读-改-写或遍历+外部修改吗？（维度 4）
    └─ 是 → 整个 RMW 包进同一把锁，或整体替换，禁止"取-改-回写"跨锁。
Q6. 依赖线程局部/上下文变量吗？
    └─ 是 → 先验证执行体连续（维度 1.3）；逐帧换线程则禁用，改每帧重绑定或显式传参。
Q7. 所有触碰该字段的路径都持锁了吗？（维度 3.1 裸出口）
    └─ 有裸 property / 模块级别名 / 读者改共享对象 → 先收边界，再谈锁。
Q8. 获取顺序固定？释放有 try/finally？进程池里没用 threading.Lock？
    └─ 否则补上（维度 7）。
```

## 维度 9：验证方法论 —— 别用信仰代替证据

锁对不对，**靠推理不够，要验证**。三类手段：

**9.1 用框架源码核实执行体假设。** 不要"框架应该是一连接一线程吧"。去读 `starlette/concurrency.py`、`anyio` 源码确认派发方式（维度 1.3 就是这样推翻 chan.py 的）。

**9.2 确定性交错复现，不靠调度运气。** 用 `threading.Event` 在关键点卡住一方、放行另一方，强制构造竞态，再断言是否抛错/串值。比"跑很多次看会不会崩"可靠 100 倍。
> chan.py 的 `repro_lock_gaps.py` 用此法对 5 个缺口 5/5 确定性命中。

**9.3 静态扫描兜底。** 不要只靠"肉眼 review"。写一条 `ast` 静态检查：凡是触碰受保护字段的方法，必须出现在持对应锁的代码路径里。
> 教训：chan.py 现有 `test_lock_v5_guards.py` 用计数包装锁，断言"这些入口持锁"——它问的是"这扇门有没有锁"，**没问"是不是所有门都上了锁"**。上面 5 个缺口因此一路溜过去。静态扫描要反向：从"受保护字段"出发，查所有访问点。

**9.4 大小相同 ≠ 安全。** `replace_names` 用条数相同的 dict 替换，绕过 CPython 的 `ma_used` 迭代检查，不抛错但**静默串表**。验证要同时检查"不崩"和"值对"。
