3. 核心判断：去掉 otg = 去掉 tqsdk（在 Broker 内部）

tqsdk 的交易通道固定经快期自建网关（otg）转发到 CTP 柜台，无论仿真（TqAccount("simnow",…)）还是实盘（TqAccount(期货公司名,…)），开源版本不提供绕开网关的本地 CTP 连接。所以本设计不是「给 tqsdk 换个地址」，而是「把 SimNowBroker 的内核从 tqsdk 换成 CTP 原生绑定」，共 1647 行里需要重写的是与 tqsdk 数据面/控制面交互的部分；超价、追价、超时重试、拒单分类（Base.py:130 classify_ctp_reject）等业务保障逻辑与传输层无关，原样保留。

同时明确：镜像的职责不因直连消失（CTP 异步回报 + 查询 1 秒流控决定了必须有本地缓存），只是镜像从「tqsdk 内部维护」变为「适配器自己维护」，且新鲜度从 25~55 秒级降到毫秒级。

5.2 线程模型

先澄清一个新增事实：现状（tqsdk 路径）的下单子进程是单线程的——tqsdk 在调用 wait_update 的那条 Python 线程里跑自己的事件循环，没有额外调度单位（此前架构讨论的结论对现状成立）。而 CTP 是 C++ SDK：调用 Init() 后它会在进程内创建自己的网络工作线程（真正的操作系统调度单位），OnRtnOrder/OnRtnTrade 等 Spi 回调由该线程触发——此时同一进程内出现两个调度单位（主线程 + SDK 线程）。这是直连方案新引入的并发事实，不是现有架构本来就有的；回调进入 Python 层仍受 GIL 约束，SDK 内部的 C++ 网络收发不受 GIL 约束。

CTP 的 Spi 回调在 SDK 自己的线程触发，与 tqsdk「单线程 wait_update」不同。适配层用「回调入队、主线程消费」桥接：Spi 回调只做入队（SDK 线程不碰任何引擎状态），pulse() 在引擎主线程把队列消费进本地镜像/订单表；所有 _wait/_wait_finished 谓词改为查消费后的本地状态。这样引擎侧时序语义与现在完全一致，不引入跨线程访问——这也是生产环境写 CTP 的标准做法。

若只想尽快验证「直连能解决延迟」：砍掉阶段 4 的追价全量迁移与阶段 8，追价先用简化版（一次超价限价 + 超时告警人工接管），合计 ≈ 10~11 人日。代价是保障级别低于现有 otg 路径，只建议作为过渡验证，不作为长期运行形态。

8.2 阶段推进方式

每阶段独立交付、可单独回退；阶段 0 结束即有一次「继续/中止」决策点（若两个绑定库在 Python 3.13 都不可用且不愿上子进程方案，本工程在此终止，只损失 1 人日）。全程不触碰缠论核心九目录与交易引擎目录，逐阶段跑 p26 术语护栏 + 既有回归（当前 76/76 等基线）。
