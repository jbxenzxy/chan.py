# M3 部署与验证指南

> 针对 2026-09-04 v6 回归跑出 `trades=0` 的修复包。
> 包含 P6（权威成交判定）、`--fresh`（回放状态重置）、连接重试与心跳三项修复。

---

## 一、这轮修了什么

### 1. P6：用 CTP 真实成交明细判定成交（核心）

**问题**：tqsdk 的 `position` 缓存会在 `insert_order` 后被**乐观**增减，CTP 拒单也不回滚。
P4/P5 拿它做判定，两头都错：

| 场景 | position 缓存表现 | P4/P5 判定 | 实际 | 后果 |
|------|------------------|-----------|------|------|
| CTP 真成交但缓存滞后 | 5s 内没同步 | 幽灵 → reject | 真成交 | v5 的 21 笔 close 死循环 |
| CTP 拒单但缓存被 +1 | 缓存显示 +1 | 成交 → accept | 未成交 | v5 的 4 笔幻象 filled |

**v5 实测铁证**：4 笔 OPEN 报 "filled"，1.5 分钟后查 SimNow 真实账户却是 **0 持仓**。

**修复**：改用 `order.trade_records` —— 这是 CTP（交易所）真正确认的成交回报明细，
只有撮合成功才会写入，不受本地缓存影响。真成交必须三层同时成立：

1. `order.status == "FINISHED"` （P3）
2. `order.volume_left == 0` （P3）
3. `sum(trade_records[*].volume) >= 委托量` （P6 · 权威）

**P4/P5 降级为纯诊断**：position 缓存不同步时只写 WARNING 日志，不再推翻 P6 的判定。

### 2. `--fresh`：回放重跑前清空派生状态

**问题（v6 trades=0 的直接原因）**：上一轮回放把 7 个 `signal_key` 标成 opened/rejected
写进 `state.db`，下一轮回放读同一份 `state.db` 时 `try_mark_signal` 全部返回 False
→ 7 笔信号全被判 `signal_dup` → `trades=0`。

**修复**：回放模式默认启动前清空 `processed_signals` / `trades` / kv 里的
`position` / `day_stats` / `bars_seen`。`events.jsonl` 与 `orders` 表保留作审计。

```bash
python run_gateway.py --source replay ...        # 回放默认 --fresh
python run_gateway.py --source sse ...           # 实盘默认 --no-fresh（保持幂等）
python run_gateway.py --source replay ... --no-fresh   # 显式保留上轮状态
```

启动时会打印：`[fresh] 已清空派生状态: processed_signals=7  trades=6`

### 3. 连接重试 + 心跳

**问题**：SimNow 对短连接敏感，gateway 跑完立即退出后，CTP 侧会把会话标成
**"用户不活跃"**，隔几分钟重连直接失败（实测 `CTP:用户不活跃` + `TqTimeoutError`）。

**修复**：
- `_connect` 失败自动退避重试（默认 3 次，5s → 7.5s → 11.25s）
- 新增 `_probe_alive()`：登录后先探一次活，挡掉"用户不活跃"的僵尸连接
- 新增 `pulse()` 心跳：引擎每处理一根 K 线调一次 `wait_update`，
  长连接空闲期不再被判不活跃（SSE 实时模式必需）

## 三、怎么判断这次跑对了

### 应该看到的

- 启动第一行：`[fresh] 已清空派生状态: processed_signals=N  trades=N`
- 7 笔信号全部走 `信号` 事件，**不再出现 `重复信号`**
- 摘要的 `成交笔数` 反映真实成交数量

### 关键日志（新增）

```
P6: CTP 成交明细只有 0 手，不足委托 1 手 ... 判定为未成交
```
→ 说明 P6 挡住了幻象成交（CTP 拒了但缓存被 +1）。这是**好事**，
   但连续出现说明下单参数有问题（多半是价格超出涨跌停板）。

```
P4/P5 诊断（不影响成交判定）: open LONG 后 position 端未按预期变化 ...
```
→ 只是 position 缓存滞后，不影响成交判定。可以忽略。

```
SimNow 第 1/3 次登录失败（5.0s 后重试）
```
→ SimNow 会话刚被标"用户不活跃"，自动重试中。等它重试完。

### 异常信号

| 现象 | 含义 | 处理 |
|------|------|------|
| `本轮没有产生成交` + 无 `重复信号` | P6 把所有单都判未成交 | 看 events.jsonl 里 P6 的 last_msg，多半是价格越界 |
| 大量 `重复信号` | state 没清干净 | 确认用了 M3 的 run_gateway.py，或手动加 `--fresh` |
| `缺少 SimNow/天勤凭据` | 环境变量没配 | 用 GUI 系统环境变量，不要 `set` 命令 |

## 六、测试文件说明（test_p5_fix.py / test_p6_fix.py 是干什么的）

这俩是**纯 Python 脚本**，不是 pytest 用例，不需要 tqsdk、不需要网络、不需要 SimNow 连接，
任何时间都能跑（`python test_p5_fix.py` / `python test_p6_fix.py`）。

| 文件 | 测什么 | 数量 | 依赖 |
|------|--------|------|------|
| `test_p5_fix.py` | P5：`_verify_position_delta` 的 `abs(cur-target)<=1` 精确容差匹配（挡"CTP 重连重发回报污染 position"的幽灵） | 9 例 | 真 import `tg.brokers.simnow` |
| `test_p6_fix.py` | P6：`_traded_volume_from_records` / `_traded_price_from_records` 的 trade_records 权威成交判定（挡"tqsdk 缓存乐观更新"的幻象 filled） | 21 例 | 真 import `tg.brokers.simnow` |

**放在哪**：`trader_gateway/tests/`（本 zip 已放好）。**不要**放进项目根的 `Test/` 目录——
那个目录是 chan.py 缠论内核的契约/比对测试框架（`contracts.py` / `comparator.py` /
`func_map_check.py`），跟 trader_gateway 不是一套体系，混进去会破坏它的 fixture 结构。
（Windows 下 `Test/` 与 `test/` 是同一目录，大小写不敏感。）

**作用定位**：这是 broker 层的**回归测试**——以后任何人改 `simnow.py` 把 P3/P4/P5/P6
的成交判定改回去，这俩测试会立即变红。M4 起已改为**真 import 真实代码**（早先版本是
把函数体复制一份来测，测的是"规格"不是"真实代码"，改了代码测试也不红，已修正并用
变异测试验证过：故意改坏 simnow.py → 4 例变红）。

## 七、收盘了还能不能跑 SimNow 回归？（重要）

**结论：能跑，但结果含义要重新定义——现在只能当"P6 反向路径压测"，不能当"真回归"。**

| 现在（收盘后） | 明天 9:30–11:30（盘中） |
|----------------|------------------------|
| 只验证 P6 **不误报**成交（反向） | 验证 P6 **能正确识别**真成交（正向） |
| 期望结果 = **trades=0 + 7 笔 rejected** | 期望结果 = **6 笔真成交** |

为什么现在只能测反向：CFFEX 没有夜盘，15:00 收盘后撮合引擎停摆，**任何委托都不可能成交**。
所以：
- 现在跑，看到 `trades=0 + 7 笔 rejected` → **这是正确结果**，说明 P6 正确没把"没成交"误报成"成交"（正是 v5 那 4 笔幻象 filled 的反面）。
- 现在跑，如果看到任何 `filled` → **立刻停止告诉我**，说明 P6 仍有幻象 bug。
- 现在跑**无法**验证 P6 的正向（真成交），那个必须等明天开盘。

两个坑要提前知道：
1. **时段风控用 bar 时间判，不是墙钟**（`tg/risk.py` `spec.in_session(bar_date)`），所以回放的 09:35/13:30 bar 不会被 `enforce_session` 拦掉，委托会真的发到 CTP——但 CTP 收盘后会拒。
2. **SimNow 日终结算窗口**（通常 15:30 后开始）可能导致登录失败/`CTP:结算中`。若看到登录失败，**不是 P6 的问题**，等结算完或明天再跑。

报单超时 `fill_timeout=30s` 会自动撤单（`simnow.py:_wait_finished`），不会留过夜委托；最坏 7 笔 × ~35s ≈ 4 分钟跑完。

**建议节奏**：
```powershell
# 现在（可选）：反向压测，确认 P6 不误报（4 分钟内，期望 7 笔 rejected）
python run_gateway.py --source replay --broker simnow --out ./run_regression_now

# 明天 9:30 后：真回归（期望 6 笔真成交）
python run_gateway.py --source replay --broker simnow --out ./run_regression_v7
```

另附 `probe_after_close.py`：随时探测 SimNow「能否登录 + 行情状态 + 非交易时段报单是否被拒」，
结果直接告诉你当前处于哪种状态，不用瞎猜。
